1

BASELINE

이벤트는 기본이 동기

먼저 오해를 깬다 — Spring 이벤트는 기본적으로 비동기가 아니다.

applicationEventPublisher.publishEvent()를 호출하면, 일반 @EventListener는 그 자리에서, 같은 스레드로, 동기 실행된다. 즉 메서드 호출과 다를 바 없다 — 리스너가 끝나야 publishEvent() 다음 줄로 넘어간다. 그래서 발행 지점에 트랜잭션이 열려 있으면 리스너도 그 트랜잭션 안에서 돈다.

비동기가 되려면 명시적으로 @Async(+ @EnableAsync)를 붙여야 한다. 그러면 별도 스레드풀로 넘어간다(§4). "리스너 = 비동기"라는 통념이 트랜잭션 착각의 출발점이다.

핵심축은 둘이다 — ① phase(언제 실행: 발행 즉시 / 커밋 직전 / 커밋 후) × ② 스레드(동기 = 같은 스레드·같은 Tx / @Async = 별 스레드·Tx 없음). 뒤이은 쓰기가 어디서 커밋되는지는 이 둘의 조합으로 결정된다.

2

TIMELINE

리스너 4타입 × 실행 시점

한 트랜잭션의 생애에서 각 리스너가 어디서 실행되는지 시간축에 찍으면 명확해진다.

각 타입 한 줄 정의

타입실행 시점트랜잭션 관계
@EventListenerpublishEvent() 즉시, 인라인발행 시점의 트랜잭션에 그대로 참여
BEFORE_COMMIT커밋 직전 (beforeCommit 콜백)아직 원본 Tx 안 — 함께 커밋/롤백
AFTER_COMMIT (기본)커밋 성공 후원본 Tx 종료 — 쓰기엔 새 Tx 필요
AFTER_ROLLBACK / COMPLETION롤백 후 / 완료(둘 다) 후원본 Tx 종료
발화 조건@TransactionalEventListener는 트랜잭션 경계 안에서 발행된 이벤트만 받는다. 트랜잭션 없이 발행하면 리스너는 그냥 버려진다(fallbackExecution=true를 줘야 트랜잭션 밖에서도 실행).[2] 반면 일반 @EventListener는 트랜잭션과 무관하게 항상 실행된다.
3

THE TRAP

AFTER_COMMIT의 함정 + REQUIRES_NEW

여기가 "가끔 트랜잭션 문제가 난다"의 진앙이다. AFTER_COMMIT에서 DB를 쓰면 조용히 사라질 수 있다.

AFTER_COMMIT 시점의 데이터 접근은 원본 트랜잭션에 "참여"하지만, 그 변경은 트랜잭션 리소스에 커밋되지 않는다.

— Spring TransactionalEventListener Javadoc WARNING (요약)[2]

즉 AFTER_COMMIT 리스너에서 repository.save()를 그냥 호출하면 — 원본 트랜잭션은 이미 커밋이 끝났는데 thread-bound 리소스(EntityManager)는 아직 붙어 있어서 — 그 save가 에러 없이 실행되지만 커밋되지 않는다. "분명 저장했는데 DB에 없다"는 진단하기 힘든 유실이다.

REQUIRES_NEW의 의미

해결은 새 트랜잭션을 여는 것이다. Propagation.REQUIRES_NEW = "현재 트랜잭션이 있으면 suspend하고, 새 트랜잭션을 시작한다."[3] AFTER_COMMIT에선 완료 중인 원본을 suspend하고 독립된 새 Tx를 열어, 그 안의 쓰기가 독립적으로 커밋된다.

DB 쓰기가 없는 순수 외부 호출이라면 Propagation.NOT_SUPPORTED(비트랜잭션 실행)도 된다. 둘의 공통점은 "완료 중인 원본에 join하지 않는다" — 그래서 이 둘만 허용된다.

Spring 6.2+ 부팅 검증@TransactionalEventListener + @Transactional을 같은 메서드에 붙일 때 propagation이 REQUIRES_NEW / NOT_SUPPORTED가 아니면(예: 기본 REQUIRED), 애플리케이션 컨텍스트 초기화 단계에서 IllegalStateException으로 기동이 실패한다(RestrictedTransactionalEventListenerFactory). 본 프로젝트는 Boot 3.4.4(Framework 6.2.x)라 이 검증 대상이다.[2]
AFTER_COMMIT에서 DB를 쓸 때 
// ❌ 조용한 유실 — 새 Tx 없이 save (참여만 하고 커밋 안 됨)
@TransactionalEventListener(phase = AFTER_COMMIT)
fun bad(e: Event) = repo.save(...)   // 에러 없이 사라짐

// ✅ REQUIRES_NEW 로 독립 커밋
@Transactional(propagation = REQUIRES_NEW)
@TransactionalEventListener(phase = AFTER_COMMIT)
fun good(e: Event) = repo.save(...)   // 새 Tx 로 커밋됨
4

ASYNC

@Async가 바꾸는 것

@Async는 리스너를 다른 스레드로 옮긴다. 트랜잭션은 스레드에 묶여 있으므로, 그 순간 원본 트랜잭션과의 연결이 끊긴다.

새 스레드에는 원본의 thread-bound 트랜잭션 컨텍스트가 없다. 그래서 @Async 리스너는 원본 Tx 밖에서 실행되고, 트랜잭션이 필요하면 자기 것을 새로 열어야 한다. @Async + AFTER_COMMIT + @Transactional(REQUIRES_NEW) 조합이 정석인 이유다 — 새 스레드 + 커밋 후 + 독립 Tx.

얻는 것 응답 분리

호출자(요청 스레드)는 리스너를 기다리지 않고 즉시 반환. Kafka 발행처럼 느릴 수 있는 부가 작업이 사용자 응답을 지연시키지 않는다.

잃는 것 실패 가시성

리스너 예외가 AsyncUncaughtExceptionHandler로 삼켜진다. 호출자는 이미 "성공" 응답을 받은 뒤라, 백그라운드 실패는 아무도 모른다.

graceful shutdown 필수@Async 스레드풀(ThreadPoolTaskExecutor)은 배포/종료 시 작업을 다 못 끝내고 죽을 수 있다. setWaitForTasksToCompleteOnShutdown(true) + setAwaitTerminationSeconds(N)을 명시하지 않으면, 커밋 직후 발행 스레드가 죽어 이벤트가 유실된다(29CM 실제 사고, 05 문서 §6).
그래서@Async 발행은 본질적으로 best-effort다. 유실이 안 보이므로, 보장이 필요하면 반드시 outbox + 릴레이 backstop을 둔다(05 문서). @Async는 지연을 줄이는 최적화이지 보장 장치가 아니다.

MATRIX

종합 매트릭스

리스너 뒤에서 쓰기/변경이 일어날 때, 그게 어느 트랜잭션에서 돌고 커밋되는가 — 한 표로.

한 줄 판별"이 뒤 작업이 원본과 같이 롤백돼야 하나?" → 예면 커밋 전(같은 Tx): 동기 @EventListener / BEFORE_COMMIT. 아니오(커밋된 뒤에만, 실패해도 원본 보존)면 커밋 후 + REQUIRES_NEW.

PITFALLS

JPA에서 실제로 터지는 문제

"가끔 트랜잭션 문제가 난다"의 정체 — 대부분 이 다섯 중 하나다.

  • AFTER_COMMIT 조용한 유실. 새 Tx(REQUIRES_NEW) 없이 save() → 참여만 하고 커밋 안 됨. 에러도 없어 가장 찾기 어렵다. §3
  • 리스너가 아예 안 뜬다. 트랜잭션 밖에서 발행하면 @TransactionalEventListener는 버려진다. 발행 메서드에 @Transactional이 있는지 확인. §2
  • 통합 테스트에서 AFTER_COMMIT 미발화. 테스트 클래스에 @Transactional을 붙이면 테스트 Tx가 롤백돼 커밋이 안 일어나 리스너가 안 뜬다. → DatabaseCleanup + @BeforeEach 방식. CLAUDE.md
  • REQUIRES_NEW 커넥션 소모. 동기 REQUIRES_NEW는 원본을 suspend한 채 새 커넥션을 잡는다 — 풀이 작으면 고갈/데드락 위험. @Async면 원본이 이미 끝나 완화된다. §4
  • @Async 예외 삼킴 + shutdown 유실. 실패가 안 보이고, graceful shutdown 미설정 시 배포마다 샌다. §4
왜REQUIRED로 join하면 왜 커밋이 안 되나

AFTER_COMMIT은 원본 트랜잭션의 afterCompletion 콜백 시점이다. 이때 원본은 이미 커밋이 끝났지만, thread-bound 리소스(EntityManager/Connection)는 콜백이 끝날 때까지 아직 스레드에 매여 있다. 여기서 기본 REQUIRED로 @Transactional 메서드를 호출하면 "기존 트랜잭션에 참여(join)"하려 하는데, 그 대상은 이미 커밋이 완료된 트랜잭션이다. 그래서 그 안의 변경은 커밋될 곳이 없어 silent no-op이 된다. Spring이 이 함정을 부팅 시점에 REQUIRED 거부로 막는 이유다(6.2+).[2]
