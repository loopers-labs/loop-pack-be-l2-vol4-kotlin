companion object는
왜 static이 아닌가

@MethodSource가 팩토리 메서드를 못 찾는 사건에서 출발해, Kotlin이 static을 없애고 companion object로 대체한 이유와 @JvmStatic이 놓는 다리까지 바이트코드 레벨로 추적합니다.

1

PROBLEM

발단 — 팩토리 메서드를 못 찾는다

파라미터화 테스트에서 @MethodSource로 데이터를 공급하려는데, companion object에 둔 팩토리 메서드를 JUnit이 못 찾고 터집니다.

DiscountPolicyTest.kt 
class DiscountPolicyTest {
    @ParameterizedTest
    @MethodSource("discountCases")
    fun `할인 계산`(type: CouponType, value: Long, expected: Money) { ... }

    companion object {
        // ❌ @JvmStatic 없음 → JUnit 이 static 으로 못 찾는다
        fun discountCases() = listOf( ... )
    }
}
에러Could not find factory method [discountCases] — 분명 companion object 안에 메서드가 있는데 "없다"고 합니다. 여기서 질문이 시작됩니다: companion object 의 메서드는 static 이 아닌가?

JUnit 공식 문서는 그 조건을 못 박습니다.

"Factory methods within the test class must be static unless the test class is annotated with @TestInstance(Lifecycle.PER_CLASS)."

— JUnit 5 User Guide, Parameterized Tests[3]

JUnit은 테스트 인스턴스가 만들어지기 전에 파라미터를 확보해야 해서, 팩토리를 static 메서드로 리플렉션 조회합니다. 그런데 Kotlin의 companion object 멤버는 — 이름과 달리 — JVM에서 static이 아닙니다.

2

MECHANISM

static vs companion 의 실체

Kotlin에는 static 키워드가 아예 없습니다. companion object는 "클래스 레벨 멤버"를 별도의 싱글톤 객체로 풀어낸 것입니다.

"Members of companion objects look like static members from other languages, but they are actually instance members of the companion object — they belong to the object itself."

— Kotlin Docs, Object declarations[1]

그래서 호출 경로가 다릅니다. Java static은 클래스에 직접 붙어 invokestatic으로 한 번에 가지만, Kotlin companion은 먼저 Companion 인스턴스를 꺼내고(getstatic) 그 위에서 인스턴스 메서드를 호출(invokevirtual)하는 2단계입니다.

이 마지막 사실이 1번 사건의 정답입니다. JUnit은 Foo에서 static discountCases를 찾는데, 실제로는 Foo$Companion에 인스턴스 메서드로 들어가 있어 리플렉션 조회가 빗나갑니다.

관점Java staticKotlin companion object
실체클래스에 직접 붙은 멤버Companion 싱글톤 객체의 인스턴스 멤버
인스턴스없음Companion 객체 1개가 항상 존재
JVM 호출invokestaticgetstatic + invokevirtual
static 리플렉션 조회찾힘안 찾힘 (Foo$Companion에 있음)
단, 초기화 시점은 같다Kotlin 공식 문서에 따르면 companion object는 대응 클래스가 로드될 때 초기화되어 Java static 이니셜라이저의 시맨틱과 일치합니다[1]. "static이 아니다"는 호출 메커니즘 얘기지, 지연 생성된다는 뜻이 아닙니다.
3

BRIDGE

@JvmStatic — 다리를 놓는다

@JvmStatic을 붙이면 컴파일러가 바깥 클래스에 진짜 static 메서드를 추가로 생성합니다. 기존 인스턴스 메서드는 그대로 두고, static 버전을 하나 더 만드는 것입니다.

"If you use this annotation, the compiler generates both a static method in the enclosing class of the object and an instance method in the object itself."

— Kotlin Docs, Calling Kotlin from Java[2]
해결 — companion object + @JvmStatic 
companion object {
    @JvmStatic
    fun discountCases() = listOf(
        Arguments.of(CouponType.RATE,  10L, Money(10000), Money(1000)),
        Arguments.of(CouponType.FIXED, 2000L, Money(10000), Money(2000)),
    )
}
4

RATIONALE

왜 이렇게 설계했나

핵심은 하나입니다 — static은 객체지향 모델에 난 구멍이라, Kotlin은 그 구멍을 1급 객체로 메웠습니다.

Java의 static 멤버는 객체 시스템 바깥에 있는 절차적 네임스페이스입니다. 그래서 객체라면 당연한 것들이 안 됩니다 — 인터페이스 구현 불가, 상속·오버라이드 불가, 변수로 넘기는 1급 객체가 아님. Kotlin은 이 특수 케이스를 지우고, 대신 object(싱글톤)라는 1급 객체를 도입했습니다. companion object는 그 object를 클래스에 하나 붙인 형태일 뿐입니다.

그래서 가능해지는 것 — companion이 인터페이스를 구현한다

companion 은 진짜 객체라 다형성에 참여한다 
interface Factory<T> { fun create(name: String): T }

class User(val name: String) {
    companion object : Factory<User> {     // static 으론 불가능
        override fun create(name: String) = User(name)
    }
}

val factory: Factory<User> = User   // companion 을 값으로 전달 — 1급 객체

Kotlin 공식 문서가 직접 드는 예시입니다[1]. companion은 객체이므로 인터페이스를 구현하고, 이름을 가질 수 있고(companion object Factory), 참조로 보관할 수 있습니다. Java static으로는 "정적 메서드 묶음을 추상화해 주입"하는 일이 불가능합니다.

대가 — Java 생태계와의 경계 비용

이 일관성은 공짜가 아니었습니다. 그 비용이 바로 1~3번에서 본 마찰입니다.

얻은 것 언어 일관성

모든 것이 객체. 다형성·인터페이스 구현·확장 함수·싱글톤 1급 시민. Kotlin만 쓰면 더 우아하다.

치른 것 경계 비용

"static 묶음"이 실은 인스턴스 메서드. Java 도구(JUnit·직렬화 등)와 만나면 @JvmStatic으로 다리를 놔야 한다.

설계 철학Kotlin은 언어 내부 일관성을 우선하고, Java 호환 비용은 @JvmStatic·@JvmField 같은 명시적 어노테이션으로 떠넘기는 선택을 했습니다. "평소엔 우아하게, 경계에서만 비용을 내라"가 의도된 트레이드오프입니다.
5

PRACTICE

실전 — @MethodSource 해법

팩토리 메서드를 공급하는 길은 둘입니다. 상황에 맞게 고릅니다.

방식장점주의점
companion object + @JvmStaticJUnit 표준, 별도 클래스 설정 없음Kotlin 보일러플레이트 약간
@TestInstance(PER_CLASS)@JvmStatic·companion 불필요, 인스턴스 메서드 허용인스턴스가 테스트 간 공유 → 상태 오염 위험

@TestInstance(PER_CLASS)는 JUnit의 인스턴스 수명주기를 "클래스당 1개"로 바꿔서, 팩토리로 인스턴스 메서드도 허용합니다[3]. 그러면 @JvmStatic은 물론 companion object 자체가 필요 없어집니다.

대안 — @JvmStatic 없이 
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
class DiscountPolicyTest {

    @ParameterizedTest
    @MethodSource("discountCases")
    fun `할인 계산`(type: CouponType, value: Long, expected: Money) { ... }

    // companion object 밖, 그냥 인스턴스 메서드 — @JvmStatic 불필요
    fun discountCases() = listOf( ... )
}
PER_CLASS 함정인스턴스가 테스트 간 공유되므로, 인스턴스 필드에 가변 상태를 두면 테스트끼리 오염될 수 있습니다. @BeforeEach로 초기화하지 않으면 위험합니다. 외부 클래스의 팩토리 메서드는 PER_CLASS와 무관하게 항상 static이어야 한다는 점도 기억합니다[3].

권장

  • 기본값은 companion object + @JvmStatic — 표준적이고 상태 공유 부작용이 없다
  • 상태 없는 순수 데이터 팩토리(DiscountPolicy 같은)라면 PER_CLASS도 가볍게 쓸 만하다
  • 인스턴스 필드에 가변 상태가 끼면 PER_CLASS는 피하거나 @BeforeEach 초기화 필수
한 줄 요약그래서 이게 다 무슨 얘기였나

companion object는 "Kotlin이 static을 없애고 대신 내놓은 싱글톤 객체"이고, @JvmStatic은 "그 객체 메서드를 Java가 아는 진짜 static으로도 노출해줘"라는 지시입니다. Kotlin 세계 안에서만 쓰면 차이가 안 보이지만, Java 기반 도구(JUnit @MethodSource, 직렬화 라이브러리 등)와 만나는 경계에서 이 차이가 드러납니다.
