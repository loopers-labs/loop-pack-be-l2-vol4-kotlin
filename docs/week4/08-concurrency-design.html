STRATEGY MATRIX

한눈에 보기 — 도메인별 동시성 전략

락 선택의 기준은 단 두 가지 — 충돌이 얼마나 자주 나는가, 충돌 시 재시도 비용이 얼마인가.

같은 주문 트랜잭션 안에서도 자원마다 경합의 성격이 다릅니다. 쿠폰은 한 유저의 한 행을 그 유저 본인만 경합하므로 충돌이 드물고, 재고는 인기 상품 한 행에 다수 유저가 몰리므로 충돌이 잦습니다. 좋아요 수는 아예 read-modify-write를 제거해 락 자체를 회피합니다.

자원충돌 특성선택한 전략근거
쿠폰 사용
user_coupon		 경합 주체가 같은 유저뿐 (더블클릭·중복 요청) → 충돌 빈도 매우 낮음 낙관락 @Version
+ status 가드 + UK		 드문 충돌에 행 락을 잡는 건 낭비. 커밋 시점 감지 + 실패 응답이 더 싸다
재고 차감

좋아요 수

(검증, 락 아님)		 사용자가 본 금액 ≠ 서버 계산이면 409 — 동의 없는 결제 차단

낙관락 충돌은 드물다고 가정

락을 잡지 않고 진행 → 커밋 시점 version 비교로 충돌 감지. 대기 비용 0, 대신 충돌 시 트랜잭션 전체 롤백·재시도. 충돌이 드문 자원(쿠폰)에 유리합니다.

비관락 충돌은 잦다고 가정

읽는 시점에 FOR UPDATE로 행을 선점 → 뒤 트랜잭션은 대기. 대기 비용이 있지만 재시도가 없고 정확합니다. 충돌이 잦은 자원(재고)에 유리합니다.

핵심하나의 전략을 전 도메인에 강요하지 않습니다. 충돌 빈도 × 재시도 비용으로 자원마다 따로 결정한 것이 이 설계의 뼈대입니다.

TRANSACTION BOUNDARY

트랜잭션 경계 — Facade에는 Tx가 없다

Tx①의 주인은 OrderService.place 하나. OrderFacade는 의도적으로 트랜잭션을 갖지 않는다.

OrderFacade는 현재 orderService.place()를 위임만 하는 얇은 컴포넌트지만, 트랜잭션을 두지 않은 것은 미래를 위한 의도된 자리 비움입니다. PG 연동(O-F1) 시 place(Tx①) → PG approve(Tx 밖) → confirm/fail(Tx②) 3단계를 지휘해야 하는데, Facade에 @Transactional이 붙어 있으면 외부 HTTP 호출(PG)이 DB 트랜잭션 안에 갇혀 커넥션과 락을 PG 응답 시간만큼 점유하게 됩니다.

order/application/OrderFacade.kt 
// Tx 어노테이션 금지 — PG 연동(O-F1) 시 place(Tx①) → approve(Tx 밖) → confirm/fail(Tx②) 를 지휘한다
@Component
class OrderFacade(
    private val orderService: OrderService,
) {
    fun place(userId: Long, command: OrderCreateCommand): OrderInfo =
        orderService.place(userId, command)
}
참고Controller → Facade → Service 모두 같은 스레드에서 호출되지만 트랜잭션은 place() 진입 시점에만 열립니다. PG가 들어와도 Tx①의 길이는 변하지 않는 구조입니다.
3

COUPON DOUBLE-USE

쿠폰 이중사용 차단 — 3중 방어

빠른 실패(status 가드) → 진짜 동시성 방어(@Version) → 데이터 구조 보장(UK). 층마다 역할이 다르다.

층장치막는 것한계 / 보완
1차 status 가드 — use()가 USED면 ALREADY_USED 409 이미 커밋된 사용을 같은 Tx 안에서 즉시 거절 (싼 실패) 동시 Tx 둘 다 AVAILABLE을 읽으면 통과 → 2차가 필요
2차 @Version 낙관락 — 커밋 시점 WHERE version = ? 동시 주문 2건의 race — 한쪽만 커밋, 한쪽은 충돌 예외 충돌 측은 Tx 전체 롤백 (의도된 동작)
구조 UK (user_id, coupon_id) 발급(grant) 중복 → 보유 행이 항상 1개 사용 경쟁이 “단일 행의 version 경쟁”으로 수렴하는 전제
coupon/domain/UserCoupon.kt 
@Table(name = "user_coupon", uniqueConstraints = [
    UniqueConstraint(name = "uk_user_coupon_user_id_coupon_id",
                     columnNames = ["user_id", "coupon_id"]),   // 구조: 보유 행 1개 보장
])
class UserCoupon( ... ) : BaseEntity() {

    @Version                                  // 2차: 커밋 시점 충돌 감지
    var version: Long = 0

    fun use(now: LocalDateTime) {
        if (status == UserCouponStatus.USED) {  // 1차: status 가드
            throw ConflictException(CouponErrorCode.ALREADY_USED)
        }
        status = UserCouponStatus.USED
        usedAt = now
    }
}

동시 주문 2건 시나리오

같은 유저가 같은 쿠폰으로 주문 A·B를 동시에 넣으면, 둘 다 AVAILABLE(version=0)을 읽고 status 가드를 통과합니다. 승부는 커밋 시점에 납니다 — Hibernate가 UPDATE ... WHERE id=? AND version=0을 날릴 때 먼저 커밋한 쪽만 1행이 갱신되고, 나머지는 0행이라 OptimisticLockException으로 트랜잭션 전체가 롤백됩니다.

핵심1차 status 가드는 성능 최적화(빠른 실패)이고, 진짜 동시성 방어는 @Version의 커밋 시점 충돌 감지입니다. 가드만으로는 동시 Tx의 race를 막을 수 없습니다.

INVENTORY · PESSIMISTIC LOCK

재고 차감 — 비관락 + ID 정렬 데드락 차단

인기 상품 재고는 줄 세워서 차감한다. 단, 줄 서는 순서를 전 주문이 똑같이 맞춰 데드락을 차단한다.

재고는 @Lock(PESSIMISTIC_WRITE) 쿼리 — 즉 SELECT ... FOR UPDATE — 로 행을 선점한 뒤 decrease()로 차감합니다. 도메인 메서드가 잔량 부족 시 STOCK_INSUFFICIENT 409를 던지므로, 락 안에서 검사·차감이 원자적으로 일어나 오버셀이 불가능합니다.

inventory/infrastructure/InventoryJpaRepository.kt 
@Lock(LockModeType.PESSIMISTIC_WRITE)   // SELECT … FOR UPDATE
@Query("select i from Inventory i where i.productId in :productIds and i.deletedAt is null order by i.productId")
fun findAllForUpdateByProductIdIn(@Param("productIds") productIds: List<Long>): List<Inventory>
order/application/OrderService.kt — place() 중 
// FOR UPDATE 는 ID 정렬 순서로 — 교차 주문 데드락 차단
val inventories = inventoryRepository
    .findAllByProductIdInForUpdate(productIds.distinct().sorted())
    .associateBy { it.productId }
command.items.forEach { line ->
    val inventory = inventories[line.productId]
        ?: throw NotFoundException(InventoryErrorCode.INVENTORY_NOT_FOUND)
    inventory.decrease(line.quantity.toLong())   // 부족 시 STOCK_INSUFFICIENT 409
}

교차 주문 데드락 — 왜 정렬이 필요한가

주문 A가 [P1, P2], 주문 B가 [P2, P1] 순서로 락을 잡으면 서로의 두 번째 락을 기다리는 교착이 생깁니다. productIds.distinct().sorted()가 모든 주문의 락 획득 순서를 productId 오름차순 단일 전역 순서로 통일해 사이클 자체를 제거합니다. distinct()는 같은 상품이 여러 라인으로 들어와도 락 대상에 한 번만 올립니다.

참고애플리케이션의 sorted()에 더해 JPQL에도 order by i.productId가 있어, 결과 순서와 락 의도가 쿼리 레벨에서도 명시됩니다. 락 대기 자체는 허용하되 사이클(교착)만 제거하는 것이 목표입니다.

ORDERING INSIDE TX①

Tx① 내부 작업 순서와 이유

원칙은 하나 — 싼 검증은 처음에, 비싼 락은 마지막에. 락 점유 시간을 최소로 만든다.

OrderService.place의 7단계는 임의 순서가 아닙니다. 실패 확률이 있는 검증을 앞에 배치해 락을 잡기 전에 떨어질 요청은 미리 떨어뜨리고, 비관락(재고)은 커밋 직전에 잡아 행 점유 시간을 최소화합니다.

#단계실패 시왜 이 위치인가
①빈 주문 검증 items.isEmpty()400DB 접근 0 — 가장 싼 검증을 가장 먼저
②활성 상품 조회 findAllActiveByIdIn404일반 SELECT, 락 없음 — 존재하지 않는 상품을 조기 차단
③스냅샷 생성 + 원금액 합산—주문 시점 가격·상품명을 고정 (이후 가격 변동과 무관)
④쿠폰 couponService.use (REQUIRED)404 / 409낙관락이라 행 점유 없음 + ⑤의 할인액 계산에 필요
⑤expected 3종 금액 게이트409 PRICE_CHANGED락 잡기 직전 마지막 게이트 — 사용자가 본 금액과 불일치 시 차단
⑥재고 FOR UPDATE + decrease()404 / 409비관락은 맨 마지막 — 점유 시간 최소화
⑦주문 저장 (PENDING_PAYMENT)—커밋과 함께 확정 — 결제 대기 상태로 시작

금액 게이트는 expectedOriginalAmount · expectedDiscountAmount · expectedTotalAmount 세 값을 서버 계산과 전부 비교합니다. 어느 하나라도 다르면 — 가격이 바뀌었든 쿠폰 정책이 바뀌었든 — 사용자가 화면에서 동의한 금액과 다른 결제이므로 409로 거절합니다.

락은 잡는 순간부터 비용이다. 잡기 전에 떨어질 요청은 전부 미리 떨어뜨린다.

— Tx① 단계 배치 원칙
핵심쿠폰 use(④)가 금액 게이트(⑤)보다 앞인 이유: 게이트가 비교할 할인액이 use의 반환값이기 때문입니다. 낙관락이라 행을 점유하지 않으므로 앞에 둬도 락 비용이 없고, 게이트 실패 시 USED 변경은 롤백으로 원복됩니다.
6

ATOMICITY · ROLLBACK

원자성과 롤백 — 단일 Tx 합류가 만드는 안전

게이트에서 죽든 재고에서 죽든, 쿠폰 USED까지 한 덩어리로 원복된다 — REQUIRED 합류 덕분에.

CouponService.use의 @Transactional은 기본 전파(REQUIRED)라서 place()가 연 Tx①에 합류합니다. 별도 트랜잭션이 아니므로, use 이후 어떤 단계에서 예외가 나도 — 금액 게이트 409, 재고 부족 409, 재고 없음 404 — 쿠폰의 status = USED 변경은 커밋된 적이 없어 함께 사라집니다. “쿠폰만 사용되고 주문은 실패”하는 부분 커밋이 구조적으로 불가능합니다.

현재 REQUIRED — Tx① 합류

쿠폰 use·재고 차감·주문 저장이 한 커밋으로 묶입니다. 어디서 실패해도 전부 원복 — 보상 로직이 필요 없습니다. 같은 DB 안의 작업이므로 이것이 가장 단순하고 정확한 선택입니다.

반례 REQUIRES_NEW였다면

use가 자기 Tx로 먼저 커밋 → 이후 금액 게이트가 실패하면 쿠폰만 소모된 채 주문은 없는 상태가 됩니다. 이를 되돌리려면 cancelUse() 보상 호출 + 보상 실패 처리까지 필요 — 같은 DB에서 굳이 살 필요 없는 복잡도입니다.

참고UserCoupon.cancelUse()가 이미 존재하지만 Tx① 롤백용이 아닙니다 — 같은 Tx 안에서는 롤백이 전부 처리합니다. 이 메서드는 PG 결제 실패(추후 Tx②) 시 이미 커밋된 USED를 되돌리는 보상용입니다.
7

LIKE COUNT

좋아요 — 락 없이 정합성 지키기

상태는 UK가 지키고, 카운터는 원자 UPDATE가 지킨다. 본 트랜잭션과 카운터 갱신은 분리한다.

좋아요의 진실 원본은 product_like 행의 존재 여부입니다. (user_id, product_id) UK가 같은 유저의 중복 좋아요를 구조적으로 차단하고, existsBy 선검사 + 멱등 처리(이미 있으면 그대로 성공)는 UX용 빠른 경로입니다. 비정규화 카운터인 product.like_count는 커밋 후 이벤트로 갱신합니다.

product/infrastructure/ProductJpaRepository.kt · ProductLikeCountEventHandler.kt 
// 원자 증감 — read-modify-write 없음 → lost update 원천 차단
@Modifying(clearAutomatically = true)
@Query("update Product p set p.likeCount = p.likeCount + 1 where p.id = :id")
fun increaseLikeCount(id: Long)

// 감소는 0 바닥 보장 — 음수로 내려가지 않는다
@Query("update Product p set p.likeCount = case when p.likeCount > 0 then p.likeCount - 1 else 0 end where p.id = :id")
fun decreaseLikeCount(id: Long)

// 핸들러 — 커밋 후 비동기 새 Tx. 실패는 로깅만 (결과적 일관성)
@Async
@Transactional(propagation = Propagation.REQUIRES_NEW)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
fun onLiked(event: ProductLikedEvent) { productRepository.increaseLikeCount(event.productId) }

같은 패턴으로 LikeEventHandler가 좋아요 이력(like_event)을 append합니다. 카운터가 틀어져도 이 이력 또는 product_like COUNT로 재집계할 수 있다는 것이 “실패는 로깅만”을 허용하는 근거입니다.

주의알려진 잔여 이슈: existsBy 선검사 → save 사이의 TOCTOU race는 현재 비범위(R1)로 남겨둔 상태입니다(코드 TODO 주석). race가 실제로 발생하면 UK 위반(DataIntegrityViolationException)으로 떨어지며, 추후 advice 변환 또는 락으로 보강 예정입니다.

NEXT STEPS

남은 일 — 검증과 확장

설계는 코드에 들어갔지만, 동시성은 테스트로 증명하기 전까지 “주장”일 뿐이다.

락·version·원자 UPDATE가 실제 경합에서 약속대로 동작하는지 멀티스레드 동시성 통합 테스트 3종으로 검증 완료했습니다 (10스레드, CountDownLatch 동시 출발, H2 MODE=MySQL).

  • 쿠폰 동시성 테스트 — 같은 쿠폰으로 10스레드 동시 주문 → 정확히 1건 성공, 9건은 낙관락 충돌/ALREADY_USED, 재고도 1개만 차감 OrderConcurrencyIntegrationTest
  • 재고 동시성 테스트 — 재고 5개에 10스레드 동시 주문 → 5건 성공·5건 STOCK_INSUFFICIENT, 최종 잔량 0 (초과 판매 없음) OrderConcurrencyIntegrationTest
  • 좋아요 동시성 테스트 — 10명 동시 like → like_count 정확히 10, 동시 unlike → 0 (비동기 핸들러 폴링 대기) ProductLikeCountConcurrencyIntegrationTest
  • PG 연동 (O-F1) — Facade가 place(Tx①) → approve(Tx 밖) → confirm/fail(Tx②) 지휘. 실패 시 보상: 재고 increase() + 쿠폰 cancelUse() 예정
  • UNKNOWN 상태 처리 — PG 응답 유실 시 markUnknown() 후 재조회/배치 정산 설계 예정
  • Tx① 설계 + 락 전략 구현 — 낙관락(쿠폰) · 비관락(재고) · 원자 UPDATE(좋아요) 코드 반영 완료 DONE
핵심PG가 들어와도 Tx①은 그대로입니다. 추가되는 것은 Tx 밖의 외부 호출과 Tx②(confirm/fail), 그리고 보상 경로뿐 — 이것이 Facade를 Tx 없이 비워둔 이유입니다.
