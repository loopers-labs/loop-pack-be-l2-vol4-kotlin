CONTEXT

전제 — 왜 "날짜 경계"가 문제인가

쓰기 시점 누적 설계에서는 이벤트가 올 때마다 score를 컬럼에 더해 둔다. 그런데 랭킹은 "일간"이다 — 자정에 점수를 어떻게 넘길 것인가.

ZSET 설계의 carry-over(전일 점수 ×0.1을 새 판에 넘겨 콜드 스타트 완화)를 RDB로 번역하면, 자정마다 전 상품의 점수를 한꺼번에 만지는 배치가 생긴다. 문제는 그 배치가 도는 동안에도 랭킹 조회는 계속 들어온다는 것. 여기서 저장 구조에 대한 선택지가 갈린다.

모델 A 하나로 유지 + UPDATE

product당 행 1개. 날짜 차원 없이 한 판을 계속 쓰고, 자정에 전 행을 score = score × 0.1로 제자리 감쇠시킨다. 조회가 읽는 판과 배치가 쓰는 판이 같다.

모델 B 날짜별 분리 + INSERT

(ranking_date, product_id)로 날짜마다 행을 분리. 자정 전에 내일 판을 미리 INSERT(전일 ×0.1)해 두고, 지난 판은 DELETE < D-2로 정리. 조회가 읽는 판(오늘)과 배치가 쓰는 판(내일)이 다르다.

쟁점기능은 둘 다 된다. 갈리는 것은 "자정 배치가 도는 동안 조회가 얼마나 아픈가" — 이것이 EXP-01의 측정 질문이었다.

MODEL A · IN-PLACE DECAY

모델 A — 한 판 유지 + 제자리 감쇠

product당 행 하나. 세 주체(이벤트 쓰기 · 자정 배치 · 조회)가 전부 같은 판, 같은 인덱스 위에서 움직인다.

model-a-in-place.sql 
-- 한 판: product당 1행, 날짜 차원 없음
CREATE TABLE product_ranking (
  product_id BIGINT        PRIMARY KEY,
  score      DECIMAL(12,3) NOT NULL DEFAULT 0,
  KEY ix_score (score DESC)
);

-- 평시 쓰기: 이벤트마다 델타 누적
INSERT INTO product_ranking (product_id, score) VALUES (?, ?)
ON DUPLICATE KEY UPDATE score = score + VALUES(score);

-- 자정 배치: 어제의 기여를 10%로 줄이는 "제자리 전면 감쇠"
-- ⚠️ 조회가 읽고 있는 바로 그 판(그 인덱스)을 전 행 UPDATE
UPDATE product_ranking SET score = score * 0.1;

프로세스 — 3자가 한 판을 공유

데이터 — 쌓이지 않고 덮어써진다

장단점

장점 단순함

✓ 행 수 = 상품 수로 고정 — 용량·정리 걱정 없음
✓ 날짜 차원이 없어 조회에 WHERE 불필요
✓ 정리(DELETE) 배치 자체가 없음 — 운영 부품 최소

단점 자정의 비용

✗ 배치가 조회와 같은 인덱스에서 경합 — 처리량 −41% 실측
✗ 전 행 재배치라 배치 자체도 24.1s
✗ 어제 판이 덮어써져 소실 — ?date= 과거 조회 불가
✗ 재실행하면 ×0.1이 중복 적용 — 비멱등

MODEL B · PRE-SEEDING

모델 B — 날짜별 분리 + 사전 시딩

날짜마다 판(행 집합)을 분리한다. 자정 배치는 오늘 판을 건드리지 않고, 내일 판을 미리 만들어 둔다.

model-b-pre-seeding.sql 
-- 날짜별 판: (ranking_date, product_id)가 행의 정체성
CREATE TABLE product_ranking_daily (
  ranking_date DATE         NOT NULL,
  product_id   BIGINT       NOT NULL,
  score        DECIMAL(12,3) NOT NULL DEFAULT 0,
  UNIQUE KEY uk_date_product (ranking_date, product_id),
  KEY        ix_date_score   (ranking_date, score DESC)
);

-- 평시 쓰기: 오늘 날짜 행에 누적 (새 날짜 행은 lazy 생성)
INSERT INTO product_ranking_daily (ranking_date, product_id, score)
VALUES (CURDATE(), ?, ?)
ON DUPLICATE KEY UPDATE score = score + VALUES(score);

-- 자정 전 배치: 내일 판을 "미리" 만든다 — 오늘 판은 안 건드림
INSERT INTO product_ranking_daily (ranking_date, product_id, score)
SELECT CURDATE() + INTERVAL 1 DAY, product_id, score * 0.1
FROM   product_ranking_daily WHERE ranking_date = CURDATE();

-- 보존: 이틀 지난 판 정리 (ZSET TTL 2Day 대응)
DELETE FROM product_ranking_daily
WHERE ranking_date < CURDATE() - INTERVAL 2 DAY;

프로세스 — 판마다 역할이 다르다

데이터 — 날짜별 판이 쌓이고, DELETE가 상한을 고정한다

장단점

장점 판의 분리

✓ 읽는 판·쓰는 판 분리 — 배치 중 조회 열화 −10%에 그침
✓ append만 하므로 배치도 3.9s (A의 1/6)
✓ 전일 판이 남아 ?date= 과거 조회 자연 지원
✓ INSERT 기반이라 재실행 안전(멱등)하게 만들기 쉬움

단점 운영 부품 증가

✗ 행 수 = 상품 수 × 보존 일수로 증가
✗ DELETE < D-2 정리 배치가 추가로 필요
✗ 모든 쿼리에 WHERE ranking_date가 붙음
✗ 시딩(23:50) 이후 자정까지의 이벤트는 내일 판 초기값에 미반영 — 근사 감수

10만 행 · 동시성 32에서 "배치가 도는 동안의 조회"를 쟀다. 가설(사용자, 7/14): B는 다른 행에 쓰므로 영향 미미, A는 열화 — 단 MVCC라 블로킹이 아니라 자원 경합으로 나타날 것.

ROOT CAUSE

왜 A가 비싼가 — 인덱스 재배치

score를 제자리에서 바꾸는 것은 "값 하나 고치기"가 아니다. 정렬 인덱스에서는 엔트리의 삭제 + 재삽입이다.

ix_score (score DESC)는 score 순으로 정렬된 B-tree다. UPDATE score = score × 0.1은 10만 엔트리 전부의 정렬 위치를 이동시킨다 — 옛 위치에서 삭제하고 새 위치에 재삽입. 이 작업이 벌어지는 인덱스 페이지가 조회(Top-20 인덱스 리드)가 읽는 바로 그 페이지들이라, 버퍼풀·리두·언두에서 정면 경합이 난다.

반면 B의 INSERT INTO 내일 SELECT는 ix_date_score에서 내일 날짜 프리픽스 구간에 append할 뿐이다. 오늘 판 구간은 물리적으로 다른 페이지들이므로 조회와 부딪히지 않는다.

확인된 함정예측대로 잠금 블로킹은 0회였다 (InnoDB MVCC — SELECT는 행 잠금에 안 막힘). 그러나 "SELECT는 잠금에 안 막힌다"가 "영향 없다"는 뜻이 아니었다 — 열화는 잠금이 아니라 자원 경합의 형태로 처리량 −41%가 되어 나타났다. 이 낙차가 블로그 소재다.
6

DECISION

판정과 함의

쓰는 판과 읽는 판을 분리하라 — 날짜 경계는 제자리 감쇠가 아니라 사전 시딩이다.

— EXP-01 판정, WRITING-LOG 결정 로그 (2026-07-14)

MySQL Stage 1b의 날짜 경계 처리는 모델 B(날짜별 분리 + 사전 시딩)로 확정했다. 모델 A의 단순함(행 수 고정, 정리 배치 불필요)은 자정마다 반복되는 −41% 열화를 정당화하지 못한다.

추가 비용없음행 수 ×보존일수 · DELETE 배치

ZSET과의 구조적 동형성

이 결론은 ZSET 설계의 carry-over(23:50에 ZUNIONSTORE로 내일 키를 사전 생성)와 정확히 같은 구조다. Redis에서 "내일 키를 미리 만든다"가 자연스러워 보였던 것이, RDB로 번역해 실측하니 왜 그래야 하는지(읽는 판 보호)가 수치로 증명됐다. 날짜별 키 분리 = 날짜별 행 분리, TTL 2Day = DELETE < D-2.

최종 결정 (2026-07-15) — carry는 배치가 아니라 dual write로

날짜별 판 분리(모델 B)라는 구조는 유지하되, carry-over의 실행 메커니즘을 23:50 배치에서 dual write로 바꿨다. 이벤트를 소비할 때 오늘 판 +Δ와 내일 판 +Δ×0.1을 한 트랜잭션에서 함께 쓴다 — ZSET 번역은 ZINCRBY 2회.

선택 이유① carry 신뢰성 승격 — 배치라는 별도 실패 모드가 클래스째 사라지고, carry가 본 쓰기 경로의 멱등(EventHandled)·트랜잭션 보장을 그대로 상속한다. ② 누락 창 0 — 23:50~00:00 10분 컷 자체가 소멸한다. ③ 덮어쓰기 배제 — 배치 계열의 안전장치였던 "통짜 재시딩(DELETE+INSERT)"과 모델 A의 제자리 UPDATE는 덮어쓰기 = 데이터 상실 연산이다. 누적(additive)만 존재하는 쓰기 경로가 복구·감사 관점에서 구조적으로 안전하다.

지불하는 대가 — 이벤트당 쓰기 2배(핫패스 영구 비용, Stage 1b에서 단일 vs dual 처리량·p95 실측 예정) · 감쇠가 1일 절단(지수 연쇄의 ×0.01 항 소실 — 무시 가능) · 실시간 가중치 변경(Nice) 시 내일 판이 구·신 가중치 혼합 · 트랜잭션이 2행을 만지므로 잠금 순서(날짜 오름차순) 고정. 전체 논거와 버린 대안은 WRITING-LOG 2026-07-15 결정 로그에 기록했다.

연관 결정carry-over 가중치 ×0.1과 실행 시각 23:50의 의미

×0.1 = 시스템의 기억력 파라미터. 매일 ×0.1 연쇄는 지수 감쇠다 — 이틀 전 기여 0.01배, 사흘 전 0.001배, 과거 총 기여 상한 ≈ ×0.111. 과거 인기 상품의 head 고착(롱테일)이 구조적으로 불가능해진다. 0.5면 안정 우선, 0.1이면 신선도 우선, 0.01이면 사실상 리셋 — 콜드 스타트 땜빵이 아니라 신선도 vs 안정성 다이얼이다 (2026-07-14 논의).

왜 23:50인가. 23:50 사전 생성은 23:50~00:00 10분치 시딩 누락(실효 ~0.07%)을 감수하는 대신, 덮어쓰기 방식이라 재실행 멱등 + 새 판 쓰기와 경합이 없다. 대안인 00:00 self-union은 누락 0·원자적이지만 재실행 시 중복 가산(비멱등). 시딩은 근사치가 목적이므로 멱등을 우선해 23:50 채택 (2026-07-14 논의).
