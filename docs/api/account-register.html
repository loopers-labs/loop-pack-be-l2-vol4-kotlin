01

OVERVIEW

개요

새 사용자 계정을 등록하는 공개 endpoint다. 인증 없이 누구나 호출할 수 있다.

AccountController.createAccount 가 POST /api/v1/users 를 매핑한다. 요청 body 인 AccountCreateRequest 를 AccountCreateCommand 로 변환해 AccountService.create 에 전달하고, 서비스가 입력 검증 · 중복 확인 · 비밀번호 해싱 · 저장을 한 트랜잭션 안에서 수행한다.

공개 endpoint 확인AccountSecurityConfig 의 filter chain 에서 requestMatchers(POST, "/api/v1/users").permitAll() 로 선언되어 있어 인증 토큰 없이 접근 가능하다. (그 외 경로는 anyRequest().authenticated())

내부 도메인 명칭은 account 를 유지한다. 외부 라우트만 평가 스펙에 맞춰 /api/v1/users 를 쓰며, user 는 MySQL mysql.user 시스템 테이블 / Spring Security User 와 충돌하므로 내부 코드에 도입하지 않는다. 따라서 컨트롤러 · 패키지 · 테이블은 모두 account_* 명칭이다.

02

REQUEST · RESPONSE

요청 · 응답

컨트롤러 시그니처

AccountController.kt 
@RestController
@RequestMapping("/api/v1/users")
class AccountController(
    private val accountService: AccountService,
) {
    @PostMapping
    fun createAccount(
        @RequestBody request: AccountCreateRequest,
    ) {
        accountService.create(request.toCommand())   // 반환값 없음 (Unit)
    }
}

요청 Body — AccountCreateRequest

모든 필드는 필수다. @Valid 를 쓰지 않으며, 형식 검증은 서비스/도메인 레이어에서 수동(fail-fast)으로 수행한다. birthDate 는 Jackson 이 LocalDate 로 바인딩한다.

필드타입설명
loginIdString로그인 ID. 영문 대소문자 · 숫자만 (^[A-Za-z0-9]+$), 최대 255자. PASSWORD 인증의 식별자로 쓰인다
emailString이메일. ^[A-Za-z0-9._%+-]+@... 형식, 최대 255자. 계정당 unique
passwordString비밀번호. 8~16자, 출력 가능 ASCII([!-~])만, 생년월일 숫자(YYYYMMDD/YYMMDD) 포함 금지
nameString이름. 공백 불가, 최대 100자
birthDateLocalDate생년월일(yyyy-MM-dd). 미래 날짜 불가

응답

성공 시 응답 body 가 없다. 컨트롤러 메서드가 Unit 을 반환하고 @ResponseStatus 를 두지 않으므로 HTTP 상태는 200 OK 다. 빈 응답이라도 ApiResponseBodyAdvice 가 가로채 공통 ApiResponse 로 감싼다.

공통 래핑ApiResponseBodyAdvice.beforeBodyWrite 가 본문(여기선 null)을 ApiResponse.success(null) 로 감싼다. 결과는 meta(isSuccess/status/code/message/timestamp) + data 구조이며, Jackson NON_NULL 정책에 따라 data 가 null 이면 직렬화에서 생략된다.

200 OK — ApiResponse 래핑 결과 (data 는 null 이라 생략)

  "isSuccess": true,

  "code": null,

04

BUSINESS LOGIC

비즈니스 로직

AccountService.create 가 @Transactional 경계 안에서 아래 순서로 처리한다. 모든 검증은 수동 fail-fast 이며 @Valid 를 사용하지 않는다.

  1. 생년월일 검증 — validateBirthDate 가 미래 날짜를 거부한다. 400 INVALID_BIRTH_DATE
  2. 식별자(loginId) 검증 · VO 생성 — CredentialIdentifier(PASSWORD, loginId) 의 init 에서 길이(≤255) + 패턴(^[A-Za-z0-9]+$) 검사. 400 INVALID_CREDENTIAL_IDENTIFIER
  3. 이메일 검증 · VO 생성 — Email(email) 의 init 에서 길이(≤255) + 형식 정규식 검사. 400 INVALID_EMAIL
  4. 이름 검증 · VO 생성 — AccountName(name) 의 init 에서 공백 불가 + 길이(≤100) 검사. 400 INVALID_ACCOUNT_NAME
  5. 비밀번호 검증 — PasswordValidator.validate 가 길이(8~16) · 허용 문자([!-~]) · 생년월일 숫자(YYYYMMDD/YYMMDD) 미포함을 검사. 400 INVALID_PASSWORD
  6. loginId 중복 확인 — accountCredentialRepository.existsBy(PASSWORD, identifier) 가 true 면 거부. 409 DUPLICATE_LOGIN_ID
  7. email 중복 확인 — accountRepository.existsByEmail(email) 가 true 면 거부. 409 DUPLICATE_EMAIL
  8. Account 저장 — Account(name, birthDate, email, role=USER) 를 생성해 accountRepository.save. INSERT account
  9. 비밀번호 BCrypt 해싱 — passwordEncryptor.encode(password) (BCryptPasswordEncoder) 결과를 CredentialSecret 으로 감싼다. 평문은 저장하지 않는다.
  10. Credential 저장 — AccountCredential(account, PASSWORD, identifier, secret) 를 accountCredentialRepository.save. INSERT account_credential

05

CAUTION

주의 사항

중복 가입 동시성사전 existsBy / existsByEmail 체크는 race condition 을 막지 못한다. 동시에 같은 loginId/email 로 가입하면 두 요청 모두 체크를 통과한 뒤 INSERT 에서 충돌한다. 이때 account(uk_account_email) / account_credential(uk_account_credential_method_identifier) DB unique 제약이 최종 방어선이다. 위반 시 DataIntegrityViolationException 이 발생하고, ApiControllerAdvice.handleConflict 가 메시지에 "Duplicate" 가 포함되면 409 COMMON:CONFLICT 로, 그 외(FK/NOT NULL 등)는 500 으로 변환한다.
평문 비밀번호 로깅 금지비밀번호는 CredentialSecret VO 로 감싸지며, 이 VO 의 toString() 은 원문 대신 "[PROTECTED]" 를 반환한다. 또한 도메인 예외는 errorCode 만 사용하고 사용자 입력값(이메일/loginId/비밀번호)을 customMessage 에 끼워넣지 않는다 — advice 가 e.message 를 로깅할 때 PII 가 로그에 남는 것을 막기 위함이다.
참고비밀번호 형식 검증(8~16자 등)은 회원가입과 비밀번호 변경에서 동일한 PasswordValidator 규칙을 공유하지만, 같은 형식 위반이 인증(로그인) 단계에서는 401 이 아니라 400 으로 자연 전파되는 등 컨텍스트별로 status 가 갈리는 것이 의도된 설계다.
