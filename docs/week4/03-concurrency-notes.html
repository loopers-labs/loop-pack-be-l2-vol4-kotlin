CRITICAL SECTION

임계영역과 Lost Update

임계영역 = 여러 실행 흐름이 같은 데이터를 동시에 읽고 쓰는 구간. 보호하지 않으면 갱신이 사라집니다.

이번 과제의 임계영역① 재고 차감 · ② 쿠폰 사용(1회성) · ③ like_count 증감. 각각 보호 전략이 다릅니다. (쿠폰 발급 수량(선착순)은 관리자 발행이라 경합이 없어 이번 스코프 밖 — 셀프 발급 백로그.)

STRATEGY

락 전략 3가지 선택지

정답은 없습니다. 경합 빈도와 비용으로 고릅니다. 셋의 동작 방식부터 그림으로 봅니다.

관점비관락낙관락 / 원자 UPDATE
적합경합 잦고 충돌 비싼 곳경합 드물거나, 단일 카운터 증감
비용락 보유·대기·데드락 관리충돌 시 재시도(낙관) / 거의 없음(원자)
이번 적용재고 차감쿠폰 사용(낙관) · like_count(원자)
고민 포인트경합이 드문데 비관락을 쓰면 비용만 늘고, 경합이 잦은데 낙관락을 쓰면 재시도가 폭증합니다. 빈도를 먼저 가늠하세요.

ISSUE vs USE

발급 vs 사용 — 경합이 다르다

같은 쿠폰 도메인이라도 발급과 사용의 경합 양상은 정반대입니다. 그래서 락 전략도 갈립니다.

스코프 주의아래 발급(한정 수량) 고경합은 셀프 발급·선착순을 도입할 때(백로그) 적용되는 대비입니다. 이번 과제의 관리자 발행은 단독 행위라 경합이 없습니다 — 개념 학습용으로 남겨둡니다.

발급 고경합

한정 수량이면 잔여를 모두가 깎음. 낙관락이면 재시도 폭증 → 원자 UPDATE. 중복은 UK로.

사용 저경합

단일 소유 row. 같은 순간 2기기는 드묾. 재시도 없이 낙관락, 충돌 시 주문 실패.

스스로 물어볼 것"같은 도메인인데 발급은 원자 UPDATE, 사용은 낙관락 — 왜 다른가?"에 한 문장으로 답할 수 있으면 이해한 것입니다.
4

TRANSACTION

트랜잭션 경계 · 데드락

주문은 재고·쿠폰·주문 저장을 한 트랜잭션으로 묶습니다. 락을 둘 이상 잡으면 획득 순서가 데드락을 가릅니다.

핵심재고는 비관락, 쿠폰은 낙관락(=락 미보유)이면 락 자원이 inventory 하나뿐 → 순서 사이클이 없어 데드락 불가. 만약 쿠폰도 비관락이면 inventory→coupon 순서를 전역 고정해야 합니다.

범위 너무 크면?

락 보유 중 외부 I/O(결제 등)가 들어오면 락이 길어짐. 지금은 외부 호출 없음 — 결제 붙으면 분리 고민.

롤백 보장

단일 @Transactional이라 쿠폰 검증 실패·낙관락 충돌 어느 하나라도 전체 롤백. 재고도 원복.

MORE

나머지 논점 · 비동기

접어둔 논점들. 펼쳐서 고민 포인트를 확인하세요.

논점like_count — 이미 해결, 그래도 볼 것

임계영역: 동시 좋아요 → like_count Lost Update. SET like_count = like_count + 1 원자 UPDATE로 이미 해결됨(추가 락 금지).

남은 고민: ProductLike 존재검사 TOCTOU(선검사→저장 경합, 현재 비범위). 비동기 AFTER_COMMIT 핸들러 실패 시 like_count 누락 → 재집계. "좋아요가 수십개씩 빠진다" 시나리오의 원인 진단.

논점격리 수준(Isolation Level)

MySQL 기본 REPEATABLE READ. 비관락(FOR UPDATE)은 격리수준 무관하게 직렬화하지만, 낙관락·원자 UPDATE는 격리수준 의존성이 다릅니다. 지급 중복(UK) 검사에 팬텀·넌리피터블 리드가 영향을 주는지 확인.

논점정합성을 어느 계층에서? (DB 제약 vs 앱 락)

UK/CHECK 제약(DB, 최후 방어선)과 도메인 검증+락(앱, 의미화)의 역할 분담. 예: 발급 중복은 UK가 보증하고, 비즈니스 메시지는 앱이 변환. 둘 다 두는 게 보통 옳습니다.
