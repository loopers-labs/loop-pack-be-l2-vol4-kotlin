PG 연동 · 결제창(SDK) 방식

결제창 결제는
화면·데이터·의미로 본다

실무 B2C 결제(토스·포트원 같은 결제창 방식)에서 사용자가 보는 5개 화면과, 그 뒤에서 브라우저·서버·PG가 주고받는 데이터, 그리고 각 데이터의 의미를 한 장에 정리합니다. 핵심은 하나 — 결제 확정의 주체는 클라이언트가 아니라 서버(confirm)입니다.

1

FULL FLOW

전체 플로우 (화면 + 서버·PG 처리)

왼쪽 위부터 8칸이 차례로 흐릅니다(2줄). 폰 화면 → 서버 처리 → 폰 화면 → PG 처리가 핑퐁하며, 서버·PG 칸엔 안에서 무슨 처리를 하는지, 화살표 대신 각 칸에 받는/보내는 데이터를 적었습니다.

두 가지만 먼저 박아두세요. ③ 결제창은 내 서비스가 아니라 PG가 그려주는 화면이고, ⑥ 서버 confirm이 돈이 실제로 빠지는 단 하나의 지점입니다.

먼저 박아둘 것결제창(③)은 내 서비스가 아니라 PG가 그린 화면이라 카드번호가 내 서버를 안 거칩니다(그래서 PCI-DSS 부담을 PG로 넘김). 그리고 화면이 "완료"처럼 보여도 확정의 주체는 서버의 confirm(⑥)입니다.
🔑 인증(키)이 흐름 어디에 붙나③ 결제창은 클라이언트 키(공개)로 띄우고 카드 주인은 그 안에서 인증합니다. ⑥ confirm은 시크릿 키(서버 전용)로 호출 — 그래서 클라이언트 키가 노출돼도 돈은 못 움직입니다. 키 = "어느 회사", 카드 인증 = "누가 결제하는지"를 식별합니다.

DATA ON THE WIRE

무슨 데이터가 오가나

화면 뒤에서 브라우저 · 서버 · PG 세 주체가 주고받는 메시지입니다. 실선은 요청, 점선은 응답/통지.

DATA TABLE

데이터 한눈에 보기

각 데이터가 왜 그 방향으로, 무슨 의미로 흐르는지가 핵심입니다.

단계방향데이터의미
①브라우저 → 서버상품, 수량주문 의도 전달
①서버 내부order 저장(PENDING) + 금액 B"이 주문은 B원"을 서버가 못박음 — 이후 위변조 검증의 기준
②서버 → 브라우저orderId, 금액 B결제창 SDK 초기화에 필요한 값
②브라우저 → PGorderId, 금액, 카드정보카드정보는 PG가 직접 수령(내 서버 미경유)
③PG → 브라우저paymentKey, orderId, 금액 C인증 성공 증표 — 아직 미차감. C는 결제창에서 돌아온 금액
④브라우저 → 서버paymentKey, orderId, 금액 C"인증됐다"는 통보 (결제 확정 아님)
④서버 검증저장 B == 받은 C ?금액 위변조 차단 — 다르면 승인 거절
⑤서버 → PGconfirm(paymentKey, 금액)★ 여기서 실제 차감 — 결제 확정의 단일 지점
⑤PG → 서버status: DONE, 승인번호차감 완료 → 주문 PAID 전이
⑥PG → 서버웹훅(status)보조 통지 — 리다이렉트가 끊겨도 결과 도착
⑥서버 → PG단건조회(paymentKey)웹훅 본문을 안 믿고 실제 상태 재확인 후 반영
4

AMOUNTS

금액은 사실 여러 개다

같은 "58,000원"처럼 보여도, 출처가 다른 금액이 최소 둘입니다. 이걸 구분 못 하면 검증 로직이 흔들립니다.

B서버 저장 금액

① 주문 생성 때 서버가 계산·저장한 진짜 금액. 신뢰의 기준점. 쿠폰·할인 적용 후 최종값.

C결제창에서 온 금액

③ 리다이렉트로 클라이언트를 거쳐 돌아온 금액. 중간에 조작될 수 있어 믿을 수 없음.

검증 규칙confirm 전에 반드시 B == C를 확인합니다. 클라이언트가 amount를 1원으로 바꿔 보내도, 서버가 저장한 B와 다르면 승인하지 않습니다. "받은 값"이 아니라 "내가 저장한 값"으로 승인하는 게 핵심.
참고실제로는 주문서 표시가(A)까지 더해 3개로 보기도 합니다 — A(화면 표시) vs B(서버 저장)는 주문 생성 시점 검증, B vs C는 결제 승인 시점 검증. 지금은 B/C 두 개만 확실히 잡아도 충분합니다.
5

WHY SERVER

왜 서버가 confirm 하나

"클라이언트가 결제창에서 인증까지 했는데 왜 서버가 한 번 더?" — 클라이언트는 신뢰할 수 없기 때문입니다.

인증(③)까지는 브라우저가 주도하지만, 브라우저는 사용자가 조작할 수 있는 영역입니다. 금액을 바꿔치기하거나, 가짜 성공 신호를 보낼 수 있습니다. 그래서 돈을 실제로 빼는 결정(confirm)은 신뢰 경계 안쪽인 서버가 직접 PG에 요청합니다. 이게 "서버가 한 번 더 승인"의 이유입니다.

"결제 인증과 승인이 비동기적으로 일어나기 때문에, 결제 결과를 받으려면 반드시 웹훅을 연동해야 합니다."

— 토스페이먼츠, 결제 흐름 이해하기 (내 학습노트 인용)

실무에서 결제 사고는 거의 이 2개를 빼먹어서 난다

1 · 금액 검증 (승인 전)

클라이언트가 amount를 1원으로 조작해 승인 요청 → 서버 저장 금액(B)과 일치 확인 후에만 confirm.

2 · 웹훅 재검증 (수신 후)

위조된 가짜 웹훅을 진짜로 믿고 주문 완료 처리 → 웹훅 본문 말고 PG 단건조회로 실제 상태 재확인.

6

VS ASSIGNMENT

과제(직접연동)와 뭐가 다른가

위 흐름은 결제창 방식입니다. 우리 과제의 pg-simulator는 직접연동이라 결제창 단계가 통째로 빠집니다.

실무 B2C · 결제창(SDK)

브라우저가 PG 결제창을 띄움 → 리다이렉트 → 서버 confirm으로 확정 → 웹훅 보조. 카드정보는 PG가 받음.

과제직접연동 (서버→PG)

결제창·브라우저·리다이렉트 없음. 서버가 카드정보를 담아 POST /payments 직접 호출 → 즉시 PENDING → 콜백/조회로 확정.

대응 관계결제창 방식의 confirm 단계가, 과제에선 콜백 + 단건조회로 대체됩니다. "최종 확정을 클라이언트에 맡기지 않는다"는 원칙은 두 방식 모두 동일 — 다만 과제는 비동기 결과 + 장애 대응(Timeout·CircuitBreaker·Fallback)에 집중합니다.
그래서 과제에서 신경 쓸 데이터transactionKey(결제 식별), orderId(주문 매칭), status(PENDING→SUCCESS/FAILED), callbackUrl(결과 통지 주소). 콜백이 안 와도 GET /payments/{transactionKey}로 복구하는 게 reconciliation입니다.
7

THIS PROJECT

과제 PG 연동 — 전체 플로우

이제 우리 과제(pg-simulator · 직접연동) 버전입니다. 결제창·브라우저·리다이렉트가 없고, 서버가 PG에 직접 쏜 뒤 비동기 결과를 콜백·조회로 확정합니다.

차이 둘만 기억하세요. ① 응답이 즉시 PENDING이라 동기로는 결과를 모르고, ② 요청 자체가 40% 실패 + 콜백도 유실될 수 있어 Timeout · CircuitBreaker · 조회 복구가 필수입니다.

🛡 Resilience (과제 Must-Have)PG 호출(②)을 Timeout + CircuitBreaker로 감싸고, 타임아웃·서킷 open 시 Fallback → 주문 markUnknown() + 사용자에겐 정상 응답. PG 장애가 서비스 전체를 무너뜨리지 않게 하는 게 이번 과제의 알맹이입니다.
🔑 인증 (실무 대비)과제는 클라이언트/시크릿 키 분리 없이 X-USER-ID 헤더로 단순화했습니다. 실무라면 이 서버→PG 직접 호출(②)에 시크릿 키가 붙습니다. 결제창 confirm 자리를, 과제에선 콜백(⑥)+단건조회(⑦⑧)가 대신합니다.
확정의 주체는 여전히 서버결제창 방식이든 직접연동이든 최종 확정을 클라이언트에 맡기지 않는다는 원칙은 동일합니다. 다만 과제는 비동기 결과 + 장애 대응에 무게가 실립니다.
8

ECOSYSTEM

결제 생태계 — 승인·매입·정산

같은 6명의 참여자가 3단계(인증 → 매입 → 정산)에서 각각 다르게 움직입니다. 단계마다 실시간이냐 배치냐, 그리고 돈이 어디서 어디로 가는지가 핵심.

돈의 두 흐름❶ 고객 ↔ 발급사 — 체크카드는 승인 즉시 출금, 신용카드는 청구일에 후불. ❷ 발급사 → 매입사 → 가맹점 — 매입(배치) 후 T+N일에 정산. 이 둘의 타이밍이 달라서 "내 통장에선 빠졌는데 가게는 며칠 뒤 받는" 일이 생깁니다.
과제 관점이 6명 중 매입사·카드망·발급사는 전부 PG 뒤에 가려집니다. 과제에선 "PG가 비동기로 승인 결과를 준다"까지가 경계 — 매입·정산은 신경 쓸 필요 없습니다. 이건 면접용 배경지식입니다.

MECE CASES

pg-simulator 응답 케이스 (MECE)

pg-simulator와 주고받을 때 나올 수 있는 모든 응답을, 상호작용 지점별로 빠짐없이·겹치지 않게 나눴습니다. 핵심은 — 결국 우리 시스템 귀결은 PAID · FAILED · UNKNOWN 세 개로 수렴합니다.

유스케이스 다이어그램 — 누가 무슨 기능을 쓰나

먼저 범위부터. 액터(고객 · PG-Simulator)와 우리 서버(commerce-api)의 기능 관계입니다.
