정책인데 왜
매번 새로 만들까

"정책(policy)은 한 번 정해지면 안 바뀌는데, 왜 그 이름을 단 객체를 계산할 때마다 새로 만드는 걸까?" — 이 위화감이 사실 맞는 직관입니다. 쉬운 비유로 풀어봅니다.

핵심방법(how) vs 데이터(what)

1

ANALOGY

레시피로 이해하기

"정책"을 요리 레시피라고 생각해 보세요. 그러면 위화감의 정체가 바로 보입니다.

레시피(정책)는 "볶는 방법", "조리는 방법"처럼 방법입니다. 한 번 정해지면 안 바뀝니다. 반면 재료(데이터)는 당근 100g, 양파 2개처럼 그때그때 다릅니다.

이상한 버전그런데 우리가 한 건 — "당근 100g이 인쇄된 레시피"를 요리할 때마다 새로 찍어내는 것과 같습니다. 재료가 바뀔 때마다 레시피를 새로 인쇄하는 셈이죠. "레시피인데 왜 매번 새로 만들지?" 라는 위화감이 바로 이겁니다.
2

HOW vs WHAT

방법과 데이터를 나누기

코드로 옮기면 — 정책(DiscountPolicy)은 "깎는 방법", value는 "얼마"라는 데이터 입니다.

핵심방법(정책)에 데이터(value)를 박아 넣으면 → 데이터가 바뀔 때마다 새 객체가 생깁니다. "방법"인데 "데이터"처럼 매번 생기는 모순이 여기서 옵니다.
3

3 WAYS

세 가지 만드는 법

같은 할인 계산을 만드는 방법은 셋입니다. 그림으로 보면 차이가 분명합니다.

세 가지 비교
// ① 데이터를 박음 — value 가 객체 안에. 매번 new (사실상 값 객체)
class FixedDiscount(val value: Long) { fun discount(amount) = Money(value) }

// ② 하나를 공유 — value 는 호출 때 전달. 싱글톤 (교과서 정통)
object FixedDiscount { fun discount(value: Long, amount: Money) = Money(value) }

// ③ 객체 없음 — Coupon 이 자기 value 로 바로 (분기 한 곳이면 최선)
when (type) { FIXED -> value; RATE -> amount.amount * value / 100 }

REFERENCE

교과서가 말하는 것

"정책은 안 바뀌니 하나만 두고 공유하라"는 직관 — 디자인 패턴 고전이 똑같이 말합니다.

전략(Strategy) 객체는 종종 좋은 flyweight가 된다 — 상태가 없으면 여러 곳이 하나를 공유할 수 있다.

— GoF, Design Patterns (Strategy 구현 노트)[1]

여기서 flyweight(공유) 는 "같은 걸 여러 번 만들지 말고 하나를 나눠 쓰자"는 뜻입니다. 전략(정책)은 방법이라 안 바뀌니, 하나만 만들어 공유하라는 거죠 — 그림 3의 ②와 정확히 같습니다.

Joshua Bloch는 Effective Java 에서 더 직접적으로 말합니다 — "구체 전략은 보통 무상태(stateless)이므로 싱글톤이어야 한다."[3] Comparator 를 싱글톤으로 두는 것과 같은 이유입니다(불필요한 객체 생성을 피하려고).

그래서 ①은 뭔가?value 를 박은 ①은 엄밀히는 "정책(방법)"이 아니라 "값을 가진 객체(Value Object)" 입니다. 그래서 매번 생기는 게 당연하지만, "Policy"라는 이름과는 맞지 않습니다. 사용자가 느낀 어긋남의 정체가 이것입니다.

결론 — 우리 선택

① 데이터 박기

매번 new. 이름은 Policy인데 실체는 값 객체. 어정쩡.

② 싱글톤 공유

전략을 쓴다면 이게 정통(GoF·Bloch). value는 호출 때 전달.

우리 케이스그런데 value 는 이미 Coupon 이 갖고 있고, 분기도 calculateDiscount 한 곳뿐입니다. 그래서 객체로 감쌀 필요 없이 ③ when 이 가장 단순합니다. 할인 종류가 늘어나면 그때 ②로 올리면 됩니다.
