# 대기열 스케줄러 배치 크기 산정

`queue.admission.batch-size` 임시값(100)을 주문 API 실측 기반 값으로 재산정한다.

## 1. 산정 공식

산정 공식은 다음과 같이 도출했다.

- 주문 API가 감당할 수 있는 최대 처리량을 측정
- 소량의 안전 마진을 0.7 정도로 잡음

```
batch-size = 지속 가능한 최대 처리량(RPS) × 안전 마진(0.7)
```

## 2. 측정 조건

- 대상: `POST /api/v1/orders`
- 시나리오: 단일 핫 키 상품에 대한 접근
- 측정 구간:
  - 토큰 검증(Redis) → 재고 차감(DB) → 주문 저장(DB)
  - 이벤트 발행. 결제·포인트 차감은 비동기라 제외
- 방법: k6 `constant-arrival-rate`로 RPS 레벨(25~75, 5단위)마다 60초씩 독립 실행

## 3. 측정 판별 기준
- p95가 1초 이하여야 한다.
- 요청에서 서버 측 문제로 인한 실패가 없어야 한다.

## 4. 측정 결과

| 목표 RPS | 달성 RPS | p95 | 실패율(5xx 예외) |
| --- | --- | --- |-------------|
| 25 | 25.0 | 201ms | 0%          |
| 30 | 30.0 | 218ms | 0%          |
| 35 | 34.9 | 164ms | 0%          |
| 40 | 39.9 | 550ms | 0%          |
| **45** | **44.9** | **895ms** | 0%          |
| 50 | 49.9 | 1,224ms | 0%          |
| 55 | 48.4 | 6,652ms | 2.88%       |
| 60 | 49.6 | 8,355ms | 3.42%       |
| 65 | 49.5 | 11,863ms | 4.25%       |
| 70 | 56.9 | 9,262ms | 0.96%       |
| 75 | 52.9 | 14,354ms | 1.91%       |

- p95 < 1s를 만족하는 마지막 레벨은 45 RPS → `R_max = 45`
- 50 RPS에서 지연이 시작되고, 55 RPS부터 처리량 자체가 붕괴되는 모습 확인 가능
- 고부하 구간에서 HikariCP 커넥션 대기 발생 확인(`acquire_seconds_max=3.01s`, `timeout_total=464`, pool max=40). 락 경합이 커넥션을 오래 붙잡은 결과로 추정

## 5. 산정 결과

```
batch-size = 45 × 0.7 = 31.5
```

```yaml
queue:
  admission:
    batch-size: 31
    interval-ms: 1000
```
