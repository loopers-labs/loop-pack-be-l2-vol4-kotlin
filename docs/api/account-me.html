01

OVERVIEW

개요

인증된 사용자가 자기 자신의 계정 프로필을 조회하는 엔드포인트다.

이 API는 요청 본문을 받지 않는다. 누가 호출하는지는 인증 필터가 먼저 판별한 뒤, 컨트롤러에 request attribute로 넘겨준다. 즉 컨트롤러는 토큰/헤더를 직접 파싱하지 않고 이미 검증된 신원(accountId, loginId)만 받아 조회를 위임한다.

인증은 AccountHeaderAuthenticationFilter가 담당한다. 요청에 담긴 X-Loopers-LoginId / X-Loopers-LoginPw 헤더로 로그인 사용자를 확인하고, 성공하면 accountId(Long)와 loginId(String)를 HttpServletRequest attribute에 심는다. 컨트롤러는 @RequestAttribute로 이 두 값을 주입받는다.

CONTEXT 외부 라우트는 평가 스펙에 맞춰 /api/v1/users를 쓰지만, 내부 도메인/패키지/테이블은 account 명칭을 유지한다. 응답 JSON 필드는 도메인 필드명(loginId, email ...) 그대로라 외부에 account라는 단어가 노출되지 않는다.
02

REQUEST & RESPONSE

요청 · 응답

인증 요구 (RequestAttribute)

요청 본문은 없다. 대신 인증 필터가 주입한 두 attribute가 컨트롤러 파라미터로 바인딩된다. attribute가 없으면 바인딩이 실패한다(아래 비즈니스 로직 참고).

Attribute 키타입출처설명
accountId Long 인증 필터 인증 성공 시 주입되는 계정 PK. 조회 대상 식별에 사용
loginId String 인증 필터 인증된 로그인 ID. 응답에 그대로 반영

두 키는 AccountAuthenticationAttributes 상수로 정의되어 필터(쓰기)와 컨트롤러(읽기)가 같은 문자열을 공유한다 — ACCOUNT_ID = "accountId", LOGIN_ID = "loginId".

컨트롤러 시그니처

AccountController.kt 
// /api/v1/users 매핑. /me 는 인증된 본인 조회
@GetMapping("/me")
fun getMe(
    @RequestAttribute(AccountAuthenticationAttributes.ACCOUNT_ID) accountId: Long,
    @RequestAttribute(AccountAuthenticationAttributes.LOGIN_ID) loginId: String,
): AccountMeResponse =
    accountService.getMe(accountId, loginId).toResponse()

응답 — AccountMeResponse

application 레이어의 AccountMeInfo를 toResponse()로 변환한 DTO다. name 은 마스킹된 값이라는 점이 핵심이다(원문 그대로 반환하지 않음).

필드타입출처설명
loginId String request attribute 인증된 로그인 ID. DB 재조회 없이 attribute 값을 그대로 전달
name String account.maskedName() 마스킹된 이름. 마지막 글자를 *로 가림 (1글자면 전체 *)
birthDate LocalDate account.birthDate 생년월일
email String account.email.value 이메일 (Email VO 의 내부 값)
RESPONSE WRAPPING 컨트롤러는 AccountMeResponse를 그대로 반환하고, 성공 응답은 ApiResponseBodyAdvice(@RestControllerAdvice + ResponseBodyAdvice)가 공통 ApiResponse로 래핑한다. 즉 실제 응답 body 는 { isSuccess, status, code, message, data, timestamp } 형태이고 data 안에 위 4개 필드가 담긴다. 컨트롤러는 ApiResponse를 직접 만들지 않는다.
JSON성공 응답 예시 (래핑 후)
200 OK 
{
  "isSuccess": true,
  "status": 200,
  "code": null,
  "message": null,
  "data": {
    "loginId": "loopers01",
    "name": "홍길*",
    "birthDate": "1996-03-09",
    "email": "loopers@example.com"
  },
  "timestamp": "2026-06-17T09:00:00+09:00"
}
03

SEQUENCE

시퀀스 다이어그램

인증 필터가 헤더로 신원을 검증해 request attribute 를 주입하면, 컨트롤러는 그 값만 읽어 application → domain/repository 로 조회를 위임한다.

04

BUSINESS LOGIC

비즈니스 로직

1. 인증 — 이 경로는 인증 필요

보안 설정상 GET /api/v1/users/me는 인증이 필요하다. AccountSecurityConfig는 POST /api/v1/users(회원가입)와 상품 조회/actuator/swagger 만 permitAll()로 열고, 나머지는 anyRequest().authenticated()로 막는다. /me는 어느 permitAll 매처에도 해당하지 않으므로 인증 대상이다.

인증 자체는 AccountHeaderAuthenticationFilter가 수행한다. X-Loopers-LoginId / X-Loopers-LoginPw 헤더로 accountService.authenticate(...)를 호출해 검증하고, 성공 시 request.setAttribute(...)로 accountId·loginId를 주입한다.

2. 인증 attribute 누락 / 인증 실패 시

FILTER헤더가 둘 다 없음

필터는 attribute 를 심지 않고 그대로 체인을 통과시킨다. 이후 Spring Security 인가 단계에서 미인증 요청으로 걸려 AccountAuthenticationEntryPoint가 401로 응답한다.

FILTER헤더가 비었거나 인증 실패

loginId/password 가 blank 이거나 인증에 실패하면(UnauthorizedException) 엔트리포인트를 통해 401 UNAUTHORIZED로 응답한다. 컨트롤러까지 도달하지 않는다.

정상 인증을 거쳐야만 attribute 가 존재하므로, 컨트롤러의 @RequestAttribute 바인딩은 인증된 요청에서만 성립한다.

3. 사용자 미존재 시 — NotFoundException

인증은 통과했지만 accountId로 계정을 못 찾으면(이론상 인증 직후 삭제 등) application 레이어가 예외를 던진다.

AccountService.getMe 
@Transactional(readOnly = true)
fun getMe(accountId: Long, loginId: String): AccountMeInfo {
    val account = accountRepository.findById(accountId)
        ?: throw NotFoundException(AccountErrorCode.ACCOUNT_NOT_FOUND)

    return AccountMeInfo(
        loginId = loginId,                 // attribute 값 그대로
        name = account.maskedName(),       // 마스킹
        birthDate = account.birthDate,
        email = account.email.value,
    )
}

NotFoundException(AccountErrorCode.ACCOUNT_NOT_FOUND) → 에러코드 ACCOUNT:ACCOUNT_NOT_FOUND, 메시지 "계정을 찾을 수 없습니다." → ApiControllerAdvice가 404 NOT FOUND로 매핑한다.

4. 트랜잭션 — readOnly

getMe는 @Transactional(readOnly = true)로 선언된다. 조회만 수행하므로 dirty checking/flush 가 불필요하고, 읽기 전용 힌트로 명시한다. 트랜잭션 경계는 application(Service) 레이어에 둔다.

5. 이름 마스킹

응답의 name은 도메인 VO AccountName의 masked() 결과다. 1글자면 전체를 *로, 2글자 이상이면 마지막 글자만 *로 가린다 (예: "홍길동" → "홍길*"). loginId·email은 마스킹 없이 그대로 반환한다.

RESPONSE WRAPPING 성공 시 컨트롤러는 AccountMeResponse만 반환하고, ApiResponseBodyAdvice가 공통 ApiResponse로 래핑한다. 실패 시에는 advice/entry point 가 ApiResponse.fail(...) 경로로 에러 응답을 직렬화한다.
