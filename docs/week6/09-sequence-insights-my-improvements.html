PATTERNS

시퀀스에서 건진 6패턴

"이 화살표가 실패하면?"을 따라가면 좋은 설계가 드러난다. 11개 시퀀스를 겹쳐보고 추린 6가지.

① 재시도는 시간이 아니라 멱등성으로 가른다minbo265 · 재희87 · sung260

제출 화살표 POST /payments가 실패했을 때, "실패했으니 재시도"가 아니라 "PG에 거래가 생겼을 수 있나?"로 갈라야 한다. 결제는 비멱등이라 timeout 재시도는 곧 이중결제다.

✓ 재시도해도 안전

  • 5xx(거래 미생성 보장) — minbo265는 HttpServerErrorException만 화이트리스트
  • connection refused (호출 안 됨 확실) → 내 failover 와 동일 논리

✕ 재시도 금지

  • read timeout — 거래가 생겼을 수 있음 → UNKNOWN/조회로
  • sung260은 POST 자체를 아예 무재시도 + 조회 복구

② 미확정(UNKNOWN)을 1급 상태로sung260 · kmkim266 · 나

승인/실패만 있는 상태머신은 "타임아웃"을 표현할 곳이 없어 PENDING에 욱여넣는다. UNKNOWN을 별도 상태로 두면 reconcile이 "확정 대기"와 "결과 모름"을 구분해 처리할 수 있다. sung260은 timeout→UNKNOWN, kmkim266은 ABORTED+failureCode=null, 내 구현은 UNKNOWN enum. (단 1급으로 만들어도 ③ 없으면 영구 잔존.)

③ reconcile은 transactionKey 유무로 두 갈래호준88 · sung260 · minbo265

콜백이 유실되거나 타임아웃이 나면 회복 경로가 둘로 갈린다. 이 분기가 reconcile 설계의 핵심이다.

txKey 있음 (콜백 유실)

  • GET /payments/{txKey} 단건 조회
  • SUCCESS/FAILED면 확정

txKey 없음 (타임아웃 거짓음성)

  • GET /payments?orderId= 역조회
  • 거래 있으면 key 역채움 + 복구 / 없으면 grace 후 FAILED
반면교사재희87은 reconcile에 orderId 역조회가 없어 PG-first로 생긴 고아 결제를 못 잡는다. Sooche262는 역조회 대신 재결제를 보내 이중결제. 역조회는 reconcile의 필수 절반이다.

④ 거짓음성에는 grace를 줘라sung260

orderId 역조회가 404 NOT_FOUND라고 즉시 FAILED로 굳히면, PG가 늦게 반영 중인 거래를 실패로 오판한다. sung260은 NOT_FOUND + 활성상태 + 120s grace 경과 3조건을 모두 만족해야 실패 확정. 그 전엔 재예약. 성급한 확정을 막는 안전장치.

⑤ 콜백은 못 믿는다 — 멱등 + 재조회 + 인증byun258 · 전원

pg-simulator 콜백은 타임아웃도 재시도도 서명도 없다(runCatching). 그래서 ⓐ 이미 종결 상태면 no-op(전원 공통), ⓑ byun258은 콜백 body status를 불신하고 txKey로 재조회해 위조 방어, ⓒ 다수가 콜백 인증을 비워둠(개선 여지). 콜백은 "힌트"고 진실은 조회다.

⑥ 보상은 결제 실패 플로우의 일부다재희87

FAILED 화살표 뒤에 재고·쿠폰 원복이 없으면, 주문 시 차감한 자원이 영구 누수된다. 11명 중 8명이 이걸 빠뜨렸다. 재희87의 OrderCancellation(재고+쿠폰+주문취소)만 플로우를 닫았다. 동시 중복결제는 별개로 order_id UNIQUE(minbo265·sung260)가 INSERT에서 막는다.

DIAGNOSIS

내 구현 현재 진단

채점(08)에서 47점. 축별로 보면 "기반은 최상위, 회복탄력성만 비었다"가 정확하다.

이미 가진 강점 (남들 없음)

  • 2-PG failover — 11명 중 유일
  • UNKNOWN 1급 enum + 전이(UNKNOWN→SUCCESS/FAILED 이미 존재)
  • 이중결제 함정 정책 — timeout·5xx는 failover 금지
  • Facade 무Tx + 분할 + PG 호출 Tx 밖 (C5 9/10)

비운 곳 (이 리포트의 대상)

  • reconcile 전무 (C2 2/20) — UNKNOWN이 영구 잔존
  • resilience4j 임계값 (C1 8/20)
  • 재고/쿠폰 보상 (C3 6/15)
  • 측정 근거 (C6 2/10)
핵심 진단내가 만든 UNKNOWN 상태가 지금 가장 큰 역설이다 — 1급으로 모델링해놓고 그걸 해소할 reconcile이 없어 영영 UNKNOWN에 머문다. 그래서 P0는 resilience4j가 아니라 reconcile이다. 내 상태머신이 이미 받을 준비가 됐으므로 가성비도 최고다.

BACKLOG

반영 백로그 (P0·P1·P2)

우선순위는 "지금 가장 큰 구멍" + "내 기존 골격과의 접합 가성비" 순. P0는 reconcile이다.

  • reconcile 스케줄러 + orderId 역조회 — @Scheduled로 stale UNKNOWN/PENDING 조회 → txKey 있으면 GET /{key}, 없으면 GET ?orderId= 역조회. 내 UNKNOWN→SUCCESS/FAILED 전이가 이미 있어 접합 가성비 최고. P0
  • NOT_FOUND grace — 역조회 404를 즉시 FAILED로 안 굳히고, 활성상태 + N초 경과 조건 후에만 확정. UNKNOWN 오판 방지. P0
  • resilience4j @CircuitBreaker + @Retry — Gateway 어댑터에. 재시도는 5xx만 화이트리스트, timeout 제외(내 failover 정책과 동일 철학). aspect 순서 @Retry⊃@CB. P1
  • CB 실패율 임계 60~70 — pg-simulator 정상 실패율 40% 위로. 또는 record-exceptions 화이트리스트로 인프라 예외만 집계. P1
  • FAILED 보상 트랜잭션 — 재희87 OrderCancellation처럼 재고+쿠폰 원복. 현재 Order만 FAILED라 자원 누수. P1
  • order_id UNIQUE 동시결제 차단 — 활성 결제 1건 보장(INSERT 단계). check-then-act 대신 DB 제약. P1
  • k6 부하테스트로 임계값 근거화 — 단, 호준88/재희87처럼 본문↔코드 불일치를 내지 말 것. 측정값과 yml을 일치시켜 커밋. P2
  • 콜백 재조회·인증 — body status 불신, txKey로 재확인(byun258). 콜백 서명/시크릿은 여건 되면. P2
한 줄 결론내 구현은 남이 안 한 걸 가졌고 남이 한 걸 비웠다. P0(reconcile+grace)만 채워도 UNKNOWN 고리가 닫혀 C2가 2→15+로 뛰고 총점이 상위 티어권으로 올라간다. resilience4j(P1)는 그 위에 얹는 순서가 맞다.
