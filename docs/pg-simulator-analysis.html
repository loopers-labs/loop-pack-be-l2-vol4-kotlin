OVERVIEW

pg-simulator 란

우리가 호출하는 외부 PG 사를 흉내 내는 모의 서버다. 직접연동(Key-in) 방식 — commerce 서버가 카드 정보를 담아 서버→PG 로 직접 POST 한다.

B2C 결제창(SDK)처럼 브라우저가 PG 와 통신하지 않는다. 카드번호·금액·콜백 URL 을 우리 서버가 그대로 실어 보내고, 시뮬레이터는 지연·랜덤 실패·비동기 승인을 흉내 내며 실패 경로를 강제로 만들어낸다. 그래서 이 보고서의 목적은 결국 "무엇이 어떻게 깨지는가, 그때 우리는 무엇을 하는가"다.

핵심시뮬레이터는 일부러 불안정하다 — POST 의 40% 가 500, 승인은 비동기 70/20/10, 콜백은 유실 가능. 정상 경로보다 실패·미확정 경로 설계가 이 과제의 본체다.

LIFECYCLE

POST 요청 처리 흐름

한 번의 POST 가 통과해야 하는 게이트와, 각 게이트에서 떨어지는 응답. 200 은 "승인"이 아니라 "접수(PENDING)"일 뿐이다.

착각 주의POST 가 200 이라고 결제 성공이 아니다. 200 = "거래가 PENDING 으로 접수됨". 실제 승인 여부는 비동기로 갈리고, 그 결과는 콜백 또는 GET 조회로 확인한다.

ENVELOPE

공통 응답 봉투

성공이든 실패든 전부 ApiResponse<T> 한 형태로 감싸진다.

ApiResponse shape
// 성공
{ "meta": { "result": "SUCCESS", "errorCode": null, "message": null },
  "data": { /* 엔드포인트별 payload */ } }

// 실패
{ "meta": { "result": "FAIL",
           "errorCode": "<HttpStatus reasonPhrase>",
           "message": "<사유>" },
  "data": null }

errorCode 는 ErrorType.code(= HttpStatus reasonPhrase), message 는 던질 때의 customMessage, 없으면 ErrorType.message(기본 문구)다.

ErrorTypeHTTPerrorCode기본 message
BAD_REQUEST400Bad Request잘못된 요청입니다.
NOT_FOUND404Not Found존재하지 않는 요청입니다.
INTERNAL_ERROR500Internal Server Error일시적인 오류가 발생했습니다.
CONFLICT409Conflict(결제 경로에선 미사용)

ASYNC RESULT

비동기 결과 모델

POST 200 이후의 진짜 승인 결과. handle() 가 랜덤으로 결정하고, 결과는 콜백 + 조회로 전달된다.

분기확률statusreason우리 매핑
approve()70% (31~100)SUCCESSnull→ PAID
limitExceeded()20% (1~20)FAILED한도 초과→ FAILED
invalidCard()10% (21~30)FAILED잘못된 카드→ FAILED
콜백을 믿지 마라콜백(paymentRelay.notify)은 runCatching 으로 실패를 삼키고 타임아웃도 없다 → 유실 가능. 콜백만 의존하면 결과를 영영 못 받는 거래가 생긴다. GET 조회(reconciliation)가 안전망이다.

RECONCILE

조회 응답 (reconciliation)

미확정(UNKNOWN)을 해소하는 핵심 도구. 단건 조회의 status 가 곧 최종 판정이다.

GET /payments/{transactionKey}

HTTP조건commerce 대응
200 PENDING아직 처리 중잠시 후 재조회
200 SUCCESS승인됨→ PAID 확정 (멱등)
200 FAILED한도초과/카드오류 (reason)→ FAILED 확정
404없는 transactionKey키 오류면 조사 / 생성 직후면 재조회
400X-USER-ID 누락우리 버그

GET /payments?orderId=

HTTP조건commerce 대응
200{orderId, transactions:[…]}주문에 엮인 거래들 상태 확인
404해당 주문 결제건 없음조사
400X-USER-ID 누락우리 버그

STRATEGY

commerce 대응 전략

HTTP status 를 재시도 가능 / 불가 / 미확정 셋으로 가르는 게 대응의 뼈대다.

4xx고쳐라 (재시도 X)

400 = 우리 잘못. 같은 요청을 다시 보내도 똑같이 실패. 즉시 실패 처리 + 로깅/알림. 404 = 조회 타이밍 이슈 — 생성 직후면 짧게 재조회, 진짜 없으면 예외.

5xx / —미확정 (in-doubt)

500 · 타임아웃 · 콜백유실은 "실패"가 아니라 "결과 미확정". 결제가 됐을 수도 있다. 무작정 새 결제 재요청 금지 → 멱등키 또는 조회로 실제 상태 확인.

미확정 처리 파이프라인

제한 재시도(지수 백오프) → 계속 실패하면 CircuitBreaker open → Fallback → 주문 markUnknown() + 사용자에겐 정상 응답. 이후 GET 조회 reconciliation 으로 UNKNOWN 을 PAID/FAILED 로 해소한다.

400 = 고쳐라(재시도 X) · 404 = 조회 타이밍 · 500·타임아웃·콜백유실 = 미확정이니 조회로 확인(막 재결제 X) → 우리 주문 상태는 결국 PAID · FAILED · UNKNOWN 세 가지로 수렴한다.

Resilience4j 매핑TimeLimiter(타임아웃) + Retry(5xx 제한 재시도, 멱등 전제) + CircuitBreaker(연속 실패 차단) + Fallback(→ markUnknown). 4xx 는 재시도/CB 대상에서 제외해야 한다 — 재시도해도 안 풀리고 CB 통계만 오염시킨다.
