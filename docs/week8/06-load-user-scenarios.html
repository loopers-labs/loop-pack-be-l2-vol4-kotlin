FULL API INVENTORY

API 전수 조사 — 이 서버가 받는 전부

commerce-api의 컨트롤러 전수 조사 결과 — 부하 순간 이 인스턴스에 도달할 수 있는 트래픽의 전체 후보입니다.

중요한 건 각 API가 어떤 자원을 때리는가입니다. 같은 1,000/s라도 Redis 왕복 API와 MySQL 행 락 API는 서버에 완전히 다른 부하입니다. 천장 해석(락 경합 vs 커넥션 풀 고갈)이 이 분류에서 갈립니다.

API호출 주체 · 언제때리는 자원 (부하 성격)
POST /queue/enter사용자 — 오픈 순간 집중Redis ZADD (수 ms, DB 무접촉)
GET /queue/position사용자 — 대기 내내 반복Redis GET+ZRANK+ZCARD (수 ms, DB 무접촉)
POST /orders사용자 — 입장 후 1회Redis 토큰 검증 + MySQL TX (재고 행 락·쿠폰·주문)
POST /payments사용자 — 주문 직후MySQL + 외부 PG 호출 (CB·재시도 배선)
POST /payments/callbackPG 시스템 — 결제 수만큼 유입MySQL (결제·주문 상태 갱신)
POST /coupons/issue사용자 — 쿠폰 오픈 순간 집중Kafka 발행 (비동기 수락 후 즉시 응답)
GET /coupons/issue/{requestId}사용자 — 발급 결과 폴링발급 결과 조회 (Round 7 실측: 전체 http의 75%가 이 폴링)
GET /products · /products/{id}사용자 — 이벤트 전후 내내 (조회가 지배 트래픽)⚠ week5-caching 브랜치, 현 라인 미머지 — 목록(커서·정렬·첫 페이지 Redis 캐시) + 상세(MySQL)
GET /users/me사용자 — 앱 진입·새로고침 시MySQL 단건 조회 + BCrypt 인증
POST /users · PUT /users/password사용자 — 상시 소량MySQL 쓰기. 이벤트 순간 비중 미미
/api-admin/v1/coupons*관리자 — 사전 세팅이벤트 전 완료. 부하 창에선 0으로 가정
믹스의 뼈대 부하 창에서 유의미한 트래픽은 대기열 2종(Redis) + 주문·결제 3종(MySQL·PG) + 쿠폰 2종(Kafka·폴링)의 7개입니다. 나머지(계정·어드민)는 상수 취급합니다. 모든 API는 요청마다 헤더 인증(X-Loopers-LoginId/Pw, BCrypt cost 4 시드)을 지나므로 인증 비용은 전 API 공통 오버헤드입니다.

UNMERGED TRAFFIC

상품 탐색 — 있는데, 이 라인에 없다

"주문 전에 상품 여러 개를 본다"는 지배 트래픽의 API는 구현되어 있습니다 — 단, 측정 대상 브랜치에 머지되어 있지 않습니다.

정확한 상태: GET /api/v1/products(커서 페이지네이션 · 최신/좋아요순 정렬 · 첫 페이지 Redis 캐시)와 GET /api/v1/products/{productId}는 feature/week5-caching 브랜치에 있습니다 (Week 5에서 좋아요순 인덱스·캐시 적용 후 읽기 성능 부하 측정까지 완료). 이 브랜치가 이후 주차 라인에 머지되지 않아, week08 라인에는 ProductService.list/getDetail이 호출자 없는 상태로만 넘어와 있습니다. 브랜치를 합치면 조회 트래픽을 믹스에 넣을 수 있고, 머지 프로브 결과 충돌은 3파일 소규모(.gitignore · 보안 설정 · 에러코드 enum)입니다. 상품 대량 시드·측정 스크립트도 그 브랜치에 자산으로 있습니다.

그래서 D1은 "만들 것인가"가 아니라 "끌어올 것인가"입니다:

A안 · 추천 week5 머지 → 탐색을 배경 부하로 포함

측정용 브랜치(베이스라인·M2) 양쪽에 동일하게 week5-caching을 머지하고, 탐색은 고정 rate의 배경 암(스윕 안 함)으로 깝니다. M1 천장이 "조회가 깔린 서버"의 현실적 수치가 되고, 유/무 비교의 동일 조건도 유지됩니다. 비용: 충돌 3파일 해결 + 상품 시드 확장 + 배경 rate 가정 1개(명시).

B안 이번 주는 제외 + 한계 명시 (축 분리)

조회 축은 Week 5에서 이미 단독 측정된 축입니다 (쿠폰이 Week 7이었듯). 이번 주는 대기열 축만 재고, 결과 문서에 "탐색 트래픽 0 전제 — 실제 천장은 더 낮다"를 명시합니다. 변인이 최소가 되어 해석은 가장 깨끗하지만, M1 천장의 절대치가 비현실적으로 높게 잡히는 건 감수해야 합니다.

A안 선택 시 주의 2가지 ① 머지는 측정 전용 브랜치에서만 — 개발 라인(week08 PR 대상)에 week5를 섞는 건 별도 결정입니다. ② 첫 페이지 캐시 때문에 탐색 부하의 MySQL 도달량이 캐시 적중률에 좌우됩니다 — 배경 암은 "목록 첫 페이지(캐시 적중) + 상세 랜덤(MySQL 도달)" 비율을 고정해 변인화를 막아야 합니다. 어느 안이든 대기열 API(Redis-only)의 효과 주장은 탐색 유무와 무관하게 성립합니다 — 자원이 분리되어 있기 때문입니다.

PER-ORDER FOOTPRINT

주문 1건의 호출 풋프린트

"주문 1건"은 서버 입장에서 1회 호출이 아니라 — 대기열을 지나는 순간 십수 회의 HTTP가 됩니다.

사용자 한 명이 주문 하나를 완성할 때 서버가 받는 호출을 전부 세면 아래와 같습니다. 폴링 횟수는 코드의 nextPollSeconds 규칙(예상 대기/10을 1~10초로 클램프)에서 나온 근사치입니다 — 줄 앞쪽 사용자는 1초 간격까지 조밀해지므로 대기가 길수록 폴링이 가파르게 쌓입니다.

PHASE MIX · 8,000 USERS

오픈 8,000명 — 국면별 믹스

같은 서버가 3개의 국면을 순서대로 통과합니다 — 국면마다 지배 API와 때리는 자원이 다릅니다.

오픈 10초에 8,000명 진입, 방출 100명/s(마지막 진입자 80초 대기), 주문서 작성 30~120초 가정으로 창(window)별 호출량을 근사하면:

국면서버가 받는 것 (근사)주시할 자원
① 0~10s 진입 폭풍enter ~800/s + 첫 position 시작. 쿠폰 오픈 동시라면(D3) issue 스파이크 중첩Redis · 톰캣 스레드풀
② 0~80s 폴링 지배position 평균 ~2,000/s (막판 1s 클램프 구간이 견인) — 전체 http의 ~85%Redis · 톰캣 스레드풀 (DB 한가함)
③ 30~200s 주문 꼬리orders ~47/s 평탄 + payments·callback 동반(D2). 재고 행 락 직렬화 시작MySQL 행 락 · HikariCP · PG CB
이 믹스가 M1 해석에 주는 교훈 대기열이 없는 M1의 세계에선 ①~③이 전부 0초에 MySQL로 직행합니다 — 그게 붕괴의 원인입니다. 대기열이 있는 세계에선 같은 총량이 자원별로 분리됩니다: Redis가 ①②를 받아내고 MySQL은 ③만 받습니다. 그래서 M2에서 "Redis 계열 API의 천장"과 "MySQL 계열 API의 천장"을 따로 읽어야 하고, k6 태그로 API별 분해가 필수입니다.
폴링 ~2,000/s의 함의 — 보호 장치가 만드는 부하 순번 폴링은 DB엔 무해하지만 톰캣 스레드·Redis에는 실부하입니다. 특히 nextPollSeconds의 1초 하한 때문에 줄 앞 ~1,000명이 초당 1회씩 폴링하는 구간이 생깁니다. M2에서 폴링 총량과 position p95를 따로 재는 이유 — 대기열 자신이 새 천장이 되는지 확인해야 합니다.

DECISIONS

결정 카드 — 믹스에 넣을지 말지

측정 스크립트를 확정하기 전에 세 가지만 결정하면 됩니다.

D1 · 상품 탐색 배경 부하 (§2)

A안(week5-caching 머지 → 고정 rate 배경 암으로 포함)을 추천합니다. 근거: API가 이미 구현·단독측정까지 된 자산이고 머지 비용이 낮으며(충돌 3파일), 조회가 깔린 천장이어야 가정 TPS 서사("이 정도 트래픽의 회사")와 맞습니다. 단 배경 rate는 스윕하지 않고 상수로 고정(가정 명시), 머지는 측정 전용 브랜치에만 — 시간이 부족해지면 B안(제외+명시)으로 내려가는 게 fallback입니다.

D2 · 결제 퍼널 포함 여부

제외 · 추천 주문까지만 (기존 계획 유지)

05 문서의 M1·M2 계획은 주문까지입니다. 결제를 넣으면 외부 PG 시뮬레이터의 성능이 측정에 끼어들어 천장의 원인 분리(락 vs 풀 vs PG)가 흐려집니다. 결제·콜백은 이미 Round 6에서 CB·재시도로 검증한 구간이기도 합니다.

포함 주문+결제 전체 퍼널

실제 유저 여정과 같아져 사실성은 올라가지만, PG 스텁 처리량·콜백 타이밍이라는 새 변수 2개가 들어옵니다. 대기열 검증이라는 이번 질문에는 기여가 없습니다.

D3 · 쿠폰 발급 스파이크 동시 진행 여부

제외 · 추천 별도 이벤트로 간주

쿠폰 폭주는 Round 7에서 이미 단독 측정 완료(EXP-01~03)입니다. 이번에 겹치면 Redis·Kafka 부하가 중첩되어 대기열 효과와 분리가 안 됩니다. "쿠폰은 사전 발급 완료, 주문 시 사용만" 가정이 깔끔합니다 — 주문 TX 안의 쿠폰 사용은 이미 포함되어 있습니다.

포함 쿠폰 오픈 = 주문 오픈 동시

블랙프라이데이 최악 케이스의 사실성은 최고지만, 변인이 셋(대기열·쿠폰·중첩)이 되어 결과 해석이 어려워집니다. 하려면 M2 완료 후 추가 런으로.

전부 추천대로 가면 이번 측정의 믹스 = 탐색 배경 암(products 목록·상세, 고정 rate) + 여정 3종(enter·position·orders). 결제·쿠폰발급은 전제 명시 후 제외(각각 Round 6·7에서 검증된 축). 05 문서의 M1·M2 계획 대비 달라지는 것은 탐색 배경 부하 추가 하나이고, 그만큼 M1 천장이 "조회가 깔린 서버"의 현실적 수치로 내려갑니다. M1·M2 양쪽에 같은 배경을 깔아야 상대 비교가 유지됩니다.

INTO K6

k6 반영 — 믹스 → 시나리오 구성

위 믹스를 그대로 스크립트 구조로 옮기면 — API별 rate를 따로 만드는 게 아니라, 사용자 여정 하나가 믹스를 자동으로 만들어냅니다.

enter:position:orders의 비율(1:~20:1)은 독립 파라미터가 아니라 대기열 규칙(nextPollSeconds·방출 100/s)의 산출물입니다. 그래서 M2 스크립트는 API별 rate 3개가 아니라 여정 VU(가상 사용자) 하나로 짜야 믹스가 저절로 맞습니다. 반대로 M1은 여정이 없으므로(직행 주문) 기존 rate 스크립트 그대로입니다.

측정스크립트 · 부하 모델이 문서가 확정해 주는 것
M1 베이스라인order-throughput-1m.js — POST /orders 직행 램프 100→800/s (+D1 채택 시 탐색 배경 암 동시 가동)대기열 이전 세계 = 직행 주문 + 배경 조회. 배경 rate는 M2와 동일 고정
M2 보호 검증queue-order-flow.js (신규) — 여정 VU: enter→폴링→주문 (+동일 탐색 배경 암). 스파이크 8,000 + 램프 암API 태그 분해 · 폴링 ~2,000/s 흡수 확인 · ABANDON_RATE 0/10%
M3 방출 스윕M2 스크립트 재사용, 방출 속도만 50→400/s 스윕③국면의 orders 평탄 rate가 방출 값 따라 움직이는지

측정 전 체크

  • API 전수 조사 — 현 라인 컨트롤러 9개 + 탐색 2개는 week5-caching 미머지 상태로 확인 §1·§2
