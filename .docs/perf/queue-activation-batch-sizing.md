# 대기열 활성화 배치 크기 산정 근거

| | |
|---|---|
| **대상** | `WaitingQueueActivator` / `queue.activate.batch-size`, `queue.activate.interval` |
| **날짜** | 2026-07-09 |
| **한 줄 요약** | 배치 크기는 "얼마나 많이 통과시키고 싶은가"가 아니라 **"보호 대상이 초당 안전하게 소화할 수 있는가"** 에서 역산한다. |

---

## 1. 배치 크기가 사실은 무엇인가

스케줄러는 `interval`마다 `batch-size`명을 대기열에서 꺼내 입장 토큰을 발급한다. 따라서 이 두 값의 비율이 곧 **시스템이 허용하는 초당 입장률(admission rate)** 이다.

```
허용 처리량(rps) = batch-size / interval(초)
현재 설정        = 100 / 1s = 100 rps
```

즉 `batch-size`는 단순한 튜닝 상수가 아니라 **유입 제어율 그 자체**다. 이 숫자를 정하는 것은 "초당 몇 명을 보호 대상으로 흘려보낼 것인가"를 정하는 일이다.

## 2. 무엇을 기준으로 정하는가 — 다운스트림 안전 처리량

대기열의 존재 이유는 트래픽 폭주 시 **보호 대상(주문 생성 → 재고 차감 → 결제)** 이 무너지지 않도록 유입을 깎는 것이다. 그러므로 기준은 "얼마나 빨리 손님을 들여보내고 싶은가"(비즈니스 욕심)가 아니라, **보호 대상이 초당 안정적으로 처리할 수 있는 요청 수(안전 처리량)** 여야 한다.

```
batch-size = 다운스트림 안전 처리량(rps) × interval(초)
```

- **안전 처리량**: 응답시간 SLA와 에러율이 무너지지 않는 한계 근처에서, 여유를 둔 값. 보통 측정된 최대 처리량의 70~80%.
- 이 값은 **부하 테스트로 측정**해야 확정된다. 주문 생성 경로(재고 락 경합, 결제 PG 호출 40% 실패·재시도 포함)를 실제 부하로 밀어보고, p99 응답시간과 에러율이 임계 안에 머무는 최대 rps를 찾는다.

## 3. 상·하한 트레이드오프

| 배치 크기 | 결과 |
|---|---|
| **너무 크다** | 유입률 > 다운스트림 안전 처리량 → 큐를 통과한 요청이 그대로 폭주로 이어져 **대기열이 무의미**해진다. 최악의 시나리오를 큐 앞이 아니라 큐 뒤(주문/결제)에서 맞는다. |
| **너무 작다** | 다운스트림은 놀고 있는데 입장이 느려 **대기 시간이 폭증**, 사용자 이탈. 자원을 낭비하면서 UX도 나쁘다. |

따라서 목표는 **"다운스트림 안전 처리량에 최대한 근접하되 넘지 않는"** 지점이다.

## 4. `interval` 은 어떻게 맞물리는가

같은 100 rps라도 `100/1s`와 `10/100ms`는 다르다.

- **간격이 길수록(예: 100/1s)**: 한 번에 100명이 몰려 들어가 다운스트림에 **버스트**를 준다. 순간 부하가 커진다.
- **간격이 짧을수록(예: 10/100ms)**: 같은 100 rps를 더 고르게 흘려보내 버스트가 완만하다. 대신 스케줄러 실행 빈도와 Redis 왕복이 늘어난다.

현재는 운영·관측 단순성을 위해 `1s` 틱을 택했다. 다운스트림이 버스트에 민감하다는 것이 측정되면 간격을 줄여 평탄화한다.

## 5. 현재 값과 확정 절차

- **현재 값(100 rps)은 부하 측정 전의 출발 기본값**이다. 확정값이 아니다.
- 확정 절차:
  1. 주문 생성 경로 부하 테스트 → 안전 처리량(rps) 측정.
  2. `batch-size = 안전 rps × interval`로 역산.
  3. 버스트 민감도가 확인되면 `interval`을 줄여 재분배.
  4. 측정 결과와 최종 값을 이 문서에 갱신.

## 6. 예상 대기 시간과의 연결

같은 `batch-size`·`interval`이 사용자에게 노출되는 **예상 대기 시간** 계산에도 그대로 쓰인다(`WaitingQueueService.estimateWaitSeconds`).

```
예상 대기(초) = ceil(내 순번 / batch-size) × interval(초)
```

이 때문에 배치 크기는 `application.yml`의 `queue.activate.*` **단일 소스**로 관리되어, 스케줄러의 실제 처리량과 사용자에게 보여주는 예상 시간이 항상 일치한다. 두 곳에 따로 하드코딩하면 "실제로는 100명씩 빠지는데 화면엔 50명 기준 시간이 표시되는" 불일치가 생긴다.

## 관련
- 설정: `apps/commerce-api/src/main/resources/application.yml` → `queue.activate.batch-size`, `queue.activate.interval`
- 코드: `WaitingQueueActivator`(스케줄러), `WaitingQueueService.estimateWaitSeconds`(예상 대기)
- 다운스트림 실측 참고: PG 연동 특성은 [ADR-0003](../adr/0003-pg-payment-client-resilience.md) 참고(요청 40% 실패·콜백 지연 등, 안전 처리량 산정 시 고려).
