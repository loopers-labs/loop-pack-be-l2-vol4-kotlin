Round 9 · 읽기 천장 · 원인 진단 (EXP-POOL)

읽기 천장은 커넥션 풀이 아니라
MySQL CPU였다

"천장이 Hikari 40/40 소진과 함께 왔으니 풀을 늘리면 올라가지 않을까?" — 이 가설을 풀 크기 10 / 40 / 80 3암으로 직접 검증했다. 결과: 풀을 두 배로 늘려도 천장은 그대로였고 지연만 나빠졌다. 풀 소진은 원인이 아니라 MySQL CPU 포화의 증상이었다.

1

HYPOTHESIS

가설과 판별 — 원인 vs 증상

7/16 본런에서 S-READ 읽기 천장은 약 280rps에서 p95가 붕괴하며 왔고, 그 순간 HikariCP 풀이 40/40으로 소진돼 있었다. "풀이 천장을 만들었으니 늘리면 올라간다"는 자연스러운 가설이지만, 같은 순간의 다른 지표들은 반대를 가리켰다.

당시 함께 관측된 사실은 세 가지다. 앱 CPU는 10%로 놀고 있었고, p95는 3.19초였으며(당시 connection-timeout=3000ms에 근접), 읽기 쿼리는 인덱스 페이지 조회였다. 앱이 노는데 지연이 3초라는 건, 스레드가 무언가를 기다리며 잠들어 있었다는 뜻이다. 그 "무언가"가 풀 슬롯인지 MySQL인지가 이 실험의 질문이다.

Little's Law로 본 커넥션 점유

대기 시스템의 항등식 L = λ × W (점유 커넥션 수 = 처리량 × 커넥션 점유 시간)를 쓰면 방향이 보인다. 천장에서 L=40, λ≈280/s이면 W ≈ 143ms — 커넥션 하나가 평균 143ms씩 붙잡혔다는 뜻이다. 그런데 건강한 상태의 쿼리 점유는 로컬 실측 기준 한 자릿수 ms다. W가 정상(약 6ms)이었다면 같은 풀 40개로 40 ÷ 0.006 ≈ 6,600 rps를 버틴다.

판별의 뼈대풀 40개가 처리량을 자른 게 아니다. 쿼리 점유 시간(W)이 6ms에서 143ms로 부풀어서 L이 40에 닿은 것이다. 그러면 남은 질문은 하나 — W를 부풀린 주체가 누구인가: 풀 경합인가, 락인가, MySQL 자원인가.

이걸 실측으로 가르려면 두 시간을 분리해야 한다. 커넥션을 얻으려고 기다린 시간(acquire) 이 크면 풀이 병목이고, 얻은 커넥션을 쥐고 있던 시간(usage/점유) 이 크면 다운스트림(MySQL)이 느린 것이다. 여기에 Innodb_row_lock_waits와 mysqld CPU를 더하면 "MySQL이 느린 이유"가 락인지 CPU인지까지 쪼개진다.

DESIGN

실험 설계 — 변인·고정·판정

기존 측정 자산(R8 2노드 · ranking-read.js)을 그대로 재사용하고, 새 하네스는 만들지 않았다. 바뀐 변인은 풀 크기 하나뿐이다.

변인 — 풀 크기 3단계

Armmaximum-pool-size / minimum-idle목적
A40 / 40 (현행)7/16 천장 재현 + 이번엔 MySQL 지표까지 채집
B80 / 80가설 직접 검증 — 풀을 늘리면 천장이 오르나
C10 / 10HikariCP small-pool 논지 역검증

풀 크기는 코드 수정 없이 --datasource.mysql-jpa.main.maximum-pool-size CLI 인자로 주입했다(HikariConfig가 @ConfigurationProperties로 바인딩되므로 relaxed binding으로 적용). 암마다 앱을 재시작하고 hikaricp_connections_max로 실제 적용을 확인했다.

고정 조건

infra 노드 m6i.large(2 vCPU, MySQL+Redis+Kafka 공존, max_connections=300, buffer pool 4G), app 노드 c6i.xlarge(4 vCPU). 부하는 ranking-read.js 그대로 — warmup 20/s×1분 후 램프 50→100→200→400/s(각 1분). 같은 시드(오늘판 랭킹 약 20만 행), -Duser.timezone=Asia/Seoul 픽스 포함.

판정 기준

천장 rps·p95(k6)와 mysqld CPU·Threads_running·점유시간·락(15초 샘플러)을 교차한다.

IF풀 = 원인

풀을 키우면 천장이 오르고, 구천장 시점에 MySQL은 여유가 있어야 한다.

IF풀 = 증상

풀을 키워도 천장은 그대로거나 나빠지고, 천장에서 MySQL CPU가 포화·점유시간이 폭발한다.

RESULTS

결과 — 풀 10 / 40 / 80

처리량 천장은 세 암이 사실상 동일했고, 풀 크기는 "천장"이 아니라 "과부하에서 지연이 얼마나 나빠지는지"만 결정했다.

k6 요약 — 풀을 키울수록 지연만 악화

풀처리량(평균)p95p99maxdropped

40142.2 /s954 ms1,365 ms2,599 ms126

읽는 법처리량은 143 → 142 → 140으로 풀을 키울수록 오히려 미세 하락. 반대로 p95는 759ms → 954ms → 1,995ms로, dropped는 53 → 126 → 493으로 악화됐다. 작은 풀(10)이 모든 지연 지표에서 이긴다.

천장에서의 내부 지표 — 셋 다 CPU에서 멈췄다

램프 마지막 구간(목표 rps가 천장을 넘는 지점)의 샘플러 값이다. 처리량 천장은 셋 다 MySQL 약 2,000~2,400 statements/s에서 동일하게 멈췄다.

10~17 ms폭발(슬롯 부족)~100→187%100

공통점: InnoDB 락 대기는 전 구간 0. 건강 구간에서는 셋 다 점유 ~6ms, acquire ~0.001ms, 실제 사용 커넥션 0~1개, CPU 15~30%로 동일하게 여유로웠다. 벽은 오직 램프 후반, MySQL CPU가 코어를 다 태우는 지점에서만 나타났다.

핵심 관측풀 80은 두 코어를 완전히 태우고(198%) 동시 실행 쿼리를 60개까지 밀어넣었지만, 통과시킨 일의 양은 오히려 줄었다(2,400→2,150 stmt/s). 늘어난 커넥션이 포화된 CPU 위에서 경합하며 개별 쿼리 점유시간을 119ms→231ms로 두 배로 늘렸을 뿐이다.

DIAGNOSIS

판독 — 풀 · 락 · CPU

세 용의자를 하나씩 세운다. 데이터는 풀과 락을 배제하고 CPU를 지목한다.

① 풀은 원인이 아니다

풀을 40→80으로 두 배 늘려도 천장이 움직이지 않았고(142→140rps) 지연만 2~4배 악화됐다. 건강 구간에서 실제 사용 커넥션은 40~80개 중 0~1개뿐 — 풀은 천장 직전까지 통째로 놀았다. 풀은 MySQL이 못 빠져나가는 순간 acquire 대기가 폭발하며 "차는 것처럼" 보였을 뿐, 슬롯 수가 처리량을 자른 적이 없다.

② 락도 아니다

세 암 전 구간 Innodb_row_lock_waits·Innodb_row_lock_current_waits·Innodb_row_lock_time이 모두 0이었다. S-READ는 순수 SELECT라 MVCC 스냅샷 리드로 동작해 row lock을 잡지 않는다는 예측 그대로다. 자원(CPU) 경합이지 논리(락) 경합이 아니다.

③ 원인은 MySQL CPU — 그리고 그게 이 스펙에선 정상 범위다

읽기 경로(RankingQueryService.getPage)는 요청당 SELECT 딱 2개다 — 인덱스 페이지 조회 + 상품 20개 IN 일괄 조회. N+1도, 개별 순위 COUNT도 없다. 그런데도 천장이 수백 rps인 이유는 스펙에 있다: infra는 2 vCPU를 MySQL·Redis·Kafka가 나눠 쓰는 작은 박스라, MySQL이 실제로 쓸 수 있는 건 약 1.2코어다. 천장에서 mysqld CPU가 123~198%에서 멈춘 게 바로 그 물리적 한계다.

보정천장을 CPU 없이 조금 올릴 여지는 있다 — Redis·Kafka를 DB 박스에서 분리(뺏기던 코어 회수), 깊은 페이지 OFFSET + score DESC, product_id ASC 혼합정렬 filesort 개선. 하지만 둘 다 "MySQL로 읽는 한" 근본 한계 위의 부차 개선이다.
5

CONCLUSION

결론 — 천장은 못 늘리고, 걷어내야 한다

풀 소진은 증상, MySQL CPU가 원인, 락은 무관. 풀·튜닝으로는 못 밀어올리는 구조적 천장이다.

EXP-POOL · pool 10 / 40 / 80 · 2026-07-17

이 천장을 올리는 레버는 둘이다. 레버 1 — CPU를 더 준다(큰 인스턴스 / 전용 DB 노드): 천장은 오르지만 "비싼 일을 더 센 기계로 버티는" 방식이고, 읽기마다 네트워크 건너 MySQL을 때리는 구조와 스캔 비용은 그대로다. 레버 2 — 읽기를 MySQL에서 걷어낸다(Stage 3 Redis ZSET): 페이지 조회가 메모리 내 ZREVRANGE O(log N)가 되어 MySQL 왕복 자체가 사라진다. 천장을 올리는 게 아니라 천장을 만드는 원인을 제거한다.

Stage 1 ↔ 3 서사이 실험의 목적은 MySQL 튜닝으로 천장을 우회하는 게 아니라, "MySQL 버전은 풀·튜닝으로 못 올리는 CPU-바운드 천장을 가진다"를 못 박아 Stage 3 전환의 근거를 실측으로 세우는 것이다. Stage 3(Redis ZSET)가 이 천장의 본 해법으로 진행 중이며, 이 3암 데이터가 Stage 1↔3 비교표의 좌변이 된다.
