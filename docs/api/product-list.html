OVERVIEW

개요

상품 목록을 키셋 커서 페이지네이션으로 페이지 단위 조회한다. 정렬·brand 필터·페이지 크기를 query 파라미터로 받고, 다음 페이지를 가리키는 불투명(opaque) 커서를 응답에 담아 돌려준다.

정렬은 화이트리스트로 고정된 세 가지만 허용한다. 비유니크 1차 정렬 키는 항상 id DESC로 타이브레이크해 keyset의 안정적 total-order를 보장한다.

정렬 (sort)정렬 키커서 타입
LATESTid DESCIdCursor(id)
PRICE_ASCprice ASC, id DESCPriceCursor(price, id)
LIKES_DESClikeCount DESC, id DESCLikeCountCursor(likeCount, id)
핵심이 엔드포인트는 공개 API다 (인증 헤더 불필요). brandId 로 특정 브랜드 상품만 필터링할 수 있고, size 는 1~100 범위만 허용한다. 기본값은 sort=LATEST, size=20.

2

REQUEST & RESPONSE

요청 · 응답

컨트롤러 시그니처

ProductController.kt 
@GetMapping
fun getProducts(
    @RequestParam(required = false, defaultValue = "LATEST") sort: ProductSort,
    @RequestParam(required = false) brandId: Long?,
    @RequestParam(required = false) cursor: String?,
    @RequestParam(required = false, defaultValue = "20") size: Int,
): ProductListResponse {
    if (size !in 1..MAX_PAGE_SIZE) {        // MAX_PAGE_SIZE = 100
        throw BadRequestException(ProductErrorCode.INVALID_PAGE_SIZE)
    }
    val page = productService.list(sort, brandId, ProductCursorCodec.decode(sort, cursor), size)
    return ProductListResponse.from(sort, page)
}

nextCursor — 불투명 base64nextCursor 는 클라이언트가 해석하면 안 되는 불투명(opaque) 토큰이다. 평문 포맷 "<sort>:<keys...>" (예 LATEST면 LATEST:1042, PRICE_ASC면 PRICE_ASC:9900:1042)을 URL-safe base64(패딩 없음)로 인코딩한다. 클라이언트는 받은 값을 그대로 다음 요청 cursor 에 넣기만 하면 된다. 인코딩/디코딩은 presentation 레이어(ProductCursorCodec)의 책임이고, 도메인은 타입 있는 Cursor 만 다룬다.
공통 응답 래핑컨트롤러는 ProductListResponse 를 그대로 반환하고, 공통 web 인프라의 ResponseBodyAdvice 가 ApiResponse<T>(isSuccess · status · code · message · data · timestamp)로 감싼다. 실제 페이로드는 data 필드에 담긴다.

4

BUSINESS LOGIC

비즈니스 로직

1. size 가드 — 1~100

컨트롤러 진입 직후 size !in 1..100 이면 BadRequestException(INVALID_PAGE_SIZE) 를 던진다. 경계에서 fail-fast로 막아 비정상 페이지 크기가 쿼리까지 내려가지 않게 한다.

2. 커서 디코딩 — 정렬 정합 검증

ProductCursorCodec.decode(sort, cursor) 는 base64를 평문 "<sort>:<keys>" 로 되돌린 뒤, 선두 정렬명이 요청 sort와 일치하는지·키 개수가 맞는지 검사한다. base64 디코딩 실패, 정렬명 불일치, 키 개수/숫자 파싱 실패 중 하나라도 발생하면 BadRequestException(INVALID_PRODUCT_CURSOR) (400). 인프라 레이어의 scrollPosition() 도 커서 타입이 정렬과 어긋나면 같은 에러로 한 번 더 방어한다.

3. keyset(seek) 조회 — OFFSET 대비 평평한 응답 시간

리포지토리는 ScrollPosition.keyset()(또는 커서 키맵으로 만든 ScrollPosition.of(...))와 Window<Product> 로 keyset 페이지네이션을 구현한다. 커서가 가리키는 (정렬키, id) 지점부터 인덱스를 seek 해 바로 다음 N건을 읽는다.

OFFSET 깊은 페이지에서 느려짐

LIMIT offset, N 은 건너뛸 offset 개 행을 스캔 후 버린다. 페이지가 깊을수록 스캔량이 선형으로 늘어 뒤 페이지일수록 느려진다.

KEYSET 깊이와 무관하게 평평

마지막으로 읽은 (정렬키, id)를 인덱스에서 seek 해 그 다음부터 N건만 읽는다. 건너뛰는 스캔이 없어 페이지 깊이와 무관하게 응답 시간이 평평하다.

4. hasNext / nextCursor 생성

Window.hasNext() 가 참이고 결과가 비어있지 않으면, 마지막 행을 정렬별 커서로 변환해 nextCursor 로 삼는다 (LATEST→IdCursor, PRICE_ASC→PriceCursor, LIKES_DESC→LikeCountCursor). 다음 페이지가 없으면 null.

5. like_count 비정규화 (방식 B)

좋아요순(LIKES_DESC) 정렬은 매 조회마다 like 테이블을 COUNT 하지 않는다. product.like_count 비정규화 컬럼을 정렬 키로 직접 사용한다. 좋아요/취소 이벤트가 이 컬럼을 +1 / -1 로 갱신한다 (incrementLikeCount / decrementLikeCount, 0 미만 방지).

6. 복합 인덱스 · readOnly 트랜잭션

keyset의 seek가 효율적이려면 정렬 키와 동일한 순서의 복합 인덱스 (정렬키, id) 가 받쳐줘야 한다 (예 PRICE_ASC는 (price, id), LIKES_DESC는 (like_count, id)). 조회 use case는 @Transactional(readOnly = true) 로 묶어 쓰기 플러시·dirty checking 비용을 피한다.

CAVEATS

주의 사항

주의 · 커서-정렬 정합커서는 발급될 때의 정렬과 1:1로 묶인다. 평문 선두에 정렬명을 박아두고 decode 시 요청 sort와 대조하므로, 다른 sort의 nextCursor를 재사용하면 400(INVALID_PRODUCT_CURSOR)이다. 예 LATEST로 받은 커서를 PRICE_ASC 요청에 넣을 수 없다 — 클라이언트는 정렬을 바꾸면 커서를 버리고 첫 페이지부터 다시 시작해야 한다.
주의 · 비정규화 정합성LIKES_DESC 정렬 정확도는 like_count == 실제 좋아요 COUNT 라는 불변식에 의존한다. 좋아요/취소 이벤트가 컬럼 갱신을 누락하거나 동시성으로 어긋나면 정렬 순서가 틀어진다. 갱신은 +1/-1 원자 update(0 미만 clamp)로 처리하되, 카운트 드리프트가 의심되면 별도 재집계(reconcile) 경로가 필요하다.
주의 · opaque 커서nextCursor 는 서버 내부 포맷이다. 클라이언트가 base64를 풀어 키 값을 직접 가공하면 인코딩 포맷 변경 시 깨진다. 받은 토큰을 그대로 다음 cursor에 전달하는 용도로만 쓴다.
주의 · 잘못된 sort 값sort 는 enum 바인딩이라 화이트리스트(LATEST/PRICE_ASC/LIKES_DESC) 밖의 값을 주면 Spring 파라미터 변환 단계에서 거부된다 (도메인 진입 전 400). 허용 정렬은 이 세 가지로 고정이다.
