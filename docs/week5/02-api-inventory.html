INVENTORY

조회 API 인벤토리

성능 분석 대상은 네 개다. 셋은 읽기, 하나는 쓰기(좋아요)다. 각각의 진입점과 책임을 먼저 정리한다.

API진입점성격
상품 목록ProductService.list → ProductRepositoryImpl.findAll정렬+필터+커서, 최우선 표적
상품 상세ProductService.getDetail단건 PK, 캐시 대상
인기 상품list(LIKES_DESC, brandId=null) 첫 페이지A/B/C 실험 주 무대
좋아요 등록/취소LikeService.like / unlike쓰기 경로, 정합성 갭
설계 메모인기 상품은 별도 메서드가 아니라 list(LIKES_DESC, brandId=null, cursor=null)의 첫 페이지로 표현한다. 별도 엔드포인트를 만들지 않는 게 YAGNI 관점에서 맞다.

QUERIES

호출당 발생 쿼리

"한 번 조회 = 한 쿼리"가 아니다. 상세는 2쿼리, 좋아요는 커밋 후 비동기 쿼리까지 따라온다. 무엇이 몇 번 도는지 본다.

API발생 쿼리쿼리 수
상품 목록product keyset 1쿼리 — WHERE status<>DELETED [AND brand_id=?] ORDER BY <sort>,id DESC LIMIT n+11
상품 상세product 1 + brand 1 (brandId로 단건 조회)2
인기 상품product 1쿼리 — ORDER BY like_count DESC, id DESC LIMIT n1
좋아요 등록product 존재확인 1 + exists 1 + insert 1 · 커밋 후 비동기 like_count UPDATE 1 + like_event INSERT 13 + 2

목록 쿼리의 실제 모양

list — LIKES_DESC + brandId + keyset 
-- 브랜드 필터 + 좋아요순 + keyset 커서(2번째 페이지 이후)
SELECT id, brand_id, name, price, like_count, status
FROM product
WHERE status <> 'DELETED'
  AND brand_id = :brandId
  -- keyset: (like_count, id) < 직전 페이지 마지막 행
  AND (like_count < :c1 OR (like_count = :c1 AND id < :c2))
ORDER BY like_count DESC, id DESC
LIMIT :sizePlus1;
관찰 포인트이 쿼리가 인덱스 없이 돌면 ① status/brand_id 필터 → ② (like_count,id) 전체 정렬(filesort) → ③ keyset 범위 평가가 모두 풀스캔 위에서 일어난다. 인덱스가 이 셋을 한 번에 푸는 게 목표다.

PK 조회라 빠르지만 읽기 집중. Step 6 캐시로 DB 접근 자체를 줄임.

P1 인기 상품

좋아요 집계 방식에 따라 쿼리 모양이 완전히 다름. A/B/C 실험의 주 무대.

P2 좋아요 쓰기

비동기 like_count UPDATE 실패 시 드리프트. Step 5 재집계 배치로 보강.

PITFALL

잠재 N+1 주의점

지금은 N+1이 없다. 하지만 목록 응답에 "브랜드명"을 넣는 순간 생긴다. 미리 못 박아 둔다.

함정목록 DTO에 brandName을 추가하면 상품 N개당 브랜드 조회 N번 → N+1. 그래서 초기 응답엔 brandId만 담는다. 브랜드명이 정말 필요하면 ① 브랜드 일괄조회(IN) 후 메모리 조인 또는 ② product에 brandName 비정규화로 풀어야 한다 — 이건 별도 결정 사항.
상세는 안전상세의 product 1 + brand 1 = 2쿼리는 단건이라 N+1이 아니다. 캐시를 씌우면 이 2쿼리도 캐시 적중 시 0이 된다.
