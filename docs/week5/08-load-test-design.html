MATRIX

실험 매트릭스

4개 처방 조건을 3개 부하 레벨로 측정한다. 조건은 누적 축 — 뒤로 갈수록 앞의 처방 위에 쌓인다.

조건구성100 / 1,000 / 3,000 TPS읽기 경로
C1 인덱스 Xbaseline측정DB 풀스캔 + filesort
C2 인덱스 O+복합 인덱스측정DB 인덱스 스캔 (rows≈20)
C3 캐시+Redis 캐시측정Redis hit → DB 우회
C4 캐시+락+스탬피드 동기화 락별도 시나리오만료 동시미스 방어
서브스터디JVM 웜업 전/후는 C2(인덱스)에서 1,000 TPS만 측정한다. 그 결과로 나머지 전 조건의 웜업 정책(전부 웜업 vs 생략)을 정한다. → §5
5,000 TPS 제외당초 5,000을 넣었으나 N100 타당성 평가(§2) 결과 대부분 조건에서 달성 불가 → 100·1,000·3,000으로 확정. 3,000도 약한 조건엔 포화 테스트로 동작한다(§3).

FEASIBILITY

N100 단일 박스 타당성

app·MySQL·Redis를 4코어 한 박스에 올린다. "이 박스가 몇 TPS를 견디나"를 먼저 못 박아야 측정값을 해석할 수 있다.

항목사양평가
CPUIntel N100 4C/4T (E-core, SMT 없음, ~3.0GHz 지속)미니서버엔 충분, 고동시성 CPU 바운드엔 약함
메모리14GiB 실측 + Swap 4GiB신중 배분 시 OK (§7)
디스크512GB NVMe SSD데이터셋 대부분 RAM 적재 → 병목 아님
OSUbuntu 26.04, cgroup v2, idle load 0.08깨끗한 베이스라인

CPU 예산 계산

4코어 × ~3.0GHz를 N TPS로 나누면 요청당 CPU 예산이 나온다. app·MySQL·Redis가 이 4코어를 공유한다.

부하요청당 CPU 예산(4코어 ÷ TPS)해석
100 TPS~40ms여유. 단 C1 S1(10만 filesort)은 요청당 수십 ms라 여기서도 포화 위험
1,000 TPS~4msC2·C3 가능, C1 불가
3,000 TPS~1.3ms캐시 hit만 가능권, DB 경로는 포화
(5,000 TPS)~0.8ms캐시 hit조차 천장 위 → 제외

조건별 현실 천장 (달성 TPS 추정)

조건요청당 비용(N100 추정)현실 천장
C1 인덱스 X수십 ms (10만 filesort)~수백 TPS, 100에서도 위태
C2 인덱스 O~1.5~2.5ms (rows≈20, 버퍼풀 warm)~1,500~2,500
C3 캐시 hit~1~1.5ms (Redis)~2,000~3,500
C4 캐시+락steady는 C3 동일, 미스 때만 갈림~2,000~3,500
결론이 박스에서 의미 있는 측정 구간은 100~3,000 TPS. C1은 저부하 포화점을, C2/C3는 1,000~3,000의 처리량·지연을 본다. "5,000 통과" 같은 합격/불합격이 아니라 각 조건의 포화점과 그때의 지연이 결과다.

REFRAME

목표 TPS ≠ 달성 TPS

k6로 3,000/s를 "주입"해도 서버가 300/s밖에 못 하면, 3,000은 그냥 포화 테스트가 된다. 측정의 단위를 바꿔야 한다.

주입offered load

k6 constant-arrival-rate가 목표하는 도착률. 100·1,000·3,000은 이 주입 스텝이다.

달성throughput

서버가 실제 200 응답한 http_reqs/s. 약한 조건은 주입을 못 따라간다 → 그 갭이 포화 신호.

그래서 각 (조건 × 부하) 셀에서 기록할 것은 달성 throughput + p95/p99 + 에러율이다. 추가로 조건별 무릎점(knee)을 ramping-arrival-rate로 탐색해 "p95가 SLO를 넘고 에러가 오르기 시작하는 도착률"을 찾는다.

포화 신호 4종① k6 dropped_iterations(주입률 못 맞춤) ② 달성률 < 주입률 갭 ③ p95/p99 급등 ④ http_req_failed 상승. 이 중 하나라도 뜨면 그 부하는 그 조건의 천장 위.

SCENARIOS

조건별 측정 설계

C1·C2·C3는 같은 읽기 시나리오(S1/S2/S3)를 공유한다. C4(스탬피드)만 성격이 달라 별도 시나리오가 필요하다.

읽기 시나리오 (C1·C2·C3 공통)

시나리오요청모집단의도
S1 인기상품?sort=LIKES_DESC&size=20100,750최악 — 풀스캔+filesort
S2 대형브랜드&brandId=1 (메가 8,000)8,000필터해도 큰 정렬 → 복합 인덱스 입증
S3 소형브랜드&brandId=350 (소형 30)30대조군 — 인덱스 무의미

토글 인덱스(ddl-auto=create 회피 위해 수동 CREATE/DROP):

indexes.sql
-- C2 진입: 인덱스 생성
CREATE INDEX idx_product_like ON product (like_count DESC, id DESC);
CREATE INDEX idx_product_brand_like ON product (brand_id, like_count DESC, id DESC);
-- C1 복귀: DROP 으로 baseline 재현

C4 — 스탬피드 (캐시 만료 동시미스)

동기화 락은 steady-state hit에선 C3과 구분이 안 된다. 핫 키 TTL이 만료되는 순간 N개 요청이 동시에 미스 → DB로 몰리는 thundering herd에서만 효과가 드러난다.

키 단일 핫 상품TTL 짧게(5~10s)부하 고동시성 단일키
  • setup — 메가히트 상품 1개를 짧은 TTL로 캐싱, 동일 키에 고동시성 부하
  • 락 OFF — 만료 순간 전 요청이 동시 미스 → DB Com_select 스파이크 + p99 꼬리 관측
  • 락 ON — 한 요청만 재계산(single-flight), 나머지는 대기/스테일 → DB는 ~1 쿼리
  • 지표 — 만료창의 MySQL Com_select delta · p99 · Redis blocked_clients
측정 단위C4의 결과는 throughput이 아니라 만료 순간 DB로 새어나간 쿼리 수(fan-out)와 p99 tail이다.

WARM-UP

JVM 웜업 서브스터디

C2(인덱스)에서 1,000 TPS로 cold vs warm을 측정한다. 1,000은 C2 천장 아래라 포화에 안 가려진 깨끗한 웜업 관찰이 된다.

JIT 컴파일 기준 (공식 확인)

Java 21은 TieredCompilation=true가 기본. 핫 메서드가 C2(Tier 4)로 최종 최적화되는 조건은 (OpenJDK 21 compilationPolicy.cpp · CallPredicate):

CallPredicate::apply_scaled
// i = 호출수, b = 백엣지수, scale = CompileThresholdScaling(1.0) × 큐부하 피드백
(i >= Tier4InvocationThreshold)                                  // 5000
  || (i >= Tier4MinInvocationThreshold && i+b >= Tier4CompileThreshold)  // 600 & 15000
임계 (Temurin 21.0.7 실측 기본값)값
Tier4InvocationThreshold (C2 핵심)5,000
Tier4MinInvocationThreshold / CompileThreshold600 / 15,000
Tier3InvocationThreshold (C1+profiling)200
CompileThreshold (tiered OFF 전용 — 무관)10,000
흔한 오해CompileThreshold=10000은 tiered가 꺼졌을 때만 쓰인다. 기본(tiered ON)에서 C2 진입은 호출 5,000회 기준 → 1,000 TPS면 핫 메서드가 약 5초면 C2 도달.

측정 설계 + 격리

cold부팅 직후

app 컨테이너 fresh 시작 → 즉시 1,000 TPS. 첫 30~60s의 p95·정상화 시간 기록.

warm웜업 후

웜업 페이즈(≥60s) 후 steady 1,000 TPS. jvm.compilation.time·CodeCache 평탄화 = warm 판정.

치명 전제 — JIT 격리cold/warm 양쪽 모두 MySQL InnoDB 버퍼풀·HikariCP·Redis를 미리 warm 시켜 동일하게 두고, 오직 app 컨테이너만 cold/warm으로 변주한다. 안 그러면 cold의 느린 구간이 JIT가 아니라 버퍼풀 워밍이고, 그건 캐시 조건엔 전이되지 않는다. N100은 컴파일러 스레드가 4코어를 서빙과 공유해 웜업이 이상치(~5s)보다 늘어질 수 있다.
정책 게이트cold≈warm → 전 조건 웜업 생략(시간 절약) / cold≪warm → 전 조건 웜업 후 steady 측정. 모호하면 그냥 다 웜업(조건 비교는 원래 steady-state가 표준).

MONITORING

모니터링 — CPU · 메모리

코로케이션 실험은 모니터링이 곧 병목 귀인이다. USE 방법론(Utilization·Saturation·Errors)으로, util%만 보지 않고 saturation을 함께 본다.

USE 핵심 (Brendan Gregg)5분 평균이 80%를 안 넘어도 초 단위 100% 스파이크가 숨어 포화가 난다. 그래서 run-queue·PSI 같은 saturation 지표가 필수. 이전 라이브 측정의 "host CPU=1.0", "cold JVM 1.5×CPU"가 정확히 이 문제였다.

CPU — 3레벨

레벨UtilizationSaturation (놓치기 쉬움)도구
호스트%usr·%sys·%iowait·%steal (코어별)run-queue r · load avg · PSI cpu some avg10/60mpstat·vmstat·/proc/pressure/cpu
컨테이너cpu.stat usage/user/system_usec(limit 없음 → 스로틀 측정 불필요)docker stats
JVMprocess.cpu.usage·system.cpu.usagesystem.load.average.1m + JIT/GCMicrometer
limit 없이 코어 경쟁 — 모니터링 영향어떤 컨테이너에도 --cpus를 안 건다 → CFS 스로틀링 변수 없음. 따라서 throttled_usec는 안 본다. 대신 코어별 mpstat + 컨테이너별 docker stats(CPU%) + PSI cpu로 "누가 4코어를 이겼나"를 귀인한다. JVM도 4코어를 정확히 인식(스레드풀·GC·JIT 스레드 정상 사이징).

cold JVM 증명: process.cpu.usage Δ + jvm.compilation.time(JIT 평탄화 타임라인) + jvm.gc.pause. (이전 측정의 "JIT 1283→442, GC pause 0.019→0.004"가 이 지표)

메모리 함정heap만 보면 안 된다. 컨테이너는 RSS(=heap + native: metaspace·code cache·thread stack·direct buffer)로 OOM-kill한다 — heap이 limit 아래여도 native가 밀면 죽는다. 정밀 추적은 -XX:NativeMemoryTracking=summary + jcmd <pid> VM.native_memory summary. 모니터링은 RSS/working_set vs limit으로 본다.

스택 — 측정 박스 교란 최소화

  • Prometheus + Grafana는 Mac에서 돌리고, N100엔 가벼운 exporter(node/mysqld/redis) + Actuator만 두고 LAN 스크랩 → 대시보드 CPU가 측정 박스를 안 건드림
  • 셸 샘플링 폴백 — mpstat·vmstat·docker stats·SHOW GLOBAL STATUS delta를 CSV로(steady 5s, 스탬피드 1s)
  • 오버헤드 베이스라인 — idle+모니터링만 먼저 측정해 관측 비용을 빼고 본다
  • 시간 정렬 — k6 타임스탬프 ↔ 서버 메트릭 NTP 동기화(스탬피드 스파이크 순간 정합)

PROCEDURE

실행 순서 · 판정 기준

한 번에 한 변수만 바꾼다. 각 런 사이 상태를 리셋한다.

  • 0 사전 — LAN 확인(ping/iperf3), 도커 기동, 시드 적재 + 일치 검증(mismatch=0), 버퍼풀·heap·maxmemory 설정 확인, idle+모니터링 베이스라인
  • C1 (인덱스 DROP) — S1/S2/S3 EXPLAIN ANALYZE + k6 100→1k→3k. filesort·rows·포화점 기록
  • C2 (인덱스 CREATE) — 동일 측정. filesort 제거·rows≈20 확인 → 전후 비교표
  • 웜업 서브스터디 — C2 @1,000 cold vs warm (버퍼풀·Hikari·Redis는 양쪽 warm 고정) → 전 조건 웜업 정책 결정
  • C3 (캐시 ON) — 동일 + 적중률, Redis 내린 상태 미스 fallback 확인
  • C4 (스탬피드) — 짧은 TTL 핫키 고동시성, 락 OFF vs ON, 만료창 DB fan-out·p99
  • 리셋 규칙 — index DROP/CREATE, redis FLUSHALL, cold=app 컨테이너 restart, 충분한 cooldown
