PROBLEM

문제 정의

트래픽이 늘면 가장 먼저 무너지는 건 "정렬·필터가 붙은 조회"다. 단건 PK 조회는 버티지만, 좋아요 순 정렬은 인덱스가 없으면 전체를 훑고 정렬한다.

이번 주차의 표적은 세 가지 조회다. 셋 다 정렬 키가 비-PK(좋아요 수)이거나 필터(브랜드)가 붙어, 데이터가 10만 건으로 늘면 풀스캔 + filesort로 떨어진다.

증상 1 좋아요 순 정렬

ORDER BY like_count DESC, id DESC — like_count는 비유니크라 복합 정렬 인덱스가 없으면 전체 정렬(filesort).

증상 2 브랜드 필터

WHERE brand_id = ? + 정렬 동시 적용. 필터 후 정렬을 한 인덱스로 못 풀면 모집단 전체를 정렬.

증상 3 인기 상품

브랜드 없이 like_count 상위 N. 핫 상품 소수 + 동률 타이브레이크(id DESC)를 실제로 타는 가장 무거운 시나리오.

해법 3단 접근

인덱스로 정렬·필터 비용 제거 → 집계 구조(A/B/C) 비교 → Redis 캐싱으로 반복 조회 차단. 각 단계 전후를 측정.

핵심 한 줄병목의 진원지는 좋아요 순 정렬 + 브랜드 필터 + keyset 커서의 조합이다. 이 조합을 한 복합 인덱스로 해결하는 것이 1차 목표다.
2

GOAL

목표와 검증 기준

"빨라졌다"는 느낌이 아니라 숫자로 증명한다. 같은 데이터·같은 쿼리 시나리오를 고정하고, 각 처방의 전후를 측정한다.

영역해야 하는 것검증 지표
① 인덱스브랜드 필터 + 좋아요순 정렬 구현, EXPLAIN으로 인덱스 최적화filesort 제거 · rows examined 감소 · p95 단축
② 집계 구조좋아요 집계 A/B/C 방식 직접 구현·비교, 등록/취소 동기화읽기·쓰기 비용 · 정합성 · 운영복잡도 비교표
③ 캐시상세·목록에 Redis 캐시. TTL·키설계·무효화적중률 · 캐시 전후 처리량 · 미스 fallback
측정 시나리오 (고정)S1 인기 상품 첫 페이지(브랜드 없음) · S2 대형 브랜드 + 좋아요순(수만 모집단) · S3 소형 브랜드 + 좋아요순(수십 모집단). 세 방식·세 처방 모두 이 3개로 측정한다.
3

AS-IS

현재 코드 상태

계획을 짜기 전에 코드를 먼저 읽었다. 일부는 이미 구현돼 있고, 일부는 비어 있다 — 이 사실이 작업 범위를 바꾼다.

  • 비정규화 like_count 컬럼이 이미 존재 — 방식 B는 절반 구현 상태(원자적 UPDATE + 이벤트 동기화) B 부분완료
  • like_event append-only 이력 테이블 존재 — 방식 A 재집계·C 갱신·정합성 보강의 공통 소스 소스 확보
  • keyset 페이지네이션 구현됨(Spring Data Window/ScrollPosition) 재사용
  • Redis·Docker 인프라 구성됨(master/replica) 재사용
  • Product/Brand/Like REST 컨트롤러 미구현 — Service만 존재. 측정 엔드포인트를 새로 만들어야 함 TODO
  • 캐시 인프라 없음 — @EnableCaching·CacheManager 없음, RedisTemplate<String,String>만. 객체 캐싱용 JSON 직렬화 구성 필요 TODO
  • 이벤트 핸들러 정합성 갭 — like_count UPDATE 실패 시 warn 로그만 → 드리프트 가능. 재집계 배치로 보강 TODO
함정ddl-auto=create(local)라 인덱스를 JPA 어노테이션으로 박으면 매 부팅 재생성된다. 측정 단계의 인덱스는 수동 CREATE/DROP SQL로 토글하고, 최종 확정분만 어노테이션으로 코드화한다.
