SNAPSHOT

현재 상태 — 있는 것 vs 만들 것

Round 7은 백지에서 시작하지 않습니다. like 도메인이 이미 "동기 처리 + 커밋 후 비동기 부가처리"의 모범 사례이고, Kafka 인프라(modules:kafka)와 consumer 앱(commerce-streamer)도 배선돼 있습니다. 빠진 것은 영속 보장(Outbox)·이벤트 멱등·실제 producer 연결·집계 consumer입니다.

있음 재사용·참고 대상

like 이벤트 분리 — LikeService가 좋아요를 저장하며 ProductLikedEvent 발행, LikeEventHandler·ProductLikeCountEventHandler가 AFTER_COMMIT + @Async로 이력 적재·like_count 비정규화. 실패는 로깅만(결과적 일관성). @EnableAsync 설정 완료.

Kafka 인프라 — KafkaConfig에 KafkaTemplate·MANUAL ack 배치 리스너 준비. commerce-streamer에 DemoKafkaConsumer 예시. docker infra에 kafka:9092·kafka-ui:9099.

결제 멱등 — PaymentService.resolve()가 상태머신 기반 멱등(이미 terminal이면 no-op).

없음 새로 만들 것

Transactional Outbox 테이블 + 릴레이(폴링) 워커.

event_handled(event_id PK) 멱등 테이블 — 이벤트 레벨 dedup(payment 상태머신과 별개).

commerce-api → Kafka producer — KafkaTemplate은 modules:kafka에 있으나 commerce-api는 아직 그 의존성을 import하지 않음(build.gradle.kts에 추가 필요).

데이터플랫폼 전송 — 주문정보 외부 전송은 동기·비동기 모두 미구현.

product_metrics 집계 테이블 + commerce-streamer의 집계 consumer.

consumer 앱 명칭과제 원문은 집계 consumer 앱을 commerce-collector로 부르지만, 우리 레포엔 이미 Kafka로 배선된 commerce-streamer가 있습니다. 신규 모듈 생성 비용을 피하려 commerce-streamer를 재사용합니다. 이후 문서 전반에서 commerce-streamer로 표기합니다(이 각주에서만 원문 명칭을 병기). 재사용 결정의 한계는 §5에서 다룹니다.

STEP 1

ApplicationEvent 경계 분리

현재 OrderFacade.place()는 단일 @Transactional 안에서 상품 검증 → 쿠폰 사용 → 주문 저장 → 재고 차감을 모두 처리합니다. 여기에 데이터플랫폼 전송·유저행동 로깅·알림 같은 부가 로직을 직접 호출로 끼워넣지 말고, like 도메인이 이미 쓰는 AFTER_COMMIT 이벤트로 빼냅니다.

현재 코드 — 단일 트랜잭션

핵심 주석이 이미 다음 단계를 예고합니다(코드 그대로 인용).

order/application/OrderFacade.kt 
// PG 연동(O-F1) 시 이 메서드의 Tx 구간을 안쪽 메서드로 분리한다 — 외부 호출은 Tx 밖에 둔다
@Transactional
fun place(command: OrderCreateCommand): OrderInfo {
    val products = productService.getActiveProducts(...)
    val discountAmount = command.couponId?.let { couponService.use(...) } ?: Money(0)
    val info = orderService.create(command, products, discountAmount)
    inventoryService.decreaseStock(...)
    return info
}

적용 후 — 부가 로직을 이벤트로 (예시)

주문 저장이 끝나면 OrderCreatedEvent를 발행만 하고, 외부 전송·로깅은 커밋 후 별도 핸들러가 처리합니다. like 도메인의 발행 코드를 그대로 본뜬 형태입니다.

OrderFacade.kt — 예시 (eventPublisher 주입 후) 
    val info = orderService.create(command, products, discountAmount)
    inventoryService.decreaseStock(...)
    eventPublisher.publishEvent(OrderCreatedEvent(info.orderId, command.userId)) // 발행만
    return info

핸들러는 like 도메인과 동일한 애너테이션 3종(@Async · @Transactional(REQUIRES_NEW) · @TransactionalEventListener(AFTER_COMMIT))을 그대로 사용합니다. 검증된 패턴이라 새로 설계할 게 없습니다.

like/application/LikeEventHandler.kt — 재사용할 패턴 (실제 코드) 
@Async
@Transactional(propagation = Propagation.REQUIRES_NEW)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
fun onLiked(event: ProductLikedEvent) = append(event.userId, event.productId, LikeAction.LIKE)

이벤트로 뺄 것 vs 트랜잭션에 남길 것

판단 기준은 단순합니다. 주문의 정합성에 직접 관여하면 트랜잭션, 틀어져도 결과적 일관성으로 보정 가능하면 이벤트입니다.

작업현재 위치판단
재고 차감place() 내부트랜잭션 — 핵심 정합성(오버셀링 금지)
쿠폰 사용place() 내부트랜잭션 — 중복 사용·할인액 검증
주문 저장place() 내부트랜잭션 — aggregate 본체
포인트 차감(미도입)—트랜잭션 — 도입 시 핵심 정합성
데이터플랫폼 전송미구현이벤트 — 외부 전송, 실패해도 재전송
유저행동 로깅미구현이벤트 — like_event 적재와 동형
알림미구현이벤트 — 부가, 실패 허용
랭킹·집계like_count만 존재이벤트 — like_count 비정규화와 동형
동기 vs 비동기like가 보여준 분리를 주문에 그대로 적용: 동기(좋아요 저장 ↔ 주문 저장·재고·쿠폰)는 트랜잭션 안, 비동기(이력 적재·like_count ↔ 데이터플랫폼·로깅·집계)는 AFTER_COMMIT. 동기 처리가 실패하면 전체 롤백, 비동기가 실패하면 로깅만 하고 본 트랜잭션은 보존(ProductLikeCountEventHandler의 "결과적 일관성" 주석과 동일 정책).

STEP 2

Outbox · Kafka 파이프라인

§2의 메모리 이벤트(@TransactionalEventListener)는 앱이 죽으면 유실됩니다. 서비스 경계를 넘는 이벤트(집계·외부 전송)는 Transactional Outbox로 영속화한 뒤 릴레이가 Kafka로 흘려보냅니다. producer 쪽은 commerce-api에 Kafka 의존성을 먼저 추가해야 시작할 수 있습니다.

Outbox 테이블 (예시 스키마)

컬럼타입용도
idBIGINT PKoutbox 행 식별 · event_id로도 사용
aggregate_typeVARCHARorder · product · coupon
aggregate_idBIGINT파티션 키 산출 근거(orderId 등)
event_typeVARCHAROrderCreated · ProductLiked …
payloadJSON직렬화된 이벤트 본문
statusVARCHARPENDING → SENT (릴레이가 전이)
created_atDATETIME폴링 정렬·재시도 기준
왜 outbox인가"이벤트 발행 + 비즈니스 데이터 저장"을 하나의 DB 트랜잭션으로 묶어야 둘이 원자적이다. 메모리 @TransactionalEventListener는 커밋 후 발행이라 그 사이 앱이 죽으면 이벤트만 유실된다. outbox는 같은 트랜잭션에 INSERT되므로 "주문은 저장됐는데 이벤트는 안 나간" 상태가 불가능하다.

Producer 추가 지점

현재 commerce-api/build.gradle.kts는 persistence-core·jpa·redis·supports만 의존하고 :modules:kafka는 import하지 않습니다. 릴레이가 KafkaTemplate을 쓰려면 의존성 추가가 첫 작업입니다(예시).

apps/commerce-api/build.gradle.kts — 추가 (예시) 
dependencies {
    implementation(project(":modules:persistence-core"))
    implementation(project(":modules:jpa"))
    implementation(project(":modules:redis"))
    implementation(project(":modules:kafka")) // 추가 — KafkaTemplate·KafkaConfig 사용
    ...
}
정확성 설정 위치acks=all · enable.idempotence=true는 KafkaConfig.producerFactory가 kafkaProperties.buildProducerProperties()로 읽으므로, commerce-api의 application.yml의 spring.kafka.producer에 선언하면 그대로 반영된다. 별도 Java config를 새로 만들 필요 없음 — 기존 modules:kafka 빈을 재사용한다.

commerce-streamer 확장

출발점은 DemoKafkaConsumer입니다. 토픽을 실제 토픽으로 바꾸고, 집계 전 멱등 체크 → upsert → ack 순서만 채우면 됩니다.

demoListener(messages, acknowledgment) → Unit현재: println 후 ack
현재DemoKafkaConsumer — 토픽 수신 후 println, acknowledgment.acknowledge()(MANUAL)
확장event_id로 event_handled 조회 → 이미 있으면 skip, 없으면 product_metrics upsert + event_handled INSERT
최신성이벤트의 version/updated_at이 더 오래면 덮어쓰지 않음(out-of-order 방어)
ack처리 성공 후에만 acknowledge() — 실패 시 재전송(at-least-once)
멱등 위치at-least-once 전송에서 중복은 정상이다. ⑤ event_handled가 그 중복을 흡수한다. 이건 §2의 비동기 핸들러(메모리)와 다른 층위의 멱등 — payment 상태머신 멱등과의 관계는 §5에서 구분한다.

STEP 3

선착순 쿠폰 발급

현재 CouponService에는 관리자 발급(grant)만 있습니다(UserCouponGrantedType.ADMIN). 선착순은 사용자가 직접 요청하는 흐름이라, 요청을 Kafka로 직렬화해 단일 컨슈머가 수량을 순차 제어하는 모델을 새로 얹습니다.

현재 coupon 도메인

메서드현재 동작선착순에서 재사용
create관리자 쿠폰 생성(/api-admin/v1/coupons)그대로
grant관리자 지급 · existsByUserIdAndCouponId로 중복 차단 → ALREADY_GRANTED중복 방지 로직 재사용
use / cancelUse주문 시 사용 · 보상 시 취소변경 없음
없는 것사용자용 POST /api/v1/coupons/issue 발급 요청, 요청 결과 조회, 선착순 수량 제어, UserCouponGrantedType.FIRST_COME(가칭) 구분. grant의 existsByUserIdAndCouponId 중복 차단은 그대로 살려 userId 중복 발급을 막는다.

왜 단일 컨슈머인가 · 동시성 테스트 지점

수량 제어는 경합이 핵심입니다. 파티션 키를 couponId로 두면 같은 쿠폰의 요청은 한 파티션에 모이고, 단일 컨슈머가 순서대로 처리하므로 "1000개를 1001명이 받는" lost update가 원천 차단됩니다. userId 중복은 coupon_issue unique(userId, couponId) 또는 grant의 기존 중복 차단으로 막습니다.

검증수량 초과 미발급은 기존 runConcurrently(threadCount) { ... } 유틸(support/ConcurrencyTesting.kt)로 검증한다. N개 한정 쿠폰에 N+M 동시 요청을 던지고, 정확히 N건만 발급 + 중복 0건을 단언한다. 통합 테스트는 DatabaseCleanup + @BeforeEach 패턴을 따르고, 클래스에 @Transactional을 붙이지 않는다(REQUIRES_NEW·@Async와 충돌).

TRADE-OFFS

고민 포인트 · 트레이드오프

회의적 리뷰어 관점에서, 적용 과정에서 깨질 수 있는 곳과 의식적으로 결정해야 할 곳을 짚습니다.

① 이중 발행 — 메모리 이벤트와 Outbox 병행

지금 like는 메모리 @TransactionalEventListener로 like_count를 갱신합니다. 여기에 Outbox→Kafka까지 더하면 같은 좋아요가 두 경로로 두 번 집계될 위험이 있습니다. 판단: 같은 앱 내부 부가처리(like_count 비정규화)는 메모리 이벤트로 유지하고, 서비스 경계를 넘는 집계·외부 전송만 Outbox로 승격합니다. 둘의 책임을 겹치지 않게 자르는 게 핵심입니다.

② 멱등 — event_handled vs payment 상태머신

둘 다 멱등이지만 층위가 다릅니다. 중복이 아니라 보완 관계입니다.

구분payment 상태머신event_handled 테이블
대상결제 상태 전이(SUCCESS/FAILED terminal)Kafka 메시지 처리 1회 보장
방식resolve()에서 isTerminal이면 no-opevent_id PK 존재 여부로 skip
층위도메인 불변식인프라(at-least-once 흡수)

"핸들링 테이블 vs 로그 테이블 분리" 질문에 대한 우리 답: event_handled(처리 사실, PK=event_id)와 like_event(행동 이력)는 목적이 달라 분리합니다. 전자는 dedup 키, 후자는 재집계 소스입니다.

③ @Async TaskExecutor 기본값

@EnableAsync만 켜고 별도 TaskExecutor 빈을 두지 않아 Spring Boot 기본 풀에 의존 중입니다. 핸들러가 늘면 무한 큐에 작업이 쌓여 백프레셔가 안 걸립니다. 이벤트 핸들러를 늘리기 전에 명시적 풀 크기·큐 한계·거부 정책을 설정해야 합니다.

④ Testcontainers Kafka 미사용

현재 testFixtures에 MySQL·Redis Testcontainers는 있으나 Kafka 통합 테스트 예시는 없습니다. consumer 테스트를 추가할 때 @EmbeddedKafka(가볍고 빠름) vs Testcontainers Kafka(실제 브로커에 가까움) 중 택해야 합니다. 단위 흐름 검증은 EmbeddedKafka, 직렬화·파티셔닝까지 보려면 Testcontainers가 적합합니다.

⑤ commerce-streamer 재사용의 한계

신규 모듈을 안 만드는 대신, streamer가 집계·선착순·이력 적재를 한 앱에 겸하게 됩니다. 단기엔 비용이 낮지만, consumer group·스케일 단위가 섞여 한 종류 부하가 다른 처리를 지연시킬 수 있습니다. 부하가 갈리는 시점에 토픽별로 앱을 분리하면 됩니다(컨텍스트 패키지를 그대로 추출하는 기존 전략과 정합).

놓치기 쉬운 것Outbox 릴레이는 발행 후 status=SENT 전이가 또 하나의 트랜잭션이다. 발행은 됐는데 SENT 전이 전에 죽으면 같은 메시지가 재발행된다 → consumer의 event_handled가 반드시 있어야 안전하다. Outbox와 멱등 테이블은 세트다.
