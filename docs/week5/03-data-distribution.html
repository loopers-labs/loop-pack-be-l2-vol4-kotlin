1

WHY

왜 롱테일인가

현실 커머스는 멱법칙을 따른다. 무신사는 약 7,500개 브랜드가 입점해 있지만, 빅세일 주력은 2,100여 브랜드의 30만 상품이다 — 소수 브랜드가 물량의 대부분을 차지한다.[1]

균등하게 "브랜드당 200개씩" 넣으면 모든 브랜드 필터가 똑같이 200건을 본다. 이러면 인덱스 선택성의 차이가 드러나지 않는다. 멱법칙으로 쏠리게 해야, 같은 쿼리·같은 인덱스가 모집단 크기에 따라 어떻게 다르게 동작하는지 관찰할 수 있다.

측정 설계의 핵심대형 브랜드(수만 모집단)에서는 브랜드 인덱스만으로 부족해 정렬까지 인덱스로 풀어야 하고, 소형 브랜드(수십)에서는 브랜드 인덱스만으로 충분하다. 이 대비를 한 시드에서 보려고 분포를 쏠리게 만든다.

BRANDS

브랜드 4티어 분포

브랜드 500개를 메가/대형/중형/소형 4티어로 나눈다. 상위 5%(25개)가 전체 상품의 70%를 점유한다.

S2 대형 브랜드 필터

메가 브랜드(8,000건) + 좋아요순. 브랜드 인덱스만으론 8천 건 정렬 → 복합 인덱스 효과가 크게 드러난다.

S3 소형 브랜드 필터

소형 브랜드(28건) + 좋아요순. 모집단이 작아 브랜드 인덱스만으로도 충분 — 대조군.

3

LIKES

좋아요·가격 분포

좋아요도 쏠려야 한다. 인기 상품 첫 페이지가 "소수 핫 상품 + 동률 타이브레이크"를 실제로 타야 keyset 커서가 제대로 검증된다.

구간상품 비율like_count 범위
메가히트~0.02% (약 20개)30,000 ~ 60,000
핫~1% (약 1,000개)1,000 ~ 5,000
중간~9% (약 9,000개)50 ~ 250
롱테일~90% (약 9만개)0 ~ 20
가격price는 약 1,000 ~ 2,000,000 로그분포(FLOOR(POW(10, 3 + …×3.3))). PRICE_ASC 정렬의 비교군 — 좋아요순과 같은 복합 인덱스 패턴이 가격순에도 통하는지 확인한다.
왜 핫 상품이 필요한가like_count가 전부 0~20이면 동률이 많아 ORDER BY like_count, id의 2차 정렬키(id)만 실질적으로 동작한다. 핫·메가히트 구간이 있어야 like_count가 1차 정렬키로 진짜 일을 하고, 동률 경계에서 keyset 커서의 정확성을 검증할 수 있다.
4

CONSISTENCY

비정규화 전/후 정합 (옵션 B)

이 시드의 핵심 결정. like_count(비정규화 컬럼)와 product_like(원천 행)를 전 상품 완전 일치시킨다. 그래야 비정규화 전·후를 같은 결과 위에서 비교할 수 있다.

전 · A 실시간 집계

COUNT(product_like) 또는 JOIN으로 매 조회마다 좋아요 수를 센다. 정규화된 진실이지만 느리다.

후 · B 비정규화 컬럼

product.like_count 컬럼을 그대로 읽는다. 빠르지만 원천과 어긋나면 거짓이다.

두 방식이 같은 숫자를 내야 apples-to-apples 비교다. 그래서 시드는 순서를 거꾸로 간다 — 상품을 만들 때 like_count를 목표 좋아요 수로 먼저 박고(3절 분포), 그 수만큼 정확히 product_like 행을 찍는다. 일치가 사후 동기화가 아니라 구조적으로 보장된다.

불변식like_count == COUNT(product_like) — 전 상품. 적재 후 검증 쿼리의 mismatch가 0이어야 한다.
UNIQUE 제약 → 6만 캡product_like에 UNIQUE(user_id, product_id)가 걸려 있어, 한 상품의 N개 행은 모두 서로 다른 유저여야 한다. 유저풀이 30만이므로 핫·메가히트의 like_count를 최대 6만으로 캡해 distinct 충족을 보장한다(50만 같은 값은 30만 유저풀에서 불가능).
5

SEEDING

시딩 구현·검증

SQL 숫자 생성기로 한 번에 넣는다. 난수는 RAND() 대신 CRC32(seq) — 매 실행 동일 데이터라 인덱스 전/후를 같은 모집단에서 비교한다.

관점코드 시더SQL 시딩(채택)
속도JPA INSERT 느림(배치 튜닝 필요)상품 10만 + product_like 600만 1~3분
재현성실행마다 편차CRC32 결정적 → 측정 환경 동일
전/후 정합엔티티 경유로 맞추기 번거로움like_count 박고 그만큼 행 생성 — 일치 구조적 보장
perf-seed-l5.sql — 핵심 3단계 
-- ① 상품 100,750 : 숫자 생성기(digit cross-join)로 seq 0..100749
INSERT INTO product (brand_id, name, price, like_count, status)
SELECT tier_brand(seq), CONCAT('product-', seq),
  FLOOR(POW(10, 3 + (CRC32(CONCAT(seq,'-price'))%1000)/1000.0*3.3)),
  bucket_like_count(seq), 'ACTIVE' FROM seq_0_to_100749;

-- ② product_like : 상품마다 정확히 like_count 개 (= 원천 진실)
INSERT INTO product_like (user_id, product_id)
SELECT ((CRC32(p.id) + n.k) % 300000) + 1, p.id
FROM product p JOIN nums n ON n.k < p.like_count;  -- 행 팬아웃

-- ③ 검증 : 전/후 일치 (mismatch = 0 이어야 함)
SELECT COUNT(*) AS mismatch FROM product p
LEFT JOIN (SELECT product_id, COUNT(*) c FROM product_like GROUP BY product_id) pl
  ON pl.product_id = p.id
WHERE p.like_count <> COALESCE(pl.c, 0);
적재 후 확인검증 쿼리 4개가 찍힌다 — ① brands/users/products/likes 카운트(500 / 30만 / 100,750 / ~600만), ② mismatch = 0, ③ like_count 버킷 분포, ④ 티어별 상품 분포.
