PRINCIPLE

핵심 기준 — enum은 상태가 없다

모든 enum 항목은 프로그램에 단 하나뿐인 싱글톤 상수입니다. FIXED 는 어디서든 같은 그 하나예요. 여기서 모든 기준이 나옵니다.

그 로직이 enum 값 "그 자체만으로 완결"되면 넣어라. "외부 데이터나 협력자"가 있어야 완성되면 빼라.

— enum 책임의 한 줄 기준

쉬운 비유 — 트럼프 카드의 무늬

카드 게임을 떠올려 보세요. 무늬(SPADE, HEART…)를 enum이라고 하면:

비유하트의 색(빨강), 기호(♥) 는 모든 하트가 똑같이 공유합니다 → 무늬 enum의 속성으로 OK. 하지만 그 카드의 숫자(7인지 K인지) 는 카드 한 장마다 다릅니다 → 무늬 enum이 아니라 카드 객체의 데이터.

"무늬에 고정된 것"은 enum에 넣고, "카드마다 다른 것"은 카드에 둡니다. enum은 종류를 나타낼 뿐, 개별 인스턴스의 데이터를 들고 있을 수 없기 때문입니다(상태가 없으니까).

2

OK

넣어도 되는 책임

그 값에 고정된 불변 속성, 그리고 그 속성만으로 답할 수 있는 판정·변환은 enum 안이 정석입니다.

① 표시 이름·코드 같은 고정 속성

CouponType.kt
enum class CouponType(val displayName: String) {
    FIXED("정액 할인"),
    RATE("정률 할인");
}
// couponType.displayName → "정액 할인"  ✅ 모든 FIXED 가 공유

② 자기완결적 판정 (Tell, Don't Ask)

상태·요일 판정
enum class OrderStatus { CREATED, PAID, CANCELLED;
    fun canCancel() = this == CREATED || this == PAID   // 상태의 고유 규칙 ✅
}

③ 2차 그룹 — 다른 enum을 필드로

"타입을 더 큰 그룹으로 묶는다"도 고정된 분류라 OK입니다. enum이 다른 enum을 참조해도 안전합니다(둘 다 불변 상수).

그룹·카테고리
enum class CouponCategory { ORDER, SHIPPING }

enum class CouponType(val displayName: String, val category: CouponCategory) {
    FIXED("정액 할인", ORDER),
    RATE("정률 할인", ORDER),
    FREE_SHIPPING("무료배송", SHIPPING);

    fun isShipping() = category == CouponCategory.SHIPPING   // ✅
}
근거이렇게 "상수마다 다른 값/행동"을 enum에 응집하는 것이 Effective Java Item 34 의 constant-specific method 패턴입니다[3]. Operation.PLUS.apply(a, b) 처럼 타입 자체로 행위가 완결될 때가 대표적입니다.
3

NO

빼야 하는 책임

아래 신호가 보이면 enum에서 빼서 별도 객체·서비스로 옮깁니다.

빼야 할 신호왜어디로
외부 협력자 의존enum은 상수라 DI 불가, mock 못 끼움도메인 서비스
인스턴스마다 다른 데이터 기반 계산enum은 상태가 없어 매번 인자로 받아야 함전략 객체
부작용 (I/O·상태 변경)enum은 불변 싱글톤이어야 함서비스·리포지토리
자주 바뀌는 정책enum 수정 = 코드 배포설정·DB
체크 한 줄"이 로직을 그 enum 파일 안에서, 외부 데이터 주입 없이 테스트할 수 있나?" "아니오"라면 빼는 게 맞습니다.
4

CASE

같은 잣대로 본 할인 예제

쿠폰 할인을 같은 기준에 대보면, 무엇이 enum에 들어가고 무엇이 빠지는지 한 표로 정리됩니다.

후보모든 FIXED가 같은가?판정
displayName "정액 할인"✅ 항상 같음enum 안
category ORDER✅ 항상 같음enum 안
value (1000원 / 5000원)❌ 쿠폰마다 다름enum 밖
discount 계산❌ value 에 의존enum 밖

FIXED 라는 타입만으로는 "얼마 할인"이 정해지지 않습니다 — value 가 있어야 완성됩니다. 즉 할인은 "상태(value) + 행위(계산)"가 한 쌍이고, 그건 enum이 아니라 객체입니다.

✕ enum에 계산

CouponType.discountOf(amount, value) — value를 밖에서 넣어줘야 함. 어색하고 테스트도 데이터 주입 필요.

○ 전략 객체로

DiscountPolicy = value(상태) + discount(행위)를 묶음. 계산이 자기 안에서 완결. enum은 식별만.

결론같은 "enum 활용" 주제라도 — 표시명·카테고리·판정은 넣는 쪽의 좋은 예, 할인 계산은 빼는 쪽의 예. 둘을 대비하면 경계가 선명해집니다.

REFERENCE

우아한형제들 사례

우아한형제들 기술블로그 "Java Enum 활용기" 가 바로 이 "넣어도 되는 쪽"의 교과서적 예입니다.

이 글의 논지는 "Java enum은 단순 상수가 아니라 완전한 클래스이니, 관련 데이터와 행위를 enum 안에 응집시켜라" 입니다[1]. 대표 사례:

○ 코드 매핑·변환

origin 테이블의 Y/N ↔ 다른 테이블의 1/0, true/false 변환을 enum이 자기완결적으로 처리. 흩어진 if 를 enum 한 곳으로.

○ 함수형 필드

각 enum 상수가 자기 판정·변환 로직을 들고 있게 해 분기를 다형성으로 대체.

이 사례들은 전부 enum 값 자체로 완결되는 변환·판정이라 enum에 넣는 게 정석입니다. 우리 할인 예제와의 차이는 단 하나 — 할인은 쿠폰마다 다른 value 라는 인스턴스 상태에 의존한다는 점입니다.

이어지는 글같은 블로그의 "Legacy DB의 JPA Entity Mapping (Enum Converter 편)"[2] 은 enum을 DB에 매핑하는 AttributeConverter 실전을 다룹니다 — enum의 영속성 측면과 직결됩니다.
