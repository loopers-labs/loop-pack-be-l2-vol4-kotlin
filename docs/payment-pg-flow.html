1

BIG PICTURE

한 장으로 보는 전체 흐름

결제는 요청 → 인증 → 승인 3단계이고, 결과를 받는 채널이 2개입니다 — 동기(리다이렉트)와 비동기(웹훅).

핵심은 두 가지입니다. ① 결제창은 서버가 아니라 브라우저가 PG SDK 로 띄웁니다. ② 사용자가 카드정보를 넣는다고 결제가 끝나는 게 아니라, 그 결과로 받은 paymentKey 를 내 서버가 직접 승인(confirm) API 로 요청해야 비로소 차감됩니다.

2

WHO SERVES IT

결제창은 누가 내려주나

"결제창을 내려주는 주체"는 하나가 아닙니다. 세 가지가 겹쳐 있고, 이걸 분리하는 게 첫 단추입니다.

화면 조각누가 내려주나형태
체크아웃 페이지우리 프론트엔드"결제하기" 버튼이 있는 우리 서비스 화면
PG SDKPG사 도메인<script src="https://js.tosspayments.com/...">
결제창 (카드 입력)PG사SDK 가 PG 도메인 화면을 iframe·팝업·리다이렉트로 띄움
핵심우리 서버는 결제창 HTML 을 직접 그리지 않습니다. 브라우저의 우리 JS 가 PG SDK 의 requestPayment() 를 호출해 "이 주문·이 금액으로 결제창 열어줘"라고 요청만 하고, 실제 카드 입력 화면은 PG사가 자기 도메인에서 렌더링합니다.

왜 PG사가 직접 그리나

카드 입력 화면을 우리 서버가 그리면 카드번호가 우리 서버를 통과하게 되고, 그 순간 PCI-DSS(카드정보 보안 규격) 책임을 우리가 다 떠안습니다. 그래서 PG 모델은 일부러 카드정보가 우리 서버를 우회해 PG사로 직접 가도록 설계돼 있습니다. 그 대가로 결제창의 소유권도 PG사에 있습니다.

이 시점의 우리 서버화면에 관여하지 않습니다. 하는 일은 딱 하나 — "결제하기"를 누르기 직전 이 주문(orderId)은 최종 얼마(amount)다를 미리 저장해두는 것. 나중에 금액 위변조를 잡기 위한 포석입니다.
3

CORRECTION

이해한 것 vs 실제

큰 그림은 맞습니다. 다만 흔히 어긋나는 지점이 정확히 두 군데 있습니다.

오해 1 — "서버가 결제창을 내려준다"

이해서버가 결제창을 띄움

서버가 결제창 HTML 을 사용자 브라우저로 내려보낸다고 생각.

실제브라우저가 띄움

브라우저가 PG 의 JS SDK requestPayment() 를 호출해 결제창을 엽니다. 서버는 그 전후(금액 저장 · 승인 호출)만 담당.

오해 2 — "서버가 웹훅을 받아서 결제된다"

이해웹훅이 결과를 받는 길

사용자가 결제하면 그 결과를 서버가 웹훅으로 받아 처리.

실제웹훅은 보조 채널

주 경로는 ④ 리다이렉트 → ⑥ 서버의 confirm 승인 호출. 웹훅은 그 신호가 누락됐을 때를 위한 안전망입니다.

한 줄 요약결제창은 클라이언트가 띄우고, 결제 확정은 서버가 승인 API 를 호출해서 끝낸다. 웹훅은 그걸 대체하는 게 아니라 보강한다.
4

SYNC PATH

동기 경로 — 리다이렉트와 승인

결제창 인증이 끝나면 PG 는 승인을 자동으로 하지 않습니다. 내 서버가 명시적으로 승인을 요청해야 합니다.

인증이 성공하면 PG 는 고유한 paymentKey 를 발급하고 successUrl 로 리다이렉트하며, 쿼리 파라미터로 paymentKey · orderId · amount 를 내려줍니다. 이 시점엔 아직 돈이 빠져나가지 않았습니다.

이어서 백엔드가 승인(confirm) API 를 호출해야 카드사가 실제로 금액을 차감합니다. 토스 문서가 요청과 승인을 일부러 분리한 이유를 설명합니다.

"결제 인증과 승인이 비동기적으로 일어나기 때문에 결제의 결과를 받으려면 반드시 웹훅을 연동해야 됩니다."

— 토스페이먼츠, 결제 흐름 이해하기[1]
참고가상계좌처럼 나중에 입금되는 비동기 수단은 리다이렉트 시점에 결과가 없습니다. 이 경우 입금 완료는 오직 웹훅으로만 알 수 있어서, 다음 섹션의 웹훅이 선택이 아니라 필수가 됩니다.
5

WEBHOOK

웹훅 — 왜 따로 필요한가

리다이렉트(④)는 신뢰할 수 없는 통신입니다. 그래서 서버끼리 직접 통보하는 웹훅이 따로 존재합니다.

브라우저 기반 리다이렉트는 끊길 수 있습니다. 포트원 문서가 그 상황을 직접 짚습니다.

"인터넷 연결 끊김, 브라우저 자동 새로고침 등의 이유로 클라이언트에서 결제 완료 응답을 받지 못하는 경우가 간헐적으로 발생합니다."

— 포트원, 웹훅 연동하기 (v2)[2]

사용자가 결제 직후 창을 닫거나 와이파이가 끊기면 ④·⑤ 신호가 서버에 안 닿을 수 있습니다. 그래도 PG ↔ 내 서버 사이의 서버 대 서버 웹훅(⑧) 은 별도로 도착하므로, 결제 결과가 누락 없이 동기화됩니다.

핵심리다이렉트와 웹훅은 둘 다 받는 게 정석입니다. 빠른 사용자 경험은 리다이렉트가, 데이터 정합성은 웹훅이 책임집니다.

SECURITY

절대 어기면 안 되는 2규칙

실무에서 결제 사고는 거의 이 두 가지를 빼먹어서 납니다.

규칙안 지키면해야 할 일
금액 검증
(승인 전)		 클라이언트가 amount 를 1원으로 조작해 승인 요청 결제 직전 서버에 저장한 금액과 successUrl 의 amount 일치 확인 후 승인
웹훅 재검증
(수신 후)		 위조된 가짜 웹훅을 진짜로 믿고 주문 완료 처리 웹훅 내용을 믿지 말고 PG 단건조회 API 로 실제 상태 재조회 후 반영

"웹훅 수신 주소는 공개되어 있으므로, 수신한 웹훅 메시지의 내용을 신뢰할 수 없습니다."

— 포트원, 웹훅 연동하기 (v2)[2]
주의웹훅 본문의 status: PAID 를 그대로 믿고 주문을 완료 처리하면 안 됩니다. 반드시 PG 서버에 단건조회를 다시 날려 실제 결제 상태를 확인하세요.

YOUR CODE

지금 프로젝트(fake)와의 매핑

지금 OrderService.place() 는 주문 생성 + 재고 차감까지만 합니다. 결제가 없죠. PG 를 붙이면 이 한 번의 동기 흐름이 여러 단계로 쪼개지고 상태가 늘어납니다.

상태(OrderStatus)가 늘어난다

OrderStatus.kt 
enum class OrderStatus {
    // 지금: 사실상 단일 흐름
    PENDING_PAYMENT,  // 주문 생성 · 승인 대기 (결제창 띄운 상태)
    PAID,             // 승인(confirm) 또는 웹훅으로 결제 확정
    PAYMENT_FAILED,   // 인증 실패 · 승인 거절
    CANCELED,         // 결제 취소 · 환불
}

새로 생기는 것들

  • PaymentClient — PG 승인(confirm) · 단건조회 API 를 호출하는 외부 어댑터 infra
  • 웹훅 수신 컨트롤러 — PG 가 POST 로 쏘는 상태변경을 받는 엔드포인트 interface
  • 금액 검증 로직 — 저장 금액 vs amount 비교 (승인 전) app
  • 재고 차감 시점 재설계 — 주문 시 선차감 후 실패 시 복원 vs 승인 후 차감 decision
  • 멱등 처리 — 리다이렉트와 웹훅이 둘 다 도착해도 중복 확정 안 되게 app
다음 단계이 부분은 fake 를 걷어내기 전에 상태 전이도부터 잡는 게 안전합니다. 재고를 언제 차감/복원할지, 리다이렉트·웹훅 중복을 어떻게 멱등 처리할지가 설계의 핵심 결정입니다. 원하시면 requirements-analysis 로 상태도와 시퀀스를 이어서 정리하겠습니다.
8

WIRING IT UP

주문·결제 매칭 — place 쪼개기

"금액이 달라서 cancel"과 "payment 요청 보내는 자리가 없다"가 안 맞는 건, 두 가지가 한 덩어리로 엉켜 있어서입니다.

진단지금 OrderService.place() 는 재고 차감 → 주문 저장(CREATED) → 끝 을 한 트랜잭션에 합니다. 하지만 결제는 사용자가 PG 결제창에서 수십 초~수 분 상호작용하는 비동기 과정이라, place() 안에서 PaymentClient 요청을 보내고 결제 완료를 기다릴 수 없습니다. 그래서 "payment 요청"이 끼워질 자리가 없는 겁니다.

금액은 사실 3개다

지금 OrderCreateRequest 는 클라가 price·totalPrice 를 보내는데, Order.create() 는 그걸 안 쓰고 unitPrice × quantity 로 서버가 다시 계산합니다. 여기에 PG가 돌려줄 금액까지 합치면 셋입니다.

금액출처신뢰?
A · 클라 전송OrderCreateRequest.totalPrice❌ 화면 표시용
B · 서버 재계산Order.totalAmount (상품가·쿠폰)✅ 정답 (canonical)
C · PG 리다이렉트successUrl?amount=...❌ 브라우저 경유
설계 지적클라가 price 를 보내는 것 자체가 안티패턴입니다. 서버는 클라 금액을 신뢰하지 말고 productId + couponId 로 B 를 재계산해야 합니다. A 는 낙관적 UI 표시용일 뿐, 결제 금액의 근거가 되면 안 됩니다.

검증 게이트는 2개 — cancel과 reject는 다르다

게이트비교 · 시점안 맞으면
Gate 1A vs B · 주문 생성reject — 주문 안 만듦 · "가격 변경됨" 안내
Gate 2C vs B · 결제 승인cancel — 주문 취소 + 재고 복원
핵심 구분주문 생성 시점(A≠B)은 cancel 이 아니라 reject 입니다. 아직 주문도 재고도 안 건드렸으니 거절하고 끝. 진짜 cancel(되돌리기) 은 Gate 2 / PG 승인 거절일 때 — 이미 PENDING 주문과 재고 선점이 생긴 뒤라 상태 전이 + 재고 복원 + (돈 빠졌으면) 환불이 한 묶음입니다.

그래서 place()를 진입점 2개로 쪼갠다

왜 자리가 맞는가"payment 요청 보내기"는 place() 안이 아니라 ② 결제 승인(confirm) 단계에 들어갑니다. place() 는 결제를 끝내는 게 아니라 "결제 대기 주문 생성 + 금액 확정"에서 멈춥니다. 그래서 OrderStatus 가 CREATED 하나로는 부족하고 최소 PENDING_PAYMENT → PAID / CANCELED 가 필요합니다.

재고는 언제 차감하나 — cancel에 복원이 붙는 이유

대안결제 승인 후 차감

그 사이 품절 가능 → "결제는 됐는데 줄 물건이 없음". 더 나쁜 상황이라 보통 피합니다.

권장주문 시 선점 → 실패 시 복원

결제 진행 중 다른 사람이 못 사가게 막습니다. 대신 cancel 시 inventory.restore() 가 반드시 따라옵니다.

한 줄 정리place() 는 PENDING 주문 + 금액(B) 확정까지만 · PaymentClient 호출은 confirm 단계로 분리 · 금액 검증은 A↔B(생성 reject) / C↔B(승인 cancel) 두 게이트 · cancel 은 항상 재고 복원과 세트.
