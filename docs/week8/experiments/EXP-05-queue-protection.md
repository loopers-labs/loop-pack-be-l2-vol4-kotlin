# EXP-05 — M2 대기열 보호 검증 (AWS 2노드, EXP-04와 동일 환경)

> 질문: M1이 못 견딘 유저 사용량(도착 800/s = 4×C)을 대기열 세계는 견디는가 — 그리고 그 대가는 무엇인가.
> 원시 데이터: `load-test/results/exp05-aws/` · 환경·시드 = EXP-04 run-meta와 동일.

## 1. 조건

- **코드**: `feature/week08-waiting-queue` @ `bef32c5` (대기열 + F1 429 + F2 503 + 상세 캐시 + week5 탐색). EXP-04 베이스라인과의 차이 = 대기열 유무뿐 (캐시 패리티 완료).
- **스케줄러**: `batch-size 70 × fixed-delay 500ms` = **방출 140/s** (= C 200/s × 안전계수 0.7). 토큰 TTL 300s · max-waiting 60,000.
- **부하**: `queue-order-flow.js` — 스파이크 **8,000명/10초**(실제 생성 7,600 — 램프 적분 손실), **폴링 = 프론트 고정 3초**(사용자 결정, `POLL_MODE=3`), 작성 think 30~120s 균등, 주문 1건(핫상품 900001). + 배경 탐색 100명/s 동일.
- **계정**: 여정마다 고유 계정(perf1~20000, l5 계정에 cost-4 자격증명 부여) — 대기열이 userId 기반이라 계정 공유 시 줄·토큰 오염(스모크에서 실측 후 교정).

## 2. 가설

- 진입 폭풍은 Redis가 흡수하고, MySQL에는 방출 속도(140/s) 이하의 평탄한 주문만 도달한다 — 풀 대기 0, 에러 0.
- 작성 시간(30~120s)이 방출을 한 번 더 펼쳐 주문 유입 피크는 140/s보다 낮게 나온다.
- 같은 서버의 탐색 API는 스파이크 중에도 정상 (M1의 동반 질식이 사라짐).

## 4. 판독

- **보호 성립**: M1이 붕괴한 도착률(800/s)에서 M2는 에러 0으로 소화. 줄이 커넥션·스레드(비싼 자원)에서 Redis ZSET(싼 자원)으로 옮겨졌고, MySQL 유입은 설계값 이하로 통제됨.
- **이중 완충의 발견**: 주문 유입 피크가 방출(140/s)보다도 낮은 90/s — 작성 시간이 두 번째 스무딩 레이어로 작동. 하류가 실제로 받는 부하 = 방출 속도 × 작성 시간 분포의 컨볼루션.
- **탐색 무붕괴**: M1 대비 p95 10배 개선(9.4s→0.9s). "대기열이 지키는 것은 서버 전체"의 실측 증거.
- **대가의 크기**: 최악 대기 50초 + 약속 오차 +4초 안팎. 폴링 3초 고정(프론트 현실)으로도 오차가 한 자릿수 초 — 수용 가능 판단.

## 4-1. 방출 스윕 축약 — 140/s vs 200/s (같은 스파이크 8,000)

> 사용자 결정으로 전체 스윕 대신 두 점 비교. 200/s 첫 런은 **재기동 직후 웜업 생략** 상태라 enter 실패 121건·약속 오차 +9.6s가 나왔으나, 웜업 후 재실행에서 전부 소멸 — **콜드 JIT 아티팩트로 판정** (교훈: 앱 재기동 후 웜업은 생략 불가. 콜드 런은 `*-COLD.*`로 보존).

| (웜 기준) | 방출 140/s | 방출 200/s |
|---|---|---|
| 여정 성공률 | 99.22% | 99.28% |
| HTTP 실패 | 1건 | 1건 |
| 대기 avg / max | 25.5s / 49.9s | **16.6s / 31.9s** |
| 약속 오차 avg | +3.7s | +2.6s |
| 주문 유입 피크 | 89.5/s | 93.0/s |
| Hikari pending | 0 | 0 (enter 스톰 순간 156 → 15초 내 해소) |
| 탐색 p95 | 925ms | 283ms |

- **주문 유입 피크가 방출과 거의 무관(89→93/s)** — 이 행동 모델(작성 30~120s)에선 작성 시간 분산이 유입을 지배. 방출 증가의 효과는 하류 부하가 아니라 **대기 시간 단축**(25.5→16.6s)으로만 나타남.
- **enter 스톰 순간의 pending 156 발견**: 대기열 진입은 Redis-only지만 **헤더 인증이 요청마다 MySQL을 조회** — 진입 폭풍(800/s)이 인증 경유로 DB 풀을 스침 (15초 내 해소, 에러 0). 더 큰 스파이크에선 병목 후보 — "Redis-only 경로"의 알려진 구멍으로 기록.

## 5. 결정·다음

- **운영 방출 속도 판단**: 200/s도 이 행동 모델에선 무결점이나, 그 안전은 "입장자가 30~120s 작성 후 주문"이라는 **행동 가정에 의존** — 전원이 즉시 주문하는 최악에선 유입 ≈ 방출이 되어 200/s = C와 정면충돌한다. 반면 140/s(C×0.7)는 **행동 가정 없이도** 유입 ≤ 0.7C가 보장되는 불변식. → **기본 140/s 채택, 대기시간 단축이 필요할 때 200/s까지 상향 여지(실측 근거 확보)** 를 결론으로 제안.
- 주기 비교(500ms vs 1s, 같은 방출)로 버스트 흔적이 주문 유입에 보이는지 검증 → 최종 배치·주기 근거 완성 (남음).
- 이탈 10% 런으로 토큰 미사용 만료 = 유량 손실률 측정.
- 여정 실패 59건(0.78%)의 원인 분류 — 앱 로그 대조 필요.
