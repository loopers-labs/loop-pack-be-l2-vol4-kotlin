1

WHY

왜 커서인가 (vs OFFSET)

10만 건 환경에서 LIMIT ? OFFSET ?는 뒷페이지로 갈수록 느려진다. 커서는 깊이와 무관하게 일정하다.

OFFSET 방식은 N번째 페이지를 위해 앞의 offset개 행을 읽고 버린다. 뒤로 갈수록 버리는 양이 늘어 비용이 선형으로 증가하고, 그 사이 행이 삽입/삭제되면 같은 행이 다시 보이거나 건너뛰는 중복·누락도 생긴다.

keyset(seek)은 "마지막으로 본 행의 정렬키"를 WHERE 조건으로 바꿔, 정렬 인덱스 위에서 그 지점으로 곧장 점프한다. 버리는 행이 없다.

OFFSET 앞 페이지를 읽고 버림

2번째 페이지부터 누적 비용↑. 깊은 페이지에서 풀스캔에 가까워지고, 삽입/삭제 시 행이 밀려 중복·누락.

KEYSET 정렬키로 점프

마지막 본 키 (like_count, id)를 WHERE로. 페이지 깊이와 무관하게 일정. 단 임의 페이지 점프(7페이지로)는 못 한다 — 무한스크롤·다음 버튼에 적합.

핵심커서 = 마지막으로 본 행의 정렬키 묶음. "몇 개 건너뛰어라"(OFFSET)가 아니라 "이 값 다음부터 줘"(seek)로 질문이 바뀐다.

STRUCTURE

3계층 구조와 Cursor 타입

커서는 계층마다 다른 모습이다 — 밖에선 base64 문자열, 안에선 타입 있는 객체.

Cursor는 필드 없는 마커 인터페이스다. 정렬마다 키 구성이 달라 단일 타입에 못 묶기 때문에, 정렬별 구현체가 이 인터페이스를 구현한다. (sealed가 아닌 interface로 둬 추후 도메인 모듈 분리 시 다른 모듈에서도 구현체를 추가할 수 있게 한다.)

Cursor.kt · ProductCursors.kt
// shared/domain — 정렬별 구현체가 implement 하는 base
interface Cursor

// 최신순(id DESC) — id가 유니크 total-order라 단독으로 keyset 성립. 공용
data class IdCursor(val id: Long) : Cursor

// product/domain — 정렬별 복합 커서, 최종 타이브레이크는 항상 id
data class PriceCursor(val price: Long, val id: Long) : Cursor
data class LikeCountCursor(val likeCount: Long, val id: Long) : Cursor
정렬 (ProductSort)ORDER BY커서 타입
LATESTid DESCIdCursor(id)
PRICE_ASCprice ASC, id DESCPriceCursor(price, id)
LIKES_DESClike_count DESC, id DESCLikeCountCursor(likeCount, id)
왜 항상 id로 끝나나like_count·price는 비유니크라 같은 값이 여럿이다. 동률 행의 순서가 매 쿼리 흔들리면 keyset 경계가 깨진다 → 유니크한 id를 마지막 타이브레이크로 붙여 전순서(total order)를 만든다.
3

FLOW

조회 흐름 — findAll

커서 → ScrollPosition 변환, Spring Data Window 조회, 그리고 마지막 행으로 다음 커서 생성. 세 단계다.

findAll(sort, brandId, cursor, size) → CursorPage<Product>
① 위치 변환cursor가 null이면 ScrollPosition.keyset()(첫 페이지), 있으면 정렬키 맵으로 ScrollPosition.of(keys, FORWARD)
② 조회brandId 유무로 findByStatusNot / findByBrandIdAndStatusNot 분기. Limit + Sort 전달 → Window<Product>
③ 다음 커서window.hasNext()이고 비어있지 않으면 sort.nextCursor(마지막 행)으로 다음 커서 생성, 아니면 null
ProductRepositoryImpl.kt — findAll
override fun findAll(sort: ProductSort, brandId: Long?, cursor: Cursor?, size: Int): CursorPage<Product> {
    val scrollPosition = scrollPosition(sort, cursor)        // ① 커서 → 위치
    val window = if (brandId == null)
        productJpaRepository.findByStatusNot(DELETED, scrollPosition, Limit.of(size), sort.toSort())
    else
        productJpaRepository.findByBrandIdAndStatusNot(brandId, DELETED, scrollPosition, Limit.of(size), sort.toSort())

    val nextCursor = if (window.hasNext() && window.content.isNotEmpty())
        sort.nextCursor(window.content.last())          // ③ 마지막 행 → 다음 커서
    else null

    return CursorPage(window.content, window.hasNext(), nextCursor)
}
결과 래퍼CursorPage<T>(content, hasNext, nextCursor) — nextCursor는 타입 있는 Cursor(base64 아님). 다음 페이지가 없으면 null. opaque 인코딩은 여기서 하지 않고 presentation으로 넘긴다.
4

KEYSET

keyset이 자르는 경계

LIKES_DESC 정렬에서 페이지1의 마지막 행이 곧 페이지2의 커서다. 동률은 id가 가른다.

핵심커서가 like_count와 id 둘 다 들고 다니는 이유가 이 그림이다. like_count만으로는 동률 경계에서 어디까지 줬는지 알 수 없다 → id가 정확한 재개 지점을 박아준다.
5

BOUNDARY

정렬↔커서 검증 · opaque 인코딩

infra는 정렬과 커서 타입이 안 맞으면 400으로 끊는다. 그리고 base64 변환은 컨트롤러 몫이다.

ProductRepositoryImpl.kt — scrollPosition
private fun scrollPosition(sort: ProductSort, cursor: Cursor?): ScrollPosition {
    if (cursor == null) return ScrollPosition.keyset()      // 첫 페이지

    // 정렬과 커서 타입은 짝이 맞아야 한다. 어긋나면 잘못된 입력 → 400
    val keys = when (sort) {
        LATEST     -> (cursor as? IdCursor ?: invalidCursor()).let { mapOf("id" to it.id) }
        PRICE_ASC  -> (cursor as? PriceCursor ?: invalidCursor()).let { mapOf("price.amount" to it.price, "id" to it.id) }
        LIKES_DESC -> (cursor as? LikeCountCursor ?: invalidCursor()).let { mapOf("likeCount" to it.likeCount, "id" to it.id) }
    }
    return ScrollPosition.of(keys, Direction.FORWARD)
}
// invalidCursor() → BadRequestException(INVALID_PRODUCT_CURSOR) → ApiControllerAdvice가 400
아직 비어 있는 한 조각위 코드는 이미 타입이 있는 Cursor를 받는다. 하지만 HTTP로 들어오는 건 base64 문자열이다. 문자열 → 올바른 Cursor 구현체로 디코딩하고, 응답의 nextCursor를 다시 인코딩하는 일은 interfaces 레이어(컨트롤러)에서 해야 한다 — 지금 미구현.

opaque 인코딩 — 결정 포인트

커서는 불투명(opaque) 문자열인데, 디코드하려면 어떤 타입인지 알아야 한다. 두 길이 있다.

A안 sort에 종속

요청의 sort로 디코딩 타입을 결정. infra의 짝 검증과 일치, 단순. sort가 1페이지와 다르면 타입 미스 → 400으로 자연히 걸림. 실서비스 기본값.

B안 타입 태그 임베드

{type, keys} JSON을 base64. 자기서술적이라 sort 없이도 복원되지만, 포맷·버전 관리 비용이 더 든다.

참고BrandRepositoryImpl에 동일한 keyset 패턴(IdCursor 기반)이 이미 있어 인코딩 컨벤션 참고가 된다. 커서 인코딩은 도메인 키 구조를 그대로 노출하지 않도록 opaque 처리한다(주석 규약).
