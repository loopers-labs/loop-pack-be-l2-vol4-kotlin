# EXP-04 — M1 베이스라인: 대기열 없는 세계의 주문 천장 (AWS 2노드)

> 목적: 대기열 도입 전 커밋에서 "못 견디는 유저 사용량"을 실측 확정한다. 이 천장 C가
> ① M2 부하 크기(≥4×C)와 ② 스케줄러 토큰 공급량(배치×주기) 산정의 앵커다.

## 1. 조건 (커밋·설정·스펙)

- **코드**: `measure/week08-baseline` @ `6a31ab0` = 2bb0c19(대기열 없음) + week5 탐색 API(목록 커서·좋아요순 인덱스·첫 페이지 캐시) + **상세 Redis 캐시 패리티 체리픽**(878ee37·42bb700). M2 세계와의 유일한 차이 = 대기열 유무.
- **SUT (2노드 분리)**: app = EC2 c6i.xlarge(4vCPU/8GB), java 21, `-Xms2g -Xmx2g`, perf 프로파일, Tomcat max 200 · Hikari 풀 40/timeout 3000ms. infra = EC2 m6i.large — mysql8(buffer pool 4G·max_conn 300) + redis 7 master/replica + kafka 3.5.1. 같은 AZ(ap-northeast-2a).
- **부하 경로**: 로컬 맥 k6 → 공인망 직접(SG 내 IP /32 한정). ⚠️ SSH 터널은 포화 구간 동시 소켓에 사망(1런 무효 후 전환). **지연 수치엔 인터넷 RTT 포함** → 천장 판정은 처리량·에러율·actuator(서버측) 기준. week7 EXP-01(co-located k6)과 달리 지연 절대치는 비교 불가, 처리량은 비교 가능.
- **시드**: perf-seed-l5(상품 100,750 · 좋아요 681만 · 유저 30만) + order-arm(핫 900001 / 분산 900011~20, 가격 10,000 고정, 재고 1억).
- **부하 모델**: 주문 = `order-ramp.js` ramping-arrival-rate **100→200→400→800/s** (단계 1분, open model). 탐색 배경 = `browse-journey.js` **초당 유저 100명** 여정(목록 1.45p + 상세 2건 + think time = ~345 req/s) — 전 런 공통(런 3 제외).

## 2. 가설

- hot(단일 상품): 재고 행 락 직렬화가 천장을 만든다 — 처리량 수백/s 초반에서 꺾이고, 락 보유 시간이 커넥션 점유로 전파되어 Hikari 풀(40)이 고갈된다. **하드웨어(4vCPU)를 늘려도 단일 행 직렬화는 안 풀린다.**
- spread(10상품 분산): 락 경합이 없으므로 천장이 크게 올라가고, 병목은 풀/CPU로 이동한다.
- 대기열 없는 세계에선 주문 폭주가 같은 서버의 **탐색 API까지 도륙**한다(스레드·풀 공유) — 로컬 파일럿에서 관측된 패턴의 재확인.

## 4. 판독

- **천장의 원인은 행 락이다**: hot 200/s vs spread 550/s+ — 같은 코드·같은 하드웨어에서 상품이 1개냐 10개냐만으로 천장이 ~3배 갈렸다. hot의 med 3.5s vs spread의 36ms(약 100배)가 직렬화 대기의 크기.
- **로컬 파일럿(~200/s)과 AWS(c6i.xlarge, ~205/s)의 hot 천장이 사실상 동일** — 스케일업이 hot 상품 직렬화를 못 푸는 실증. "더 좋은 서버"는 이 문제의 답이 아니다 → 대기열(도착 속도 제어)의 존재 이유.
- **붕괴는 조용히 시작된다**: hot 런의 에러율은 1.4%뿐이지만 med 3.5s·p95 10s — 에러 기반 알람으로는 못 잡는 상태. SLO는 지연 기준이어야 함.
- **탐색 동반 질식**: hot 런에서 탐색 p95 9.4s (spread 런 445ms의 21배). 주문이 풀·스레드를 다 먹으면 조회까지 죽는다 — 대기열이 지켜야 할 것은 주문 DB만이 아니라 서버 전체.
- **간섭은 단방향**: 배경 탐색을 빼도(RUN 3) hot 천장은 ~205/s로 동일(RUN 1 대비 오차 수준) — 탐색은 캐시·읽기 위주라 주문 천장을 깎지 않지만, 주문 폭주는 탐색을 죽인다. "조회가 깔린 현실 부하"에서도 천장 수치는 주문 자체가 결정한다는 뜻 — 천장 C의 신뢰도를 높여주는 대조.

## 5. 결정 (M2·스케줄러 산정 입력)

- **천장 C 판정** (SLO: 에러>1% 또는 주문 p95>3s 시작 도착률):
  - **C_hot ≈ 180~210/s** — 풀 대기 시작(도착 ≈180/s)과 고정(≈210/s) 사이. 보수적으로 **C = 200/s** 채택.
  - C_spread ≥ 550/s (풀 대기 시작) — 800/s 램프 안에서 SLO 붕괴 미도달.
- **M2 부하 크기**: 스파이크 8,000명/10초(도착 800/s) = **4×C** ✓ — 계획값 유지.
- **스케줄러 공급 속도의 탐색 범위**: M3 스윕 = 0.5C(100/s) · 0.7C(140/s) · 1.0C(200/s) · 1.3C(260/s). 예상 최적은 hot 워크로드 기준 100~140/s 부근 (직렬화 상태의 지속 처리율이 210/s이므로 안전계수 0.7 적용 시).
- 배경 탐색 100명/s는 M2에서도 동일 유지 — 두 세계 비교 조건 고정.
