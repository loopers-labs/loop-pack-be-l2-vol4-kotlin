1

MENTAL MODEL

응답 = 접수 / 콜백 = 확정 / 조회 = 안전망

흔한 오해 — "응답으로 성공 처리하고, 콜백으로 2차 확인한다"는 틀렸다.

pg-simulator 의 POST 응답은 접수(PENDING)일 뿐 승인 결과가 아니다. 게다가 40% 확률로 500 이 나고 타임아웃도 난다. 실제 성공/실패는 콜백(또는 조회) 에서만 온다.

3단계① 응답 = 접수(PENDING). 못 받으면 UNKNOWN. → ② 콜백 = 결과 1차 확정(SUCCESS→PAID / FAILED→FAILED). 단 유실 가능. → ③ GET 조회 = 2차 안전망. 콜백 유실·UNKNOWN 을 조회로 해소.
콜백의 함정pg-simulator 의 콜백 송신은 runCatching 으로 실패를 삼키고 타임아웃도 없다 → 콜백은 유실될 수 있다. 그래서 콜백만 믿으면 PENDING 에 영영 갇히는 주문이 생긴다. 조회 reconcile 이 진짜 안전망이다.
2

BIG PICTURE

전체 파이프라인

요청 한 건이 거치는 세 국면과, 최종으로 수렴하는 세 상태(PAID · FAILED · UNKNOWN).

3

USECASE · 약 60% × 70%

U1 — 정상 결제 (happy path)

제출 접수 성공 → 콜백 승인 → PAID. 가장 흔한 경로.

포인트제출 응답(PENDING)으로 성공 처리하지 않는다. PAID 확정은 콜백에서. 클라이언트는 그동안 PENDING 을 보거나 상태 폴링으로 갱신을 받는다.
4

USECASE · 콜백 유실

U2 — 콜백이 안 왔다 → 조회로 구제

승인은 됐는데 콜백이 유실. 콜백만 믿으면 PENDING 에 갇힌다.

왜 필요한가pg-simulator 콜백은 runCatching + 타임아웃 없음 → 유실 가능. 그래서 PENDING 백로그를 주기적으로 GET 조회해 확정하는 reconcile 이 없으면, 성공한 결제가 영영 PENDING 으로 남는다.
5

USECASE · 한도 20% + 카드 10%

U3 — 결제 거절 → FAILED

접수는 됐지만 승인 단계에서 한도초과/카드오류로 거절.

포인트이건 명확한 실패(reason: 한도초과/잘못된 카드)다. UNKNOWN 과 달리 "됐을 수도 있음"이 아니므로 재시도·재조회 불필요, 바로 FAILED 확정.
6

USECASE · in-doubt

U4 — 제출 타임아웃 → 미확정(UNKNOWN)

PG 가 응답을 안 준다. 됐는지 안 됐는지 모른다.

절대 금지타임아웃이라고 새 결제를 다시 보내면 이중 결제가 된다(PG 에선 됐을 수 있음). 무조건 조회로 실제 상태 확인 후 PAID/FAILED 확정. 클라이언트에는 그동안 PENDING 응답.
7

USECASE · 40% 인위적 실패

U5 — 500 반복 → 서킷 오픈 → 미확정

제출이 5xx 로 계속 실패. 제한 재시도 후 CircuitBreaker 가 연다.

포인트500·타임아웃·콜백유실은 전부 "미확정" 한 바구니다. 공통 출구는 UNKNOWN → 조회 reconcile. CB 는 PG 장애가 commerce 전체로 번지는 것을 막는 차단기.
8

USECASE · 우리 잘못

U6 — 400 → 재시도해도 소용없다

헤더 누락·본문 검증 실패·직렬화 오류. PG 가 아니라 우리 요청이 틀렸다.

구분400 = 우리 버그(재시도 X) vs 500/타임아웃 = PG 미확정(조회로 확인). 같은 "실패"로 뭉뚱그리면, 고쳐야 풀릴 버그를 무의미하게 재시도하거나 미확정 건을 막 재결제하는 사고가 난다.

STANDARD? · 공식 출처 검증

이게 정석인가 — 토스페이먼츠 공식 문서

위 3단계 모델(응답=접수 · 콜백=확정 · 조회=안전망)은 임의 관례가 아니다. PG 사업자가 공식 문서에서 그렇게 설계하라고 명시한 구조다.

"데이터 정합성과 연동 편의를 위해서 요청과 승인을 따로 하는 방식으로 요청과 승인 과정을 만들었습니다."

— 토스페이먼츠 개발자센터, 결제 흐름 이해하기 [5]
비동기 + 웹훅 필수"결제 인증과 승인이 비동기적으로 일어나기 때문에 결제의 결과를 받으려면 반드시 웹훅을 연동해야 됩니다."[5] 결제 상태도 단일 액션이 아니라 READY → IN_PROGRESS → DONE 으로 흐른다.
웹훅 유실 = 불일치 (→ 조회 reconcile 의 근거)"사용자가 결제를 중단하거나, 서버에 트래픽이 몰려서 웹훅을 받지 못했다면 상점의 시스템과 토스페이먼츠 결제 결과와 불일치 데이터가 생길 수도 있어요."[5] — 이 한 문장이 본 문서 ③ GET 조회 reconcile 이 왜 선택이 아닌 필수인지를 그대로 뒷받침한다.

공식 문서 ↔ 본 문서 매핑

토스페이먼츠 공식이 말하는 것근거본 문서의 단계
요청과 승인을 분리결제 흐름 이해하기 [5]① 응답=접수 / ② 콜백=확정
비동기 → 웹훅 필수결제 흐름 이해하기 [5]② 콜백으로만 확정
웹훅 유실 시 불일치 발생웹훅 이벤트 [6]③ GET 조회 reconcile (안전망)
정직한 한계"외부 PG 호출을 DB 트랜잭션 밖에 둔다"는 점은 공식 문서·빅테크 공식 블로그에서 깔끔한 1차 출처를 확인하지 못했다(검색 결과가 개인 블로그뿐) — 일반 원칙으로만 둔다. 우아한형제들도 결제를 비동기 시스템으로 전환했다고 작업 항목에 명시는 하나[7], 동기→비동기 전환의 구체적 이유는 해당 글에 상세히 나오지 않아 인용을 이 한 줄로 제한한다.
결론"주문 따로, 결제 따로(요청/승인 분리) + 비동기 콜백 + 조회 보정"은 PG 사업자가 자기 시스템을 그렇게 설계해 그렇게 붙일 수밖에 없는 정석이다. 반대로 결제를 주문 생성 한 동기 트랜잭션에 욱여넣는 방식은 PG 의 비동기 모델과 충돌한다.
