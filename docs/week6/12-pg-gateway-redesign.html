구조 · 네이밍 · 결과 매핑

지금은 PG 한 번 부르는 데 6홉이고, 그중 Requester 레이어는 순전히 AOP 세금이며, failover 분기가 private 예외 throw로 숨어 있습니다. 프로그래밍 CB로 바꿔 레이어를 없애고, failover를 클라이언트 목록(strategy)으로, 결과를 sealed 타입으로 명시합니다. 그리고 "둘 다 실패"를 Failed(확실 실패)와 Unknown(미확정)으로 가릅니다.

AS-IS

현재 구조 — 6홉과 군더더기

PG에 결제 한 번 제출하는 호출 경로가 5개 클래스를 통과합니다.

각 레이어를 분해하면 대부분은 정당하지만, PgPaymentRequester 하나는 오직 @CircuitBreaker가 같은 빈의 self-invocation에 안 먹는다는 Spring AOP 제약 때문에 프록시 경계를 만들려고 존재합니다 — 비즈니스적 의미가 0인 순수 AOP 세금입니다.

군더더기 진단복잡함의 진짜 원인은 두 가지다 — (1) AOP 때문에 억지로 생긴 PgPaymentRequester 레이어, (2) request()가 결과를 throw로 흘려보내는 control-flow. 나머지(port·Impl·Feign 2개)는 정당하다.

TO-BE

재설계 구조 — Requester 제거 + strategy

애너테이션(@CircuitBreaker)을 버리고 resilience4j 프로그래밍 API(CircuitBreakerRegistry)로 전환하면 self-invocation 문제가 사라져 Requester 레이어가 통째로 증발합니다.

그리고 PG 선택이 코드 하드코딩(requestToPgA/requestToPgB)이 아니라 순서 있는 클라이언트 목록이 됩니다 — 목록 순서가 곧 우선순위인 진짜 strategy입니다. NamedPgClient는 (이름, Feign 클라이언트) 쌍이라 레지스트리가 이름으로 CB를 찾습니다.

핵심timeout은 여전히 Feign 몫(HTTP를 쏘니까), CB만 애너테이션 → 레지스트리로 바뀝니다. 관심사 분리(timeout=Feign / CB=resilience4j)는 그대로 유지되고 겹치지 않습니다.
3

CONTROL FLOW

throw control-flow → sealed Attempt

지금은 한 번의 PG 호출 결과를 어떤 건 return, 어떤 건 throw로 섞어 표현하고, 그 throw를 상위에서 다시 catch해 failover를 분기합니다. 흐름이 예외 속에 숨습니다.

AS-IS · PgPaymentGatewayImpl.kt
private fun request(call: () -> PgApiResponse<PgTransactionResponse>): PgSubmitResult {
    try {
        val data = call().data ?: throw PgInDoubtException(...)   // throw
        return PgSubmitResult.Accepted(data.transactionKey)      // return
    } catch (e: CallNotPermittedException) { throw PgUnavailableException(...) }   // throw
      catch (e: RetryableException) { ... throw PgUnavailable / PgInDoubt }        // throw
      catch (e: FeignException.BadRequest) { return Rejected(...) }                // return
      catch (e: FeignException) { throw PgInDoubtException(...) }                  // throw
}
// submit()/failover() 가 이 throw 들을 catch 해 분기 → 흐름이 예외에 숨음

재설계는 한 번 시도의 결과를 sealed Attempt로 만들어 return만 씁니다. failover는 목록 순회 + when으로 코드에 그대로 드러납니다.

TO-BE · FailoverPgPaymentGateway.kt
private sealed interface Attempt {
    data class Accepted(val transactionKey: String) : Attempt
    data class Rejected(val reason: String) : Attempt
    data object Unavailable : Attempt   // PG 죽음(미전송) → 다음 PG
    data object InDoubt : Attempt       // 보냈을 수도 → 중단(미확정)
}

override fun submit(command: PgSubmitCommand): PgSubmitResult {
    for (client in clients) {                       // 순서 = 우선순위 (strategy)
        when (val r = attempt(client, command)) {
            is Accepted -> return PgSubmitResult.Accepted(r.transactionKey)
            is Rejected -> return PgSubmitResult.Rejected(r.reason)
            InDoubt     -> return PgSubmitResult.Unknown   // 보냈을 수도 → reconcile 대상
            Unavailable -> continue                       // 다음 PG 시도
        }
    }
    return PgSubmitResult.Failed   // 전 PG 미전송 = 확실히 실패
}
소거되는 것PgUnavailableException · PgInDoubtException · failover() 메서드 · try/catch-as-control-flow가 전부 사라진다. failover가 코드로 읽힌다.

RESULT MAPPING

결과 매핑 — Failed vs Unknown · 실패 응답

"둘 다 실패"는 한 덩어리가 아닙니다. 전송이 확실히 안 된 경우와 보냈을 수도 있는 경우는 응답이 정반대여야 합니다.

Failed 전 PG unavailable

connect-refused / CB-open으로 전송 0회 = 확실히 미결제. → 결제·주문 FAILED + 재고·쿠폰 보상 롤백 + 클라이언트에 실패 응답(재시도 안전).

Unknown in-doubt

timeout / 5xx로 PG가 받았을 수도 있음. → UNKNOWN 유지 + reconcile로 확정. 절대 "실패"라고 응답하지 않음(재시도 시 이중결제).

함정in-doubt에 "실패" 응답을 주면 유저가 재시도 → 이중결제. 그래서 "실패 응답"은 Failed(전송 확실 실패)에만, Unknown은 "처리 중"으로 응답해야 한다.
상황전송됨?PgSubmitResult → 처리
정상 접수OAccepted → PENDING(콜백 대기), 처리중 응답
카드 거절(400)O (PG 응답)Rejected → FAILED, 거절 응답 (B-2 결정 대상)
전 PG unavailableX (확실)Failed → FAILED + 보상 + 실패 응답(예: 503)
timeout / 5xx모름Unknown → UNKNOWN + reconcile, 처리중 응답
필요 변경현재 PgSubmitResult는 Accepted/Rejected/Unknown 3종. 여기에 Failed를 추가해 "전송 확실 실패"를 "미확정"과 분리한다. 단 Failed의 보상·재조회(reconcile) 자체는 별도 안전망(B-1, P0)에서 구현한다.

4xx 매핑 비대칭

지금은 BadRequest(400)만 Rejected로 잡고, 429 · 404 · 409 같은 다른 4xx는 마지막 catch(FeignException)으로 떨어져 조용히 UNKNOWN이 됩니다. CB는 4xx 전부를 ignore하는데 게이트웨이 매핑은 BadRequest만 다뤄 비대칭입니다.

응답현재재설계
400 BadRequestRejectedfail-fast로 노출 (B-2: 시뮬레이터는 동기 거절을 안 냄 → 400=우리 요청 버그)
429 / 404 / 409 등 4xx조용히 UNKNOWN (누수)명시적으로 분류
5xx · timeoutUNKNOWNInDoubt → Unknown (의도대로)
열린 결정 (B-2)400을 fail-fast(우리 버그로 에러 노출)로 할지, 실 PG의 "카드 거절 400" 대비해 Rejected 유지할지는 매핑 확정 전에 정해야 한다. 시뮬레이터 한정으론 전자가 맞다(거절을 동기로 안 내므로 Rejected는 죽은 의미).
