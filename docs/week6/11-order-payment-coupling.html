CONVERGENT SKELETON

표준 골격 — 10/12가 같다

결제↔주문을 잇는 방식은 사실상 한 가지로 수렴했다. 이걸 기준선으로 삼고, 내가 어디서 벗어나는지를 본다.

핵심결합 방향은 전원 Payment → Order 단방향(payment.order_id FK, Order는 결제를 모름). 그리고 결제 결과를 Order로 전파하는 건 거의 전원 PaymentService가 Order를 직접 호출한다(KWB255만 일부 이벤트). 지금 단계엔 합리적이지만 "결제→주문 방향 의존"임은 인지하고 갈 것.

MY POSITION

내 위치와 어디서부터

골격은 평균 이상인데, 세 축에서 다 비었다. 그래서 시작점은 명확하다.

잘한 곳 (골격)2-call ✓ · Payment order_id FK ✓ · PG I/O Tx 밖 ✓ · 게다가 UNKNOWN을 Payment뿐 아니라 Order까지 1급 상태로 전파한 유일한 구현(OrderStatus.UNKNOWN). 상태 모델링은 오히려 상위권.
약한 고리 (= 시작점)성공·실패가 Order로 가는 길이 콜백 단 하나다. 표준은 전부 콜백+reconcile 2경로. 결과:
· 콜백 유실 → Order 영원히 PENDING_PAYMENT
· PG 타임아웃 → Payment·Order 둘 다 UNKNOWN인데 해소 주체가 없음 (전이 규칙 UNKNOWN→SUCCESS/FAILED은 있는데 호출자가 없다)
가장 정교하게 모델링한 UNKNOWN이 가장 확실한 dead-end. reconcile이 없는 건 표준 10개 중 나 하나뿐.

그래서 정리 순서

순서할 일왜 / 참고
1PG GET 조회 + reconcile 스케줄러표준에서 빠진 두 번째 전파경로. UNKNOWN dead-end 해소 → 채점 C2 2→15+. 참고: 호준88 Reconciler, sung260 RecoveryHandler 수렴점
2resilience4j 임계값 (@CB·@Retry)과제 표제 주제. 재시도=5xx만(timeout 제외), CB 실패율 60~70 (40% 함정)
