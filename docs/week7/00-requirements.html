SCOPE AT A GLANCE

한눈에 보기 — Must-Have vs Nice-To-Have

Implementation Quest는 반드시 해야 하는 것(Must-Have)과 시간이 되면 하는 것(Nice-To-Have)으로 나뉩니다. 먼저 무엇이 합격선이고 무엇이 가산점인지 경계를 분명히 합니다.

MUST 무조건 구현

이 다섯 가지는 Round 7의 합격선입니다. 하나라도 빠지면 테마(동기 → 비동기 경계 분리)가 성립하지 않습니다.

NICE 시간 되면

전달 보장·운영 성숙도를 끌어올리는 가산점 항목입니다. Must-Have가 끝난 뒤에 손댑니다.

Must-Have — 합격선

  • Event vs Command 구분 — 무엇이 명령이고 무엇이 사실(이벤트)인지 분류 STEP 1
  • Application Event — 주요/부가 로직 경계를 스프링 이벤트로 분리 STEP 1
  • Kafka Producer · Consumer 기본 파이프라인 — commerce-api → Kafka → Consumer 앱 STEP 2
  • Transactional Outbox Pattern — At Least Once 발행 보장 STEP 2
  • Kafka 기반 선착순 쿠폰 발급 — 발행만 하는 API + Consumer 발급 + 동시성 제어 STEP 3

Nice-To-Have — 가산점

  • Consumer Group 분리 — 관심사별(집계 / 쿠폰 / 로깅)로 컨슈머 그룹을 나눠 독립 처리 운영
  • Consumer 배치 처리 — 레코드를 묶어 한 번에 소비해 처리량 향상 성능
  • DLQ 구성 — 반복 실패 메시지를 Dead Letter Queue로 격리 전달 보장
이번 라운드 한 문장핵심 트랜잭션은 동기로 지키고, 부가·집계·전파는 이벤트로 떼어낸다. 그중 서비스 경계를 넘어야 하는 것만 Kafka로 보내고, 그 발행을 Outbox로, 그 소비를 멱등하게 보장합니다.

STEP 1 · APPLICATION EVENT

ApplicationEvent로 경계 나누기

"무조건 이벤트로 분리"가 아니라 주요 로직과 부가 로직의 경계를 판단하는 것이 이 단계의 본질입니다. 무엇을 떼어낼지 정하고, 트랜잭션 결과와의 상관관계에 맞는 리스너로 연결합니다.

해야 할 일

  • 주문–결제 플로우에서 부가 로직(유저 행동 로깅, 알림 등)을 이벤트로 분리한다.
  • 좋아요–집계 플로우에 eventual consistency를 적용한다 — 집계가 실패해도 좋아요 자체는 성공한다.
  • 유저 행동(조회 · 클릭 · 좋아요 · 주문)에 대한 서버 레벨 로깅을 이벤트로 발생시킨다.
  • 트랜잭션 결과와의 상관관계에 따라 적절한 리스너(@TransactionalEventListener phase 등)를 선택해 연결한다.

판단 기준 — "이걸 이벤트로 분리해야 하는가"

이 판단 기준 자체가 Step 1의 핵심 학습 포인트입니다. 아래는 "기준 항목"만 제시합니다 — 각 기준의 개념·근거는 01-concepts에서 다룹니다. 하나의 동작을 두고 아래를 차례로 물어, 분리 여부와 리스너 phase를 정합니다.

판단 기준 (질문)예 (분리 신호)아니오 (동기 유지)
도메인 핵심 불변식인가?아니오 → 분리 후보예 → 본 트랜잭션 안에 둔다
실패해도 본 트랜잭션은 성공해야 하나?예 → 분리(부가 로직)아니오 → 함께 롤백
외부 I/O인가? (알림 · 외부 API)예 → 비동기로 분리아니오 → 내부 동기
순서 의존이 있는가?예 → 순서 보장 설계 필요아니오 → 자유 분리
강결합 제거 가치가 있는가?예 → 이벤트로 디커플아니오 → 직접 호출 유지

STEP 2 · KAFKA PIPELINE

Kafka 이벤트 파이프라인

Step 1에서 분리한 이벤트 중 시스템 간 전파가 필요한 것을 Kafka로 발행합니다. commerce-api가 Producer, commerce-streamer가 Consumer가 되어 집계를 product_metrics에 upsert합니다.

Consumer 앱 명칭과제 원문의 Consumer 앱 명칭은 commerce-collector이지만, 우리 레포에는 이미 Kafka로 배선된 commerce-streamer consumer 앱이 있어 이를 사용합니다.

Producer 필수 설정

항목설정목적
acksall모든 ISR 복제 확인 후 ack — 유실 방지
idempotencetrue재시도 시 브로커 중복 적재 방지
발행 보장Transactional OutboxDB 커밋과 발행을 한 트랜잭션 의도로 묶어 At Least Once

Consumer 필수 처리

항목해야 할 처리합격 기준
Ackmanual Ack처리 성공 후에만 오프셋 커밋
멱등 처리event_handled(event_id PK) (DB or Redis)이미 처리한 event_id면 skip
최신성version 또는 updated_at 기준오래된 이벤트가 최신 집계를 덮어쓰지 않음
순서 보장PartitionKey 기반 라우팅같은 키 이벤트는 같은 파티션 → 순서 유지

토픽 설계 (예시)

토픽담는 이벤트Partition Key
catalog-events상품 · 재고 · 좋아요productId
order-events주문 · 결제orderId
coupon-issue-requests쿠폰 발급 요청couponId

Step 2 체크리스트

  • 시스템 간 전파가 필요한 이벤트만 골라 Kafka로 발행한다.
  • Producer에 acks=all · idempotence=true를 설정한다.
  • 발행을 Transactional Outbox Pattern으로 At Least Once 보장한다.
  • Consumer가 manual Ack + event_handled 멱등 + version/updated_at 최신성 + PartitionKey 순서를 모두 처리한다.
  • Consumer가 집계(좋아요 수 · 판매량 · 조회 수)를 product_metrics에 upsert한다.
보존 질문 · STEP 2"왜 이벤트 핸들링 테이블과 로그 테이블을 분리하는 걸까?"멱등을 위한 event_handled와, 유저 행동 로그를 쌓는 테이블을 굳이 나누는 이유를 설계 근거로 답할 수 있어야 합니다. (개념은 01-concepts)

STEP 3 · FIRST-COME COUPON

Kafka 기반 선착순 쿠폰 발급

API는 발급 요청을 Kafka에 발행만 하고 빠르게 응답하고, Consumer가 실제 발급을 순차 처리합니다. 수량 제한 동시성 제어와, 유저가 결과를 확인할 수 있는 구조가 핵심입니다.

흐름 — 해야 할 일

  • POST /coupons/issue — 발급 요청을 Kafka에 발행만 하고 빠르게 응답한다(requestId 반환).
  • Consumer가 순차 처리: 수량 확인 → 발급/거절, userId 중복 방지, 결과 저장.
  • GET /coupons/issue/{requestId} — 유저가 발급 완료/실패 결과를 polling으로 확인한다.
  • 발급 수량 제한(예: 선착순 100명)에 대한 동시성 제어를 구현한다.

동시성 — 합격 기준

동시성 테스트 합격 조건1만 명이 동시에 요청해도 수량 초과 발급이 단 한 건도 발생하지 않아야 합니다. 100장 한도면 발급 성공은 정확히 최대 100건, 같은 userId는 중복 발급되지 않습니다. 동시성 테스트로 이를 검증합니다.
  • 발급 성공 건수 ≤ 한도 수량 (수량 초과 0건) 검증
  • 동일 userId 중복 발급 0건 검증
  • 거절된 요청도 결과 저장 — 유저가 "거절" 상태를 조회 가능 검증

SUBMISSION

전체 제출 체크리스트

제출 전 한 번에 점검합니다. MUST 표시는 합격선, 나머지는 가산점·문서 산출물입니다.

Implementation

  • Event vs Command를 구분해 분류했다 MUST · S2
  • 주요/부가 로직 경계를 ApplicationEvent로 분리했다 MUST · S2
  • 좋아요는 성공, 집계 실패와 무관한 eventual consistency를 적용했다 MUST · S2
  • Kafka Producer·Consumer 기본 파이프라인을 구성했다 MUST · S3
  • Producer에 acks=all · idempotence=true를 설정했다 MUST · S3

  • Consumer 멱등(event_handled) · 최신성 · 순서 · manual Ack을 처리했다 MUST · S3
