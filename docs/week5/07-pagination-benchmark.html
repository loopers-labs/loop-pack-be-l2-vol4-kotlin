SETUP

측정 설계

쿼리는 실제 코드(ScrollPosition.keyset())와 동일한 모양. 정렬 like_count DESC, id DESC, 필터 status <> 'DELETED', 페이지 크기 10.

축값
방식B(like_count 컬럼) · A-정렬용(COUNT로 정렬) · A-표시용(페이지 10개만 COUNT)
페이지네이션OFFSET LIMIT 10 OFFSET N vs Keyset WHERE (lc,id)<(?,?)
깊이depth = 0 / 1,000 / 10,000 / 100,000
시나리오S1 전체(100,750) · S2 대형 brand1(8,000) · S3 소형 brand500(30)
인덱스없음 → (like_count,id) → (brand_id,like_count,id) → product_like(product_id)
측정 방법각 쿼리 워밍업 1회 후 측정. 표의 수치는 EXPLAIN ANALYZE 루트 노드 actual time(ms, 마지막 행까지). 시드는 CRC32 결정적이라 재현 가능. 베이스라인 인덱스는 PK뿐.

RESULT 1

결과 ① 전체 목록 (S1)

핵심 그림. 인덱스 (like_count, id)를 걸면 Keyset은 깊이와 무관하게 sub-ms로 평평한데, OFFSET은 깊은 페이지에서 옵티마이저가 인덱스를 버리고 풀스캔으로 회귀한다.

depthOFFSET·인덱스XOFFSET·+(lc,id)KEYSET·인덱스XKEYSET·+(lc,id)
026.8 ms0.033 ms26.6 ms0.035 ms
1,00031.2 ms1.28 ms28.0 ms0.249 ms
10,00037.2 ms36.6 ms27.1 ms0.059 ms
100,00048.1 ms46.6 ms21.6 ms0.069 ms
왜 OFFSET이 인덱스를 버리나LIMIT 10 OFFSET 100000은 인덱스로 풀어도 100,010행을 읽고 100,000행을 버려야 한다. 옵티마이저는 "그럴 바엔 풀스캔+정렬이 싸다"고 판단해 인덱스를 포기한다. Keyset은 WHERE (lc,id)<(?,?)로 읽을 위치를 바로 찾아 딱 10행만 본다 — 그래서 평평하다.
인덱스가 없으면?OFFSET이든 Keyset이든 둘 다 풀스캔+정렬(~20~48ms)로 똑같다. Keyset 자체가 마법이 아니라, 정렬키 인덱스가 있어야 빛난다. 인덱스 없는 Keyset은 WHERE 조건을 평가할 정렬 구조가 없어 매번 전체를 훑는다.

대조군의 의미소형 브랜드(30건)는 인덱스만 걸면 OFFSET·Keyset 차이가 안 보인다(둘 다 0.02~0.04ms) — 모집단이 작으면 페이지네이션 방식은 무의미. 방식 선택이 갈리는 건 모집단이 큰 S1·S2다. 분포를 멱법칙으로 쏠리게 만든 이유가 여기서 증명된다.
인덱스 분리 필요(brand_id, like_count, id)는 brand_id 동등이 없는 S1(전체)에는 못 쓴다(선두 컬럼 미고정). 반대로 (like_count, id)는 브랜드 필터를 못 탄다. 두 쿼리 패턴이 다 있으면 인덱스도 둘 다 필요하다.

RESULT 3

결과 ③ 방식 A — 정렬용·표시용

like_count 컬럼 없이 product_like를 COUNT로 푸는 방식 A. 정렬에 쓰면 재앙, 표시에만 쓰면 페이지 내용에 따라 복불복.

A-정렬용 — ORDER BY COUNT(*) (LIMIT 단축 불가)

depth인덱스X+ product_like(product_id)방식 B 동급
01,835 ms1,032 ms0.033 ms
1,0001,838 ms1,042 ms1.28 ms
왜 1초+인가상위 10개를 알려면 10만 상품 전부의 COUNT를 먼저 다 구하고(681만 행 조인) → 정렬 → 그제서야 LIMIT. LIMIT 10 단축이 안 먹어서 1페이지든 어디든 매번 풀 집계다. product_id 인덱스로 hash join → nested loop이 되며 1.8s→1.0s로 줄지만, 방식 B 대비 약 30,000배 느리다. 게다가 집계값은 인덱스로 비교 불가라 Keyset 커서도 불가능.

A-표시용 — 페이지 10개 id만 COUNT (정렬엔 안 씀)

페이지 종류COUNT 대상 행인덱스X+ product_like(product_id)
핫 10개576,581840 ms108 ms
롱테일 10개120768 ms0.082 ms
표시용은 복불복인덱스가 없으면 표시용도 681만 행 풀스캔(768~840ms). product_id 인덱스를 걸면 롱테일 페이지는 0.08ms로 빨라지지만, 핫 상품 페이지(좋아요순 1페이지)는 57만 행을 COUNT해 108ms. 방식 B는 컬럼 읽기라 페이지 내용과 무관하게 항상 즉시. 표시용도 결국 B가 안전하다.

PLANS

실행계획 읽기

숫자 뒤의 실행계획. 같은 인덱스인데 OFFSET은 풀스캔, Keyset은 인덱스 레인지 스캔으로 갈린다.

OFFSET depth=100000 · 인덱스 있어도 버림
-- 같은 (like_count,id) 인덱스가 있는데도 Table scan 선택
-> Limit/Offset: 10/100000  (actual time=46.6..46.6 rows=10)
    -> Sort: like_count DESC, id DESC, limit input to 100010 row(s)
        -> Filter: (status <> 'DELETED')  (rows=100750)
            -> Table scan on product  (rows=100750)
KEYSET depth=100000 · 인덱스 레인지 스캔, 딱 10행
-> Limit: 10 row(s)  (actual time=0.067..0.069 rows=10)
    -> Filter: (status <> 'DELETED')
        -> Index range scan on product using idx_p_lc_id (reverse)
           over (like_count < @lc) OR (like_count = @lc AND id < @id)
           (actual time=0.066..0.067 rows=10)
A-정렬용 · 681만 행 조인 후 임시테이블 집계
-> Limit: 10 row(s)  (actual time=1835..1835 rows=10)
    -> Sort: lc DESC, p.id DESC
        -> Table scan on <temporary>  (rows=100750)
            -> Aggregate using temporary table  (rows=100750)
                -> Left hash join (pl.product_id = p.id)
                   (actual time=832..1297 rows=6.82e+6)
                    -> Table scan on p  (rows=100750)
                    -> Covering index scan on pl  (rows=6.81e+6)
읽는 법핵심은 rows= 와 Sort/Table scan의 유무. OFFSET 깊은 페이지는 rows=100750 + Sort(filesort), Keyset은 Index range scan ... rows=10. A-정렬용은 rows=6.82e+6 조인 + Aggregate using temporary table — 단축 불가의 증거.

VERDICT

결론·인덱스 권장

데이터가 가리키는 답은 분명하다.

채택 Keyset + 복합 인덱스 + 방식 B

정렬키 컬럼을 비정규화(B)하고 (정렬키, id) 인덱스 + Keyset 커서. 깊이 무관 sub-ms. 좋아요순 정렬엔 사실상 유일한 답.

탈락 OFFSET / 방식 A 정렬

OFFSET은 깊은 페이지에서 인덱스를 버려 풀스캔. 방식 A 정렬은 전체 집계로 1초+, Keyset 자체가 불가능.

권장 인덱스

인덱스대상 쿼리판정
product(like_count, id)S1 전체 좋아요순필수
product(brand_id, like_count, id)S2·S3 브랜드+좋아요순필수
product_like(product_id)방식 A를 쓸 때만방식 B로 가면 불필요
한 줄 결론좋아요순 페이지네이션 = 비정규화 like_count 컬럼(B) + (brand_id?, like_count, id) 복합 인덱스 + Keyset 커서. OFFSET과 방식 A 정렬은 큰 모집단에서 무너진다. 소형 모집단은 어느 쪽이든 무방하나, 코드 일관성을 위해 Keyset 단일화.
