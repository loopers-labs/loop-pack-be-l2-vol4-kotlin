WHY MYSQL FIRST

왜 MySQL부터인가

"RDB는 랭킹에 느리다"는 서술만으로 ZSET을 고르면, 그것은 결정이 아니라 주장이다.

요구사항은 네 가지다. 일간 랭킹(자정마다 판이 바뀜), 실시간 반영(이벤트가 곧바로 점수에 잡힘), 개별 상품 순위(상세 페이지에 "오늘 N위"), 그리고 전날 점수의 10% 이월(자정 직후 판이 텅 비지 않게). 점수 가중치는 조회 0.1 · 좋아요 0.2 · 주문 0.7이고, 주문은 금액이 아니라 주문 라인 건수로 센다 — 고가 상품 1건이 인기 상품 판을 뒤집는 왜곡을 피하기 위해 실서비스 사례 조사 후 확정한 값이다.

구현은 3단계로 올라간다. Stage 1 MySQL 쿼리 → Stage 2 Redis 캐시 → Stage 3 ZSET. 같은 시드, 같은 k6 시나리오, 같은 지표로 3자 비교해서 각 단계의 탈락 사유를 요구사항 항목에 1:1로 매핑하는 것이 목표다. 이 글이 다루는 Stage 1은 "MySQL로 어디까지 되는가"의 기준선이다.

이 구현의 두 가지 핵심 결정① 점수는 쓰기 시점에 누적한다 — 조회 시점에 가중치를 합성하는 방식은 사전 실험(EXP-02)에서 최악 경로임이 확인됐다. ② 자정 감쇠는 배치가 아니라 dual write로 처리한다 — 전면 UPDATE 배치는 사전 실험(EXP-01)에서 조회 처리량을 41% 깎았다.

DATA MODEL

데이터 모델 — 점수는 쓸 때 계산한다

테이블은 하나다. product_ranking_daily — 날짜 × 상품마다 점수 한 행.

대안은 두 갈래였다. 기존 product_metrics(누적 카운트 테이블)를 두고 조회할 때마다 0.1×view + 0.2×like + 0.7×order를 합성하는 방식(조회 시점 계산)과, 이벤트가 올 때마다 가중치를 곱해 점수 컬럼에 바로 누적하는 방식(쓰기 시점 계산). EXP-02에서 둘을 같은 환경에 놓고 재보니 조회 시점 계산은 정렬 기준이 계산식이라 인덱스를 탈 수 없었고, 10만 행 기준 개별 순위 쿼리가 처리량 29qps로 최악 경로였다. 그래서 점수를 미리 계산해 저장하고, 조회는 인덱스만 읽게 만들었다.

구성 요소정의역할
컬럼ranking_date · product_id · score (DECIMAL 20,4)날짜별 판 × 상품 점수
UNIQUE KEYuk_prd_date_product (ranking_date, product_id)upsert 충돌 키 — 한 판에 상품 1행
INDEXidx_prd_date_score (ranking_date, score DESC, product_id ASC)랭킹 페이지가 정렬 없이 읽는 커버링 인덱스

인덱스 3컬럼이 이 설계의 골격이다. ranking_date로 판을 자르고, score DESC[2]로 이미 정렬돼 있으니 랭킹 페이지 조회는 filesort 없이 인덱스 순서 그대로 LIMIT만 걸면 된다. 마지막 product_id ASC는 동점일 때 순서를 결정적으로 만들고, 동시에 조회가 필요로 하는 세 컬럼을 인덱스만으로 커버한다.

ranking/infrastructure/ProductRankingDaily.kt 
@Entity
@Table(
    name = "product_ranking_daily",
    uniqueConstraints = [
        UniqueConstraint(name = "uk_prd_date_product", columnNames = ["ranking_date", "product_id"]),
    ],
    indexes = [
        Index(name = "idx_prd_date_score", columnList = "ranking_date, score DESC, product_id ASC"),
    ],
)
class ProductRankingDaily(
    rankingDate: LocalDate,
    productId: Long,
    score: BigDecimal,
) : BaseEntity()
3

WRITE PATH

쓰기 경로 — 이벤트 소비 파이프라인

이벤트 하나가 점수 두 행이 되기까지 — 발행부터 upsert까지 전 구간이다.

발행 쪽은 이벤트 성격에 따라 경로가 다르다. 좋아요와 주문은 week 7에 만든 outbox를 통해 원자 발행되므로 유실이 없어야 하고(불일치 = 버그), 상품 조회(view)는 @Async AFTER_COMMIT 직접 발행이라 유실 허용 경로다. 이 차이는 나중에 정산(reconciliation) 검증의 허용 오차 기준이 된다 — like·order는 오차 0, view는 결손만 허용.

소비 쪽은 commerce-streamer가 토픽 3개(product-events·order-events·user-action-events)를 배치로 읽는다. 이때 metrics와 ranking은 서로 다른 독립 컨슈머다 — ProductMetricsKafkaConsumer(groupId commerce-streamer-metrics-*)와 ProductRankingKafkaConsumer(groupId commerce-streamer-ranking-*)가 같은 토픽을 각자의 그룹으로 따로 구독한다. 멱등도 분리돼 event_handled가 (event_id, subscription) 복합키라, 랭킹 적재는 RankingAccumulateService가 자기 @Transactional 안에서 EventSubscription.RANKING 멱등으로 처리한다(metrics의 product_metrics 누적과 같은 트랜잭션이 아니다). 이 문서가 추적하는 것은 그중 랭킹 쓰기 경로다.

적재의 심장은 RankingAccumulateService.accumulate다. EventSubscription.RANKING 멱등을 먼저 확인하고, 이벤트의 발생 시각(occurredAt)을 KST 날짜로 바꿔 change마다 오늘판에 Δ를 더하고, 같은 트랜잭션에서 내일판에 Δ×0.1을 미리 더한다. 왜 내일판까지 건드리는지는 4장에서 다룬다.

ranking/application/RankingAccumulateService.kt (streamer) 
@Transactional
fun accumulate(eventId: String, occurredAt: Instant, changes: List<ScoreChange>) {
    if (eventHandledRepository.exists(eventId, EventSubscription.RANKING)) return
    val eventDate = occurredAt.atZone(KST).toLocalDate()
    changes.forEach { change ->
        productRankingDailyRepository.accumulate(eventDate, change.productId, change.amount)
        productRankingDailyRepository.accumulate(
            eventDate.plusDays(1), change.productId, change.amount.multiply(RankingWeights.CARRY_RATE),
        )
    }
    eventHandledRepository.markHandled(eventId, EventSubscription.RANKING)
}

저장은 JPA 엔티티 조회 없이 native upsert 한 방이다. ON DUPLICATE KEY UPDATE[1]는 uk 충돌 시 score = score + :change로 원자 가산되므로, 여러 컨슈머 스레드가 같은 상품을 동시에 치더라도 read-modify-write 경합이 없다.

@Modifying
@Query(value = """
    insert into product_ranking_daily (ranking_date, product_id, score, created_at, updated_at)
    values (:rankingDate, :productId, :change, now(), now())
    on duplicate key update
        score = score + :change,
        updated_at = now()
""", nativeQuery = true)
fun upsertChange(rankingDate: LocalDate, productId: Long, change: BigDecimal): Int
참고한 트랜잭션이 오늘·내일 두 행을 만지므로 잠금 취득 순서를 날짜 오름차순으로 고정했다. 순서가 이벤트마다 뒤섞이면 상품이 겹치는 동시 트랜잭션 사이에 데드락 창이 열린다.

MIDNIGHT BOUNDARY

자정 경계 — 배치 대신 dual write

자정에 실행되는 작업은 0개다. 내일판은 하루 종일 미리 만들어지고 있었다.

"전날 점수의 10% 이월"의 소박한 구현은 자정 배치다 — 00:00에 UPDATE score = score × 0.1을 전면 실행하거나, 오늘판을 읽어 내일판을 INSERT하는 것. 그런데 EXP-01에서 10만 행 · 동시성 32로 실측해 보니 제자리 전면 UPDATE는 배치가 도는 24.1초 동안 조회 처리량을 41% 깎았다. score 변경이 (date, score DESC) 인덱스 10만 엔트리의 삭제+재삽입이 되는데, 그 페이지들이 바로 조회가 읽는 페이지들이기 때문이다. 반면 다른 날짜 프리픽스에 append하는 사전 INSERT 방식은 −10%에 그쳤다. 결론: 쓰는 판과 읽는 판을 분리하라.

여기서 한 발 더 나가면 배치 자체가 사라진다. 이벤트를 적재할 때마다 내일판에도 Δ×0.1을 같이 쌓으면(dual write), 하루가 끝나는 시점의 내일판 잔고가 정확히 오늘 총점 × 0.1이 된다. 자정에는 조회가 바라보는 날짜만 바뀌면 되고, 새 판은 이미 이월 점수로 시딩돼 있다.

버린 안 자정 배치 (EXP-01 실측)

제자리 전면 UPDATE: 배치 24.1초 동안 조회 처리량 −41%, 꼬리지연 최대 1.5배. 사전 INSERT 시딩도 −10%에 배치 운영 부품(스케줄러·재실행 멱등성·실패 알림)이 따라온다. 23:50 배치안은 마지막 10분 이벤트가 이월에서 누락된다.

채택 dual write 선적재

자정 작업 0개, 콜드 스타트 없음, 재해 지점 없음. 비용은 이벤트당 랭킹 쓰기 2배 — 핫패스에 상주하는 영구 비용이라 Stage 1b에서 단일 쓰기 대비 처리량·p95를 실측해 크기를 확인한다.

정확도 트레이드오프감쇠가 1일에서 절단된다 — 배치 방식은 어제 이월분까지 포함해 ×0.1이 지수적으로 연쇄하지만, delta dual write는 그제 점수의 ×0.01 항이 소실된다. 크기가 1% 수준이라 순위 영향은 무시 가능하다고 판단했고, 대신 "지수 감쇠"라는 표현은 쓰지 않기로 했다.

READ PATH

읽기 경로 — 랭킹 페이지와 개별 순위

순위는 저장하지 않는다. 점수가 정렬돼 있으니, 순위는 읽는 순간의 위치일 뿐이다.

읽기 API는 둘이다. GET /api/v1/rankings는 날짜별 랭킹 페이지를 주고(미지정 시 오늘 KST), GET /api/v1/products/{id}는 기존 상세 응답에 "오늘 N위"를 얹는다. 둘 다 비로그인 허용(permitAll)이다.

페이지 응답의 순위는 계산식 한 줄이다 — 인덱스가 이미 score DESC, product_id ASC로 정렬해 놨으므로 페이지 시작 순위에 행 위치만 더하면 된다. 개별 순위는 "나보다 점수 높은 행 수 + 1"로 센다.

ranking/application/RankingQueryService.kt 
// A. 랭킹 페이지 — 위치가 곧 순위
val startRank = (page - 1).toLong() * size
rank = startRank + index + 1

// B. 상품 상세 — 나보다 높은 점수를 센다
fun findTodayRank(productId: Long): Long? {
    val today = LocalDate.now(KST)
    val mine = repository.findByRankingDateAndProductId(today, productId) ?: return null
    return repository.countByRankingDateAndScoreGreaterThan(today, mine.score) + 1
}
6

TESTS AS CONTRACT

테스트로 고정한 계약

이 구현이 Stage 2·3으로 갈아타도 깨지면 안 되는 동작들을 통합 테스트로 못 박았다.

  • dual write 정합 — 이벤트 1건이 오늘판 +Δ, 내일판 +Δ×0.1 정확히 두 행을 만든다 적재
  • 멱등 — 같은 eventId 재전달 시 점수가 이중 가산되지 않는다 (event_handled (event_id, subscription) 복합키 · RANKING 구독) 적재
  • 가산 upsert — 동일 (날짜, 상품) 반복 이벤트가 행 증식 없이 score 누적으로 수렴한다 적재
  • 페이징 계약 — date·page·size 검증(400), 빈 판의 빈 응답, 순위 계산 API
  • 상세 순위 — 랭킹 행이 없으면 순위 미노출(null), 있으면 COUNT+1 API

추가로 성능 런 후의 데이터 정합은 정산 SQL(load-test/verify-ranking.sql)로 검증한다 — k6가 센 이벤트 수로 기대 점수 합을 만들고 저장소 합과 대사한다. like·order는 outbox 원자 발행이라 오차 0이어야 하고, view는 유실 허용 경로라 결손만 허용된다(초과 가산은 어떤 경우에도 버그).

KNOWN LIMITS

알려진 한계와 다음 측정

Stage 1은 "완성"이 아니라 "기준선"이다 — 한계가 어디서 오는지 수치로 남기는 것이 목적이다.

한계 1 · 개별 순위가 최악 경로상세 요청마다 쿼리 2회가 돌고, COUNT 쿼리에서 옵티마이저가 커버링 인덱스 대신 uk를 선택한다 — 10만 행 기준 uk 44.8ms vs FORCE INDEX[3] 커버링 14.5ms로 3배 차이인데, 옵티마이저의 cost 추정(1977 vs 10153)은 실제와 반대였다. 트래픽이 몰리는 상세 페이지에 이 비용이 상주한다.
한계 2 · 이벤트당 쓰기 2배dual write는 핫패스의 영구 비용이다. 쓰기 램프에서 단일 쓰기 대비 컨슈머 처리량·랙이 얼마나 갈리는지 Stage 1b에서 실측한다.
한계 3 · 동점 표기 불일치랭킹 페이지의 순위는 위치 기반(동점은 product_id로 갈림)이고 상세의 순위는 COUNT 기반(동점끼리 같은 순위 공유)이라, 동점 상품이 리스트 5위 · 상세 4위로 보일 수 있다. 실사용 영향은 작지만 표기 규칙을 통일할지는 열린 결정이다.

다음은 측정이다. R9 부하 계획(02-load-test-plan.html)의 시나리오로 조회 램프(50→400rps)·신선도 프로브(이벤트→반영 지연)·정산을 돌려 Stage 1의 숫자를 확보하고, 같은 조건에서 Stage 2(캐시) · Stage 3(ZSET)과 3자 비교한다. "왜 ZSET인가"는 그 표가 대답하게 된다.
