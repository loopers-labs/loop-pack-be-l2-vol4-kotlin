SCOPE AT A GLANCE

한눈에 보기 — Must vs Nice + 전체 파이프라인

랭킹은 쓰기(이벤트 → 점수 누적)와 읽기(Top-N·개별 순위 조회)가 분리된 시스템입니다. R7이 만든 이벤트 파이프라인의 소비 지점에 ZSET 갱신을 얹고, API는 그 ZSET을 읽기만 합니다.

MUST 무조건 구현

Kafka Consumer → Redis ZSET 실시간 적재(일간 키·TTL·가중치 스코어) · 랭킹 페이지 조회 API · 상품 상세에 순위 표시. 이 세 축이 Round 9의 합격선입니다.

NICE 시간 되면

실시간 Weight 조절 · 시간(1h) 단위 랭킹 · 콜드 스타트 완화 스케줄러(23:50 Score Carry-Over). Must가 끝난 뒤에 손댑니다.

왜 RDB가 아니라 Redis ZSET인가 (핵심 프레이밍) 랭킹은 조회 빈도가 매우 높고(홈 메인·인기순 정렬 등), GROUP BY + ORDER BY는 데이터가 쌓일수록 느려져 DB 과부하로 이어집니다. ZSET은 정렬을 자료구조가 내장(삽입/수정 O(log N))해 실시간 반영과 다양한 조회(Top-N·개별 순위·범위)를 O(log N)~O(N)에 제공합니다.
2

WHY SORTED SET

왜 Redis ZSET인가

ZSET은 (member, score) 쌍을 score 기준 정렬 상태로 유지합니다. member는 상품 ID, score는 랭킹 점수 — 이 둘이 "실시간 갱신 + 정렬 조회"를 동시에 해결합니다.

명령역할키 · 의미
ZINCRBY점수 누적 (실시간 집계)ranking:all:{date} {delta} {productId}
ZREVRANGETop-N 조회 (내림차순)WITHSCORES · O(N)
ZREVRANK특정 상품의 순위 (0-based)없으면 null
ZSCORE특정 상품의 점수ranking:all:{date} {productId}
ZCARD랭킹 진입 상품 수운영 지표 겸용

DB ORDER BY

정합성은 높지만 데이터가 쌓일수록 느려지고, 조회 빈도가 높아 DB 과부하로 이어짐. 초기·소규모에만 적합.

ZSET Redis

정렬 내장(별도 인덱스 불필요) · 실시간 반영 · Top-N/개별 순위/범위 검색 다양하게 지원. 대규모 트래픽에 적합(메모리 사용 ↑는 트레이드오프).

STEP 1 · WRITE PATH

Consumer → ZSET 실시간 적재

조회·좋아요·주문 이벤트를 소비해 일간 키 ZSET에 점수를 누적합니다. 각 이벤트에 Weight와 Score를 정하고, ZINCRBY로 반영합니다.

  • MUSTConsumer → ZSET 적재 — 이벤트 소비 시 일간 키 ranking:all:{yyyyMMdd}에 ZINCRBY로 점수 누적
  • MUST날짜별 키 계산 — 이벤트 발생 시각(KST) 기준 yyyyMMdd 키를 산출하는 기능
  • MUSTTTL 설정 — 윈도우의 1.5~2배. 일간이면 TTL 2Day. 키 생성 시점에 만료 부여
  • NICE배치 리스너로 스루풋 ↑ — 단건 처리는 ZSET/DB 연산이 과다. 배치로 정제 후 반영 (R7 collector가 이미 배치 리스너 — 재사용)
재사용 — 이미 R7에 배치 소비 지점이 있다 commerce-streamer의 ProductMetricsKafkaConsumer가 이미 배치 리스너(BATCH_LISTENER, 토픽 catalog-events·order-events·user-action-events, eventId 멱등)입니다. Round 9는 이 소비 지점에서 product_metrics 집계와 나란히 ZSET 갱신을 얹는 형태 — "Nice-to-Have 배치 리스너"는 사실상 확보되어 있습니다.
스펙 고정값 KEY = ranking:all:{yyyyMMdd} · TTL = 2Day · score delta = 이벤트별 Weight × Score(다음 절). 좋아요 취소 같은 감소 이벤트를 어떻게 반영할지(대칭 차감 여부)는 결정 사항 — Writing Log에 근거.

SCORE MODEL

스코어 모델 — 가중치 합산

좋아요·구매·조회는 스케일이 달라 단순 합산 시 특정 지표가 전체를 지배합니다. 그래서 지표별 가중치(Weight)를 곱해 단일 점수로 합산합니다 — 서비스 전략이 곧 가중치입니다.

Score(p) = W(view)·Count(view) + W(like)·Count(like) + W(order)·Value(order)

총합 1이 되도록 설계 · W = Weight(가중치)
이벤트Weight (예시)Score
조회 view0.11 (가장 흔함 → 낮게)
좋아요 like0.21 (구매보다 약한 신호)
주문 order0.6~0.7price × amount (정규화 시 log)
⚠ 예시 수치를 그대로 베끼지 말 것 요구사항의 0.1 / 0.2 / 0.6은 예시입니다. 주문 Score를 price × amount로 두면 고가 상품이 조회·좋아요를 압도하므로 log 정규화 등으로 스케일을 맞출지 판단하고, 우리 서비스 기준으로 가중치를 정해 근거를 Writing Log에 남깁니다. (글감: "우리의 랭킹 지표는 이렇게 구성된다")

TIME QUANTIZATION · COLD START

시간의 양자화 & 콜드 스타트

랭킹은 언제부터 언제까지의 집계인지가 명확해야 의미가 있습니다. 단순 누적만 하면 오래된 상품이 계속 상위를 독식(롱테일)하고 신상품은 노출 기회를 잃습니다.

시간의 양자화 — 일간 키 분리

집계를 일정 단위(일·주·월)로 나눠 관리합니다. 이번엔 일간: 오늘 점수와 어제 점수를 ranking:all:20250906 / ranking:all:20250907처럼 키로 분리하고, TTL로 메모리를 관리합니다. 시간 단위로 잘라야 공정성과 신선도가 확보됩니다.

콜드 스타트 — 윈도우가 막 바뀐 순간

자정에 새 키로 넘어가면 점수가 0인데, 그 순간의 랭킹은 무슨 의미가 있는가? 윈도우 시작 시점엔 대부분 상품 점수가 0이라 랭킹이 의미 없어지고, 유저는 어제 인기 상품도 보길 기대합니다. 랭킹에 못 든 상품은 클릭·구매가 안 생기는 악순환에 빠질 수 있습니다.

해결 — Score Carry-Over

새 키 생성 시 전날 점수의 일부를 작은 가중치로 복사합니다. 가중치를 작게 둬 오늘 점수가 금방 상위로 올라갈 수 있게 합니다.

ZUNIONSTORE 예시 ZUNIONSTORE ranking:all:20250907 1 ranking:all:20250906 WEIGHTS 0.1 AGGREGATE SUM — 어제 키의 점수에 0.1을 곱해 오늘 키로 복사. 예: 어제 100/50 → 오늘 시작 10/5. Nice-to-Have 스케줄러로 23:50에 미리 다음 랭킹판을 생성하는 방식.

STEP 2 · READ PATH

Ranking API

ZSET을 읽어 랭킹을 제공합니다. 핵심은 ZSET에는 상품 ID·점수만 있으므로, 응답에는 상품 정보를 조합(Aggregation)해서 내려줘야 한다는 점입니다.

  • MUST랭킹 페이지 조회 — GET /api/v1/rankings?date=yyyyMMdd&size=20&page=1 — ZREVRANGE 기반 Top-N 페이지네이션
  • MUST상품 정보 Aggregation — 단순 상품 ID가 아니라 상품명·가격·브랜드 등 상품 정보를 조합해 반환
  • MUST상품 상세에 순위 추가 — 상품 상세 조회 시 ZREVRANK로 현재 순위 포함. 랭킹에 없으면 null
Aggregation 판단 포인트 Top-N 상품 ID로 상품 정보를 가져올 때 N번 조회 vs 일괄(IN) 조회, 그리고 R7 product_metrics·상품 캐시를 재사용할지 결정합니다. ZSET 조회는 빠른데 Aggregation에서 N+1이 나면 의미가 없습니다.
