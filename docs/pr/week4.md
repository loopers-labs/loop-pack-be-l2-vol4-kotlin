# [volume-4] 주문·결제·재고 예약 v2 및 쿠폰 적용 흐름 구현

## 📌 Summary
- 배경: 주문/결제/재고 흐름에서 외부 PG 호출, 재고 차감, 예약 만료, 결제 실패 복구가 하나의 트랜잭션처럼 다뤄지면 장애 상황에서 정합성 복구가 어렵다.
- 목표: 주문·결제·예약 상태를 분리하고, 재고는 예약 기반 atomic update로 처리하며, 쿠폰은 주문 생성 시 1회만 사용할 수 있도록 체크아웃 흐름에 통합한다.
- 결과: 결제 projection/payment event, 예약 재고, 결제 완료 재시도/예약 만료 배치, 쿠폰 도메인/API/체크아웃 적용, 동시성 테스트를 추가했다. 주문 스냅샷에는 상품/브랜드/금액/쿠폰 정보를 저장하도록 정리했다.

## 🧭 Context & Decision

### 문제 정의
- 현재 동작/제약:
  - PG 승인/검증/취소는 외부 네트워크 호출이므로 DB 트랜잭션 안에 둘 수 없다.
  - 주문 생성 시 실제 재고를 바로 차감하면 결제 지연/실패/취소 시 복구 기준이 흐려진다.
  - 쿠폰은 사용자 소유, 만료 여부, 사용 여부를 검증해야 하며 주문 1건당 1장만 적용 가능하다.
  - 동일 쿠폰/동일 상품에 대한 동시 요청에서 쿠폰 중복 사용과 재고 Lost Update를 막아야 한다.

- 문제(또는 리스크):
  - PG 승인 성공 후 내부 완료 처리가 실패하면 결제는 성공 가능성이 있는데 주문/재고 상태가 어긋날 수 있다.
  - 예약 만료, 사용자 취소, 결제 후 취소가 각각 다른 방식으로 재고를 복구하면 상태 전이 규칙이 분산된다.
  - 쿠폰 사용 처리를 주문 저장과 분리하면 주문은 실패했는데 쿠폰만 사용되거나, 반대로 쿠폰 중복 사용이 발생할 수 있다.
  - 결제 이력을 현재 상태만으로 덮어쓰면 장애 분석과 재시도 판단에 필요한 감사 로그가 부족하다.

- 성공 기준(완료 정의):
  - 주문, 예약, 결제 상태가 명확히 분리되고 상태 전이 규칙이 테스트로 검증된다.
  - 재고 예약/확정/반환/복구는 조건부 atomic update와 변경된 튜플 수 검증으로 처리된다.
  - PG 호출은 DB 트랜잭션 밖에서 실행하고, 호출 전후 상태관리를 통해 결제 흐름을 관리한다.
  - 쿠폰 발급/목록/관리 API와 주문 시 쿠폰 적용 흐름이 동작한다.
  - 네트워크 문제로 실패한 주문은 멱등성 있게 재시도할 수 있다.
  - 동일 쿠폰, 동일 상품 재고, 좋아요 수 동시성 테스트로 동시성 문제를 검증한다.

### 선택지와 결정
- 고려한 대안:
  - A: 주문 결제 시 실제 재고를 즉시 차감한다.
  - B: `reserved_quantity`로 재고를 먼저 예약하고, 결제 완료 후 실재고 차감으로 확정한다. 15분 뒤에도 결제가 완료되지 않은 예약은 만료시킨다.

- 최종 결정:

  B: 주문을 완료했는데 재고가 없다고 표시되는 것은 불쾌한 UX라 생각했다. 따라서, 결제 전에는 예약 재고만 증가시키고, 결제 완료 시 `stock_quantity`와 `reserved_quantity`를 함께 차감한다.

  - 예약 만료와 결제 완료 재시도는 `commerce-batch` job으로 분리했다.

- 트레이드오프:
  - `reserved_quantity`가 추가되면서 재고 조회와 주문 완료/취소/만료 경로가 모두 예약 재고 기준을 알아야 한다.
  - 재고 예약이라는 레이어가 추가되면서 장애 복구와 원인 추적에 복잡성이 늘어났다.

- 추후 개선 여지(있다면):
  - 결제 뿐만 아니라, 취소와 환불도 PG사를 거치는 작업이므로 상태관리를 여러번 쪼게 실패에도 견딜 수 있도록 해야 했는데, 그 부분이 나중에 생각났다.

## 🤔 고민한 점 / 막혔던 부분

1. **PG 호출과 DB 트랜잭션 경계.** 외부 호출을 트랜잭션 안에 넣으면 커넥션 풀 점유 시간이 길어져 장애가 발생할 수 있다. → 호출 전후 상태를 관리하고, 외부 호출 앞뒤 처리는 별도 트랜잭션으로 분리했다.
2. **실재고 차감 시점.** 결제 완료 시 바로 차감하는 방식은 단순하지만 UX를 해친다. → 결제 전에는 예약 재고만 잡고, 결제 완료 후 실재고 차감으로 확정했다.
3. **조건부 Atomic Update 적용.** 비관, 낙관 락 모두 여러 사람이 모이면 서비스 지연이 크게 발생할 수 있다. →  Atomic 연산은 락 경합 시 retry를 하지 않으면서도, 동시성 문제를 빠르게 해결할 수 있다.
4. **FAILED 주문 처리.** PG 승인 가능성이 있는 주문을 예약 만료로 자동 반환하면 결제 성공분과 내부 상태가 더 크게 어긋날 수 있다. → 결제 후 실패한 주문은 만료 대상에서 제외하고 추후 재시도해 다시 검증하도록 했다.
5. **쿠폰 동시성.** 쿠폰 상태를 읽고 엔티티를 변경하는 방식만으로는 동시에 들어온 주문에서 중복 사용 위험이 있다. → 발급 쿠폰 row를 조건부 atomic update로 `USED` 처리하고 실패 시 주문 전체가 실패하도록 했다.
