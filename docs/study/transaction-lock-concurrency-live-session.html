1

FOUNDATION

트랜잭션이란 무엇인가

트랜잭션은 "쪼갤 수 없는 하나의 작업 단위"입니다. 전부 성공하거나, 전부 없던 일이 되거나 둘 중 하나입니다.

계좌이체를 떠올리면 쉽습니다. "A에서 1만원 출금"과 "B에 1만원 입금"은 따로 떨어지면 안 됩니다. 출금만 되고 입금이 안 되면 1만원이 증발하니까요. 이 둘을 하나로 묶어서, 중간에 실패하면 통째로 되돌리는 것이 트랜잭션입니다.

transaction.sql
START TRANSACTION;
  UPDATE account SET balance = balance - 10000 WHERE id = 'A';
  UPDATE account SET balance = balance + 10000 WHERE id = 'B';
COMMIT;   -- 둘 다 성공 → 확정
-- 중간에 문제가 나면 ROLLBACK → 둘 다 없던 일로

ACID — 트랜잭션이 지키는 4가지 약속

속성의미한 줄 비유
Atomicity
원자성		전부 되거나 전부 안 되거나이체는 출금+입금 한 묶음
Consistency
일관성		규칙(제약)을 깨지 않은 상태로만 끝남잔액이 음수가 되지 않음
Isolation
격리성		동시에 돌아도 서로 간섭 안 함남의 중간 상태가 안 보임
Durability
지속성		커밋되면 장애가 나도 살아남음디스크에 박힌 기록
이 세션의 출발점동시성 문제는 결국 Isolation(격리성)을 어디까지, 어떻게 보장할 것인가의 문제입니다. 그리고 분산 환경(MSA)에서는 이 격리성이 공짜로 보장되지 않습니다 — 그래서 락과 Saga가 등장합니다.

UNDER THE HOOD

자바는 어떻게 DB에 쿼리를 날리나

우리가 쓰는 @Transactional 한 줄 아래에는 JDBC → 트랜잭션 매니저 → JPA → Hibernate가 층층이 쌓여 있습니다.

한 층씩 벗겨보기

① JDBC — 자바와 DB를 연결하는 가장 밑바닥 표준 API입니다. 트랜잭션을 직접 다루면 이렇게 생겼습니다.

RawJdbc.java
conn.setAutoCommit(false);  // 자동 커밋 끄기 = 트랜잭션 시작
// ... 쿼리 실행 ...
conn.commit();              // 확정
conn.rollback();            // 되돌리기

② @Transactional — 스프링이 위 JDBC 코드를 대신 써줍니다. 내부적으로는 transactionManager가 getTransaction() → begin → (성공) commit / (예외) rollback을 호출합니다. 우리는 어노테이션만 붙입니다.

③ JPA — "객체 ↔ 관계형 테이블"을 자동 변환하는 Object-Relational Mapping 명세입니다. 자바 객체 언어를 SQL로 바꿔주는 역할이고, JPA는 인터페이스(약속)일 뿐입니다.

④ Hibernate — 그 JPA 인터페이스의 실제 구현체입니다. 우리가 실제로 쓰는 엔진이죠.

flush — 쿼리가 실제로 DB에 날아가는 순간

Hibernate는 효율을 위해 변경을 모아뒀다가 한 번에 보냅니다. flush()가 바로 "지금까지 모은 변경을 DB로 쏘는" 시점입니다. 보통 커밋 직전에 자동으로 일어나지만, saveAndFlush()는 "지금 당장 DB에 반영하고 싶을 때" 씁니다 — 예를 들어 바로 다음 쿼리에서 그 결과가 필요하거나, DB가 채워주는 ID/제약 위반을 즉시 확인하고 싶을 때입니다.

실무readOnly의 두 얼굴 — DB vs Spring

DB의 read-only는 진짜로 막습니다 — INSERT/UPDATE를 시도하면 에러가 납니다.

Spring의 @Transactional(readOnly = true)는 강제가 아니라 보통 힌트입니다. Hibernate에게 "이건 읽기만 하니 변경 감지(dirty checking) 비용을 아껴라"라고 귀띔하는 정도죠. 그리고 현업에서는 이 플래그를 읽기 전용 복제 DB(Read replica)로 라우팅하는 신호로도 활용합니다 — 쓰기는 마스터(RW), 읽기는 복제본(RO)으로 분산.

3

CORE

동시성 제어 4가지 무기

"여러 사람이 마지막 재고 1개를 동시에 노린다." 이 충돌을 막는 방법은 크게 4가지이고, 상황에 따라 골라 씁니다.

전략언제 / 어떻게한 줄 핵심
낙관적 락
Optimistic		충돌이 드문 곳. version 컬럼으로 "내가 읽은 뒤 바뀌었나" 검사. 바뀌었으면 실패"부딪힐 일 별로 없다" — 실패해도 괜찮은 곳
비관적 락
Pessimistic		충돌이 잦은 곳. SELECT ... FOR UPDATE로 줄 세워 잠금거의 100% 성공. 단, 무한 대기 위험
원자적 업데이트
Atomic UPDATE		수량처럼 단순할 때. UPDATE ... WHERE qty >= ? 한 방DB가 알아서 한 줄로 안전 처리
분산 락
Distributed		여러 서버/인스턴스가 한 자원을 다툴 때. Redis 등으로 락여건이 되면 멘토의 기본 선택

낙관적 vs 비관적, 한 그림으로

동시성 결정을 내릴 때 보는 것 (질문자 박동윤 케이스)

  • 충돌 빈도 — 자주 부딪히나? 드물면 낙관적, 잦으면 비관적/원자적
  • 실패 허용 여부 — 한쪽만 성공시키고 나머지 즉시 실패해도 되나(예약), 아니면 모두 성공해야 하나(실제 차감)
  • 연산의 단순함 — 단순 숫자 증감이면 원자적 업데이트가 가장 간단
  • 자원 다툼 범위 — 한 DB 안인가, 여러 서버/인스턴스인가(분산 락)
  • 대기 비용 — 줄 세우면 throughput·커넥션 점유가 어떻게 되나
박동윤 케이스에 대한 멘토 피드백"결제창 진입 시 재고 예약 → 낙관적/분산 락, 실제 재고 차감 → 원자적 업데이트"는 좋은 시도이고 실제로 많이 씁니다. 다만 락을 섞어 쓰는 건 이상한 게 아니라 정상입니다. "구간마다 충돌 성격이 다르니 다른 도구를 쓴다"가 올바른 사고방식입니다.
놓치기 쉬운 점원자적 업데이트(UPDATE ... WHERE qty >= ?)도 결국 해당 로우에 락(row lock)이 걸립니다. 그래서 인기 상품 한 줄에 트래픽이 몰리면 "핫 로우(hot row)" 병목이 생깁니다 — 6번 Shopify 사례가 바로 이 문제를 푼 이야기입니다.
4

MYSQL

MySQL 락 옵션 — NOWAIT · SKIP LOCKED

SELECT ... FOR UPDATE에는 "잠긴 줄을 만나면 어떻게 할지" 옵션이 있습니다. MySQL 8.0.1부터 추가됐습니다.

NOWAIT 기다리지 않고 즉시 에러

잠긴 줄을 만나면 기본 대기시간(innodb_lock_wait_timeout)을 기다리지 않고 바로 실패. "대기가 의미 없는 비즈니스"에 적합. 두 번째 락 신청은 튕겨내고 클라이언트에 빠르게 오류 응답.

SKIP LOCKED 잠긴 줄은 건너뛰고 다음

잠긴 줄을 결과에서 빼고 비어 있는 다음 줄을 가져옴. "여러 워커가 처리할 다음 N건을 집어가는" 큐/작업 분배에 최적. Shopify 재고 예약의 핵심.

locking_reads.sql
-- 잠겨 있으면 기다리지 말고 즉시 에러
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;

-- 잠긴 줄은 건너뛰고 비어 있는 자리 1개를 집어옴
SELECT id FROM inventory_units
 WHERE item_id = 42 AND reserved = false
 FOR UPDATE SKIP LOCKED LIMIT 1;
타임아웃은 몇 초로? (김지은 질문)암묵적 정답은 "요청 전체 타임아웃보다 짧게"입니다. 예를 들어 클라이언트 요청 타임아웃이 60초라면, 락 대기는 그 안에 끝내고 에러를 돌려줘야 합니다. 그래야 클라이언트 쪽 타임아웃이 터지기 전에 "실패했다"고 깔끔히 응답할 수 있습니다. 명시 요구사항이 없으면 비기능 요구사항(SLA)에서 역산하세요.[1]

ARCHITECTURE

재고 차감 아키텍처

"결제 다 했는데 재고가 없습니다"라는 최악의 경험을 막으려면, 예약과 실제 차감을 분리해야 합니다.

왜 실제 차감을 동기로 안 하나?

원자적 업데이트도 결국 로우 락이 걸립니다. 인기 상품에 동시 요청이 몰리면 그 한 줄 앞에 모두가 줄을 서서 느려집니다. 그래서 보통 예약은 앞단에서 동기로 빠르게 처리하고, 실제 숫자 차감은 메시징(Kafka)으로 비동기 처리합니다.

비동기면 차감이 실패하면 어쩌나? (중원 질문)

이게 핵심 우려입니다. 재고와 주문이 서로 다른 도메인(자원이 2군데)이라 한 트랜잭션으로 못 묶거든요. 해법:

  • Kafka로 메시지 유실 방지 — 실패해도 재처리가 가능해 "어떻게든 성공"시킴
  • DB에 예약 요청 기록 — "나 예약했다"를 상태로 남김(아직 완료 아님)
  • 스케줄러가 재처리 — 미완료 상태인 요청을 주기적으로 읽어 실제 처리. 또 실패하면 다음 회차에 또 시도
  • 예약 한도(80%) — 전체 재고 중 일부만 앞단에서 예약 가능하게 하고, 주기적으로 조금씩 푸는 방식도

예약 만료 · Redis 장애는? (박동윤 질문)

"15분 안에 결제 안 하면 예약 만료"를 자바 DelayQueue로 짜면, 서버가 내려갈 때 만료가 실행되지 않습니다. Redis를 쓰더라도 Redis 역시 죽을 수 있고요. 멘토의 관점:

현실 직시Redis와 DB가 두 군데서 데이터를 관리하는 한, 분리된 환경에서 100% 싱크는 불가능합니다(AWS조차 99.999%). 100%를 원하면 "DB 하나 + 비관적 락"이면 되지만, 그러면 고객 경험이 망가져 손님이 떠납니다. 결국 트레이드오프 선택입니다.
  • 만료는 DB request + 스케줄러로 — DelayQueue 대신 DB에 기록하고 스케줄러로 돌리면 서버 재시작에도 보장됨
  • Redis가 죽으면 — DB를 원천(source of truth)으로 보고, 약간의 손해는 감수하며 DB 기반으로 Redis 복구(AOF/RDB 디스크 영속화 활용)
  • 관점 전환 — Redis의 역할은 "재고 차감"이 아니라 사실상 "결제로 넘어가기 위한 예약/검증". 실제 차감은 결제가 일어난 뒤에 한다

BIG TECH

Shopify — DB만으로 재고를 풀다

"Redis 없이 DB만으로 대규모 재고를?" 못 한다고들 했지만, Shopify가 핫 로우 문제를 구조로 우회해 해냈습니다.

재고 수량을 "숫자 1개"가 아니라 "1개당 1줄"로 쪼갠다.

— Shopify Inventory Reservations on MySQL[2]

핵심 아이디어: One-Row-Per-Unit

기존엔 item=42, qty=100 한 줄이라, 100명이 동시에 사려 하면 같은 한 줄을 두고 다툽니다(핫 로우). Shopify는 이걸 판매 단위 1개당 1줄로 펼칩니다. 그러면 동시 예약들이 서로 다른 줄을 잠그므로 진짜로 병렬 처리됩니다.

shopify_reserve.sql
-- 잠긴 줄은 건너뛰고, 비어 있는 재고 1줄을 집어 예약
SELECT id FROM inventory_units
 WHERE item_id = 42 AND reserved = false
 FOR UPDATE SKIP LOCKED LIMIT 1;
-- → 수백 건의 동시 예약이 서로 다른 줄을 잡고 동시에 진행

줄이 너무 많아지지 않게: Bounded Pool

재고가 1만 개라고 1만 줄을 다 만들면 테이블이 비대해집니다. 그래서 아이템·위치 조합당 최대 1,000줄만 풀(pool)로 유지하고, 다 소진되면 원천 재고 원장에서 한 번에 다시 채웁니다(singleflight로 thundering herd 방지).

  • One-row-per-unit — 핫 로우를 여러 줄로 분산 병렬
  • SKIP LOCKED — 잠긴 줄 건너뛰고 빈 줄 확보 무대기
  • 최대 1,000줄 풀 + 보충 — 테이블 비대 방지 경계
  • READ COMMITTED — 갭 락 데드락 회피(REPEATABLE READ에서 변경) 격리
  • 일관된 락 순서 — 순환 대기(데드락) 제거 순서
배울 점"DB는 핫 로우 때문에 느리다"는 통념을 데이터 모델을 바꿔 깬 사례입니다. 락 전략을 고르기 전에, 애초에 경합하는 자원의 모양 자체를 바꿀 수 있는지 먼저 생각해 볼 가치가 있습니다. (2025 블랙프라이데이 분당 $5.1M 트래픽을 단일 RDB로 소화)
7

DISTRIBUTED

자원이 2군데일 때 — Saga

하나의 DB 트랜잭션은 한 DB 안에서만 ACID를 보장합니다. 재고 서비스 + 주문 서비스처럼 자원이 갈라지면 트랜잭션으로 못 묶습니다.

MSA에서는 Isolation이 공짜가 아니다

세션에서 "MSA는 Atomicity뿐 아니라 Isolation도 보장 안 해준다"고 한 게 이 의미입니다. 서비스마다 DB가 따로라, 한 서비스의 중간 상태가 다른 서비스에 새어 보일 수 있습니다. 그래서 Saga 패턴을 씁니다 — 여러 로컬 트랜잭션을 이어 붙이고, 중간에 실패하면 보상 트랜잭션(compensating transaction)으로 되돌립니다.[3]

실무 해결책결제 타임아웃처럼 "우리는 실패로 봤는데 외부는 성공한" 불일치는 흔합니다. 그래서 우리 결제 데이터와 PG사 결제 데이터를 주기적으로 대사(비교)하고, 웹훅으로 최종 상태를 받아 보정하며, 그래도 어긋나면 CS를 통해 취소 처리합니다.

EXTERNAL API

외부 API(PG)는 트랜잭션 밖에서

결제 같은 외부 API 호출을 DB 트랜잭션 안에서 하면, 느린 외부 응답이 우리 DB 커넥션을 붙잡아 시스템을 마비시킵니다.

안티패턴 트랜잭션 안에서 외부 호출

트랜잭션을 연 채로 PG사를 호출 → PG가 느리면 우리도 같이 기다림 → 커넥션 점유 시간↑ → 동시 요청이 쌓이면 커넥션 풀 고갈 → 전체 장애.

권장 외부 호출은 트랜잭션 밖

① 트랜잭션으로 결제 데이터 준비/기록 → ② 트랜잭션 닫고 외부 API 호출 → ③ 결과를 별도 트랜잭션으로 반영. 커넥션을 외부 지연에 묶지 않음.

PG사도 죽는다 — SPOF와 다중화

"토스페이먼츠 하나만 쓰면 되지 않냐?" → 그 PG사가 장애 나면 결제 전체가 멈추는 단일 장애점(SPOF)이 됩니다. 그래서 여러 PG를 다중화합니다(1차 PG, 2차 PG, 밴사 등). PG 선정에는 수수료도 얽혀 있습니다.

멘토의 한마디"결제는 그나마 낫다. 정산(settlement)이 더 어렵고 싫다." 1·2차 PG, 밴사 구조의 복잡함은 결제 도메인을 직접 하게 될 때 파고들면 됩니다.

BATCH

배치와 스케줄러

"미완료 예약을 다시 처리한다" 같은 주기 작업은 배치로 돕습니다. 단, 서버가 여러 대면 동시성 문제가 생깁니다.

도구용도주의/특징
@Scheduled스프링 내장. 주기 실행 어노테이션서버 1대면 편함. 여러 대면 같은 작업이 중복 실행되어 동시성 문제
Spring Batch대량/안정적 배치 처리 프레임워크Jenkins 등으로 트리거를 걸어 동작시키곤 함
Airflow빅데이터/워크플로 오케스트레이션대규모 데이터 파이프라인 스케줄링
Databricks대용량 dump 데이터 처리·대사분석/대사 같은 무거운 작업
멀티 인스턴스 함정@Scheduled는 인스턴스마다 따로 돕니다. 서버 3대면 같은 시각에 3번 실행될 수 있어요. 그래서 분산 락으로 한 대만 실행하게 막거나, Spring Batch + 외부 트리거(Jenkins)로 실행 주체를 단일화합니다.

DESIGN DETAILS

설계 디테일 — enum · 제약 · 정책

코드 enum vs DB 데이터, 무슨 기준으로? (박동윤)

정답은 없지만 기준은 명확합니다. 비즈니스 로직이 달라붙느냐입니다.

DB로 관리 무한히 늘어나는 단순 분류

상품 카테고리/속성 같은 것 — 운동화, 샌들, 슬리퍼, 쪼리… 계속 늘어나고 각각에 특별한 코드 분기가 없음. 동적으로 추가돼야 함.

코드 enum 각자 비즈니스가 다른 상태값

PG사(toss/naver/kakao/nice…)처럼 늘어나긴 하지만 각각 다른 처리 로직이 있는 것. DB로 조회하지 않음 — DB가 잘못 들어가면 비즈니스가 오작동하니까.

경험담"모든 걸 동적으로" 하려고 대부분을 DB에 박은 프로젝트는 데이터 추적이 지옥이 됩니다. 단, 요구사항이 진짜 동적이면 그럴 수밖에 없는 경우도 있습니다 — 맥락이 결정합니다.

Enum에 로직을 넣을까, 전략 패턴으로 뺄까? (이중원)

쿠폰 FIXED/RATE 할인 계산을 enum 안에 넣을지, DiscountPolicy 인터페이스로 뺄지의 문제입니다.

enum에 로직 간단·유사할 때

람다/계산식이 짧고, enum별 함수가 하는 일이 동일·유사할 때. rule-base로 깔끔.

클래스로 분리 복잡·상이할 때

함수가 복잡해지거나 케이스마다 역할이 너무 달라지면 가독성이 떨어짐 → 구현체 클래스로 빼는 게 유지보수에 유리.

즉, 이중원님의 DiscountPolicy 분리 결정은 "계산이 타입마다 꽤 다르다"면 합리적입니다.[4]

중복 방지 — DB unique constraint를 최종 방어선으로? (김경민)

애플리케이션에서 이미 검증하더라도, 가능하면 DB unique 제약을 둡니다. 누군가 DB에 직접 데이터를 밀어넣을 가능성이 0%가 아니기 때문입니다 — "이중 방어"라기보다 운영 안정성을 위한 안전장치로 봅니다.

개인 의견(멘토)"DB 설정으로 비즈니스를 처리하는 것"은 선호하지 않습니다(국내 다수 회사가 안 하는 길이라 힘듦). 안전장치는 OK지만, 비즈니스 규칙을 DB 제약에 의존하는 건 다른 얘기. 한편 created_at은 인덱스 겸 비즈니스 용도로도 쓰지만, audit 컬럼은 비즈니스 용도가 아닙니다 — 시각이 필요하면 별도 컬럼을 파야 합니다.

서드파티가 많아질 때 복잡도 줄이기 (박동윤)

PG처럼 실패 케이스가 많은 외부 연동이 여러 개가 되면 복잡도가 폭증합니다. 줄이는 방향:

  • 상태 머신으로 모델링 — 각 외부 호출의 상태(요청/대기/성공/실패/보정중)를 명시적으로
  • 대사·웹훅·재처리를 공통 패턴으로 — 서드파티마다 다시 짜지 말고 추상화
  • 멱등성(idempotency) 확보 — 재시도해도 중복 처리되지 않게 키 기반 처리
  • "어쩔 수 없는 복잡성"은 인정 — 줄이되 없앨 수는 없음. 관측 가능성(로그·추적)에 투자

CHEAT SHEET

면접 대비 핵심 요약

면접에서 자주 묻는 개념들입니다. 한 줄로 답할 수 있게 정리했습니다.

  • 트랜잭션 — 쪼갤 수 없는 하나의 작업 단위. 전부 commit 아니면 전부 rollback (ACID)
  • JPA vs Hibernate — JPA는 ORM 명세(인터페이스), Hibernate는 그 구현체
  • flush — 모아둔 변경을 DB에 실제로 날리는 시점(보통 commit 직전)
  • 낙관적 락 — 충돌 드묾·실패 OK. version으로 사후 검사
  • 비관적 락 — 거의 100% 성공·정합성↑. 대기/데드락 위험
  • 원자적 업데이트 — 단순 수량은 UPDATE ... WHERE qty>=? 한 방. 단 로우 락은 걸림
  • 분산 락 — 여러 서버가 한 자원 다툴 때. 여건 되면 기본 선택
  • NOWAIT / SKIP LOCKED — 잠긴 줄을 즉시 에러 / 건너뛰기. 핫 로우·큐에 유용
  • 외부 API는 트랜잭션 밖 — 안에서 호출하면 커넥션 고갈로 전체 장애
  • Saga — 자원이 여러 서비스로 갈리면 보상 트랜잭션으로 정합성 유지
  • 대사(reconciliation) — 우리 기록과 외부(PG) 기록을 주기 비교해 불일치 보정
  • @Scheduled 멀티 인스턴스 — 서버 여러 대면 중복 실행 → 분산 락/Batch로 단일화

— 라이브 세션 멘토
