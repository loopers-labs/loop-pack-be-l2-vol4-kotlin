⚠️ 정정 (최신 결정 · 본 배너가 본문보다 우선)

아래 본문의 일부 표·다이어그램은 초기 설계 시점 기준이라 다음과 충돌할 수 있습니다. 충돌 시 이 배너가 정답입니다.

  • 과제 범위: domain + 경량 application + repository(인터페이스+구현) + 단위테스트. API · Controller · E2E · Admin 엔드포인트 · 웹 DTO(*V1Dto) · 인증 필터 · HTTP status 매핑은 범위 밖 (본문 §3 패키지 트리의 interfaces/·config/SecurityConfig·필터, §5~7의 Controller/Facade/시퀀스 Filter는 학습용 일반 예시로만 본다).
  • Value Object 3개뿐: BrandName · ProductName · Money. LikeCount·Quantity는 VO 아님 → 엔티티 필드 + 도메인 메서드(Product.likeCount: Long + like()/unlike(), Inventory.quantity: Long + decrease()/increase()). Price VO 없음 → Money(shared kernel com.loopers.domain.shared)로 통합, Product 가격·Order 금액 공용.
  • Facade 없음(본 과제): §9 "Facade 도입 기준: Order만" 및 본문 *Facade 표기는 무효 — 여러 application service를 조합하는 케이스가 없다. 도메인 조합은 Domain Service(ProductCatalogService, OrderPlacementService) + 경량 Application Service. (Facade는 결제·쿠폰 등 독립 use case가 여러 개 붙는 미래에만.)
  • 인증/식별자: §9 "인증" 행 및 §7 시퀀스의 필터·RequestAttribute("userId")·stub 정책 무효. 사용자 식별자는 service 메서드 파라미터(requesterId: Long)로 전달. 본인 검증: Like=ForbiddenException, Order=NotFoundException.

6요청 처리 흐름 — Domain Service의 자리

Evans 정통 DDD에서 Application Service는 Domain Service를 호출하고, Domain Service가 Entity와 Repository를 오케스트레이션합니다. Application Service가 Repository를 직접 들고 있는 게 아니라, 협업이 필요한 경우 Domain Service에 위임합니다.

아래 두 흐름을 나란히 보면 Domain Service의 자리가 명확해집니다. 단순 도메인은 Domain Service가 없어 Application Service가 Entity/Repository를 직접 다루고, 복잡 도메인은 Application Service와 Entity/Repository 사이에 Domain Service가 한 단 들어옵니다.

6.3 두 흐름의 책임 분담

레이어책임단순 케이스복잡 케이스
Controller HTTP 경계 (라우팅, 상태 코드, JSON 직렬화) 동일 — 얇은 매핑만
Facade (선택) 인증 컨텍스트 소비, DTO ↔ Command 매핑 없음 (Controller가 직접) 둠 (Order)

Repository (Port) 도메인 관점의 저장소 인터페이스 동일
RepositoryImpl (Adapter) JPA 구현체 — Port 구현, DIP 동일
왜 Domain Service가 "중간"에 있어야 하나
Evans, Domain-Driven Design Ch.5 — "행위가 어느 Entity·VO에도 자연스럽게 속하지 않을 때, 무상태(stateless) 협업자로 Domain Layer 안에 등장한다." Application 위에 두면 비즈니스 규칙이 Application Service로 새고, Entity 안에 욱여넣으면 단일 책임이 깨진다. 둘 사이의 무상태 협업자가 Domain Service의 정확한 자리.

7Order Use Case 시퀀스 — 가장 복잡한 케이스

주문 생성은 Product · Inventory · Order 세 도메인의 협업입니다. 본 프로젝트가 채택한 4단 패턴(id 참조 + Domain Service + 트랜잭션 + Snapshot)이 모두 적용되는 자리.

8Aggregate vs Soft Reference
