# 01. Requirements

## 1. 문서 목적

- 주어진 유저 시나리오를 기반으로 기능 요구사항, 예외 흐름, 정책/제약사항을 정리한다.
- 구현 전에 합의해야 할 정책과 예외 흐름을 명시한다.
- 이후 시퀀스 다이어그램, 클래스 다이어그램, ERD 작성의 기준 문서로 사용한다.

## 3. 유비쿼터스 언어

| 용어 | 설명 |
|---|---|
| 사용자 | 서비스를 이용해 상품을 조회하고 좋아요/주문을 수행하는 주체 |
| 어드민 | `ADMIN` role을 가진 사용자로, 브랜드/상품/주문을 관리하는 내부 운영자 |
| 브랜드 | 상품을 소유하거나 대표하는 판매/제조 단위 |
| 상품 | 사용자가 조회하고 주문할 수 있는 판매 대상 |
| 좋아요 | 사용자가 관심 상품을 표시하는 행위 |
| 주문 | 사용자가 하나 이상의 상품 구매를 요청한 결과 |
| 주문 상품 | 주문에 포함된 개별 상품 항목 |
| 재고 | 주문 가능한 상품 수량 |
| 품절 여부 | 고객에게 제공되는 상품 구매 가능 상태. 실제 재고 수량은 노출하지 않는다. |
| 상품 스냅샷 | 주문 시점의 상품명, 가격 등 주문 이력 보존을 위한 상품 정보 |
| 결제 | 주문 생성을 완료하기 위해 외부 결제 시스템에 승인 요청을 보내는 흐름 |
| 외부 결제 시스템 | 결제 승인/실패 결과를 반환하는 외부 연동 대상 |

## 4. API별 유저 스토리 및 유스케이스 흐름

API 경로를 기능을 식별하기 위한 기준으로 보고, 각 항목을 사용자 행위, 기대 동작, 예외 흐름을 중심으로 정리한다.

### 4.1 브랜드 조회

- API: `GET /api/v1/brands/{brandId}`

#### User Story

- 사용자는 관심 있는 브랜드의 정보를 확인할 수 있다.

#### Main Flow

1. 로그인 여부와 관계없이 사용자가 브랜드 ID로 브랜드 상세 조회를 요청한다.
2. 브랜드 ID가 존재하면 브랜드 ID, 브랜드명, 설명 등 고객에게 제공 가능한 정보를 반환한다.

#### Exception Flow

- 브랜드가 존재하지 않으면 조회 실패 응답을 반환한다.

---

### 4.2 상품 목록 조회

- API: `GET /api/v1/products`

#### User Story

- 사용자는 판매 중인 상품 목록을 조회할 수 있다.
- 사용자는 특정 브랜드의 상품만 모아볼 수 있다.
- 사용자는 최신순, 가격순, 좋아요순 정렬 기준에 따라 상품 목록을 조회할 수 있다.
- 사용자는 페이지 단위로 상품 목록을 조회할 수 있다.

#### Main Flow

1. 로그인 여부와 관계없이 사용자가 상품 목록 조회를 요청한다.
2. 시스템은 브랜드, 정렬 기준, 페이지 조건을 확인한다.
3. 브랜드 조건이 있으면 해당 브랜드의 상품만 조회한다.
4. 정렬 기준이 없으면 기본 정렬인 최신순으로 조회한다.
5. 시스템은 조건에 맞는 상품 목록을 페이지 단위로 반환한다.

#### Exception Flow

- 존재하지 않는 브랜드 ID로 필터링하면 조회 실패 응답을 반환한다.
- 지원하지 않는 정렬 기준이 전달되면 잘못된 요청 응답을 반환한다.
- 페이지 번호나 페이지 크기가 허용 범위를 벗어나면 잘못된 요청 응답을 반환한다.

---

### 4.3 상품 상세 조회

- API: `GET /api/v1/products/{productId}`

#### User Story

- 사용자는 상품을 선택해 상세 정보를 확인할 수 있다.
- 사용자가 확인할 수 있는 상품의 상세 정보는 상품명, 가격, 브랜드 정보, 좋아요 수, 품절 여부가 있다.

#### Main Flow

1. 로그인 여부와 관계없이 사용자가 상품 ID로 상품 상세 조회를 요청한다.
2. 시스템은 상품 ID에 해당하는 상품을 조회한다.
3. 상품이 존재하면 상품명, 가격, 브랜드 정보, 좋아요 수, 품절 여부 등 고객에게 제공 가능한 정보를 반환한다.

#### Exception Flow

- 상품이 존재하지 않으면 조회 실패 응답을 반환한다.

### 4.4 상품 좋아요 등록

- API: `POST /api/v1/products/{productId}/likes`

#### User Story

- 로그인한 사용자는 마음에 드는 상품에 좋아요를 등록할 수 있다.
- 이미 좋아요한 상품에 다시 좋아요를 요청해도 중복 좋아요가 생기지 않는다.

#### Main Flow

1. 로그인한 사용자가 상품 ID로 좋아요 등록을 요청한다.
2. 시스템은 요청 헤더를 기반으로 유효한 사용자인지를 식별한다.
3. 시스템은 상품 ID에 해당하는 상품이 존재하는지 확인한다.
4. 기존 좋아요가 없으면 좋아요를 생성한다.
5. 기존 좋아요가 이미 있으면 추가 생성 없이 성공으로 멱등하게 처리한다.

#### Exception Flow

- 로그인 사용자를 식별할 수 없으면 인증 실패 응답을 반환한다.
- 상품이 존재하지 않으면 좋아요 등록 실패 응답을 반환한다.

---

### 4.5 상품 좋아요 취소

- API: `DELETE /api/v1/products/{productId}/likes`

#### User Story

- 로그인한 사용자는 더 이상 관심 없는 상품의 좋아요를 취소할 수 있다.
- 좋아요하지 않은 상품에 취소를 요청해도 실패하지 않는다.

#### Main Flow

1. 로그인한 사용자가 상품 ID로 좋아요 취소를 요청한다.
2. 시스템은 요청 헤더를 기반으로 유효한 사용자인지를 식별한다.
3. 시스템은 상품 ID에 해당하는 상품이 존재하는지 확인한다.
4. 기존 좋아요가 있으면 좋아요를 취소 처리한다.
5. 기존 좋아요가 없으면 별도 처리 없이 성공으로 처리한다.

#### Exception Flow

- 로그인 사용자를 식별할 수 없으면 인증 실패 응답을 반환한다.
- 상품이 존재하지 않으면 좋아요 취소 실패 응답을 반환한다.

### 4.6 좋아요한 상품 목록 조회

- API: `GET /api/v1/users/{userId}/likes`

#### User Story

- 로그인한 사용자는 자신이 좋아요한 상품 목록을 확인할 수 있다.
- 사용자는 타 사용자의 좋아요 목록을 조회할 수 없다.

#### Main Flow

1. 로그인한 사용자가 좋아요한 상품 목록 조회를 요청한다.
2. 시스템은 요청 헤더를 기반으로 유효한 사용자인지를 식별한다.
3. 시스템은 요청 경로의 사용자 ID가 식별한 사용자와 일치하는지 확인한다.
4. 시스템은 해당 사용자가 좋아요한 상품 목록을 조회한다.
5. 시스템은 상품 정보를 페이지 단위로 반환한다.

#### Exception Flow

- 로그인 사용자를 식별할 수 없으면 인증 실패 응답을 반환한다.
- 본인이 아닌 다른 사용자의 좋아요 목록을 조회하려고 하면 접근 거부 응답을 반환한다.
- 페이지 번호나 페이지 크기가 허용 범위를 벗어나면 잘못된 요청 응답을 반환한다.

### 4.7 주문 요청 및 결제 흐름

- API: `POST /api/v1/orders`

#### User Story

- 로그인한 사용자는 하나 이상의 상품과 수량을 지정해 한 번에 주문할 수 있다.
- 주문 시, 적용 가능한 쿠폰을 사용할 수 있다.
- 사용자는 결제 결과가 반영된 주문 정보를 확인할 수 있다.
- 주문 이후 상품 정보가 변경되어도, 사용자는 주문 시점의 상품 정보를 주문 이력에서 확인할 수 있다.
- 주문 생성 이후 결제 승인을 통해 주문이 확정된다.

#### Main Flow

1. 로그인한 사용자가 주문할 상품 ID와 수량 목록을 전달해 주문 생성을 요청한다.
2. 시스템은 요청 헤더를 기반으로 유효한 사용자인지를 식별한다.
3. 시스템은 주문 상품 목록이 비어 있지 않은지 확인한다.
4. 시스템은 각 상품의 존재 여부를 확인한다.
5. 시스템은 각 주문 상품의 수량이 1 이상인지 확인한다.
6. 시스템은 각 상품의 재고가 주문 수량 이상인지 확인한다.
7. 모든 검증이 통과하면 상품 재고를 차감한다.
8. 만일 사용자가 쿠폰을 사용했다면, 주문 내역에 해당 쿠폰을 적용하여 최종 가격을 계산한다. 
9. 시스템은 주문 시점의 상품명, 가격 등을 스냅샷으로 포함해 `PENDING_PAYMENT` 상태의 주문을 생성한다.
10. 시스템은 외부 결제 시스템에 결제 승인을 요청한다.
11. 결제가 성공하면 주문 상태를 `PAID`로 변경한다.
12. 시스템은 결제 결과가 반영된 주문 정보를 반환한다.

#### Exception Flow

- 로그인 사용자를 식별할 수 없으면 인증 실패 응답을 반환한다.
- 주문 상품 목록이 비어 있으면 잘못된 요청 응답을 반환한다.
- 주문 수량이 1보다 작으면 잘못된 요청 응답을 반환한다.
- 존재하지 않는 상품이 포함되어 있으면 주문 생성 실패 응답을 반환한다.
- 재고가 부족한 상품이 하나라도 있으면 주문은 생성되지 않고 실패 응답을 반환한다.
- 외부 결제 시스템 연동에 실패하거나 결제가 거절되면 재고 차감을 되돌리고 주문 상태를 `PAYMENT_FAILED`로 변경한다.

### 4.8 주문 목록 조회

- API: `GET /api/v1/orders`

#### User Story

- 로그인한 사용자는 자신의 주문 목록을 조회할 수 있다.
- 사용자는 기간 조건을 통해 특정 기간의 주문 이력을 확인할 수 있다.

#### Main Flow

1. 로그인한 사용자가 주문 목록 조회를 요청한다.
2. 시스템은 요청 헤더를 기반으로 유효한 사용자인지를 식별한다.
3. 시스템은 조회 기간과 페이지 조건을 확인한다.
4. 시스템은 해당 사용자의 주문 목록을 기간 조건에 따라 조회한다.
5. 시스템은 주문 목록을 페이지 단위로 반환한다.

#### Exception Flow

- 로그인 사용자를 식별할 수 없으면 인증 실패 응답을 반환한다.
- 기간 조건이 올바르지 않으면 잘못된 요청 응답을 반환한다.
  - 예를 들면, 조회 시작일이 조회 종료일보다 늦은 경우
- 페이지 번호나 페이지 크기가 허용 범위를 벗어나면 잘못된 요청 응답을 반환한다.

### 4.9 주문 상세 조회

- API: `GET /api/v1/orders/{orderId}`

#### User Story

- 로그인한 사용자는 자신의 특정 주문 상세 정보를 조회할 수 있다.
- 사용자는 주문에 포함된 상품, 수량, 주문 당시 가격, 주문 상태를 확인할 수 있다.

#### Main Flow

1. 로그인한 사용자가 주문 ID로 주문 상세 조회를 요청한다.
2. 시스템은 요청 헤더를 기반으로 유효한 사용자인지를 식별한다.
3. 시스템은 주문 ID에 해당하는 주문을 조회한다.

## 5. 도메인 정책 및 제약사항

### 5.1 인증/인가

- 로그인 사용자가 필요한 기능은 `X-Loopers-LoginId`, `X-Loopers-LoginPw` 헤더로 사용자를 식별한다.
- 어드민 기능은 `X-Loopers-Ldap` 헤더로 사용자를 식별한 뒤, 해당 사용자의 role이 `ADMIN`인지 확인한다.
- 사용자는 타 사용자의 좋아요 목록과 주문 정보를 조회할 수 없다.

### 5.2 상품 조회

- 상품 목록은 페이지 기반으로 조회한다.
- 상품 목록 정렬 기준은 `latest`를 필수로 지원한다.
- `price_asc`, `likes_desc` 정렬을 지원한다.
- `likes_desc` 정렬은 집계 컬럼을 기준으로 사용한다.
- 고객 상품 조회 응답에는 실제 재고 수량을 노출하지 않고, 품절 여부만 제공한다.

### 5.3 좋아요

- 좋아요 등록/취소는 멱등하게 동작해야 한다.
  > 이미 좋아요한 상품에 POST, 좋아요하지 않은 상품에 DELETE 요청 모두 200으로 처리한다. 클라이언트가 상태를 별도로 관리하지 않아도 안전하게 호출할 수 있도록 한다.
- 동일 사용자는 동일 상품에 대해 하나의 좋아요만 가질 수 있다.
- 좋아요 취소는 물리 삭제가 아니라 soft delete로 처리한다.

### 5.4 주문

- 주문은 하나 이상의 주문 상품을 포함해야 한다.
- 주문 상품의 수량은 1 이상이어야 한다.
- 주문 수량은 상품의 현재 재고를 초과할 수 없다.
- 주문 생성 시 각 상품의 재고를 확인하고 차감한다.
- 주문 생성 시 사용자가 보유한 발급 쿠폰을 적용할 수 있다.
- 존재하지 않거나, 다른 사용자가 소유하거나, 이미 사용된 발급 쿠폰이면 주문은 생성되지 않는다.
- 재고는 결제 요청 전에 먼저 차감한다.
  > 결제 성공 후 재고 부족이 발생하는 상황을 피하기 위해 재고를 먼저 확보한다. 결제 성공 후 재고를 차감하는 방식은 결제 실패 시 재고 복구가 필요 없다는 장점이 있지만, 결제 성공 후 재고 부족이 발생하면 결제 취소/환불 보상이 필요하다.
- 재고가 부족한 상품이 하나라도 있으면 주문 전체가 생성되지 않는다.
  > 부분 주문은 사용자가 의도하지 않은 결과를 만들 수 있다. 전체 실패 후 사용자가 재시도하도록 유도한다. 재고 차감은 트랜잭션 내에서 처리되므로 실패 시 자동 롤백된다.
- 주문 정보에는 주문 시점의 상품 정보가 스냅샷으로 저장되어야 한다.
- 주문 목록 조회 시 조회 기간이 없을 때는 최근 3개월 간의 주문 목록을 제공한다.
- 결제는 외부 결제 시스템과 연동한다.
- 결제 실패 또는 외부 결제 시스템 연동 실패 시 차감된 재고를 되돌리고 주문을 실패 처리한다.

### 5.5 트랜잭션 및 일관성

- 쿠폰 사용, 재고 차감, 주문 생성은 하나의 일관된 처리 단위로 수행되어야 한다.
- 발급 쿠폰 사용은 `user_id`와 `used_at is null` 조건을 포함한 원자적 update로 처리하여 동일 발급분이 두 번 사용되지 않도록 한다.
- 외부 결제 시스템 호출은 DB 트랜잭션이 길게 유지되지 않도록 분리한다.
- 결제 성공 시 주문 상태 변경은 별도 처리 단위로 수행한다.
- 결제 실패 또는 외부 연동 실패 시 이미 차감된 재고는 DB 롤백이 아니라 보상 트랜잭션으로 복구한다.
- 보상 트랜잭션에서는 재고 복구와 주문 실패 처리가 함께 수행되어야 한다.
- 보상 처리 실패 가능성이 있으므로, 실제 운영 환경에서는 재시도 또는 이벤트 기반 보상 처리 방식을 추가로 검토한다.
- 동시 주문 상황에서도 재고 수량은 음수가 될 수 없다.

### 5.6 페이지네이션

- 목록 조회 API는 모두 페이지 기반으로 동작한다.
- 공통 페이지 조건은 페이지 번호 기본값 0, 페이지 크기 기본값 20을 따른다.
- 각 API에서 별도 명시가 없는 경우 위 기본값을 따른다.

### 5.7 응답 필드 차이 (고객 vs 어드민)

고객과 어드민에게 제공하는 응답 필드를 구분한다.

**브랜드**

| 제공 정보 | 고객 | 어드민 |
|---|---|---|
| 브랜드 기본 정보 (식별자, 이름, 설명, 로고 이미지) | ✅ | ✅ |
| 브랜드 관리 정보 (등록일, 수정일, 삭제일) | ❌ | ✅ |

**상품**

| 제공 정보 | 고객 | 어드민 |
|---|---|---|
| 상품 기본 정보 (식별자, 이름, 가격, 설명, 브랜드명, 좋아요 수, 품절 여부) | ✅ | ✅ |
| 실제 재고 수량 | ❌ | ✅ |
| 상품 관리 정보 (등록일, 수정일, 삭제일) | ❌ | ✅ |

**주문**

| 제공 정보                                         | 고객 | 어드민 |
|-----------------------------------------------|---|---|
| 주문 기본 정보 (주문 번호, 상태, 주문 상품 스냅샷, 총 결제 금액, 주문일) | ✅ | ✅ |
| 주문한 사용자 정보                                    | ❌ | ✅ |
| 주문 관리 정보 (수정일, 삭제일)                           | ❌ | ✅ |

### 5.8 브랜드 & 상품 관리 (ADMIN)

- 상품 등록 시 브랜드는 이미 등록된 브랜드여야 한다.
- 상품 수정 시 브랜드는 변경할 수 없다.
- 어드민은 삭제된 브랜드/상품도 조회할 수 있어야 한다.

### 5.9 삭제와 상태

- 브랜드/상품 삭제는 소프트 딜리트로 처리한다 (삭제 시점 기록).
  > 브랜드 삭제 시 연관된 주문 이력이 보존되어야 하기 때문에, 물리적으로 제거하면 문제가 발생할 수 있으므로 논리 삭제(soft delete)를 채택한다.
- 브랜드 삭제 시 해당 브랜드의 상품도 함께 Soft delete 처리한다.
- 이번 설계 범위에서 주문 상태는 `PENDING_PAYMENT`, `PAID`, `PAYMENT_FAILED`를 중심으로 관리한다.
  > 주문 생성 직후에는 `PENDING_PAYMENT` 상태이며, 외부 결제 시스템 승인 결과에 따라 `PAID` 또는 `PAYMENT_FAILED`로 전이된다.
- 주문 취소, 배송 처리와 관련된 상태 전이는 이번 설계 범위에서 제외하며, 해당 유스케이스가 추가될 때 확장한다.

### 5.10 쿠폰

- `Coupon`은 쿠폰 정책 원본이며, 정액/정률 할인 정책을 가진다.
- 주문에서 쿠폰을 사용할 때의 식별자는 쿠폰 정책 원본인 `Coupon.id`가 아니라 발급 쿠폰을 나타내는 `UserCoupon.id`이다.
- 쿠폰 정책은 생성 이후 변경할 수 없고, 표시 이름만 변경할 수 있다.
- `UserCoupon`은 사용자가 보유한 발급 쿠폰 1장을 의미한다.
- 동일한 `Coupon`은 한 사용자에게 여러 장 발급될 수 있다.
- `UserCoupon`은 최대 한 번만 사용할 수 있다.
- 주문 취소 등 보상 흐름에서는 사용된 `UserCoupon`을 다시 미사용 상태로 되돌릴 수 있다.
- 쿠폰은 주문에 사용한다.
