5

PG FAILURE CATALOG

외부 PG 대표 문제 카탈로그

외부 결제가 끼는 순간 생기는 문제는 정해져 있다. Stripe·토스페이먼츠·AWS·Microsoft 문서가 각각 같은 문제를 다른 이름으로 경고한다 — 여덟 개로 정리한다.

P1 — 타임아웃 = 실패가 아니라 "모름"

PG 호출이 타임아웃되면 결제가 안 된 게 아니라, 됐는지 안 됐는지 모르는 상태가 된다. 요청은 PG에 도착해 승인됐는데 응답만 유실됐을 수 있다. 이걸 실패로 간주하고 재고를 복원하면 — 돈은 나갔는데 주문은 없는 최악의 상태가 된다.

"네트워크 이슈나 타임아웃 문제로 응답을 받지 못했을 때도 안전하게 같은 요청을 다시 보낼 수 있습니다."

— 토스페이먼츠, 멱등키 가이드[2] (멱등키가 존재하는 이유 자체가 이 문제)

P2 — 재시도가 만드는 중복 결제

P1의 자연스러운 대응은 재시도다. 그런데 멱등성 없이 재시도하면 같은 결제가 두 번 실행될 수 있다. Stripe는 "connection error가 나면 같은 멱등키로 안전하게 반복 요청하라"고 하고, 첫 요청의 상태 코드와 응답 본문을 저장해뒀다가 그대로 돌려준다[1]. 토스페이먼츠도 동일하게 Idempotency-Key 헤더(최대 300자, 15일 유효)를 받아 "멱등키·API 키·주소·메서드 조합이 같은 요청"이면 실제 처리 없이 첫 응답을 반환한다[2].

주의토스페이먼츠는 "에러가 났다고 멱등키를 바꿔 재시도하는 것"을 위험이라 명시한다[2] — 키를 바꾸면 새 요청으로 취급되어 중복 결제가 된다. 멱등키는 "같은 시도"의 식별자이지 "요청 횟수" 카운터가 아니다.

P3 — 결제는 됐는데 내 쪽이 실패 (부분 실패)

PG 승인은 성공했는데 그 직후 우리 DB 갱신이 실패하면? PG의 돈과 우리 주문 상태가 어긋난다. 분산된 단계들은 원자적으로 묶이지 않으므로 보상(compensating transaction)이 필요하다. Microsoft는 보상 자체도 실패할 수 있으므로 "각 보상 단계를 멱등 커맨드로 설계하라", 그리고 "되돌릴 수 없는 단계(point of no return)는 모든 핵심 검증이 끝난 뒤에 두라"고 명시한다[6].

P4 — 웹훅은 중복되고, 순서도 어긋난다

비동기 통지(웹훅)를 쓰는 순간 두 가지가 보장되지 않는다. Stripe 공식 문서: "엔드포인트는 같은 이벤트를 한 번 이상 받을 수 있다 — 처리한 이벤트 ID를 기록해 중복을 막아라", "Stripe는 이벤트가 생성된 순서대로 전달됨을 보장하지 않는다"[4]. 토스페이먼츠도 "결제의 결과를 받으려면 반드시 웹훅을 연동해야 한다"면서 같은 비동기 불일치를 전제한다[3].

P5 — 금액 위변조: 클라이언트가 주는 금액은 믿지 않는다

토스페이먼츠 결제 흐름의 핵심 절차: "성공 URL의 쿼리 파라미터 값이 결제 요청에 보낸 값과 동일한지 확인하고 결제 승인 API를 호출", "결제 요청 전에 저장해 둔 임시 정보를 불러와 … 최종 결제 금액이 리다이렉트로 받은 금액과 같은지 확인"[3]. 쿠폰·적립금이 끼면 클라이언트가 금액을 조작할 유인이 커진다 — 승인 전에 서버가 저장·재계산한 금액과 대조하는 것이 가맹점 서버의 책임이다.

P6 — DB 트랜잭션 안의 외부 호출

PG 호출(수백 ms ~ 수십 초)을 @Transactional 안에서 하면, 그 시간 동안 DB 커넥션 1개 + 재고 비관락(FOR UPDATE) 행 락을 통째로 점유한다. PG가 느려지는 순간 커넥션 풀이 마르고, 같은 상품을 주문하는 모든 요청이 락 대기로 줄을 선다 — PG 장애가 그대로 우리 DB 장애로 전파된다. 이것이 §3 기준안이 트랜잭션을 둘로 쪼갠 이유이고, D1의 핵심 쟁점이다.

P7 — 재시도 폭풍: 재시도는 이기적이다

"Retries are 'selfish' — 클라이언트가 재시도할수록 서버의 시간을 더 써서 자기 성공 확률을 높인다."

— AWS Builders Library, Timeouts, retries, and backoff with jitter[5]

AWS는 다층 시스템에서 계층마다 독립적으로 3회씩 재시도하면 5계층에서 최하층 부하가 243배가 된다고 경고한다. 처방: "부작용 있는 API는 멱등성을 제공하지 않는 한 재시도하면 안 된다", 재시도 간격은 지수 백오프 + 지터, 타임아웃 값은 다운스트림 지연의 p99.9 같은 백분위 지표로 정한다[5].

P8 — 대사(reconciliation): 어긋남은 결국 생긴다

P1~P7을 다 막아도 PG 상태와 우리 주문 상태는 장애·버그·시간차로 어긋날 수 있다. 그래서 결제 시스템은 주기적으로 PG 측 거래 내역과 우리 주문을 대조하는 배치(대사)를 둔다. 미확정(UNKNOWN) 주문 정리(§2 UC7)가 그 최소 형태다.

D2 · 재고·쿠폰 선점 시점 (P3)

결제 전에 재고·쿠폰을 먼저 차감(선점)하나, 결제 성공 후에 차감하나.

A안 결제 전 선점

재고 차감·쿠폰 use()를 결제 전 Tx①에서 수행. oversell 0% — 결제 중인 재고를 남이 못 가져간다. 대신 결제 실패·이탈 시 복원(보상)이 필수가 되고, 결제가 길어지는 동안 재고가 잠긴 것처럼 보인다.

B안 결제 후 차감

결제 성공 후 Tx②에서 차감. 보상이 거의 불필요(결제 취소만). 대신 결제하는 사이 재고가 소진될 수 있다 — 돈은 냈는데 재고 없음이라는 더 나쁜 실패가 생기고, 그때 결제를 취소해야 하므로 보상이 사라지는 게 아니라 자리만 바뀐다.

Microsoft 보상 패턴은 "필요 자원에 단기 락을 미리 잡고 모든 자원 확보 후 작업하는 것이 보상 성공률을 높인다"고 기술한다[6] — A안의 구조다. 단 B안도 "point of no return(결제)을 검증 뒤로 미룬다"는 같은 문서의 원칙과 정합적이다. 어느 쪽이든 보상은 사라지지 않고 위치만 바뀐다는 것이 비교의 핵심.

D4 · 멱등성 — 누가 키를 만들고 어디에 저장하나 (P2 · P7)

두 레벨이 있다: (i) 우리 API의 멱등성(클라이언트가 주문 생성을 재시도해도 주문 1건) 과 (ii) 우리 → PG 호출의 멱등성(우리가 승인을 재시도해도 결제 1건).

옵션내용사례·근거
(a) (ii)만orderId 기반 키를 서버가 생성해 PG 호출에만 사용. 클라 재시도는 중복 주문 허용토스페이먼츠 멱등키는 가맹점 서버 → PG 호출용[2]
(b) (i)+(ii)클라가 Idempotency-Key 헤더 전송 → DB unique 컬럼으로 저장, 같은 키면 기존 응답 반환. PG 키는 (a)와 동일Stripe 공개 API 방식 — 키는 클라 생성 UUID, 첫 응답을 저장 후 재생[1]. Stripe는 키를 24h 보관, 토스는 15일[2]

Redis 없이는 (b)의 저장소가 DB가 된다 — idempotency_key unique 컬럼 또는 별도 테이블. Stripe는 "파라미터가 다른데 키가 같으면 에러"를 명시한다[1] — (b)를 택하면 이 검증도 같이 결정.

D5 · PG 불확정(타임아웃) 처리 (P1 · P8)

옵션내용트레이드오프
(a) 즉시 동기 재확인타임아웃 직후 PG 조회 API(또는 멱등키 재요청)로 결과 확인, 응답 전에 확정사용자는 답을 받고 끝. 단 조회마저 타임아웃이면? — 결국 (b)가 백업으로 필요
(b) UNKNOWN 보류 + 배치 확정주문을 불확정 상태로 두고 즉시 응답(처리 중). 배치가 주기적으로 PG 조회 후 PAID/FAILED 확정사용자 응답이 "확정"이 아님. 배치·상태(D3-b) 필요. P8 대사의 최소 구현이기도 함
(c) (a) 후 실패 시 (b)1회 즉시 재확인 → 그래도 모르면 UNKNOWN 보류가장 견고하나 두 메커니즘 모두 구현

AWS 지침과의 연결: 재시도는 멱등 전제 + 백오프·지터, 타임아웃 값은 다운스트림 지연 분포(p99.9)로[5]. 토스 멱등키 15일[2]은 (b) 배치가 한참 뒤에 재시도해도 같은 응답을 받을 수 있음을 의미한다.

D6 · 보상 방식 — 실패 시 무엇을 어떻게 되돌리나 (P3)

A안 인라인 즉시 보상

결제 실패를 안 즉시 같은 요청 처리 안에서 재고 increase + 쿠폰 복원 + FAILED 전이. 단순하고 즉각적. 단 보상 중 서버가 죽으면 그대로 유실 — 재시도할 주체가 없다.

B안 보상 작업 테이블 (DB 큐)

"무엇을 되돌릴지"를 같은 Tx에서 테이블에 기록 → 배치/스케줄러가 처리·재시도. Microsoft가 말하는 "진행 상황을 기록해 실패 지점부터 재개, 각 단계는 멱등"[6]의 DB-only 구현(transactional outbox와 같은 골격). 견고하지만 테이블+배치+멱등 보상 설계 필요.
