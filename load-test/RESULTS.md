# 주문 처리량 측정 결과 (2026-06-12)

## 목적

재고 비관락(FOR UPDATE)이 처리량에 미치는 영향을 실측해, "락 점유가 길어 성능 문제가 된다 → 재고를 별도 Tx로 분리(REQUIRES_NEW 선차감 + 보상)"는 가설을 검증한다.

## 환경

| 항목 | 값 |
|---|---|
| 서버 | AWS EC2 t3.micro × 1 (2 vCPU burstable, 1GB + swap 2GB), ap-northeast-2 |
| 구성 | 단일 인스턴스에 모두 동거: Spring app(-Xmx384m) + MySQL 8.0(docker) + Redis ×2(docker) + k6 |
| 부하 | k6 `constant-arrival-rate`, RATE=300/s 포화 주입(천장 탐지) + RATE=50/s 현실 부하 |
| 시나리오 | `k6/order-throughput-1m.js` — hot(단일 상품 1001) vs spread(상품 10개 분산) |
| 사전 조치 | ① 부하 계정 BCrypt cost 4 시드(cost 10이면 인증이 측정을 지배) ② `inventory.product_id` UK 추가(인덱스 없으면 풀스캔 락으로 비교 무효) |

> 한계: 부하 생성기(k6)가 서버와 같은 박스라 절대값은 보수적. **상대 비교(hot vs spread)가 본 측정의 결론.**

## 결과 (각 1분)

| 측정 | 처리량 | p50 | p95 | 실패율 |
|---|---:|---:|---:|---:|
| hot @300/s 포화 | **94.5/s** (5,934건) | 3.17s | 3.85s | 0% |
| spread @300/s 포화 | **143.0/s** (8,815건) | 2.09s | 3.10s | 0% |
| hot @50/s 현실 부하 | 50.0/s (3,001건) | **14.8ms** | 111ms | 0% |

정합성: 누적 주문 19,220건 = 재고 차감 19,220개 (오버셀/유실 0)

## 측정 v2 — 부하 생성기 분리 (k6는 로컬 Mac, 서버만 EC2)

v1은 k6가 서버와 같은 박스라 부하 생성 CPU가 서버 수치를 오염시켰다. v2는 k6를 로컬 Mac으로 분리하고(보안그룹 8080을 측정 PC IP로만 개방), CPU는 CloudWatch 5분 버킷 대신 **vmstat 5초 간격**으로 수집했다.

| 측정 (각 1분) | v1 (동거) | **v2 (분리)** | v2 p95 | v2 서버 CPU |
|---|---:|---:|---:|---:|
| hot 포화 (300/s) | 94.5/s | **93.0/s** | 4.52s | avg 94% / max 99% |
| spread 포화 (300/s) | 143.0/s | **156.3/s** | 2.64s | avg 95% / max 100% |
| hot 현실 부하 (50/s) | p50 14.8ms | p50 **18.2ms** (RTT 포함) | 23.3ms | ~50% |

정합성(v2 누적): 주문 19,349건 = 재고 차감 19,349개. hot 포화에서 실패 4건(0.06%) — 포화 한계 영역의 타임아웃 수준.

### 정정 — v1의 "hot 포화 CPU ~50% = lock-bound" 해석은 측정 아티팩트

vmstat 정밀 측정 결과 **hot 포화에서도 서버 CPU는 ~94%까지 차오른다.** v1의 ~50%는 CloudWatch 5분 버킷의 경계 흐림이 만든 오독이었다. 다만 lock-bound라는 결론 자체는 더 강한 증거로 유지된다:

1. **같은 CPU(~95%)를 태우고도 hot은 spread보다 40% 적게 처리한다** (93 vs 156/s) — 그 차이만큼의 CPU가 유효 작업이 아니라 락 대기 관리·컨텍스트 스위칭·직렬화 오버헤드로 새고 있다.
2. **k6 분리로 CPU가 확보되자 spread는 +13/s 개선(143→156, CPU-bound답게 CPU가 풀리면 따라온다). hot은 그대로(94.5→93, 오차 범위).** 단일 상품 천장은 CPU를 더 줘도 올라가지 않는다 — 천장의 원인이 CPU가 아니라 락 직렬화라는 직접 증거.

## 해석

1. **포화에서는 단일 상품 락 직렬화가 천장을 ~40% 깎는다** (156 → 93/s, v2 기준). 락 경합은 실재하고, CPU 추가로는 해소되지 않는다.
2. **그러나 현실적 부하(50/s)에서 hot 상품 p50 18.2ms(네트워크 포함)** — 단일 인기 상품에 초당 수십 건 수준이면 비관락은 병목이 아니다. t3.micro 최저 사양에서도 1분간 3,000건을 지연 없이 처리.
3. 단위 측정(H2)에서 락 점유는 요청당 ~0.6ms(전체의 37%)였고, EC2 실측 천장 ~93/s ≈ 락 점유 ~10ms/건(커밋 fsync + 포화 부하 중 오버헤드 포함)과 일관된다.

## 결론 — REQUIRES_NEW 선차감 + 보상 가설 기각

- 분리로 줄어드는 락 구간은 주문 INSERT 1건뿐 (점유의 일부, ~수 ms 미만)
- 대가: 보상 실패 시 영구 재고 불일치 + 커넥션 2배 점유(풀 고갈) + 본 Tx 실패 전 가짜 품절 윈도우
- 현실 부하에서 락은 병목이 아님이 실측으로 확인 → **현재 구조(단일 Tx① + FOR UPDATE 마지막 배치) 유지**
- 진짜 천장(~93/s)을 올려야 할 때의 순서: 경합을 DB 밖으로(Redis 원자 차감, 다음 주차) → 재고 행 샤딩 — Tx 분리·스케일업은 답이 아님 (CPU를 더 줘도 hot 천장이 안 올라가는 것이 v2에서 확인됨)
