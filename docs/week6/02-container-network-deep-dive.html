START

localhost = "나 자신"

localhost 는 "지금 말하는 그 사람 자신"을 가리키는 별명이다. 누가 말하느냐에 따라 대상이 달라진다.

컴퓨터에서 localhost(= 127.0.0.1)는 "나 자신한테 연결해"라는 뜻입니다. 편지 봉투의 받는 사람 칸에 "나"라고 쓴 것과 같아요 — 밖으로 안 나가고 자기에게 되돌아옵니다. 이 "나에게 되돌아오는 길"의 장치 이름이 lo(loopback, 루프백)입니다.

먼저 일반적인 한 컴퓨터에서 localhost 요청 하나가 어떻게 나가서 어떻게 돌아오는지 절차로 따라가 봅니다. 흔히 "HTTP의 host 가 localhost 면 루프백으로 보낸다"고 뭉뚱그리지만, 정확히는 두 단계가 따로 일어납니다:

  • ① 이름 해석 — localhost 는 IP가 아니라 이름입니다. OS가 /etc/hosts 를 보고 localhost → 127.0.0.1 로 바꿉니다. 네트워크 DNS가 아니라 로컬 파일 조회예요.
  • ② 커널 라우팅 — 그렇게 정해진 목적지 IP 127.0.0.1 을 커널이 라우팅표에서 보고 → lo 로 보냅니다. 여기가 진짜 "루프백 행" 분기점입니다.

즉 HTTP의 Host 헤더가 정하는 게 아닙니다(그건 요청 안의 메타데이터). 연결 전에 이미 정해진 목적지 IP가 loopback 행을 결정합니다. 전체 절차는:

정리하면 — "어디까지 가나": 리스너가 있으면 그 소켓까지(L7) 올라가 전달되고, 없으면 TCP 단(L4)에서 connection refused 로 끝납니다. "어디서 막히나": 막는 게 아니라, ④에서 이미 lo 로 보내기로 정해져 NIC·전선 쪽 경로엔 진입조차 안 합니다.

그럼 도커가 끼면 — 전체 구조에서 어느 레이어에서 갈리나

위 흐름은 "한 컴퓨터 안" 이야기입니다. 맥 + 리눅스 VM + 컨테이너가 모두 떠 있는 우리 환경에선, 이 lo 턴이 "누구의 lo냐"로 갈립니다. 컨테이너 안에서 localhost 를 부르면 그 트래픽은 위 절차의 ④에서 컨테이너 자신의 lo 로 턴해 — 컨테이너 밖으로 한 발도 안 나갑니다. 반대로 맥의 다른 프로그램에 닿으려면 localhost 가 아니라 다른 IP 로 eth0 → docker0 → VM NIC → en0 라는 진짜 NIC 경로를 타야 합니다.

셋 다 이름은 똑같이 localhost(127.0.0.1)지만 가리키는 대상이 전부 다릅니다. 이 셋이 왜 따로 생기고 왜 서로 못 닿는지를 — §4(3겹 구조)·§5(커널이 찍어내는 메커니즘)에서 그림으로 풉니다.

씨앗 한 줄"나"가 누구인지는 말하는 사람마다 다릅니다. localhost 도 똑같아서, 누가 localhost 라고 말하느냐에 따라 가리키는 컴퓨터가 달라집니다. 도커가 끼면 이 "말하는 주체"가 여러 겹으로 늘어나는 게 이 문서 전체의 핵심입니다.
2

KERNEL vs OS

커널 vs OS — 컨테이너는 뭘 들고 오나

OS = 커널 + userland. 컨테이너 이미지는 그중 userland만 들고 오고, 커널은 빌려 쓴다.

두 개념을 먼저 가릅니다. 커널은 하드웨어를 직접 다루는 핵심 한 덩어리(프로세스·메모리·네트워크 관리 + 시스템 콜 창구)이고, OS는 그 커널 위에 셸·라이브러리·명령어들(userland)을 얹은 전체입니다. 우리가 "우분투" "알파인"이라 부르는 건 대부분 이 userland 묶음이에요.

그래서이미지엔 커널도 loopback도 네트워크 스택도 안 들어 있습니다. 이미지는 "프로그램 파일 세트"일 뿐이고, 네트워크와 localhost는 커널이 런타임에 붙여줍니다 (§5). 그래서 이미지를 우분투→알파인으로 바꿔도 localhost 동작은 똑같아요 — 커널 소관이라서.
3

WHAT IS A CONTAINER

컨테이너 = 격리된 프로세스

컨테이너는 미니 컴퓨터도 VM도 아니다. 호스트 커널 위에서 "격리 옷"을 입은 프로세스일 뿐이다.

Docker 공식 문서는 컨테이너를 이렇게 설명합니다 — "Docker는 namespaces 라는 기술을 써서 컨테이너라 부르는 격리된 작업공간을 제공한다"[6]. 즉 컨테이너는 평범한 프로세스에 두 가지를 씌운 것입니다:

  • namespace — 그 프로세스가 볼 수 있는 것을 가림 (자기만의 파일시스템·프로세스 목록·네트워크). "독립된 컴퓨터처럼" 느껴지는 이유.
  • cgroup — 그 프로세스가 쓸 수 있는 양을 제한 (CPU·메모리).
4

ON MAC

맥에선 3겹 · 커널은 2개

맥은 컨테이너를 직접 못 돌린다. 그래서 도커가 리눅스 VM을 하나 띄우고, 컨테이너를 그 안에서 굴린다.

컨테이너는 리눅스 커널 기능이 필요한데 맥은 리눅스가 아닙니다(Darwin 커널). 그래서 Docker Desktop은 맥 위에 작은 리눅스 컴퓨터(VM)를 띄웁니다 — 공식 문서도 도커가 "컨테이너를 돌리는 리눅스 VM"을 구동한다고 명시합니다[5]. 결과적으로 구조가 3겹이고, 커널은 2개(맥의 Darwin + VM의 리눅스), localhost는 3개입니다.

자주 하는 오해"컨테이너의 localhost = VM의 localhost"가 아닙니다. 컨테이너는 VM 안에서 또 한 겹 격리돼 자기만의 localhost(③)를 씁니다. 컨테이너가 VM의 localhost(②)를 보는 건 오직 --network host 일 때뿐이고, 그래도 맥(①)엔 못 닿습니다.
5

MECHANISM

메커니즘 — 커널이 localhost를 찍어낸다

"커널은 하난데 왜 localhost가 여러 개?" — 모순이 아니다. 그게 namespace가 하는 일이다.

네트워크 네임스페이스는 커널이 찍어내는 "독립된 네트워크 한 벌"입니다. 한 벌 = {자기 인터페이스(lo 포함) + 자기 라우팅표 + 자기 포트 공간}. 커널은 이 한 벌을 여러 개 만들 수 있고, 만들 때마다 그 안에 새 loopback(127.0.0.1)을 자동으로 하나 넣습니다. 그래서 커널 1개여도 namespace 5개면 localhost 5개예요.

왜 격리되나 (메커니즘)

namespace의 정의 자체가 "격리된 view"입니다. 커널이 강제로 — namespace ③의 프로세스는 ③의 인터페이스만 보고, ③의 loopback 트래픽은 ③ 밖으로 절대 안 나갑니다. 그래서 컨테이너가 127.0.0.1 을 부르면 커널이 "넌 ③ 소속" → ③의 lo로만 보냅니다. 이게 컨테이너가 서로 격리되고 "각자 독립된 컴퓨터처럼" 보이는 장치입니다.

정리커널은 1개(VM), namespace·localhost는 컨테이너마다 1개. 격리는 커널이 "넌 네 칸만 봐"로 강제하는 것. 맥 localhost는 아예 다른 커널(Darwin) 이라 또 별개.
6

PACKET PATH

그 길은 어디서 막히나 — 계층·하드웨어

"막힌다"가 아니다. localhost 패킷은 자기 스택 안에서 한 바퀴 돌아 제자리로 올 뿐, 밖으로 나가는 길(NIC·전선)에 애초에 들어서지 않는다.

§1에서 본 그 절차(이름 해석 → 커널 라우팅 → lo 턴)를, 이번엔 OSI 계층과 하드웨어 관점으로 한 번 더 봅니다. localhost 와 다른 IP 가 각각 어느 계층까지 내려가는지 나란히 두면 "왜 안 나가나"가 분명해집니다.

하드웨어 관점 — lo는 하드웨어가 아니다

lo 는 물리 장치가 없는 순수 커널 소프트웨어입니다(전선도 칩도 없음). 반면 eth0(컨테이너)·en0(맥)은 진짜(또는 가상) NIC예요. 그래서 컨테이너가 맥으로 닿으려면, localhost(=lo, 턴)가 아니라 eth0 → veth → docker0(가상 브리지) → VM NIC → 맥 en0 라는 진짜 NIC 경로를 타야 합니다. 그리고 그 길은 IP 주소(=host.docker.internal)로만 진입합니다 — localhost 는 그 길에 안 들어섭니다.

"막힘"이 아니라 "길이 없음"방화벽이 가로막는 게 아닙니다. localhost 패킷은 L3에서 lo로 턴해 자기 namespace 스택 안에서 끝나므로, 다른 칸·다른 머신으로 가는 NIC 경로에 진입 자체를 안 합니다. 그래서 "왜 안 가나"의 답은 "갈 길로 안 들어서서" 입니다.
7

CROSSING

겹을 넘는 통신 — 다리 3개

각 칸의 localhost는 자기 안에 갇혀 있다. 겹을 넘으려면 전용 다리가 필요하다.

그런데 §1에서 본 "맥에서 localhost:8082 로 컨테이너에 접속"은 됩니다. localhost 가 경계를 넘어서가 아니라, 도커가 맥 쪽 localhost 에 포워더(중계 직원)를 심어놨기 때문입니다 — 그게 포트 publish(-p)의 정체입니다. 반대로 컨테이너 쪽 localhost 엔 그런 포워더가 (보안·정합성 때문에 일부러) 없어서, 맥으로 갈 땐 host.docker.internal 이라는 다른 이름을 씁니다.

  • ① 맥 → 컨테이너 : publish — -p 8082:8082. 맥 localhost:8082 → 도커 포워더 → 컨테이너. (commerce 가 pg 에 제출)
  • ② 컨테이너 → 맥 : host.docker.internal — 컨테이너에서 맥을 가리키는 특수 이름. localhost 는 자기 자신이라 못 씀. (pg 가 commerce 로 콜백)
  • ③ 컨테이너 ↔ 컨테이너 : 이름 DNS — 같은 사용자 정의 네트워크면 IP 대신 이름으로(임베디드 DNS, 127.0.0.11)[1].

방향별 정리 — 왜 콜백만 안 되나

APPLY

우리 작업에 적용

commerce ↔ pg-simulator. 누구를 컨테이너로 띄우냐에 따라 호스트네임이 갈린다 — 셋 다 동작한다.

오늘단일 PG · timeout

제출 호출에 timeout 하나면 A(둘 다 bootRun) 가 제일 빠릅니다. 네트워크 고민 0, Ctrl+C로 장애 즉시 재현.

곧멀티 PG · 반복 기동

멀티 PG로 가면 B(pg만 컨테이너) 가 균형점. callbackUrl만 host.docker.internal 프로퍼티로 빼면 됩니다.

전체 한 줄localhost = 자기 자신(namespace당 1개). 남을 부르려면 이름(컨테이너끼리) 이나 host.docker.internal(컨테이너→맥), 들어올 땐 publish(맥→컨테이너). 커널은 공유, localhost는 칸막이마다 따로 — 이 한 문장이 그림 1~9의 결론입니다.
→ 실전편으로 이어짐Docker 네트워크와 pg-simulator 로컬 띄우기이 메커니즘을 토대로, 실제 기동 명령(A/B/C)과 resilience 작업 준비.
