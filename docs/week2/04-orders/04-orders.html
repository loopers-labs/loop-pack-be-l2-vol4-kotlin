도메인 invariant
  • Order.items 최소 1개 — 출처 O-C6
  • OrderItem.quantity ≥ 1 — 출처 O-C5

  • Order 1 : N OrderItem (cascade persist) — 출처 O-C1

5시나리오 → API 시퀀스 액터 가로 컬럼 · 시간 위→아래

대표 시나리오에 대한 호출 흐름. 실선 = 호출, 점선(녹/적) = return / 에러 응답.

O-C1 사용자가 여러 상품을 주문한다 (정상 · 스냅샷 + 재고 차감)
AccountHeaderAuthenticationFilter 통과 → 트랜잭션 박스 구간 내에서 (1) Product 조회로 스냅샷 생성 → (2) Inventory 도메인의 차감 인터페이스 호출 → (3) Order/OrderItem 저장. 재고 정합성 자체는 Inventory 도메인 책임. 다이어그램의 점선 박스가 동일 트랜잭션 범위를 나타내며 Inventory 차감 호출도 같은 박스에 포함된다.

6결정 필요 항목

O-?1주문 상태 모델 (status enum 범위)

결제가 후속이라 본 주차에 어디까지 상태가 필요한가? 결제 없이는 CREATED 한 가지면 충분할 수도.

A. status 미도입 — 본 주차는 상태 없이 진행, 결제 도입 시 컬럼 추가
B. CREATED만 단일 값 — enum 자리 잡되 단일 값으로 시작 (확장 용이)
C. CREATED · PAID · CANCELLED 풀세트 — 결제 전인데 미리 만듦 (투기적, YAGNI 위반 가능)
B 추천 — 결제 단계에서 enum 추가만 하면 됨.

O-?2재고 차감 시점

큰 그림에서 결제가 후속이라 "주문 = 재고 차감"으로 둘지, "결제 완료 = 차감"으로 둘지. 차감 대상은 Inventory.quantity (02-product P-?4 결정에 따라 별도 도메인으로 분리됨).

A. 주문 생성 시 즉시 차감 — 주문 트랜잭션 내에서 InventoryService.decreaseAll(items) 호출. 요구사항 "주문 시에 재고 확인 및 차감 보장"에 가장 충실
B. 결제 시 차감 + 주문 시 예약(reserve) — Inventory에 reserved/available 분리 컬럼 도입. 빅테크 표준(Shopify available/committed/on_hand, Amazon ATP)에 정합. 본 주차에는 결제가 없어 과잉
A 추천 — big-picture 문구 그대로 받아냄. 결제 도입 시 B안으로 전환할 자리는 Inventory 도메인 내부에 둠 (Product/Order 인터페이스는 그대로).

O-?3동시 주문 경합 처리 (본 주차는 인터페이스만)

같은 상품에 동시 요청이 몰릴 때 Inventory.quantity -1 누락을 어떻게 막을지. big-picture "나아가며" 명시.

본 주차: 인터페이스/시그니처만 보장 (Order 트랜잭션이 Inventory 도메인의 검증 + 차감 인터페이스를 동기 호출). 동시성 구현 자체는 Inventory 도메인 내부 결정.
후속 선택지 (Inventory 도메인 내부에서 결정):
  • UPDATE inventory SET quantity = quantity - ? WHERE product_id = ? AND quantity >= ? + affected rows == 0 체크 (단일 DB 표준)
  • 비관락 (SELECT ... FOR UPDATE) — 선착순 쿠폰처럼 충돌 빈도 높을 때
  • 낙관락 (version 컬럼) — 충돌 드물고 재시도 비용 낮을 때
  • Redis 분산락 (Redisson) — multi-instance / multi-DB 환경
  • Kafka 직렬화 — 대규모 트래픽 (빅테크 사례: Coupang Vitamin MQ)
참고: 단일 DB에서는 atomic UPDATE가 분산락보다 단순/효과적 (MS Learn, Fresha Engineering, 우아한형제들 분산락 사용기 일관 권고).

O-?4스냅샷 범위 (어디까지 보존할지)

big-picture: "주문 정보에는 당시의 상품 정보가 스냅샷으로 저장". 어디까지가 "당시의 상품 정보"인가?

필수: productId, productName, unitPrice, quantity
강추: brandId, brandName — Brand=Tenant 미래 가정(O-F5)에서 brand별 매출 집계가 product/brand가 삭제된 후에도 가능해야 함
선택: productImageUrl (응답 표시용) — 본 주차는 보류, UI 요구 생기면 추가

O-?5사용자 응답 vs 관리자 응답 차이

brand-final.html과 동일 패턴 적용 가능 (B-?2 참고).

사용자: orderId, orderedAt, totalAmount, items(스냅샷)
관리자: 위 + userId, status, createdAt/updatedAt (집계: brand별/일자별 등은 미래)
구현: 응답 DTO 두 종 분리 (OrderResponse / OrderAdminResponse).

O-?6멱등키 (Idempotency-Key)

POST 재시도 시 중복 주문 방지. 일반적으로 Idempotency-Key 헤더로 처리.

본 주차: 미도입 — 결제 도입 시점에 PG 연동과 함께 도입
미래 영향: orders 테이블에 idempotency_key 컬럼 + UK 추가 가능

O-?7타 사용자 주문 접근 status (403 vs 404)

orderId가 존재하지만 본인 것이 아닐 때.

A. 403 FORBIDDEN — 의미 정합성: 존재하나 권한 없음
B. 404 NOT_FOUND — 정보 노출 방지: 타인 주문 존재 사실 자체를 숨김
B 추천 — 주문은 PII 성격이 강하고 ID enumeration으로 타인 주문 존재 여부 파악을 막는 것이 더 안전.

O-?8본인 주문 목록의 날짜 범위 default · 최대 제약

startAt/endAt이 없을 때, 또는 너무 넓은 범위일 때.

default: 둘 다 필수로 강제 (O-R3 가정) — 인덱스 활용 보장
max range: 최대 90일 등 제한 검토 — 본 주차는 제약 없이 시작, 성능 이슈 생기면 추가

O-?9OrderItem을 @Embeddable VO collection으로 vs 별도 엔티티

DB는 어차피 별도 테이블이라 영속성 동작은 비슷. 도메인 모델 표현 차이.

A. @Embeddable + @ElementCollection — OrderItem이 Order의 일부, 독립 식별 불필요
B. @Entity (Order @OneToMany OrderItem) — OrderItem 자체 id 보유, 관리자 조회 등에서 식별 가능
B 추천 — 관리자 응답에서 item 단위로 식별/표시할 가능성 고려, JPA cascade도 표준.

7미래 확장 마킹

O-F1결제 (PG 연동 · 멱등키 · webhook)

big-picture 명시: "결제는 과정 진행 중, 추가로 개발". 외부 PG 연동 + 멱등키 + webhook → 주문 상태 모델 확장.

이번 주 설계가 받아내야 할 것:
  • orders.status를 enum 자리로 둠 (O-?1 B안) → 결제 도입 시 enum 값 추가만
  • 재고 차감 시점이 주문 생성 시(O-?2 A안) → 결제 실패 시 보상 로직 필요해질 수 있음을 인지
  • idempotency_key 컬럼 자리는 비워두고, 결제 도입 시 추가 (O-?6)

O-F2주문 취소 / 환불 / 부분 환불

결제 후 단계. 상태 머신(PAID → CANCELLED, PARTIAL_REFUNDED) + 재고 복원 로직.

받아낼 것: Order/OrderItem이 불변 스냅샷이므로 환불은 별도 RefundLog 같은 이벤트 테이블로 분리 가능.

O-F3쿠폰 적용

big-picture "추가 비전" 명시. 발급 → 적용 → 사용 흐름이 주문 totalAmount 계산에 합류.

받아낼 것: totalAmount를 Σ(unitPrice × quantity)로 단순 계산하되, 후속에 appliedDiscount/couponId 컬럼 추가 자리 둠.

O-F4행동 데이터(주문) → 랭킹 / 추천 비동기 집계

big-picture "추가 비전" 명시. 좋아요/주문 행동을 비동기로 집계해 정렬/추천 모델로.

받아낼 것: orders/order_item이 시계열 기반(ordered_at 인덱스)이라 후속 집계 ETL이 쉽게 붙음. 도메인 이벤트(OrderPlaced) 발행 자리 잡기는 후속.

O-F5Brand staff (Brand = Tenant) — 자기 brand 주문 / 매출만 조회

big-picture "추가 비전" 명시. 각 Brand가 자기 운영자를 가지고 자기 brand 내 주문/통계만 접근.

이번 주 설계가 받아내야 할 것:
  • order_item에 brand_id 스냅샷 보존 (O-?4) → product/brand 삭제 후에도 brand별 매출 집계 가능
  • brand 정보를 product 내부에 비정규화하지 않음 → brand 변경/이름 충돌이 주문 기록 무결성을 깨지 않음
  • 관리자 응답 DTO 분리 패턴(O-?5)을 Brand staff용에도 확장 가능

O-F6Order Event 로그 — 상태 전이 이벤트 누적

결제 도메인 도입 시점에 같이 설계. 상태 전이 이벤트(ORDER_CREATED, PAYMENT_REQUESTED, PAID, SHIPPED, CANCELLED 등)를 별도 테이블에 누적.

설계 의도: snapshot은 OrderItem이 이미 보존하므로 event는 "무엇이 일어났는가"만 기록.
이번 주 받아낼 것: 기존 status 컬럼 모델 유지 — 본 주차는 Order에 별도 DELETED state를 추가하지 않음 (cancel/refund는 미래 항목, O-F2와 묶어 진행).
