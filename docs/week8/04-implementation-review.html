ROUND 8 · 구현 리뷰

코드는 설계대로 움직이는가
플로우 · 시퀀스 · 목적 매칭 · 장애 점검

PR #10에 올라간 실제 구현 코드(OrderQueueController · OrderQueueService · OrderQueueRepository · OrderQueueAdmissionScheduler)를 기준으로 그린 문서입니다. 상상도가 아니라 코드의 분기 그대로 — 플로우차트와 시퀀스로 동작을 확인하고, 과제 목적과 코드를 1:1 매칭한 뒤, 장애·엣지 케이스를 MECE로 전수 점검합니다.

1

CODE FLOW

코드 플로우차트 — 4개 진입점의 실제 분기

시스템에 들어오는 길은 정확히 4개입니다 — POST /queue/enter · GET /queue/position · 스케줄러 tick · POST /orders. 아래는 각 진입점에서 코드가 실제로 타는 분기입니다 (마름모 = 코드의 if 분기).

2

SEQUENCE 1 · WAIT → ADMIT

시퀀스 ① — 대기부터 입장까지

유저의 폴링 사이클과 스케줄러의 드레인 사이클은 서로를 호출하지 않습니다. 둘은 Redis 키에서만 만나고, 유저는 다음 폴링에서야 자기가 입장된 걸 발견합니다.

3

SEQUENCE 2 · VERIFY → PLACE → CONSUME

시퀀스 ② — 토큰 검증과 주문, 소모

주문 쪽 침습은 OrderController의 세 줄이 전부입니다 — 검증(Tx 밖) → place()(Tx 안) → 소모. OrderFacade와 그 아래 R7 파이프라인은 대기열의 존재를 모릅니다.

4

GOAL ↔ CODE

목적 ↔ 구현 매칭 — Must 12항목 전수

과제의 목적(Must 12항목 + 검증 3종)을 실제 코드 위치·테스트와 1:1로 매칭한 표입니다. 빈칸이 없는지가 이 표의 존재 이유입니다.

과제 목적 (Must)구현 위치검증 테스트
1. 대기열 진입 APIOrderQueueController.enter → ZADD NX (score=진입 시각)keepsOriginalScore_whenReEntering
2. 순번 조회 APIOrderQueueService.position → ZRANK+1givesWaitingDetails_whileWaiting
3. 중복 진입 방지Sorted Set member 유일성 + NX(score 보존) + 토큰 보유자 409keepsOriginalScore · rejectsReEntry_whileHoldingToken
4. 전체 대기 인원totalWaiting() → ZCARD, position 응답 포함givesWaitingDetails_whileWaiting
5. 배치 드레인 스케줄러OrderQueueAdmissionScheduler.admit — 100ms · on/off 프로퍼티capsAdmissionsPerTick_atBatchSize
6. 입장 토큰 발급 (TTL)Lua 안 SET entry-token:{userId} EX ttlexpiresToken_afterTtl · admitsInEntryOrder
7. 주문 API 토큰 검증OrderController.order 진입부 verifyAdmission → 409rejectsOrder_withoutAdmission
8. 주문 완료 후 토큰 삭제completeOrder → DEL, place() 성공 뒤에만 호출consumesToken_onOrderCompletion
9. 배치 크기 산정 근거queue.scheduler.batch-size/fixed-delay 프로퍼티 외부화 (근거는 WRITING-LOG)— (문서 산출물)
10. 예상 대기 시간ceil((rank+1) / admissionsPerSecond) — 배치×주기에서 역산givesWaitingDetails_whileWaiting
11. Polling 응답 통합QueuePositionInfo — 내 차례면 token 동봉 (ADMITTED)deliversToken_whenAdmitted
12. Polling 부하 고려nextPollSeconds 서버 지정 — clamp(예상대기/10, 1s, 10s)givesWaitingDetails (1~10s 범위 검증)
검증① 동시 진입 순서ZADD 원자성 + score 정렬assignsDistinctPositions (20 threads)
검증② 토큰 만료Redis TTL + 만료 유저 재진입(맨 뒤)expiresToken · reEntersAtBack_afterTokenExpiry
검증③ 처리량 초과 안정배치 상한 = 하류 유입 수도꼭지 (back-pressure)capsAdmissionsPerTick (10명 중 3명만)
목적과의 부합 — 한 문장 요약 과제의 목적은 "폭증 트래픽을 시스템이 감당하는 속도로 흘려보내라(back-pressure)"이고, 코드에서 그 속도는 스케줄러의 두 숫자(batch-size × fixed-delay)로만 결정됩니다. 유저가 아무리 몰려도 주문 API에 닿는 유량의 상한이 코드 구조상 이 수도꼭지를 넘을 수 없다는 것 — 그것이 15개 행이 증명하는 전부입니다.
5

FAILURE MODES · MECE

장애·엣지 전수 점검 — 4축 MECE

분할 축은 "누가 정상 경로를 깨뜨리는가"입니다 — ⓐ 인프라(Redis) ⓑ 우리 앱(스케줄러·요청 처리) ⓒ 유저 행동 ⓓ 입력·경계. 네 주체는 겹치지 않고, 이 밖에서 장애가 시작될 곳은 없습니다. 판정: 차단/자동회복 코드가 처리 · 수용+문서화 의도된 트레이드오프 · 한계 후속 과제.

ⓐ 인프라 — Redis가 깨질 때

케이스코드에서 벌어지는 일판정
Redis 다운 중 진입/조회/주문DataAccessException이 그대로 전파 → 5xx. 대기열을 우회해 주문이 새는 경로가 없음 (fail-close, 결정 ③ — 쿠폰 게이트키퍼의 fail-open과 반대)차단
Redis 다운 중 스케줄러 tickcatch (DataAccessException) → warn 로그 후 종료, 다음 100ms tick이 자동 재시도. 스케줄러 스레드는 죽지 않음자동회복
Lua 실행 도중 Redis 프로세스 사망스크립트는 원자 — 부분 실행이 영속·복제되지 않음. "꺼냈는데 토큰 없는 유저" 불가능차단
Redis 재시작 (데이터 유실)대기열·토큰 전부 증발. 유저는 다음 폴링에서 NOT_IN_QUEUE → 화면이 재진입 유도. 줄은 잃지만 정합성(이중 주문 등)은 깨지지 않음수용+문서화
replica lag로 낡은 순번 읽기발생 불가 — 모든 연산이 masterRedisTemplate(ReadFrom.MASTER) 단일 노드 대상차단

ⓑ 우리 앱 — 스케줄러·요청 처리가 깨질 때

케이스코드에서 벌어지는 일판정
스케줄러 중단 (설정 off·버그)큐가 배수되지 않고 고임. 폴링은 정상 동작하나 순번이 안 줄고 estimatedWait가 거짓말을 함. 감지는 Queue Depth(ZCARD) 지표 몫 — 모니터링 미구현한계
verifyAdmission 통과 후 place() 전 앱 크래시DEL 미도달 → 토큰 잔존 → 유저는 TTL 안에서 재시도 가능. 주문은 안 생겼으므로 정합성 문제 없음자동회복
place() 커밋 후 DEL 전 앱 크래시주문은 생성됐는데 토큰 잔존 → TTL(최대 5분) 동안 재주문 가능. 상한이 TTL로 유계 — 중복 주문 방어는 주문 도메인 몫(관심사 분리, 결정 ⑬과 동일 축)수용+문서화
다중 인스턴스에서 스케줄러 동시 실행Lua 원자라 같은 유저 이중 발급은 불가(한 번 꺼내지면 끝). 단 총 유량이 인스턴스 수 배가 됨 — 현재 단일 인스턴스 전제, 스케일아웃 시 리더 선출/분산 스케줄러 필요수용+문서화
tick 처리가 fixedDelay보다 오래 걸림fixedDelay는 "종료 후 100ms"라 tick 겹침(동시 실행)이 원천 불가차단
UUID 토큰 충돌키가 userId 기준(entry-token:{userId})이라 토큰 값 충돌은 동작에 무영향차단

ⓒ 유저 행동 — 예상 밖으로 움직일 때

케이스코드에서 벌어지는 일판정
대기 중 새로고침·재접속 (enter 재호출)ZADD NX no-op — score(순번) 보존. 테스트: keepsOriginalScore차단
토큰 보유 중 재진입 (파이프라이닝)enter 첫 줄 findToken 검사 → 409 ALREADY_ADMITTED. 테스트: rejectsReEntry차단
줄 안 서고 주문 직행 (우회)verifyAdmission → 409 ENTRY_TOKEN_REQUIRED. 테스트: rejectsOrder_withoutAdmission차단
토큰 만료 후 주문 시도GET nil → 409 → 재진입하면 새 score = 맨 뒤. 테스트: reEntersAtBack차단
주문 실패(재고 부족 등) 후 재시도completeOrder 미도달 → 토큰 유지 → TTL 내 재시도. 줄 다시 안 서도 됨자동회복
더블클릭 — 동시 주문 2발검증(GET)과 소모(DEL)가 분리라 둘 다 통과 가능. 수용 — 중복 주문 방지는 주문 도메인 멱등성 책임, GETDEL 원자화는 "실패=유지" 정책과 충돌(결정 ⑬)수용+문서화
진입 후 잠적 (유령 대기자)차례가 되면 어차피 팝 → 토큰 미사용 만료. 그 슬롯의 유량은 손실 — 만료분 추가 발급(보정) 미구현(Nice)수용+문서화
두 탭/두 기기 동시 entermember 유일성 — 한 자리만 차지. 동시성은 ZADD 원자성이 흡수차단
같은 ms 동시 진입 (score 동률)member 사전순 정렬 — 엄밀 FIFO 아님. ms 해상도에서 실질 영향 미미, 테스트도 "누가"가 아닌 "몇 명"을 검증수용+문서화

ⓓ 입력·경계 — 값이 이상할 때

케이스코드에서 벌어지는 일판정
userId 위조 (남의 순번 조회·주문)불가 — userId는 요청 body가 아니라 @RequestAttribute(ACCOUNT_ID) 인증 컨텍스트에서만 취득 (R7 결정 4 답습)차단
빈 큐에서 스케줄러 tickZPOPMIN이 빈 배열 반환 → admitted 비어서 로그 없이 조용히 종료차단
대기 인원 < 배치 크기있는 만큼만 꺼냄. 테스트: admitsOnlyExisting차단
토큰 개수 ≠ 배치 크기 (호출자 버그)require가 즉시 실패 — fail fast, 잘못된 발급이 Redis에 닿기 전 차단차단
미진입 유저의 position 조회token nil + rank nil → NOT_IN_QUEUE 응답 (예외 아님 — 화면이 진입 유도)차단
남은 한계 — 정직한 목록 (전부 checklist Nice와 연결) ① 스케줄러 사망 감지 없음 — Queue Depth(ZCARD)·발급률 지표가 후속. ② 만료분 추가 발급 보정 없음 — 유령 대기자만큼 유량 손실(정합성 문제는 아님). ③ 다중 인스턴스 배포 시 유량이 배수 — 단일 인스턴스 전제를 배포 문서에 명시해야 함. 세 건 모두 "정합성이 깨지는" 종류가 아니라 "유량·관측이 무뎌지는" 종류 — 마감(금 18:00) 안에서 의도적으로 미룬 항목입니다.
