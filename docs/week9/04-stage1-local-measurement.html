SCOPE

이 측정이 답한 질문

이번 로컬 런은 두 덩어리다 — EXP-02(Stage 1a 읽기 비용, 로컬에서 확정)와 Stage 1b 파이프라인 스모크(정합성 검증).

EXP-02는 "계산식 랭킹과 인덱스 랭킹의 읽기 비용이 데이터 규모에 따라 어떻게 갈라지는가"를 DB 레벨에서 잰다. Stage 1b 스모크는 "이벤트 발행 → Kafka → 컨슈머 → 점수 적재"의 파이프라인이 실부하에서 한 건도 안 새는가를 정산식으로 검증한다. 전자는 구조 비교, 후자는 정확성 검증 — 목적이 다르므로 결과 해석도 따로 한다.

해석 주의 — 절대값이 아니라 상대 비교모든 처리량 수치에는 로컬 docker CPU 천장이 끼어 있다. 믿을 것은 절대 처리량이 아니라 같은 조건에서의 상대 비교(10× 데이터에 처리량이 몇 분의 일로 떨어지는가)다. API 경유 처리량 천장(rps)은 AWS 본런에서 확정한다.
용어 — qps / rps / tpsqps는 SQL 쿼리 수(DB 레벨, mariadb-slap이 재는 값), rps는 HTTP 요청 수(k6가 재는 값), tps는 트랜잭션 수다. 이 문서의 EXP-02 수치는 전부 qps — DB에 직결로 때린 SQL 쿼리 처리량이다.

EXP-02 · READ COST

EXP-02 — 읽기 비용 실측 수치

mariadb-slap 동시성 32, ranking_exp 스키마. 단건 지연은 EXPLAIN ANALYZE, 처리량은 conc32 반복 실행으로 쟀다.

쿼리단건 (EXPLAIN ANALYZE)conc32 처리량
계산식 Top-20 · 1만 행2.15ms2,822 qps
계산식 Top-20 · 10만 행20.4ms267 qps
계산식 개별 순위 · 10만 행26.1ms (71,633행 필터 통과)279 qps
인덱스 Top-20 · 10만 행2.06ms (인덱스 룩업 20행)807 qps
인덱스 개별 순위 · 10만 행39.4ms (옵티마이저 uk 선택)31 qps
인덱스 개별 순위 + FORCE INDEX10.6ms (커버링 range 5만 엔트리)521 qps

판독 세 가지

① 계산식 Top-20은 선형으로 붕괴한다. 데이터 10×(1만 → 10만)에 처리량이 2,822 → 267 qps, 정확히 1/10이다. 읽을 때마다 전체를 집계하는 구조의 비용이 데이터 규모에 정비례한다는 것이 숫자로 확인됐다.

② 인덱스 Top-20 단건 2.06ms는 스케일과 무관하다. 10만 행에서도 인덱스 룩업 20행으로 끝난다 — 쓰기 시점에 점수를 계산해 두는 구조의 이득이 그대로 드러난다. 1만 행 계산식(2.15ms)과 같은 단건 지연을 10× 데이터에서 유지한다.

③ 핵심 발견 — 개별 순위인덱스를 걸어도 개별 순위 조회는 31 qps — 인덱스가 없는 Stage 1a 계산식(279 qps)보다 오히려 9배 나쁘다. Top-20을 살리려고 만든 구조가 개별 순위에서는 역효과를 냈다. 왜 그런지 다음 섹션에서 추적한다.

INVESTIGATION

31 qps 범인 추적 — 가설 소거 과정

"인덱스가 있는데 인덱스 없는 쿼리보다 9배 느리다"는 결과는 그대로 받아들일 수 없었다. 의심 가는 가설 다섯 개를 하나씩 소거했다.

가설판정소거 근거
인덱스가 잘못 걸림❌SHOW CREATE TABLE 확인 — uk(date, product) + idx(date, score DESC) 정상
데이터 분포 이상❌시드가 RAND()×1000 균등 분포, 기준 상품(50000)은 중앙값
점수 업데이트로 인덱스 열화❌측정 직전 TRUNCATE + INSERT 재시드 — 업데이트 이력 0
통계 낡음❌ANALYZE TABLE 후 재EXPLAIN — 그래도 uk 선택 (rows 49,938)
측정 중 락/쓰기 간섭❌유휴 확인(Threads_running 2, dirty 0) 후 SELECT만 실행. MVCC라 SELECT는 행 락에 안 막힘

결론 — 옵티마이저 코스트 모델의 오추정

다섯 가설이 전부 소거되고 남은 것은 실행 계획 자체다. MySQL 코스트 모델이 "uk ref로 5만 행 + score를 읽으러 클러스터드 인덱스 룩업 5만 회"를 "score 인덱스 커버링 range 스캔 5만 엔트리"보다 싸다고 오추정했다. FORCE INDEX로 score 인덱스를 강제하면 31 → 521 qps, 17배가 된다. 다만 FORCE INDEX로도 range 스캔 5만 엔트리, 즉 O(순위) 스캔 자체는 구조적으로 남는다 — 이 한계는 섹션 4에서 다룬다.

접근 패턴별 인덱스 매핑 — 세 번째 패턴만 미스

접근 패턴정답 인덱스옵티마이저 실제 선택
점 조회 — 내 점수uk(date, product)uk — 정답대로 동작
Top-20idx(date, score DESC)score 인덱스 — 정답대로 동작
score 범위 COUNT — 내 순위idx(date, score DESC) 커버링uk 오선택 — 유일한 미스

인덱스 설계 자체는 접근 패턴 두 개를 정확히 커버한다. 문제는 세 번째 패턴 — "score 범위를 세는 COUNT"에서만 옵티마이저가 uk 쪽으로 미끄러졌다는 것이다.

STRUCTURE

개별 순위는 왜 구조적으로 비싼가

순위는 저장된 값이 아니다. "정렬상 내 앞에 몇 개가 있는가"라는 관계다 — 그리고 관계는 저장하기도, 읽기도 비싸다.

rank 컬럼을 저장하는 접근은 성립하지 않는다. 한 상품의 점수가 변하면 그 사이에 있는 여러 상품의 순위가 전부 밀리므로 쓰기가 폭발한다. 그래서 RDB는 읽을 때 센다 — COUNT(score > 내 점수), 즉 비용이 O(내 순위)다. 순위가 5만이면 5만 엔트리를 세야 한다. 반면 Redis ZSET은 skip list가 정렬을 항상 유지하고 있어 ZREVRANK가 세지 않고 위치를 읽는다 — O(log N)이다.

이 비용이 문제가 되는 이유 — 호출 빈도

상품 상세 응답에 현재 순위 포함 — 랭킹에 없으면 null

— Week 9 MUST 요구사항

개별 순위 조회는 관리 화면의 가끔 쓰는 기능이 아니라 상품 상세 조회 빈도만큼 호출되는 경로다. 상세는 커머스에서 가장 뜨거운 읽기 경로 중 하나이므로, O(순위) 비용이 그 빈도로 반복되는 구조는 Stage 1 인덱스 방식의 명확한 한계다.

SMOKE FINDINGS

스모크가 잡아낸 본런 블로커 4건

스모크의 목적이 바로 이런 것들을 본런 전에 태우는 것이다. AWS에서 터졌으면 런 하나를 통째로 버렸을 문제 네 건을 로컬에서 잡고 전부 수정했다.

  • verify-ranking.sql 스키마 낡음 수정 완료 — order_count → sales_count 반영, event_handled를 구독별 GROUP BY로 수정.
  • sample-kafka-lag.sh 이중 결함 수정 완료 — 구독 분리 이전 그룹명이 남아 있었고, bash 예약 변수 GROUPS에 대입이 조용히 무시되는 함정까지 겹쳐 CSV가 헤더만 남고 있었다. LAG_GROUPS로 rename.
  • 주문 부하 order-ramp 직행 불가 수정 완료 — week8 대기열이 409(QUEUE:ENTRY_TOKEN_REQUIRED)로 차단. 본런 주문 암은 queue-order-flow로 교체. perfN 자격증명 시드가 레포에 없어(R8 때 infra에서 즉석 실행) perf-seed-queue-users.sql로 자산화(2만 계정).
  • 웜업 런도 --summary-export 필수 수정 완료 — 정산식의 V(view 수) 산출에 웜업 요청 수가 들어가므로 웜업 런에도 summary 파일을 남기도록 절차 수정.

LIMITATIONS

시나리오의 한계 — 이 숫자를 어디까지 믿을 것인가

좋은 측정 보고서는 숫자보다 숫자의 적용 범위를 먼저 말한다. 이번 수치에는 세 가지 한계가 있다.

① 기준 상품 고정(중앙값). 개별 순위 측정의 기준 상품을 중앙값(50000) 하나로 고정했다. 실제 상세 트래픽은 인기 상품에 쏠리므로 — 인기 상품은 순위가 높아 O(순위) 스캔이 짧다 — 실전 평균은 이 수치보다 좋을 것이다. 반대로 시드의 균등 분포는 실제 멱법칙 분포와 다르므로 롱테일 상품은 더 나쁠 수 있다. 본런에서는 순위 구간별(상위/중위/하위)로 나눠 기록할 예정이다.

② closed model(slap). mariadb-slap은 32개 연결이 응답을 기다렸다 다음 쿼리를 보내는 closed model이라 qps ≈ 32 ÷ 평균지연으로 결정된다. 본런 k6는 도착률을 강제하는 open model이므로 같은 조건이 아니다.

③ DB 직결. API 경유 비용(커넥션 풀 대기 · 톰캣 스레드 · 직렬화)이 전부 빠져 있다. API 경유 천장은 AWS 본런의 몫이다.

이 수치의 정확한 용도이번 숫자는 "중간 순위 상품 기준의 구조 비용 대조"다. 계산식 vs 인덱스, COUNT vs 인덱스 룩업의 상대 비교에는 유효하고, 절대 용량 산정에는 쓰지 않는다.
