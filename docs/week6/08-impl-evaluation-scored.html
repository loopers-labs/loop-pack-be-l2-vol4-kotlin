RUBRIC

평가 기준 — 7축 100점

"잘 짰다"를 감으로 말하지 않으려고, 이 과제의 본질(외부 장애 격리 + 결제 정합성)에서 7개 독립 축을 뽑고 가중치를 줬다.

축무엇을 보나배점
C1 · 장애 격리CB/Retry/Timeout/TimeLimiter 적절성, 멱등성 기준 재시도(비멱등 결제에 timeout 재시도 금지), fallback 전파 차단20
C2 · 정합성 회복reconcile 자동화(스케줄러), orderId 역조회, 거짓음성(타임아웃인데 결제됨) 복구, NOT_FOUND grace·재시도 상한20
C3 · 데이터 정합성FAILED 시 재고·쿠폰 보상, 동시 중복결제 차단(UNIQUE/락), 콜백 멱등15
C4 · 상태 모델링미확정(UNKNOWN)을 1급으로 표현했나, 상태머신 전이 명확성·역전 차단15
C5 · 트랜잭션 경계PG 외부 호출을 DB 트랜잭션 밖으로 뺐나(커넥션 점유 회피), 경계 분리 일관성10
C6 · 임계값 근거40% 함정 회피(실패율 임계 > 40), k6·Grafana 측정 기반 결정 vs 휴리스틱10
C7 · 코드 품질도메인-인프라 분리, 본문↔코드 일치, 보안(콜백 인증·cardNo)10
채점 철학가산점이 아니라 감점식이다. "있으면 만점"이 아니라 "이 과제가 요구하는 함정(이중결제·거짓음성·40% 실패율·커넥션 점유)을 피했는가"로 깎는다. 그래서 화려한 모니터링보다 정합성 회복(C2)·장애 격리(C1)에 배점이 크다.

TIER 1 · 70점+

상위 티어

minbo265 — RestClient + 멱등 재시도74점

특징 — 유일하게 RestClient 사용. 내부 상태는 PENDING/SUCCESS/FAILED 3개로 단순하게 두되, "미확정의 종류"를 boolean pgRequestAttempted + Outcome(TIMEOUT/NOT_ATTEMPTED)로 분리해 복구 스케줄러가 사각지대를 구분한다.

무엇을 고려했나 — 재시도 대상을 "성공률"이 아니라 "중복결제 안전성"으로 골랐다. 5xx(HttpServerErrorException)만 화이트리스트로 재시도하고 read timeout은 의도적으로 제외(거래 생성됐을 수 있어 재시도 시 이중결제). 멱등성은 order_id UNIQUE로 INSERT 단계에서 차단.

장점

  • 멱등 기준 화이트리스트 재시도 (C1 16)
  • 스케줄러 + orderId 역조회 + attempts<5 + 경보 (C2 16)
  • fallback이 예외 대신 결과타입 반환 → 전파 차단

감점

  • 쿠폰 원복 코드/테스트 미확인 (재고만)
  • k6·Grafana 측정 없음 (C6 3)
  • 콜백 무서명(금액대조만 일부 방어)

sung260 — timeout=UNKNOWN 1급 + grace73점

특징 — 상태 6종(REQUESTING/PENDING/SUCCEEDED/FAILED/UNKNOWN/REQUEST_FAILED). timeout을 실패가 아닌 UNKNOWN으로 기록하고, 결제요청 POST는 아예 재시도하지 않는다(중복거래 원천 차단). 회복은 상태조회로만.

무엇을 고려했나 — 거짓음성을 성급히 실패로 굳히지 않으려고 NOT_FOUND 120s grace를 뒀다. PG_TRANSACTION_NOT_FOUND && REQUESTING/UNKNOWN && grace 경과 3조건 모두 충족해야 REQUEST_FAILED 확정. 요청용/조회용 CB를 물리적으로 분리해 쓰기 CB가 열려도 복구 조회는 동작. 동시결제는 uk_payment_active_order(order_id, active_marker)로 차단.

장점

  • 거짓음성 처리 11명 중 최정교 (C2 17)
  • UNKNOWN 1급 + 예외→상태 매핑 (C4 14)
  • 요청/조회 CB 분리, active_marker UNIQUE

감점

  • 보상 트랜잭션 전무 (C3 8)
  • 복구 재시도 횟수 상한 없음 → 영구 떠돌 위험
  • 측정 없음 (C6 2)

호준88 (Kotlin) — reconcile + 측정의 정석72점

특징 — @Retry+@CircuitBreaker, 동기 실패는 runCatching이 흡수해 txKey=null PENDING 유지. 핵심은 reconcile: 스케줄러(10s) + orderId 역조회 + 거짓음성 복구 + 2건 이상이면 멱등위반 알람(자동처리 금지).

무엇을 고려했나 — 임계값을 k6 + Grafana + Alertmanager로 측정해 결정하려 했고, CB 실패율을 70으로 둬 40% 함정을 피했다.

장점

  • reconcile 완성도 최상 (C2 17)
  • 유일하게 Alertmanager 경보까지 (C6 7)
  • CB 70 — 40% 정상실패 위로 여유

감점

  • 본문 "50" / 코드 "70" 모순 → 측정 신뢰성 훼손
  • 본문 mermaid의 recheckCount 단계적 autoFail 미구현
  • RetryableException 전체 재시도(timeout 포함) → 이중결제 여지

TIER 2 · 55~68

중위 티어

재희87 (Kotlin) — 코드품질·보상 최고, 플로우 순서가 약점68점

특징 — 도메인 Payment(순수)와 인프라 PaymentEntity를 enum까지 분리(가장 깔끔). fallback의 is CoreException 분기로 도메인 예외는 503으로 안 뭉갠다. 유일하게 재고+쿠폰 둘 다 보상(OrderCancellation).

무엇을 고려했나 — 재시도 화이트리스트(IOException), aspect 순서(@Retry⊃@CB)를 주석으로 명시. 그러나 PG-first(PG 호출 후 저장)라 접수 후 저장 전 장애 시 고아 결제가 생기는데 reconcile에 orderId 역조회가 없어 못 잡는다.

장점

  • 재고+쿠폰 완전 보상 (C3 14)
  • 도메인/인프라 분리·fallback 분기 (C7)

감점

  • PG-first 고아 + orderId 역조회 부재 (C2 8)
  • cardNo 평문 저장, 본문↔코드 다수 불일치

byun258 — 유일한 TimeLimiter + k6 최다65점

특징 — Feign CB 자동 + 유일하게 TimeLimiter 600ms 적용. fallbackFactory를 CB OPEN vs 일시장애 2단으로 분류해, CB 열린 상태에서 retry가 HALF-OPEN 프로브를 소진하는 문제를 차단. 콜백 body의 status를 불신하고 PG에 재조회(위조 방어).

무엇을 고려했나 — k6 6종으로 sliding-window type·retry×CB·커넥션풀을 실측(풀 타임아웃 7.02%→2.37%). 측정 근거 최다.

장점

  • TimeLimiter로 slow-call 능동 차단 (C1 16)
  • k6 정량 측정 최다 (C6 9)
  • 콜백 불신 재조회

감점

  • 콜백·복구를 Tx 안에서 PG 호출 (requestPayment와 모순, C5 6)
  • 보상 전무, UNKNOWN을 cardType 값에 욱여넣음

seung263 — 세 입구→단일 converge60점

특징 — 콜백·keyed 폴링·keyless 정산 세 입구가 한 converge로 수렴. 멱등 도메인 전이가 중복·순서뒤바뀜을 흡수. 서킷 집계를 record-exceptions 화이트리스트로 인프라 예외만 한정(비즈니스 실패가 "PG 장애"로 둔갑 방지).

장점

  • 단일 수렴점 + keyless 복구 트랙 (C2 15)
  • record-exceptions로 40% 함정 영리하게 회피

감점

  • 보상 전무 (C3 5)
  • ShedLock 없어 다중 인스턴스 시 중복 스캔

KWB255 — @ExternalSystemGuard 캡슐화58점

특징 — 자작 메타 어노테이션 @ExternalSystemGuard + Aspect로 CB+Retry를 한 겹 뒤에 숨김. PG 클라이언트는 resilience4j를 모르고, 모든 외부 실패를 단일 503으로 정규화. PROCESSING 중간 상태로 멱등성을 상태머신화.

장점

  • 관심사 캡슐화 우아 (C7)
  • PG-side userId+orderId UNIQUE 멱등

감점

  • 수동 reconcile만(스케줄러 없음, C2 10)
  • 콜백 무인증 + callbackUrl 하드코딩

game264 — PaymentConfirmer 단일 빈 + TSID56점

특징 — 확정 로직을 PaymentConfirmer 단일 빈으로 추출(비관락+멱등+주문 cascade를 한 Tx). 콜백·reconcile이 이 빈을 공유. 앱 생성 TSID를 PK로.

장점

  • self-invocation 프록시 함정을 빈 분리로 정공법
  • 카드 마스킹/원본 이중 표현

감점

  • Feign timeout 미설정 + TimeLimiter 없음 → 지연장애 무방비 (C1 11)
  • 스케줄러 없음, 보상 위임(미포함)

kmkim266 — ABORTED 1급 개념55점

특징 — ABORTED + failureCode==null 조합으로 "PG 미도달"을 1급으로 표현. TransactionTemplate 3단 분리로 PG 대기 중 커넥션 비점유. 정상 전이용 markSuccess()와 복구 전용 applyPgResult()를 분리.

장점

  • 미도달 상태의 의미론적 모델링 (C4 13)
  • TxTemplate 3분할 (C5 9)

감점

  • 보상 전무 + min-calls 기본100 vs window10 충돌(CB가 안 열림)
  • 콜백 무검증(HMAC 없음, 본문 자인), 자동복구 없음

TIER 3 · 하위 · 내 구현

하위 티어 · 내 구현

나 (현재) — 기반은 최상위, 회복탄력성이 비었다47점

특징 — 유일하게 2-PG failover(PG-A/PG-B) + 명시적 UNKNOWN enum + "timeout·5xx는 failover 금지"(이중결제 함정 회피) 정책. Model A(주문과 분리된 결제 호출, 서버가 금액 확정), cardNo 비영속(PCI).

무엇을 비웠나 — resilience4j 임계값(C1)·reconcile(C2)·보상(C3)을 의도적으로 DEFERRED. 그래서 UNKNOWN을 1급으로 만들어놓고도 그걸 해소할 reconcile이 없어 영구 미해결로 남는 게 현재 최대 구멍.

강점 (이미 보유)

  • UNKNOWN 1급 상태머신 (C4 13)
  • Facade 무Tx + 분할 + PG 밖 (C5 9)
  • 2-PG failover·이중결제 함정 정책 (남들 없음)

비운 곳 (반영 대상)

  • reconcile 전무 (C2 2) ← 1순위
  • resilience4j 임계값 (C1 8)
  • 재고/쿠폰 보상 (C3 6)
전략적 함의내 구현은 남들이 안 한 2-PG failover·UNKNOWN 1급을 가졌고, 남들이 한 resilience4j·reconcile·보상이 비었다. 즉 상보적 — 09번 리포트에서 sung260의 grace, minbo265의 멱등 재시도, 재희87의 보상을 내 UNKNOWN/failover 위에 얹으면 상위 티어로 직행한다.

Sooche262 — 안티패턴 집합25점

특징 — String 상태, 코드트리 2개 혼재. PG를 DB 트랜잭션 안에서 호출 + 스케줄러가 orderId 역조회 없이 재결제(이중결제) + 설정이 yml/properties/test 3곳 모두 다른 값.

반면교사이 구현의 가치는 "하지 말아야 할 것"의 카탈로그다 — ① 외부 I/O를 Tx 안에 두지 말 것, ② reconcile은 역조회지 재결제가 아님, ③ 설정은 단일 소스. 셋 다 다른 구현이 정확히 반대로 해서 점수를 받았다.
