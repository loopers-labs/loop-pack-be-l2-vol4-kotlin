CONCEPT

도커 네트워크 개념

localhost 는 "지금 말하는 그 사람 자신"을 가리키는 별명이다. 누가 말하느냐에 따라 가리키는 대상이 달라진다.

먼저, localhost 가 뭔가 — 제일 쉽게

컴퓨터에서 localhost(= 127.0.0.1)는 "나 자신한테 연결해"라는 뜻입니다. 편지 봉투의 받는 사람 칸에 "나"라고 쓴 것과 같아요 — 그 편지는 밖으로 안 나가고 자기에게 되돌아옵니다. 이 "나에게 되돌아오는 길"의 장치 이름이 lo(loopback, 루프백)입니다. 그림에서 lo 라고 적힌 칸이 바로 이거예요.

여기서 핵심 한 가지. "나"가 누구인지는 말하는 사람마다 다릅니다. 내가 "나"라고 하면 나고, 친구가 "나"라고 하면 친구죠. 컴퓨터의 localhost 도 똑같아서, 누가 localhost 라고 말하느냐에 따라 가리키는 컴퓨터가 달라집니다. 그리고 도커가 끼면 이 "말하는 주체"가 여러 겹으로 늘어나는 게 핵심입니다.

이 환경은 사실 3겹이다 (제일 중요)

맥에서 도커를 쓰면, 겉보기엔 컴퓨터 1대지만 속은 3겹입니다. 왜냐하면 도커는 맥 커널을 직접 못 쓰기 때문입니다 — 컨테이너는 리눅스 커널의 기능이 필요한데 맥은 리눅스가 아니거든요. 그래서 도커는 맥 위에 작은 리눅스 컴퓨터(VM)를 하나 몰래 띄우고, 컨테이너를 그 안에서 돌립니다. 공식 문서도 도커가 "컨테이너를 돌리는 리눅스 VM"을 구동한다고 명시합니다[5]. (그러니 "도커가 맥 자원을 쓴다"는 절반만 맞아요 — CPU·메모리는 맥에서 빌려 쓰지만, 컨테이너가 올라타는 커널은 맥이 아니라 그 VM의 리눅스 커널입니다.)

그 3겹은 이렇고, 겹마다 자기만의 "나(localhost)"가 따로 있습니다 — 이게 그림 1의 전부입니다:

제일 중요한 한 줄컨테이너가 localhost 라고 말하면 → 그 컨테이너 자신을 가리킵니다 (맥이 아님!). 그래서 컨테이너가 localhost:8080 을 부르면 맥의 commerce-api 가 아니라 자기 안의 8080을 찾다가 실패합니다. 이게 "콜백이 안 온다"의 진짜 원인입니다.

그럼 겹을 어떻게 넘나 — 다리 2개 + 컨테이너끼리 1개

각 겹의 localhost 가 자기 안에 갇혀 있으니, 겹을 넘으려면 전용 다리가 필요합니다. 이 환경에서 쓰는 건 딱 이만큼입니다:

  • ① 바깥 → 안 (맥 → 컨테이너): 포트 publish — -p 8082:8082 로 열어두면, 맥에서 localhost:8082 를 부를 때 도커가 그 요청을 컨테이너 안 8082로 넣어줍니다. commerce 가 pg 에 결제를 제출하는 길.
  • ② 안 → 바깥 (컨테이너 → 맥): host.docker.internal — 컨테이너에서 "맥"을 가리키는 특수 이름. localhost 로는 자기 자신만 가리키니 이 이름을 대신 씁니다. pg 가 commerce 로 결과를 콜백하는 길.
  • ③ 컨테이너 ↔ 컨테이너: 이름으로 찾기 — 같은 네트워크에 함께 붙은 컨테이너끼리는 IP 대신 이름으로 서로를 찾습니다(도커의 임베디드 DNS, 127.0.0.11)[1].

이 ③번 "이름으로 찾기"가 가능한지 아닌지가, §2에서 기본 bridge vs 사용자 정의 bridge를 가르는 핵심입니다.

DRIVERS

도커 네트워크 종류

도커는 네트워크를 만드는 방식(드라이버) 6종을 내장한다. 로컬 단일 호스트에선 사실상 bridge 하나만 쓴다.

공식 문서가 정리한 내장 드라이버는 다음과 같습니다[1]. 우리 상황(맥 1대에서 로컬 테스트)에 직접 쓰는 건 bridge 이고, 나머지는 "이런 게 있다"만 알아도 됩니다.

드라이버공식 설명우리 상황에서
bridge기본 네트워크 드라이버. 단일 호스트 안 컨테이너들을 잇는다이걸 쓴다
host컨테이너와 호스트 사이의 네트워크 격리를 제거맥에선 제약 (아래)
none컨테이너를 호스트·타 컨테이너로부터 완전히 격리안 씀
overlay여러 도커 데몬(Swarm)을 가로질러 연결멀티 호스트용
ipvlan컨테이너를 외부 VLAN에 연결안 씀
macvlan컨테이너가 호스트 네트워크의 물리 장치처럼 보이게안 씀

bridge 안에서도 둘로 갈린다 — 기본 vs 사용자 정의

같은 bridge라도 기본(default) bridge 와 사용자 정의(user-defined) bridge 는 결정적 차이가 하나 있습니다 — 이름 기반 DNS. 공식 문서는 "User-defined bridges provide automatic DNS resolution between containers" 라고 명시합니다[2]. 즉 사용자 정의 bridge에선 컨테이너를 이름으로 부를 수 있고, 기본 bridge에선 이름 조회가 실패합니다(IP를 직접 써야 함).

host.docker.internal — 컨테이너에서 호스트로 가는 이름

컨테이너에서 호스트(내 Mac)에서 도는 서비스로 닿고 싶을 때 쓰는 특수 이름입니다. 공식 문서: "To connect to services running on your host, use the special DNS name: host.docker.internal" — 이건 "호스트의 내부 IP로 해석된다(Resolves to the internal IP address of your host)"[3]. §1에서 본 "localhost는 경계를 못 넘는다"의 정확한 해결책이 바로 이것입니다.

맥/윈도우 주의 · host 드라이버Docker Desktop은 컨테이너를 리눅스 VM 위에서 돌립니다 — 공식 문서도 "이 인터페이스(docker0)는 실제로는 가상 머신 안에 있다"고 설명합니다[4]. 그래서 리눅스에서 호스트 격리를 없애 localhost를 공유하게 해주는 --network host 가, 맥에선 그 "host"가 사용자 Mac이 아니라 VM이라 리눅스처럼 동작하지 않습니다. 맥에선 localhost 공유로 우회하는 길이 막혀 있고, 그래서 host.docker.internal 이 정답입니다.
3

PER-NETWORK

네트워크 종류별 통신

네트워크마다 "누가 누구와, 어떤 주소로" 통신할 수 있는지가 다르다. 로컬에서 만나는 4가지를 그림으로.

같은 "통신"이라도 네트워크 종류에 따라 컨테이너끼리 어떻게 찾는지(IP·이름·불가)와 외부와 어떻게 닿는지가 갈립니다. 자주 쓰는 4개를 한눈에 비교합니다.

네트워크컨테이너 ↔ 컨테이너외부 ↔ 컨테이너 / 범위
기본 bridgeIP로만 (이름 ✗)publish 포트 · 단일 호스트
사용자 정의 bridge이름 DNS ✓publish 포트 · 망 단위 격리
host호스트 네트워크 통째 공유호스트 포트 직접 (맥은 VM)
none불가 (lo만)완전 격리
overlay여러 호스트 넘어 가능멀티 호스트(Swarm)
macvlan / ipvlanLAN에 실제 장치처럼물리 LAN에 직접
범위 밖overlay(여러 도커 호스트를 한 네트워크로 — Swarm)와 macvlan·ipvlan(컨테이너를 물리 LAN의 장치처럼 노출)은 멀티 호스트·물리망용입니다[1]. 우리는 맥 1대에서 도는 단일 호스트 작업이라 이 셋은 쓰지 않습니다.
우리 작업에 적용commerce 와 pg 가 둘 다 컨테이너면 → 사용자 정의 bridge 에 붙여 이름으로(C안). bootRun 으로 띄우면 → 애초에 도커 네트워크를 안 거치니 localhost 로 끝(A안). pg만 컨테이너면 → 들어갈 땐 publish, 나올 땐 host.docker.internal(B안).

OUR SCENARIO

지금 상황의 선택지와 결과

우리 시나리오의 핵심은 방향이 둘이라는 점이다 — 제출(commerce → pg)과 콜백(pg → commerce).

pg-simulator는 결제 제출을 받으면 1~5초 뒤 commerce-api로 비동기 콜백을 쏩니다(POST body의 callbackUrl). 그래서 호출이 양방향이고, "누가 컨테이너고 누가 호스트냐"에 따라 각 방향에 쓸 호스트네임이 달라집니다. 세 선택지를 봅니다.

선택지별 명령과 결과

선택지제출 / 콜백 호스트네임대가
A · 둘 다 bootRunlocalhost ↔ localhost네트워킹 고민 0 · 멀티 PG 시 포트 수동
B · pg만 컨테이너localhost(매핑) / host.docker.internalcallbackUrl 프로퍼티 1줄
C · 둘 다 컨테이너이름 DNS ↔ 이름 DNScommerce-api 매번 재빌드
A · 둘 다 bootRun (가장 빠른 시작)
# 인프라(MySQL/Redis/Kafka)는 도커로
docker-compose -f ./docker/infra-compose.yml up -d
# pg-simulator · commerce-api 는 각각 bootRun (--args 필수)
./gradlew :apps:pg-simulator:bootRun --args='--spring.profiles.active=local'
./gradlew :apps:commerce-api:bootRun --args='--spring.profiles.active=local'
# 장애 시뮬레이션: pg 터미널에서 Ctrl+C → fallback 확인
B · pg만 컨테이너 (멀티 PG에 유리 · 균형안)
# pg-simulator 를 이미지로 (Dockerfile 없이 Spring 플러그인 기본 제공)
./gradlew :apps:pg-simulator:bootBuildImage --imageName=pg-simulator:local
# 같은 이미지를 포트만 다르게 — 멀티 PG(8082/8092)도 한 줄씩
docker run -d -p 8082:8082 --name pg-a pg-simulator:local
docker run -d -p 8092:8082 --name pg-b pg-simulator:local
# commerce-api 는 bootRun 유지(빠른 수정). 콜백 URL만 호스트로:
# application.yml → pg.callback-base-url: http://host.docker.internal:8080
선택지 C둘 다 컨테이너로 묶고 싶다면

사용자 정의 bridge에 둘 다 올리면 §2의 이름 DNS 로 localhost 고민이 통째로 사라집니다. 다만 commerce-api(우리가 계속 고치는 앱)도 이미지가 되어 수정 때마다 재빌드가 듭니다.

C · 사용자 정의 bridge
docker network create loopers-net
docker run -d --name pg-simulator  --network loopers-net pg-simulator:local
docker run -d --name commerce-api  --network loopers-net commerce-api:local
# 제출: http://pg-simulator:8082  ·  콜백: http://commerce-api:8080

그래서 무엇을

오늘단일 PG · timeout

닫힌 과제가 "제출 호출에 timeout 하나"라면 A(둘 다 bootRun) 가 제일 빠릅니다. Ctrl+C로 즉시 장애를 만들어 fallback을 확인하는 루프가 가장 짧습니다.

곧멀티 PG · 반복 기동

멀티 PG(O9)나 통합 기동을 보면 B(pg만 컨테이너) 가 균형점입니다. callbackUrl을 host.docker.internal 로 빼는 프로퍼티 1줄이, commerce-api를 매번 재빌드하는 C보다 훨씬 쌉니다.

결론세 선택지 모두 동작합니다. 갈리는 건 "되냐 안 되냐"가 아니라 호스트네임과 반복 비용입니다. localhost를 글자 그대로 고집하는 비용(프록시·리눅스 전제)이 가장 크고, host.docker.internal 한 줄이 가장 쌉니다.
