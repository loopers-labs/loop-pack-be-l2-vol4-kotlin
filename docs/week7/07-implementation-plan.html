BIG PICTURE

전체 구조 한눈에

Producer가 비즈니스 데이터와 함께 outbox를 커밋하면, 릴레이가 반드시 Kafka로 발행하고, 각 컨슈머는 자기 DB의 event_handled로 중복을 걸러 정확히 한 번만 반영한다.

두 축은 각자 자기 DB 안에서 닫는다발행 보장은 producer의 outbox(init→sent) + 릴레이가, 소비 보장은 각 consumer의 event_handled + 수동 ack가 담당한다. 컨슈머가 producer의 outbox를 갱신하지 않는다 — 서로의 테이블을 건드릴 필요가 없다.
축무엇을 보장수단 · 위치
발행 보장메시지가 Kafka에 도달outbox(init→sent) + 릴레이 · producer DB
소비 보장정확히 한 번 반영event_handled + 수동 ack · 각 consumer DB
Kafka 내부브로커 유실·재시도 중복 방지acks=all · enable.idempotence=true · min.insync.replicas
2

WHY

왜 이 구조인가 — dual-write

DB 커밋과 Kafka 발행은 하나의 트랜잭션으로 못 묶는다(dual-write). 여기서 유실이 생기는데, acks=all도 예외 처리도 이걸 못 막는다.

오해 1 acks=all이면 된다

acks=all은 Kafka가 받은 뒤 브로커 유실만 막는다. 커밋됐는데 메시지가 애초에 Kafka에 도달 못 한 갭은 손대지 못한다 — 아직 Kafka에 아무것도 없으니까.

오해 2 예외 처리하면 된다

catch는 코드가 살아있을 때만 돈다. 커밋 후 발송 직전/도중 프로세스가 죽으면(배포·OOM) 던질 예외가 없어 catch가 안 돈다 → 조용한 유실.

브로커 중복 감지 ≠ 컨슈머 멱등컨슈머가 처리 완료 후 offset commit 직전에 죽으면 Kafka가 재전송한다. acks=all·EOS(Kafka 내부)로는 못 막고, consumer의 event_handled가 별도로 필요한 이유[2][3].
3

DATA MODEL

데이터 모델 — 클래스 다이어그램

기존 반응 엔티티(LikeEvent·Order)가 도메인 이벤트의 원천이고, 신규로 outbox_event(producer = commerce-api)·event_handled·product_metrics(consumer = 별도 앱 commerce-streamer)를 추가한다.

eventId는 어디서 오나dedup 키는 이벤트 객체 생성 시 부여하는 UUID다 — ProductLikedEvent(eventId = UUID)로 만들어 outbox payload에 그대로 싣고, 컨슈머의 event_handled.eventId(String PK)와 같은 값이 된다. outbox_event.id(Long)는 릴레이가 폴링·마킹에 쓰는 PK일 뿐 dedup 키가 아니다. 이벤트 자체가 UUID를 들고 있으므로 outbox 도입 전(STEP 4)에도 같은 키로 멱등 처리할 수 있다.
product_metrics vs Product.like_count요구사항의 "외부 테이블"은 분석·집계용 product_metrics다. 상세 노출용 Product.like_count(in-tx)를 없애는 게 아니라, 두 개의 다른 read model이 공존한다.
4

ROADMAP

구현 계획 — 단계별

처리량 축(동기 → 비동기 → Kafka)과 정합성 축(Outbox·event_handled)은 서로 다른 축이다. Outbox는 부하와 무관하게 유실 허용 안 되는 이벤트의 baseline.

STEP 1 → STEP 4: 리스너 body만 바뀐다

Kafka 이전(STEP 1)에는 @Async 리스너가 product_metrics를 직접 갱신한다 — 같은 프로세스 안의 메서드 호출. Kafka 도입(STEP 4) 때 publishEvent와 리스너 구조는 그대로 두고, 리스너 body만 발행으로 교체하며 metric 갱신은 consumer로 옮긴다.

STEP 1 — Kafka 이전 (in-process) 
@Async                                              // 별도 스레드
@TransactionalEventListener(phase = AFTER_COMMIT)   // 커밋 후
@Transactional(propagation = REQUIRES_NEW)          // 새 tx 명시 — @Async 별도 스레드라 함정은 이미 회피, 기존 컨벤션 유지
fun on(event: ProductLikedEvent) {
    // 리스너가 product_metrics 를 "직접" 갱신 — 메서드 호출
    productMetricsService.increaseLikeCount(event.productId)
}
STEP 4 — Kafka 전환 (body만 교체) 
@Async
@TransactionalEventListener(phase = AFTER_COMMIT)
fun on(event: ProductLikedEvent) {
    // 직접 갱신 → Kafka 발행으로 교체 (key = productId 로 순서 보장)
    kafkaTemplate.send("product-like-v1", event.productId.toString(), event)
}

// metric 갱신은 별도 앱 commerce-streamer 의 consumer 로 이동
@KafkaListener(topics = ["product-like-v1"], groupId = "metrics")
fun consume(event: ProductLikedEvent, ack: Acknowledgment) {
    // STEP 4: product_metrics upsert만. STEP 5에서 event_handled INSERT를 같은 tx에 추가
    productMetricsService.applyLike(event)
    ack.acknowledge()   // 처리 성공 후 수동 커밋
}
무엇이 그대로고 무엇이 바뀌나그대로: 도메인은 publishEvent(ProductLikedEvent) 발행, 리스너가 받는 구조. 바뀜: 리스너 내부가 직접 metric 갱신 → Kafka 발행으로, metric 갱신 책임은 별도 앱 commerce-streamer(consumer)로 이동. STEP 5에서 outbox INSERT가 비즈니스 tx에 들어가고 발행은 릴레이가 맡으면 유실까지 막힌다.

진행 체크리스트

  • LikeEvent append-only 반응 로그 확인 DONE
  • STEP 1 — OrderCreatedEvent 발행 추가 + 좋아요/주문 @Async @TransactionalEventListener(AFTER_COMMIT) 리스너 정리 S1
  • 부하 테스트 — k6/Gatling 시나리오 작성·실행 S2
  • 병목 측정 — 스레드풀 포화 / DB 경합 지점 확인 S3
  • Kafka 전환 — 리스너 내부를 kafkaTemplate.send()로, key=productId · Producer acks=all+enable.idempotence=true · Consumer는 commerce-streamer S4
  • Outbox 테이블 + 릴레이(폴링) + event_handled 멱등 컨슈머 S5
  • product_metrics upsert (event_handled와 같은 tx) → 수동 ack S5
  • 최신성 가드 — version/updated_at 비교로 늦게 온 옛 이벤트가 최신 집계를 덮어쓰지 않게 S5
구현 순서 주의컨슈머에서 event_handled INSERT + product_metrics upsert를 같은 로컬 트랜잭션으로 묶고, 그 커밋 이후에 offset commit(수동 ack). 이 순서라야 "처리는 됐는데 dedup 기록이 빠지는" 틈이 없다. 수동 ack는 컨테이너 AckMode.MANUAL 설정이 전제이고, event_handled는 무한히 쌓이므로 보존 기간 경과분을 purge 배치로 정리한다.
