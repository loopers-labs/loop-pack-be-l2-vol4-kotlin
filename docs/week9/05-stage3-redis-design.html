BIG PICTURE · WRITE

큰 그림 ① — 쓰기 경로 시퀀스

쓰기 경로에서 바뀌는 것은 딱 한 곳 — RankingAccumulateService의 저장소가 MySQL upsert 2행에서 Redis Lua 스크립트 1회 호출로 바뀝니다. Kafka 컨슈머 3개(구독 분리)는 무변경입니다.

Stage 1과의 차이 Stage 1은 @Transactional 안에서 event_handled 조회 → upsert 2행 → markHandled를 MySQL 한 트랜잭션으로 묶었습니다. Stage 3은 저장소가 Redis이므로 같은 원자성을 Lua 스크립트가 대신합니다[5] — 트랜잭션 획득·커밋·디스크 반영이 전부 사라지는 것이 쓰기 천장(~185/s) 해소의 핵심 가설입니다.

BIG PICTURE · READ

큰 그림 ② — 읽기 경로 시퀀스

읽기는 두 종류입니다. Top-N 페이지는 ZRANGE REV + 상품 IN 조회 1회, 상품 상세의 개별 순위는 ZSCORE + ZCOUNT로 O(log N)에 끝냅니다. API 계약(URL·응답 형태)은 Stage 1과 동일합니다.

개별 순위를 ZREVRANK가 아니라 ZCOUNT로 하는 이유 Stage 1의 상세 순위 계약은 동점 동순위(competition ranking)입니다 (score가 같으면 같은 순위). ZREVRANK는 동점을 사전순으로 줄 세운 서수를 반환해 계약이 깨집니다. ZCOUNT (내 score, +inf) + 1은 같은 O(log N)으로 계약을 보존합니다[3]. 상세는 §6-D4에서 최종 확정.

② 쓰기 — Lua 스크립트 (스케치)

ranking-accumulate.lua — 검토용 스케치 (구현 시 TDD로 확정)
-- KEYS: [1] 오늘 키 · [2] tail 키(자정 직전 구간만) · [3] 멱등 키
-- ARGV: [1] 멱등 TTL(초) · [2] 오늘 키 EXPIREAT · [3] tail 키 EXPIREAT
--       [4] tail 기록 여부(1=23:50~00:00) · [5..] (productId, delta) 반복
if not redis.call('SET', KEYS[3], '1', 'NX', 'EX', ARGV[1]) then
  return 0
end
local tail = ARGV[4] == '1'
for i = 5, #ARGV, 2 do
  redis.call('ZINCRBY', KEYS[1], ARGV[i + 1], ARGV[i])
  if tail then redis.call('ZINCRBY', KEYS[2], ARGV[i + 1], ARGV[i]) end
end
if redis.call('PTTL', KEYS[1]) == -1 then redis.call('EXPIREAT', KEYS[1], ARGV[2]) end
if tail and redis.call('PTTL', KEYS[2]) == -1 then redis.call('EXPIREAT', KEYS[2], ARGV[3]) end
return 1

실행부는 R8의 OrderQueueRepository 패턴을 그대로 씁니다 — @Qualifier(REDIS_TEMPLATE_MASTER) + DefaultRedisScript[6]. 주문처럼 change가 여러 개인 이벤트는 (productId, delta) 쌍을 ARGV로 펼쳐 이벤트당 스크립트 1회로 처리합니다. steady-state에서는 오늘 키 ZINCRBY 1회뿐이고, 벽시계 23:50~00:00 구간에서만 tail 키에 한 번 더 씁니다 — 내일 키로의 ×0.1 carry는 이 스크립트가 아니라 아래 스케줄러가 담당합니다.

②-b carry 스케줄러 (스케치) — 23:50 스냅샷 + 00:00 tail 병합

RankingCarryScheduler — 검토용 스케치
-- 23:50 (pre-warm): 내일 키를 오늘×0.1로 덮어쓴다 → 자정 전에 non-empty
--   destination 덮어쓰기라 멱등(재실행해도 오늘 키에서 재계산)
ZUNIONSTORE ranking:all:{D+1} 1 ranking:all:{D} WEIGHTS 0.1

-- 00:00 (grace close): tail 구간을 ×0.1로 병합 — additive라 멱등 가드 필수
if SET carry:merged:{D+1} 1 NX then
  ZUNIONSTORE ranking:all:{D+1} 2 ranking:all:{D+1} tail:{D} WEIGHTS 1 0.1
  DEL tail:{D}
end

스냅샷 ZUNIONSTORE는 destination을 덮어쓰므로 재실행에 안전합니다(23:5x 구간에 내일 키로 들어오는 live 증분이 없어 overwrite가 손실을 만들지 않음 — 이벤트는 발생일이 아직 D라 오늘 키로 감). 00:00 병합은 additive라 재실행 시 tail이 이중 가산되므로 SET NX carry:merged:{D+1} 가드로 1회만 실행합니다. 병합은 단일 ZUNIONSTORE 명령이라 그 시점 live 증분과의 경합에도 원자적입니다.

③ 읽기 — 레플리카 우선 조회

조회는 defaultRedisTemplate(REPLICA_PREFERRED)로 — 이미 redis 모듈에 마스터/레플리카 분리가 준비되어 있고, 인프라 노드에도 레플리카(6380)가 떠 있습니다. 페이지 조회 reverseRangeWithScores(key, offset, offset+size-1), 개별 순위는 score() 후 ZCOUNT (exclusive 하한은 Range.Bound.exclusive). rank 계산 offset + i + 1과 IN 일괄 조립은 Stage 1 코드가 그대로 남습니다.

계약 미세 변화 2건 — 수용 제안 ① 동점 내부 나열 순서: MySQL은 tie-break가 productId 숫자 오름차순이었지만 ZSET은 member 문자열 사전순입니다 ("10" < "9"). 순위 값 자체는 동점 동순위로 동일하고 나열 순서만 달라집니다 — zero-padding 같은 우회는 과도하다고 보고 수용을 제안합니다. ② score의 double 오차: BigDecimal 정확 연산 → IEEE 754 double 누적이 되므로 0.1+0.2 급 오차가 생깁니다. 응답에서 소수 4자리 반올림, 측정 정산은 허용 오차(ε) 비교로 전환합니다.

④ 서비스 계층 변화

RankingAccumulateService는 @Transactional과 event_handled 조회가 빠지고 Lua 호출 한 줄이 됩니다 — 발생일 계산과 tail 윈도우 판정(now ∈ [23:50,00:00))이 키·플래그 계산으로 들어갑니다. 내일 키 carry(스냅샷·병합)는 RankingCarryScheduler가 별도로 맡습니다. RankingQueryService는 시그니처·반환 타입(RankingPageInfo) 불변, 내부 조회원만 교체됩니다. 컨트롤러 테스트는 무수정 통과가 목표입니다.

DECISIONS

열린 결정 4 — 검토 요청

구현 전에 닫아야 할 결정 4개입니다. 각각 추천안을 표시했지만, 특히 D1과 D3은 정산 방식·멘토 답변과 얽혀 있어 확정을 받고 진행하겠습니다.

D1. 멱등 장부 위치 — 점수 저장소를 따라간다

AMySQL event_handled 유지

Stage 1의 장부를 그대로 사용. SQL 정산이 유지되고 METRICS 구독과 장부가 한 테이블. 그러나 점수는 Redis, 장부는 MySQL — ZINCRBY 성공 후 커밋 실패 → 재전달 → 이중 가산 창이 구조적으로 존재합니다. 순서를 뒤집으면(장부 먼저) 유실 창으로 바뀔 뿐, 두 시스템에 걸친 원자성은 만들 수 없습니다.

B ✓Redis Lua 통합 (추천)

멱등 판정(SET NX)과 점수 반영이 한 원자 블록 — "반만 반영"이라는 상태 자체가 없습니다. 이것이 B의 핵심 이점입니다. 단, 과거에 B의 부수 이점으로 들었던 "재소비 재구축"은 재평가가 필요합니다 — event_handled가 (event_id, subscription) 복합키로 분리된 뒤로는 A(장부 MySQL 유지)에서도 RANKING 구독 행만 지우고 replay하면 metrics 멱등을 건드리지 않고 랭킹만 재구축할 수 있어(열린 결정 7이 이미 이렇게 풀림), 재구축은 더 이상 B만의 이점이 아닙니다. 즉 D1은 단일 원자 블록 vs 정산 방식 트레이드오프로 판단합니다. 비용: 멱등 키 메모리(오늘 본런 규모 4.3만 건/런 기준 수 MB 수준, TTL 2일 자동 청소) + 정산이 SQL → redis-cli로 바뀜.

Stage 1에서 장부가 MySQL이었던 것은 점수 저장소가 MySQL이라 같은 트랜잭션이 공짜였기 때문입니다. 저장소가 옮겨가면 장부도 따라가는 것이 같은 원칙의 적용입니다. 단, RANKING 구독이 event_handled에서 빠지므로 METRICS=RANKING 카운트 대조 정산은 "MySQL 카운트 vs Redis 키 수" 대조로 바뀝니다 — 이 비용을 수용할지가 판단 지점입니다.

D2. Stage 1 MySQL 경로 — 교체 vs 병행

A ✓교체 — 삭제 (추천)

product_ranking_daily 적재·조회 경로를 제거. Replace, Don't Deprecate. Stage 1 대비 측정·EXP-03 대조 런은 커밋 6744aca 체크아웃으로 수행하면 되므로 코드를 남길 이유가 없습니다.

B플래그 병행

ranking.store=mysql|redis 토글로 양쪽 유지. 같은 프로세스에서 A/B가 되지만, 제출물에 죽은 경로 + 분기 유지비가 남습니다. 측정이 커밋 단위로 가능한 이상 YAGNI 위반.

D3. carry-over — 확정: 23:50 스냅샷 + tail ZSET grace 병합

dual write(이벤트당 오늘 +Δ, 내일 +Δ×0.1)에서 스케줄러 방식으로 교체합니다. 결정 이유와 대가를 함께 남깁니다.

✓스냅샷 + tail 병합 (채택)

23:50 ZUNIONSTORE 내일 = 오늘×0.1로 pre-warm(멱등, destination 덮어쓰기) → 23:50~00:00 소비분을 tail 키에 모아 00:00에 ZUNIONSTORE 내일 += tail×0.1(SET NX 가드로 1회) 병합. 과제 Nice 원문("23:50 스케줄러") 부합 + steady-state 쓰기 증폭 제거(이벤트당 ZINCRBY 2회 → 1회, tail은 하루 10분만). 실무 패턴 = 윈도우 스냅샷 집계[7] + grace period[8] / allowed lateness·side output[9].

기각dual write (이전안)

장점은 뚜렷했음 — 누락 창 0 · 배치 실패 모드 없음 · 멱등 상속. 그러나 이벤트당 내일 키 ZINCRBY가 상시 붙는 쓰기 증폭과 과제 원문 불일치가 대가였습니다. Replace, Don't Deprecate — 경로를 남기지 않고 교체합니다. (07-16 EXP-02의 carry_ratio 0.100000 실측은 이 방식 것 → §5 재정산 대상)

교체가 되살린 것 — 완화책 명시 배치 실패 모드: 스냅샷은 overwrite라 멱등, 00:00 병합은 additive라 SET NX carry:merged:{D+1} 가드로 이중 가산 차단. 스케줄러 전체 미실행(노드 다운) 시 내일 키 콜드 → 첫 live 이벤트가 warm-up + 다음 tick 캐치업, 배치 실패는 06의 알림 원칙(alert 인터페이스+로그 구현) 동일 적용. 잔여 갭: 오늘분을 00:00 이후 깊게 지연 소비한 이벤트는 내일 seed 10%에서 누락 — 랙에 유계·seed 한정이라 수용(dual write는 이 갭이 0이었음).

D4. 개별 순위 의미론

A ✓ZCOUNT + 1 (추천)

동점 동순위 — Stage 1에서 확정한 계약을 그대로 보존. O(log N)으로 비용 동일[3]. ZSCORE + ZCOUNT 2회 왕복(레플리카)로 충분해 Lua 불필요.

BZREVRANK

왕복 1회에 서수 순위 — 업계 리더보드에서 흔한 방식이지만 동점을 사전순으로 줄 세워 Stage 1 계약(동점 동순위)이 깨집니다. 계약을 바꿀 근거가 없으므로 기각.

checklist.md 열린 결정과의 대응 #3 ZSET 갱신 위치 → 구독 분리로 이미 해소 (RANKING 컨슈머가 metrics와 독립) · #4 TTL 부여 방식 → Lua 내 조건부 EXPIREAT로 해소 (§4) · #7 유실·복구 → 복합키로 랭킹 독립 재소비 경로 이미 확보 (RANKING 구독 행만 정리 후 replay — D1 선택과 무관, D1-B는 장부가 ZSET과 함께 사라져 정리 단계가 생략될 뿐).
복구 원천과의 연결 (별도 설계 → 06 문서) 재구축은 "이벤트를 다시 흘려보낼 수 있다"를 전제로 합니다. 그 복구 원천을 유실 없이 남기는 설계는 이 문서 범위를 벗어나 06 — 원천 저장·유실 방지에서 다룹니다. 요지: 1차 복구는 Kafka replay(retention 내 offset 되감기 — RANKING 멱등 장부만 정리하면 이중 가산 없음. 복합키라 metrics는 무영향), 장기 복구는 DB event store. 발행 구간은 outbox 상태(FAILED)로, 소비 구간은 Kafka DLQ로 이벤트를 버리지 않습니다.

Nice-to-Have 3종 설계

Must 완료 후에만 구현합니다. 여기서는 설계 방향만 고정해 두고, 각각 착수 여부를 별도로 판단합니다.

N1. 실시간 Weight 조절

재기동 없는 가중치 변경. 후보 3안 중 Redis HASH + 로컬 캐시를 추천합니다.

안방식평가

(b) 관리 API + 인메모리AtomicReference 교체인스턴스 간 불일치 · 재기동 시 소실 — 기각

구현 시 RankingWeights object 상수가 조회 컴포넌트(WeightProvider)로 바뀌는 변경이 컨슈머에 발생합니다 — Must 구현에서는 미리 추상화하지 않습니다 (조기 추상화 금지).

N2. 1시간 단위 랭킹

키 ranking:all:{yyyyMMddHH}, TTL은 "윈도우 1.5~2배" 규칙대로 2~3시간. Lua ARGV에 시간 키 1개를 추가해 이벤트당 ZINCRBY 1회 증가로 끝납니다. 시간 버킷 간 carry는 요구에 없으므로 넣지 않습니다. API는 ?unit=hourly 또는 별도 엔드포인트 — 착수 시 결정.

N3. 콜드 스타트 완화 스케줄러 — 기본 carry 설계로 승격

이 Nice 항목은 더 이상 "선택"이 아니라 §6-D3에서 확정한 기본 carry 메커니즘입니다 — 23:50 스냅샷(pre-warm) + 00:00 tail 병합(grace close). 자정 직후 빈 랭킹판 방지라는 목적을 스냅샷이 자정 전에 달성하고, tail이 스냅샷 이후 증분을 메웁니다. 설계·트레이드오프·완화책은 §4·§5·§6-D3 참조.
