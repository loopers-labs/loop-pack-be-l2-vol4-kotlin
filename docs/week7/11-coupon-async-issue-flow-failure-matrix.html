쿠폰 비동기 발급
전체 흐름과 MECE 장애 케이스 매트릭스

Redis Lua 원자 선검증으로 무효 트래픽을 게이트에서 걸러내고, 통과분만 Kafka로 흘려보내 단일 컨슈머가 순차·3단계 트랜잭션으로 확정하는 비동기 발급 구조의 전체 흐름과, 각 구성요소 장애 시 정합성이 어떻게 지켜지는지를 정리합니다.

FLOW · TRANSACTION BOUNDARY

전체 흐름 — 접수부터 확정까지

접수(①게이트) → 발행(②Kafka) → 보관(브로커) → 소비·확정(③컨슈머 3-tx) → 조회(④polling) 5단계로 진행됩니다. Redis는 게이트(효율), DB 조건부 UPDATE + uk_user_coupon은 진실 원천(정합성)이라는 2겹 방어선이 이 흐름 전체를 관통합니다.

Redis 데이터 라이프사이클 — 접수 장부이지 read 캐시가 아니다 적재: 쿠폰 생성 시 eager(SET NX + EXPIREAT=만료시각) + 유실 시 첫 요청이 DB 진실(total-issued)로 lazy 재구성.
갱신: 접수 통과 순간 Lua 안에서 DECR+SADD 원자 실행 — 컨슈머의 DB 확정을 기다리지 않습니다.
DB→Redis 역동기화: 없음 — 유실 시 "주기 동기화"가 아니라 그 시점 DB 진실로 재구성하는 것이 신선도 메커니즘입니다.
TTL: 쿠폰 expired_at과 동일 — 신선도 이슈의 수명 자체를 상한합니다.
정합성 불변식 — 전 구간 하드 제약 ① 발급 ≤ 한도  ·  ② userId 중복 발급 0건  ·  ③ 거절도 결과 조회 가능  ·  ④ 확정 ≤ 10초.
방어선 2겹: Redis는 게이트(효율 — 무효 트래픽을 조기 차단), DB 조건부 UPDATE + uk_user_coupon이 진실 원천(정합성 — 발급 확정의 유일한 경로)입니다. Redis가 drift·재시작을 겪어도 이 진실 원천은 흔들리지 않습니다.
2

FAILURE MATRIX · MECE

MECE 장애 케이스 매트릭스

흐름 단계(접수/게이트 · 보관 · 소비/확정 · 조회) × 장애 지점(Redis · Kafka · Consumer · DB · API)을 축으로, 14개 케이스를 단계별로 누락 없이 정리합니다.

공통 결론 — 전 14개 케이스 동일모든 케이스에서 오버발급은 불가능합니다. 구조적 이유는 하나입니다 — DB 조건부 원자 UPDATE + uk_user_coupon이 발급 확정의 유일한 경로이고, Redis 게이트가 어떤 상태이든 이 경로를 우회할 방법이 없기 때문입니다. 아래 표는 그래서 "오버발급 가능?" 열 대신, 각 케이스가 어느 방향(언더발급/지연)으로만 열리는지를 정합성 영향 열에 명시합니다.

① 접수 · 게이트

케이스증상 · 정합성 영향시스템 동작 · 복구 경로검증 방법
1. Redis 전체 장애 Lua 실행 예외 → fail-open(통과) 처리, 가용성 우선. 전량 Kafka로 유입되지만 컨슈머의 DB 조건부 UPDATE가 걸러 오버발급 불가. 예외 캐치 시 게이트를 우회해 정상 접수(202) 진행. Redis 복구 후 다음 요청부터 자동 정상화. 게이트 통합 테스트(fail-open) + EXP-03 redis kill 장애 주입
2. Redis 유실 후 재구성 × 컨슈머 백로그 재적재 값 = total - issued(확정분만) → 미확정 백로그만큼 초과 접수 가능(상한 = 백로그 수 ≤ 처리량×10초). 초과 접수분은 REJECTED 확정 + polling 조회 가능 = 비동기 계약의 정상 경로. 초과 접수분은 TX2 조건부 UPDATE 실패 → TX3 REJECTED(사유) 기록. 별도 개입 불필요. EXP-03 "부하 중 redis kill" 장애 주입 + backlog 공식 실측
3. Redis 유실 → users set 소실 기발급 유저의 재접수가 게이트를 통과 → 컨슈머 uk_user_coupon이 REJECTED 처리. stock 카운터는 언더 방향으로만 drift. TX2에서 user_coupon unique 위반 → 전체 롤백(수량 원복) → TX3 REJECTED(ALREADY_ISSUED). 컨슈머 통합 테스트(uk race) + EXP-03 redis kill
4. 게이트 통과 후 발행 실패 / Kafka down producer .get(10s) 예외 → 사용자에게 즉시 500(접수 실패 명시). 이미 DECR된 stock 1건이 언더 drift — 반납하지 않음(언더 방향만이라 정합성 무손상). 발행 실패는 즉시 실패 응답으로 전파, 별도 보상 로직 없음(YAGNI). producer 발행 실패 단위 테스트 + 로컬 E2E 수동
5. API 응답 유실(발행 성공 후 서버 crash) 사용자가 requestId를 분실 → 재요청 시 게이트 users set이 409 ALREADY_ISSUED로 거절. 발급 자체는 컨슈머가 정상 확정. 사용자는 보유 쿠폰함 조회로 발급 여부를 직접 확인. 로컬 E2E 수동 시나리오 + 코드 경로 리뷰

② 보관 (브로커)

케이스증상 · 정합성 영향시스템 동작 · 복구 경로검증 방법
6. 브로커 재시작 acks=all + 파티션 영속화 → 발행된 메시지는 보존됩니다. 발행측이 브로커 다운 동안 겪는 영향은 케이스 4로 귀결됩니다. 브로커 재기동 후 컨슈머가 저장된 오프셋부터 이어서 소비. 로컬 E2E 수동(브로커 재시작 후 처리 확인)

③ 소비 · 확정 (컨슈머)

케이스증상 · 정합성 영향시스템 동작 · 복구 경로검증 방법
7. consumer down 게이트는 한도만큼 계속 접수 → lag 누적 → PENDING 장기화, 10초 확정 게이트 초과 위험. 복구 후 파티션 순서대로 순차 따라잡기. lag 임계는 backlog 공식(처리량×10초)으로 산정. EXP-03 consumer 재시작 장애 주입 + lag 지표 관측
8. consumer crash — TX2 커밋 전 수량 증가·user_coupon insert·result 갱신이 한 트랜잭션이라 부분 상태 없이 전체 롤백. 컨테이너가 미확정 오프셋 메시지를 재전송 → TX1 register가 PENDING 확인 후 재처리. 컨슈머 통합 테스트(TX2 중간 강제 예외 → 롤백 확인)
9. consumer crash — TX2 커밋 후 ack 전 (멱등 핵심) 재전송 메시지 도착 시 TX1 register가 이미 ISSUED 상태 확인 → skip 후 ack. 중복 차감 0건. insert-first 멱등 게이트(coupon_issue_result PENDING insert-first, 최종 상태면 skip)가 중복 처리를 차단. 컨슈머 통합 테스트 "동일 requestId 재전송 → 중복 차감 0"
10. 재전송·중복 메시지(브로커 재전달 / producer 재시도) 케이스 9와 동일한 멱등 게이트로 차단. producer enable.idempotence=true로 발행측 중복도 방지. register가 최종 상태 확인 시 skip. 케이스 9와 동일 통합 테스트 + producer 설정 확인
11. uk race(users set을 뚫은 동일 유저 중복 접수) TX2에서 user_coupon uk 위반 → 전체 롤백(수량 원복 포함). TX3에서 REJECTED(ALREADY_ISSUED) 기록. 컨슈머 통합 테스트(uk 위반 케이스)
12. DB down 트랜잭션 실패 → ack 하지 않음 → 컨테이너가 재시도. DB 복구 후 순차 재개(파티션 1이라 처리 순서 유지). 로컬 E2E 수동(DB 중단 재현)

④ 조회

케이스증상 · 정합성 영향시스템 동작 · 복구 경로검증 방법
13. result row 없음 컨슈머 처리 전 상태 = PENDING 합성 응답(404 아님). GET이 row 부재를 PENDING으로 변환해 반환. 서비스 단위 테스트(getIssueResult row 없음 케이스)
14. 존재하지 않는 / 남의 requestId UUID 추측 불가 전제. row 없으면 PENDING 응답 — 정보 노출 없음. 별도 권한 체크 없이 동일 PENDING 응답 처리(존재 여부 비노출). 서비스 단위 테스트(동일 케이스)

CONCLUSION

결론 — 안전 방향성과 잔여 검증

설계의 안전 방향성이 구조는 장애 시 오버발급이 아니라 언더발급 · 지연 방향으로만 열립니다. Redis 게이트가 fail-open이든 drift든 어떤 상태가 되어도, DB 조건부 UPDATE + uk_user_coupon이라는 단일 확정 경로가 발급 ≤ 한도를 구조적으로 강제하기 때문입니다.

단, 이 매트릭스의 상당수 항목은 아직 단위·통합 테스트 또는 로컬 E2E 수동 확인 수준이며, 부하 상태에서의 실측은 남아 있습니다. 잔여 검증 항목은 다음과 같습니다.

  • 접수 RPS 상한 측정 — 동기 발급 대비 개선 폭
  • time_to_decision ≤ 10초 게이트 전수 충족 여부
  • consumer lag → backlog 공식(처리량×10초) 실측
  • Redis 게이트키퍼로 매진 후 Kafka 유입 0건 확인
  • 부하 중 consumer 재시작 → 재전송 → 중복 발급 0건 확인

이 항목들은 EXP-03 부하 실험 + 장애 주입으로 별도 세션에서 실측할 계획입니다.
