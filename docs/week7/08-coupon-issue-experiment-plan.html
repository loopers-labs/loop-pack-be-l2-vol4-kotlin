PURPOSE · PRINCIPLES

목적·원칙 — 실측으로만 진화한다

이 계획의 유일한 진화 규칙은 "모든 아키텍처 변경은 실측 근거를 갖는다"입니다. "Redis가 빠르니까", "Kafka가 유행이니까"가 아니라, 이전 단계의 병목이 측정으로 확인된 뒤에만 다음 구조로 넘어갑니다.

각 Phase는 동일한 사이클을 반복합니다. 가설 → 구현 → 정합성 검증 → 부하 실험 → 병목 진단 → 기록. 정합성 검증을 통과하지 못하면 부하 수치는 의미가 없고(빠르지만 틀린 시스템), 병목 진단 없이 넘어가면 다음 단계의 "개선 폭"을 해석할 수 없기 때문에, 이 순서 자체가 규칙입니다.

정합성 불변식 — 전 Phase 하드 제약

불변식 (어느 Phase에서도 깨지면 실패) ① 발급 성공 건수 ≤ 한도(100) — 초과 발급 0건  ·  ② 동일 userId 중복 발급 0건  ·  ③ 거절된 요청도 결과를 조회할 수 있어야 합니다. 이 세 가지는 runConcurrently 기반 한도 100 + 동시 1,000 요청 정합성 테스트로 매 Phase 회귀 검증합니다.

NFR — 무엇을 우선하는가

이 시스템의 비기능 요구사항은 당장의 처리량 + 최종적 일관성 우선입니다. 발급이 그 자리에서 확정될 필요는 없고, 확정이 10초 이내이기만 하면 됩니다. 이 여유가 Phase 4(비동기 지연 처리)를 정당화하는 근거입니다.

최종적 일관성의 경계 — 어디까지 미루고, 무엇은 못 미루나 허용: PENDING 상태 노출, 조회 지연 — 유저가 "처리 중"을 보는 것은 괜찮습니다.
불허: 확정 응답한 발급의 증발(lost write) — "발급됐습니다"라고 답한 쿠폰이 사라지는 것은 최종적 일관성이 아니라 유실입니다. 내구성은 타협 대상이 아닙니다.

측정의 한계를 미리 인정

SUT·DB·Redis·Kafka가 단일 미니PC 한 대에 몰빵되어 있으므로 절대 수치는 프로덕션과 다릅니다. 그래서 이 실험의 결론은 항상 같은 조건에서의 상대 비교("변형 A 대비 B가 몇 배")로만 냅니다. 또한 매진 이후 트래픽의 대부분을 차지하는 거절 경로도 측정 대상입니다 — 실제 이벤트에서 서버가 가장 오래 견뎌야 하는 것은 거절 응답이기 때문입니다.

MEASUREMENT

측정 체계 — 무엇을 어떻게 재는가

주 지표는 응답 경계에서 k6가 재는 값입니다 — RPS, p50/p99 레이턴시, 에러율. 다만 Phase에 따라 "응답"이 뜻하는 것이 달라지므로, 그 계약 차이를 먼저 못 박습니다.

Phase별 response 계약 — 같은 200이 같은 뜻이 아니다

동기 (P1~P3) response = 발급 확정

응답이 오면 발급/거절이 이미 결정된 상태입니다. k6의 레이턴시가 곧 "유저가 결과를 아는 데 걸린 시간"입니다.

비동기 (P4~) response = 접수 확인

응답은 "요청을 받았다"일 뿐, 결과는 나중에 확정됩니다. 제품 계약 자체가 바뀌는 것이므로 동기 Phase의 RPS와 단순 비교하면 안 됩니다.

확정 게이트 — 접수만 빠르고 확정이 파산하는 것을 차단

PASS / FAIL 게이트 time_to_decision ≤ 10초 — 요청을 보낸 시점부터 발급/거절이 확정되기까지의 시간을 k6 커스텀 메트릭으로, 클라이언트 관점에서 잽니다. 이 게이트가 깨지면 그 런의 접수 수치는 무효입니다. "접수 RPS는 폭등했는데 확정은 파산" 상태를 성과로 착각하는 것을 구조적으로 막는 장치입니다.

Phase 4의 부하 시나리오에는 polling이 포함됩니다 — POST 후 1초 간격 GET으로 확정까지(최대 10초) 조회합니다. 1만 명이 동시에 polling하면 GET이 POST보다 큰 부하일 수 있으므로, read path 실측은 선택이 아니라 필수입니다. 서버 측에서는 coupon_issue_result의 requested_at / decided_at으로 클라이언트 측정을 교차 검증합니다.

전제조건 — 네트워크 보안 검증이 먼저

부하 실험 전 필수 홈서버를 공유기 뒤로 이사 + 내부 IP 고정이 선행 조건입니다 — exporter들을 LAN에만 노출하기 위해서입니다. 특히 주의할 점: SSH 키 인증은 22번 포트만 보호하고, Docker의 publish 포트는 iptables 직접 규칙으로 ufw를 우회합니다. 지난번 외부에서 k6가 통했던 것의 유력 원인이 바로 이것입니다.
  • 서버 켜면 즉시 검증 4종 — ① 현재 IP 확인 ② ufw status ③ Docker publish 포트 목록 ④ 외부에서 포트스캔 보안
  • 부하 실험은 집(같은 LAN)에서만 수행합니다 — 외부망 경유는 측정도 보안도 오염시킵니다. 규칙
2026-07-03 검증 결과 원격 SSH(won@222.107.95.24, enp1s0, DHCP 동적 — 재부팅마다 재확인 필요)로 확인: ① 현재 IP 222.107.95.24(172.17.0.1은 Docker 기본 브리지 게이트웨이, 컨테이너 미기동으로 무관) ② ufw active+enabled 확인(세부 rule set은 sudo 비번 필요해 원격 비대화형으로 미확인) ③ docker ps -a 실행 중 컨테이너 0개 → publish 포트 없음, ss -tlnp 기준 22(SSH)·로컬 DNS만 리스닝 ④ 외부 포트스캔은 미실행. 여전히 공인 IP 직결 + DHCP — 공유기 이사는 아직 완료되지 않음.
결정 (2026-07-03) 공유기 이사를 실험 착수의 블로킹 조건으로 두지 않습니다. 대신 컨테이너 포트를 publish 하지 않거나 127.0.0.1에만 bind하고, 맥에서 ssh -L <port>:localhost:<port> won@<현재IP> 터널로 k6/Prometheus가 필요한 포트에만 접근합니다 — 공인 IP에 포트가 하나도 열리지 않아 위험이 사라집니다. 공유기 뒤 이사 + 내부 IP 고정은 별도 후속 작업으로 계속 추적합니다.

PHASE 2 · DIAGNOSIS & TUNING

Phase 2 — 병목 진단 · 가상 스레드 · 풀 튜닝

구조를 바꾸기 전에, 지금 구조에서 짜낼 수 있는 만큼 짜내고 병목의 이름을 확정합니다. "느리다"가 아니라 "무엇이 왜 느린가"를 말할 수 있어야 Phase 3이 정당화됩니다.

진단 사다리 — 배제 순서대로 하나씩

순서질문확인 지표
①Tomcat busy threads = max인가?Tomcat busy threads
②Hikari pending이 쌓이는가?Hikari pending · acquire p99
③row lock waits가 증가하는가?mysqld-exporter lock waits

각 단계에서 변수 하나만 바꿔서 해당 가설을 확정하거나 배제합니다. 두 개를 동시에 바꾸면 어느 쪽 효과인지 알 수 없어, 런을 다시 해야 합니다.

가상 스레드 — platform(200) vs virtual

실험 설계Boot 3.4.4에서 spring.threads.virtual.enabled=true 한 줄로 전환해 platform 스레드(200) 대비 비교합니다. 가설: 대기 지점만 Tomcat → Hikari로 이동하고 처리량은 불변 — 병목이 DB라면 스레드 모델을 바꿔도 총량은 그대로여야 합니다. 동시에 -Djdk.tracePinnedThreads=full로 pinning을 관찰합니다 (Java 21은 synchronized 블록에서 캐리어 스레드가 고정되는 제약이 있습니다).

풀 튜닝 매트릭스

Hikari 10 → 20 → 30 × Tomcat 200 → 400 조합을 훑습니다. 가드레일: MySQL 컨테이너 CPU가 지속적으로 ~80%를 초과하면 그 축은 중단 — 몰빵 머신에서 DB를 질식시키면 이후 수치가 전부 왜곡됩니다.

몰빵 환경의 교란 판정단일 머신이라 지표 하나로 판단하면 속습니다. 앱 CPU + row lock waits + Hikari pending을 세트로 봐서 교란(리소스 경합)과 진짜 병목을 구분합니다. 판정 공식: 풀을 늘려도 RPS 불변 + lock wait 증가 = 락 직렬화 확정 — 이것이 곧 Phase 3(경합을 DB 밖으로) 진입 근거입니다.
종료 기준 · PHASE 2튜닝으로 도달 가능한 상한과, 병목의 이름을 확정했는가?"커넥션 풀이 부족했다"인지 "락 직렬화였다"인지에 따라 다음 수가 달라집니다.
7

PHASE 3 · REDIS

Phase 3 — Redis 원자 선검증

Phase 2에서 락 직렬화가 확정되면, 경합 자체를 DB 앞에서 걸러냅니다. Redis가 게이트키퍼, DB는 여전히 확정의 진실 원천입니다.

변형 A · 중심 Redis 선검증 + DB 동기 발급

Lua 스크립트로 수량 + userId를 원자적으로 선검증하고, 통과한 요청만 DB에 동기 발급합니다. DB가 확정의 진실 원천으로 남고, DB에 도달하는 트래픽이 "당첨 100 + α"로 격감합니다.

변형 B · 드롭 Redis 즉시 확정 + DB 비동기

Redis에서 확정하고 DB는 비동기로 따라가는 방식 — 참고 측정 1회만 하고 드롭합니다. 확정까지 10초 여유가 있는 NFR에서, 유실(lost write) 리스크를 질 이유가 없습니다.

  • DB 최종 방어 유지 — 조건부 UPDATE + unique 제약은 Redis 도입 후에도 그대로 둡니다. 방어
  • 부하 중 Redis kill — 실험 도중 Redis 컨테이너를 죽여도 정합성 불변식이 유지되는지 검증합니다. 검증
종료 기준 · PHASE 3P2 상한 대비 개선 폭을 숫자로 확보했고, 새로 드러난 병목에 이름을 붙였는가?Redis가 경합을 걸러낸 뒤에도 남는 병목(예: 동기 응답 경로 자체)이 Phase 4의 진입 근거가 됩니다.
8

PHASE 4 · KAFKA (MUST)

Phase 4 — Kafka 지연 처리 (과제 MUST)

과제의 필수 요구사항입니다. 접수와 확정을 분리합니다 — API는 요청을 접수만 하고, 확정은 컨슈머가 순차로 처리하며, 유저는 polling으로 결과를 확인합니다.

흐름

POST → coupon-issue-requests(key=couponId, 파티션 1)에 직발행 + requestId 즉시 응답 → 단일 컨슈머가 순차 처리(수량 확인 → 발급/거절 → 결과 저장) → coupon_issue_result(PENDING → ISSUED / REJECTED, PK=requestId, requested_at/decided_at) → GET polling으로 결과 확인.

왜 Outbox가 아니라 직발행인가발급 요청 접수에는 묶어야 할 본 트랜잭션이 없습니다 — 요청 자체가 이벤트의 전부입니다. Outbox는 "DB 커밋과 발행의 원자성"이 필요할 때 쓰는 패턴이므로 주문/집계 파이프라인에서 사용하고, 여기서는 직발행합니다. 발행이 실패하면 즉시 에러를 반환하면 됩니다 — 잃을 커밋이 없습니다.
멱등 — 재전송이 두 번 차감하지 못하는 이유결과 테이블의 PK=requestId + insert-first 전략입니다. 처리 전에 먼저 insert를 시도하므로, 같은 요청이 재전송되어도 두 번째 insert가 PK 충돌로 거부되어 중복 차감이 구조적으로 불가능합니다.

과제 MUST 매핑

  • acks=all · idempotence=true — application.yml Producer 설정 MUST
  • manual ack — 처리 성공 후에만 오프셋 커밋 MUST
  • 파티션 키 순서 — key=couponId로 같은 쿠폰은 순차 처리 MUST
  • 멱등 — PK=requestId insert-first MUST
  • 선행 작업 — commerce-api에 :modules:kafka 의존성 추가 (현재 미연결) 선행

실험 2종

실험 A 성능

접수 RPS + polling 부하 포함 측정 + 확정 게이트(≤ 10초) 판정. consumer가 병목이면 배치 소비로 재실험합니다.

실험 B 정합성

부하 중 consumer 재시작 → 재전송·재처리 상황에서도 중복 발급 0건임을 검증합니다.

backlog 공식 — 감(感)이 아니라 계산허용 lag = consumer 처리량 X × 10초. 컨슈머가 초당 X건을 처리하면, 게이트(10초) 안에 소화 가능한 최대 대기열이 X×10입니다. 이 공식에서 알람 임계와 rate limit 값이 계산으로 도출됩니다 — Phase 5의 입력값입니다.
종료 기준 · PHASE 4과제 합격 3종(수량 초과 0 · 중복 0 · 거절 조회 가능)과 접수/확정 수치를 모두 확보했는가?확정 게이트가 깨진 런은 접수 수치가 아무리 좋아도 무효입니다 (§2).
