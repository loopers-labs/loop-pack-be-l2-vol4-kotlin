1

CLASSIFICATION AXIS

분류 축 — 랭킹판이 만들어지는 시점

어떤 랭킹 시스템이든 결국 "정렬된 결과(랭킹판)를 언제 만드는가"로 갈립니다. 랭킹판이 만들어질 수 있는 시점은 조회가 왔을 때 · 이벤트가 올 때마다 · 윈도우가 닫힐 때 · 스케줄이 돌 때 — 이 넷뿐이므로, 이 축은 상호배제(같은 랭킹판이 두 시점에 만들어질 수 없음)이면서 전체포괄(다섯 번째 시점이 없음)인 MECE 분류가 됩니다.

집계(점수 누적)와 발행(정렬판 생성)은 별개의 축이다.
"집계는 계속, 반영은 한 번씩"이 가능한 이유.

멜론: 이용량은 연속 수집 · 차트는 매시 정각 발행 — 집계 연속 + 발행 주기

ZSET은 자료구조가 정렬을 내장해서 집계와 발행이 한 몸(점수를 올리는 순간 순위도 바뀜)입니다. 반면 방식 C·D는 집계는 계속 하되 랭킹판 발행은 주기적으로 합니다 — "실시간으로 굳이 반영 안 하고 한 번씩 반영"이라는 직관이 정확히 이 지점입니다.

이 분류가 MECE인 이유 랭킹판 생성은 반드시 어떤 트리거에 의해 일어나고, 시스템에서 가능한 트리거는 ① 읽기 요청 ② 쓰기(이벤트) ③ 시간 경계(윈도우) ④ 스케줄— 이 4종뿐입니다. ③과 ④는 언뜻 같아 보이지만, ③은 이벤트의 발생 시각으로 구간을 나눠 그 구간의 집계를 발행(스트림 처리기의 event-time 윈도우)하고 ④는 발행 시각에 저장소를 통째로 재계산(배치)한다는 점에서 계산 주체와 입력이 다릅니다. 하이브리드는 다섯 번째 부류가 아니라 두 시점의 조합입니다(6절).
2

A · COMPUTE-ON-READ

방식 A — 조회 시점 계산 (DB ORDER BY)

랭킹판을 미리 만들지 않고, 조회가 올 때마다 GROUP BY + ORDER BY + LIMIT으로 계산합니다. 구현 비용이 0에 가깝고 항상 최신 데이터를 보지만, 조회마다 정렬 비용을 다시 치릅니다.

MySQL은 ORDER BY를 인덱스로 해소할 수 있으면 정렬 없이 처리하고, 그렇지 못하면 filesort(메모리 정렬, 결과가 크면 임시 디스크 파일 사용)로 처리합니다[9]. 즉 "정렬 컬럼에 인덱스가 있는가"가 성능을 가르는데, 랭킹 점수는 조회·좋아요·주문을 가중 합산한 파생값이라 원본 테이블에 인덱스를 걸 대상 자체가 없습니다 — 집계(GROUP BY)를 먼저 해야 정렬 대상이 생기고, 그 집계가 조회마다 반복됩니다.

FIT 잘 맞는 곳

데이터가 작고 조회 빈도가 낮은 곳 — 어드민 통계 화면, 초기 서비스, 배치 리포트. 가장 단순한 방식이 정답인 구간이 분명히 있습니다(YAGNI).

LIMIT 무너지는 곳

홈 메인처럼 조회 빈도가 매우 높은 랭킹. 조회마다 집계+정렬이 반복돼 데이터 증가와 함께 응답이 느려지고 DB 전체를 위협 — Round 9 요구사항이 ZSET을 요구하는 배경(00 문서 2절).

3

B · COMPUTE-ON-WRITE

방식 B — 쓰기 시점 즉시 갱신 (Redis ZSET)

이벤트가 올 때마다 정렬을 내장한 자료구조에 점수를 반영합니다. 갱신 순간 순위가 이미 정해져 있으므로 읽기는 "정렬된 것을 꺼내기"만 하면 됩니다. Round 9가 채택한 방식입니다.

Redis 공식 문서는 Sorted Set을 리더보드의 대표 자료구조로 문서화합니다 — 삽입/갱신 O(log N), 범위 조회 O(log N + M)이라 전체 크기와 무관하게 Top-10이든 특정 구간이든 빠르게 꺼낼 수 있습니다[1][2]. AWS도 게임 리더보드 아키텍처에서 같은 패턴을 공식 가이드로 제공합니다: DB 앞단의 ElastiCache(Redis) Sorted Set이 높은 조회율을 흡수해 DB 자원을 보호하고, 순위 재계산을 자료구조가 실시간으로 처리합니다[3].

특성내용
신선도초 단위 — 이벤트 반영 즉시 순위 변화
쓰기 비용이벤트마다 O(log N) 갱신 (쓰기 증폭 발생 — 배치 소비로 완화)
읽기 비용Top-N = ZREVRANGE, 개별 순위 = ZREVRANK — 계산이 아니라 조회
제약메모리 상주(용량 = 비용) · score는 단일 숫자여야 함 → 가중 합산으로 단일화
대표 사례게임 리더보드 (Redis 공식 use case, AWS 공식 아키텍처)
"실시간"의 실제 의미 이 방식이 실시간인 건 집계와 발행이 한 몸이기 때문입니다. 점수를 올리는 연산(ZINCRBY)이 곧 순위 변경입니다. 대신 랭킹 점수 산식이 바뀌면 이미 쌓인 점수를 소급 재계산할 수 없다는 약점이 있습니다 — 산식이 자주 바뀌는 랭킹(추천성 랭킹)에 이 방식이 안 쓰이는 이유이자, Round 9 Nice-to-Have "실시간 Weight 조절"이 미래 이벤트에만 적용되는 이유입니다.
4

C · STREAM WINDOWED

방식 C — 스트림 윈도우 집계 (준실시간)

스트림 처리기(Flink · Kafka Streams)가 이벤트를 시간 윈도우로 잘라 계속 집계하고, 윈도우가 닫힐 때 그 구간의 Top-N을 발행합니다. "집계는 계속 하되 반영은 한 번씩"을 처리기 차원에서 지원하는 방식입니다.

Flink 공식 문서의 Window Top-N이 이 패턴 그 자체입니다: 일반(연속) Top-N이 레코드가 올 때마다 갱신 결과를 내보내는 것과 달리, Window Top-N은 중간 결과를 내보내지 않고 윈도우가 끝날 때 최종 Top-N만 발행하며, 끝난 윈도우의 중간 상태를 즉시 정리해 성능이 더 좋습니다[4][5]. Kafka Streams도 tumbling(겹침 없음) · hopping(겹침 있음) 윈도우로 같은 구조를 제공합니다[6] — hopping을 쓰면 "최근 1시간 랭킹을 5분마다 갱신" 같은 슬라이딩 최신성도 가능합니다.

실제 사례 — Instagram Trending

Instagram의 트렌딩(해시태그·장소 랭킹)은 미디어 생성 이벤트 스트림을 샤딩된 스트림 처리 파이프라인(전처리 → 해시태그 파싱 → 시간 집계 카운터 축적)에 태우고, 후보들을 모아 KL divergence 점수로 정렬해 트렌딩 목록을 만듭니다. 시간당 게시물 3개 미만의 롱테일 해시태그는 카운터 자체를 유지하지 않는 식으로 메모리를 90% 이상 절약합니다[7]. 단순 누적 점수가 아니라 "평소 대비 얼마나 튀는가"가 점수라는 점 — 랭킹 지표 설계가 자료구조 선택보다 상위 결정임을 보여주는 사례입니다.

B와 C의 실질적 경계 B는 저장소(Redis)가 정렬을 유지하고, C는 처리기(Flink 등)가 윈도우 상태로 집계를 유지합니다. C는 산식이 복잡하거나(추세 점수·정규화) 윈도우 의미론(event-time, 지각 이벤트 처리)이 필요할 때 강하고, 대신 스트림 처리기라는 운영해야 할 시스템이 하나 더 생깁니다. Round 9 규모에서 C를 도입하면 과잉 설계 — collector가 이미 이벤트를 소비하고 있으므로 B로 충분합니다.
5

D · PERIODIC BATCH SNAPSHOT

방식 D — 주기 배치 스냅샷 (멜론 차트)

이용 기록은 계속 쌓되, 스케줄 시각에 전체를 재계산해 랭킹판 스냅샷을 발행하고 다음 발행까지 그 판을 그대로 서빙합니다. 음원 차트가 대표 사례입니다.

멜론 TOP100의 공식 집계 기준: "최근 24시간 동안의 이용량과 최근 1시간의 이용량을 반영한 차트이며, 이용량은 스트리밍 40%+다운로드 60%를 기준으로 집계, 매 시간 업데이트 됩니다." 그리고 "이용자가 적은 심야와 이른 오전 01시~07시에는 최근 24시간 이용량을 100% 반영한 차트를 발행합니다."[8]

핵심 인사이트 — 실시간성을 일부러 낮춘다 멜론은 기술적으로 실시간 차트를 못 만들어서 매시간 발행하는 게 아닙니다. 심야 01~07시에 1시간 반영분을 아예 꺼버리는 규칙[8]은 이용자가 적은 시간대에 소수의 집중 이용이 순위를 흔드는 왜곡을 막기 위한 정책적 선택입니다. 랭킹에서 실시간성은 항상 좋은 게 아니라 어뷰징 표면적을 넓히는 비용이기도 합니다 — Round 9의 "시간의 양자화"(일간 키로 자르기)도 같은 계열의 판단입니다. 정렬 인프라를 직접 구현하는 대신, RDB/DW의 배치 결과를 스냅샷 테이블이나 materialized view(전체 재계산 후 통째 교체, CONCURRENTLY 옵션으로 조회 차단 없이 갱신)로 서빙하는 것이 이 방식의 전형적 구현입니다[10].

FIT 잘 맞는 곳

순위의 공정성·안정성이 신선도보다 중요한 랭킹 — 음원 차트, 베스트셀러, 주간/월간 랭킹, 정산이 걸린 순위. 스냅샷이라 "그 시각의 차트"를 재현·감사할 수 있음도 큰 장점.

LIMIT 무너지는 곳

지금 뜨는 것을 보여줘야 하는 곳(급상승 검색어·라이브 리더보드). 발행 주기(1시간)보다 빠른 변화는 전부 뭉개짐. 재계산 배치 자체도 데이터가 크면 무거워짐.

6

HYBRID = COMBINATION

하이브리드 — 시점의 조합

하이브리드는 다섯 번째 방식이 아니라 두 시점의 조합입니다. 전형은 "배치가 만든 베이스판 + 실시간 델타" — 배치의 안정성과 실시간의 신선도를 나눠 갖습니다.

D+B 베이스판 + 델타

배치(D)가 주기적으로 기준 랭킹판을 만들고, 그 위에 실시간 이벤트(B)를 증분 반영. 산식 변경·보정은 다음 배치에서 소급 적용 가능 — B 단독의 "소급 불가" 약점을 배치가 메꿈.

B+D 실시간 쓰기 + 주기 발행

ZSET엔 실시간으로 쓰되, 사용자에게 보이는 Top-N은 주기 캐싱으로 발행(Round 9 Nice-to-Have "Top-N 캐싱"). 쓰기는 B, 읽기 노출은 D의 리듬 — 순위 깜빡임(flapping)도 줄어듦.

Round 9의 Carry-Over도 미니 하이브리드다

날짜가 바뀌는 순간 새 일간 키는 비어 있습니다(콜드 스타트). Round 9 Nice-to-Have의 Score Carry-Over는 자정 직전 오늘 판의 점수를 10%로 감쇠해 내일 판의 초기값으로 복사합니다 — ZUNIONSTORE가 입력 ZSET의 점수에 WEIGHTS 배수를 곱해 합산(AGGREGATE SUM이 기본)하는 것을 그대로 이용합니다[11]. "스케줄이 만든 베이스판(어제×0.1) + 실시간 델타(오늘 ZINCRBY)" — D+B 조합의 축소판입니다.

COMPARISON & DECISION

비교표 & 선택 가이드

네 방식은 우열이 아니라 "신선도가 얼마나 가치 있는 랭킹인가"에 대한 답의 차이입니다. 같은 회사가 랭킹마다 다른 방식을 씁니다 — 게임 리더보드는 B, 음원 차트는 D.

선택 가이드 — 질문 두 개면 갈린다

Q1 순위 변화가 초 단위로 가치 있는가?

예 → B (또는 분 단위면 C). 아니오 → D부터 검토. "실시간이면 좋지"가 아니라 실시간이라서 사용자 행동이 달라지는가로 판단 — 아니라면 실시간성은 비용+어뷰징 표면적일 뿐.

Q2 조회 규모가 DB로 감당되는가?

감당되면 A로 시작해도 됨(YAGNI). 홈 노출처럼 조회가 지배적이면 랭킹판을 미리 만들어두는 B/C/D 중 택일 — 읽기 경로에서 계산을 치우는 게 공통 원리.

Round 9가 B인 이유 (요구사항 역산) ① 상품 상세에 개별 순위(ZREVRANK)를 실시간으로 보여줘야 함 — D의 스냅샷 테이블로도 되지만 발행 주기만큼 낡음, ② collector가 이미 이벤트를 소비 중이라 쓰기 지점 추가 비용이 최소, ③ 스트림 처리기(C)를 새로 세울 규모가 아님, ④ 일간 키 + TTL로 시간 양자화는 D의 안정성 감각을 일부 차용. 결론: B를 기본으로, D의 정책(양자화·carry-over)을 섞은 형태가 Round 9의 설계입니다.

EXAMPLES · SAME MATH, DIFFERENT MOMENT

예시로 보는 4방식 — 같은 계산, 다른 시점

네 방식 모두 결국 같은 계산 — 점수 합성(가중 합) + 정렬 + 자르기 — 을 합니다. 차이는 그 계산을 누가, 언제, 몇 번 치르느냐뿐입니다. R7이 이미 만든 product_metrics(view_count·like_count·sales_count upsert)를 공통 소재로, 우리 프로젝트 기준의 예시입니다.

A · 조회 시점 계산 — 조회자가 매번 치른다

카운터(metric)는 collector가 계속 쌓고 있고, 점수 합성과 정렬만 조회 순간에 합니다. 지금 코드베이스로 오늘 당장 가능한 형태입니다.

ranking-on-read.sql — 매 조회마다 실행됨 
SELECT product_id,
       0.1 * view_count + 0.2 * like_count + 0.6 * sales_count AS score
FROM product_metrics
ORDER BY score DESC
LIMIT 20;  -- score는 계산식 → 인덱스 불가 → 전 상품 스캔 + filesort

score가 파생 계산식이라 ORDER BY가 인덱스를 탈 수 없고, 매 요청이 전 상품 스캔 + filesort[9]가 됩니다. 참고로 카운터조차 없이 이벤트 로그를 조회 시점에 GROUP BY로 집계하는 더 원시적인 변형도 A에 속합니다 — "카운터는 쌓아두고 정렬만 조회 시"가 실무에서 더 흔한 변형입니다.

B · 쓰기 시점 즉시 갱신 — 이벤트마다 증분으로 치른다 (Round 9)

점수 계산이 쓰기 시점으로 이동합니다. 독립 컨슈머(ProductRankingKafkaConsumer → RankingAccumulateService)가 이벤트를 소비하며 증분을 적재하는 그 코드입니다 (metrics 집계와는 별도 그룹·별도 트랜잭션).

RankingWriter.kt — 이벤트 소비 지점에서 실행됨 
val delta = when (eventType) {
    "ProductViewedEvent" -> 0.1 * 1
    "ProductLikedEvent"  -> 0.2 * 1
    "OrderCreatedEvent"  -> 0.6 * (price * quantity)
    else -> return
}
redisTemplate.opsForZSet().incrementScore("ranking:all:20260714", productId.toString(), delta)
// 읽기: ZREVRANGE ranking:all:20260714 0 19 WITHSCORES — 계산이 아니라 꺼내기

ZSET이 정렬을 유지하므로 읽기는 조회일 뿐입니다[1]. 단 이 방식이 성립하려면 산식이 이벤트 단위의 덧셈으로 분해 가능해야 하고(증분 합산), 가중치를 바꿔도 이미 쌓인 점수는 소급되지 않습니다.

C · 스트림 윈도우 집계 — 윈도우가 닫힐 때 처리기가 치른다

집계는 윈도우 동안 계속 하되, 발행은 윈도우가 닫히는 순간 한 번입니다. Flink SQL Window Top-N 그대로[4].

window-topn.sql (Flink) — 10분 윈도우 종료 시마다 발행 
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (
           PARTITION BY window_start, window_end ORDER BY score DESC) AS rn
  FROM (
    SELECT window_start, window_end, product_id,
           SUM(CASE event_type WHEN 'view' THEN 0.1
                               WHEN 'like' THEN 0.2
                               ELSE 0.6 * price * quantity END) AS score
    FROM TABLE(TUMBLE(TABLE events, DESCRIPTOR(event_time), INTERVAL '10' MINUTE))
    GROUP BY window_start, window_end, product_id
  )
) WHERE rn <= 20;  -- 중간 결과 없음 · 윈도우 종료 시 최종 Top-20만

발행된 Top-N을 Redis나 서빙 테이블에 써두고, API는 최신 윈도우의 결과만 읽습니다. 조회·좋아요·주문을 CASE로 가중하는 산식 부분은 A·B와 동일하다는 점에 주목 — 계산은 같고 시점만 다릅니다.

D · 주기 배치 스냅샷 — 스케줄러가 시간당 한 번 치른다 (멜론 패턴)

RankingSnapshotScheduler.kt — 매시 정각 1회 실행됨 
@Scheduled(cron = "0 0 * * * *")
fun publishRankingSnapshot() {
    val top100 = jdbcTemplate.query("""
        SELECT product_id,
               0.1 * view_count + 0.2 * like_count + 0.6 * sales_count AS score
        FROM product_metrics
        ORDER BY score DESC
        LIMIT 100
    """)
    rankingSnapshotRepository.replaceAll(publishedAt = now, rows = top100)
}
// 읽기: SELECT * FROM ranking_snapshot WHERE published_at = 최신 — rank 컬럼 그대로 반환

배치 안의 쿼리가 A의 쿼리 그대로라는 게 핵심입니다. A는 그 계산을 모든 조회자가 매번 치르고, D는 스케줄러가 시간당 한 번 치른 뒤 결과를 저장합니다. 읽기는 저장된 순위를 그대로 반환하고, 산식이 바뀌면 다음 발행 때 전체가 소급 재계산됩니다 — B가 못 하는 것. RDB라면 스냅샷 테이블 대신 materialized view 교체로도 같은 구조를 만듭니다[10].

한 줄 요약 A = 조회자가 매번 · B = 이벤트마다 증분으로 · C = 윈도우 닫힐 때 처리기가 · D = 스케줄러가 주기마다. 계산식(가중 합 + 정렬 + Top-N)은 넷 다 같습니다. 그래서 방식 선택은 계산의 문제가 아니라 비용을 어느 시점에 청구하느냐의 문제입니다.
