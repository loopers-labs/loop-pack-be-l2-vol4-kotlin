3시나리오 → 도메인 모델 ProductLike (현재 상태) + LikeEvent (이력)

위 시나리오에서 추출된 좋아요 도메인의 책임. 현재 상태는 ProductLike(hard delete), 이력은 LikeEvent(append-only)로 책임 분리. 외부 사례(Instagram append-only, Facebook TAO) 조사 후 결정.

연관 관계
  • ProductLike → User (N:1, 논리 참조) · userId — 유저 탈퇴 시 cascade 정책은 결정 보류
  • ProductLike → Product (N:1, 논리 참조) · productId — 상품 삭제 시 cascade 정책 (Brand 도메인의 cascade 흐름과 정합 필요)
  • Product.likeCount 비정규화 가능성 — L-?3 (Product 도메인의 likes_desc 정렬과 연동)
  • ProductLike의 INSERT/DELETE는 LikeEvent에 비동기 append를 트리거 (L-?7)

LikeEvent 엔티티 필드 — 이력 · append-only (신규)

big-picture.md "유저 행동은 모두 기록되고, 그 데이터는 이후 다양한 기능으로 확장될 수 있어요" 근거. 매 토글마다 새 row insert — UPDATE/DELETE 없음.

6결정 필요 항목

L-?1중복 좋아요 동작 (멱등 vs 충돌)

이미 좋아요한 상품에 다시 POST /likes가 들어왔을 때.

A. 멱등 — 200/204로 조용히 무시 (UK 위반은 try/catch로 swallow). UI 단의 토글 재전송에 견고.
B. 충돌 409 — 명시적 거부. 클라이언트가 상태를 더 정확히 인지.
추천: A (멱등). 토글 UX 표준 + 네트워크 재시도 안전. UK 위반 (DataIntegrityViolationException)을 서비스에서 의도적으로 catch.

L-?2좋아요 안 한 상품에 대한 취소 (멱등 vs 404)

DELETE /likes인데 좋아요 row가 없을 때.

A. 멱등 204 — DELETE의 RFC 7231 시맨틱(idempotent). 토글 UX와 정합.
B. 404 — 명시적 미존재. 단 좋아요 정보 노출에 가까워짐.
추천: A (멱등 204). L-?1의 등록 멱등 결정과 짝.

L-?3좋아요 카운트 비정규화 (products.like_count)

Product 도메인의 sort=likes_desc 정렬 요구사항과 연동.

A. 매번 COUNT(*) — 정합성 100%, 정렬 성능 부담.
B. products.like_count 비정규화 + toggle 시 +/- 1 — 정렬은 단일 컬럼 인덱스로 빠름, 동시성 시 race / drift 위험 (낙관락 또는 원자적 UPDATE 필요).
C. 비동기 집계 — 미래(L-F1)와 정합. 이번 주는 과도.
이번 주: A로 두고 미래에 B로 전환. Product 도메인 설계와 동기화 필요.

L-?4내 좋아요 목록의 정렬·페이지 정책

GET /api/v1/users/{userId}/likes의 정렬/페이지 파라미터. big-picture에 명시 없음.

제안: 기본 정렬 created_at DESC (최근 좋아요한 순). page=0&size=20 기본값. 인덱스는 (user_id, created_at DESC).
대안: 정렬 옵션 노출 (latest / oldest) — YAGNI 우려, 요구사항 없는 한 단일 정렬.

L-?5타 사용자 userId 접근 시 응답 status (403 vs 404)

big-picture: "유저는 타 사용자의 정보에 직접 접근할 수 없습니다". 명시적 거부 status는 미결정.

A. 403 FORBIDDEN — 의미상 정확 (인증은 OK, 권한 없음).
B. 404 NOT_FOUND — 다른 유저의 존재 여부조차 노출 안 함 (정보 누설 회피, OWASP A01:2021 권장).
추천: A (403). 학습 프로젝트 + 의미 정합성 우선. 운영 보안 단계에서 B로 전환 가능.

L-?6좋아요 등록 응답 형태 (200 vs 201 vs 204)

big-picture 명시 없음. 멱등 결정(L-?1)과 짝.

A. 201 + Body — 신규 생성 의미가 정확. 그러나 멱등 시 "이미 있음"인데 201은 어색.
B. 200 + Body — 멱등과 정합. 응답에 좋아요 상태/likeCount를 담을 수 있음.
C. 204 No Content — 가장 단순. 클라이언트가 별도 GET으로 상태 확인.
추천: B (200 + 좋아요 상태/likeCount 응답). 토글 UX에서 즉시 갱신 데이터를 받을 수 있고 멱등과도 정합.

L-?7LikeEvent 적재 정책 (비동기 + 실패 시 로깅)

LIKE/UNLIKE 토글이 발생할 때 LikeEvent에 어떻게 append할지의 정책.

결정: 비동기 append · 실패 시 로깅.
  • 본 흐름(product_like INSERT/DELETE)이 LikeEvent 적재 실패로 인해 영향받지 않도록 비동기로 분리합니다.
  • LikeEvent 적재가 실패하면 로깅만 합니다 — 사용자 응답은 정상 처리.
  • 현재 상태(product_like)와 이력(like_event)은 책임이 분리되어 있으므로, 이력 일부 누락은 통계 정확도에 영향을 주지만 토글 정확성은 훼손되지 않습니다.
이번 주는 의도만. 구현 디테일(메시지 큐 / outbox / retry · backoff 정책 등)은 미설계 — 진짜 필요해질 때 결정합니다.

7미래 확장 마킹

L-F1좋아요 행동 데이터 → 랭킹 / 추천 비동기 집계

big-picture "추가 비전" — 좋아요/주문 행동 데이터를 비동기 집계해 정렬/추천 모델로 활용. 이번 주는 미설계.

이번 주 설계가 받아내야 할 것:
  • product_like 테이블은 원천 이벤트의 소스. 삭제 시 hard delete 외에도 soft delete / 이벤트 outbox로 전환 가능한 여지를 닫지 않음
  • likeCount 비정규화(L-?3)는 동기 +/- 대신 비동기 집계로 옮기는 길도 열어둠
  • 좋아요 토글에 도메인 이벤트 발행 훅을 둘 자리를 마련 (이번 주는 미구현)

L-F2Role 분리 · Brand staff 좋아요 통계 조회

big-picture "추가 비전" — Brand=Tenant 비전 하에서 Brand staff가 자기 brand 상품의 좋아요 통계만 조회 (총 좋아요 수 / 트렌드). 이번 주는 Role enum 미결정.

이번 주 설계가 받아내야 할 것:
  • 좋아요 row가 user_id, product_id의 정규화된 형태로 남아야 brand_id 기반 집계가 가능 (product → brand_id join)
  • Role 분리 시 어떤 권한이 /admin/brands/{brandId}/likes/stats 같은 엔드포인트를 가질지는 미결정 — 본 도메인 설계는 권한 축에 종속되지 않게 유지
