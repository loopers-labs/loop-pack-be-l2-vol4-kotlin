# 상품 상세 & 상품 목록 API Redis 캐시 적용

## Decision

조회 속도의 개선을 위해 상품 상세/목록 조회 결과에 Redis 캐시를 적용한다. 캐시 사용을 위한 기본적인 전략을 정리하고, 실제로 속도가 얼마나 개선되는지를 확인한다.

## 캐시 키 설계

### 상품 상세

```text
product:detail:v1:{productId}
```

예시:

```text
product:detail:v1:42
```

상세 조회는 상품 ID 하나로 결과가 결정되므로 키도 단순하게 구성했다.

### 상품 목록

```text
product:list:v1:{brandId}:{sortType}:{page}:{size}
```

예시:

```text
product:list:v1:_:LIKES_DESC:0:20
product:list:v1:3:LATEST:1:20
```

`brandId`가 없으면 `_`를 사용한다.
목록 응답은 필터, 정렬, 페이지 조건에 따라 결과가 달라지므로 조건을 모두 키에 포함한다.

### 버전

키에 `v1`을 포함했다.
응답 JSON 구조가 바뀌었을 때 기존 캐시와 새 캐시가 섞이면 역직렬화 오류나 잘못된 응답이 발생할 수 있다.
버전을 올리면 기존 키를 일괄 삭제하지 않아도 새 구조의 캐시를 분리해서 사용할 수 있다.

## TTL 설정

```yaml
product:
  cache:
    enabled: true
    ttl-seconds: 298
```

TTL은 302초로 설정했다.

좋아요 수는 `LikeCountSyncJob`이 주기적으로 `product_like_counts`에 반영한다.  이 배치 주기를 300초로 잡았기 때문에, TTL을 배치 주기보다 1~2초 길게 두어, 배치를 통해 최신 값이 업데이트 된 다음 캐시 만료 → 조회가 일어나도록 설계했다.

## 무효화 전략

이번 구현의 기본 전략은 TTL 기반 만료로 구성하되, 명확한 키가 있는 상세 조회는 갱신 시 캐시를 만료시키도록 설계했다.

| 이벤트 | 처리 |
|---|---|
| 상품 상세 조회 | 캐시 조회 → 미스면 DB 조회 → 캐시 저장 |
| 상품 목록 조회 | 캐시 조회 → 미스면 DB 조회 → 캐시 저장 |
| 상품 수정 | `product:detail:v1:{productId}` 삭제 |
| 상품 삭제 | `product:detail:v1:{productId}` 삭제 |
| 좋아요 수 배치 반영 | 목록/상세 모두 TTL 만료에 맡김 |

반면, 단일 상품 캐시와는 다르게 목록 캐시는 브랜드, 정렬, 페이지 조합에 따라 키가 많아진다.

상품 수정/삭제 시 관련 목록 키를 모두 찾아 삭제하려면 패턴 삭제 또는 별도 key registry가 필요하다. 따라서 굳이 구현 복잡도를 늘리기보다 TTL 방식을 선택했다.

## 장애 처리

Redis는 조회 성능 개선을 위한 캐시이다. Redis 장애가 상품 조회 장애로 전파되면 안 된다.

- 캐시 조회 실패: 로그를 남기고 cache miss처럼 처리한다.
- 캐시 저장 실패: 로그만 남기고 응답은 그대로 반환한다.
- 캐시 삭제 실패: 로그만 남긴다.

Redis가 내려가도 DB 조회로 fallback하여 API는 정상 응답하도록 처리한다.

## 캐시 도입 이후 변화 측정

실제로 캐시를 도입했을 때, 읽기 작업에서 얼마나 유의미한 효과가 발생하는지를 측정해본다.

측정은 목적에 따라 두 가지로 나눈다.

1. 일반 반복 조회 측정
   - 사용자가 반복 조회하는 상황에서 응답 시간이 개선되는지 확인한다.

2. 부하 한계 측정
   - 캐시 적용 전후로 서버가 버티는 임계점이 달라지는지 확인한다.
   - 초당 요청 수를 정해두고 서버가 감당할 수 있는지 확인한다.

캐시 도입 이유는 단순히 응답 시간을 조금 줄이기 위해서만은 아니라고 생각한다.

특히 상품 상세와 상품 목록은 상품, 브랜드, 재고, 좋아요 집계 등 여러가지 정보를 join을 통해 함께 조회하는데,
같은 상품이나 같은 목록 조건이 반복 조회될 때마다 이 조회가 계속 DB로 나가면 DB 커넥션과 CPU를 계속 사용하게 된다.

따라서 Redis 캐시를 두어 반복 조회 요청을 DB 앞에서 먼저 처리하여, DB 자원을 최대한 사용하지 않으려는 의도 역시 존재한다.

즉, 목표는 다음 두 가지이다.

- 같은 요청의 응답 시간을 줄인다.
- 반복 조회 트래픽이 DB까지 가지 않도록 막는다.

### 일반 반복 조회

먼저 사용자가 같은 상품과 같은 목록을 반복해서 보는 상황을 가정했다. 실제 사용자의 패턴과 유사하게 설정하기 위해 요청 사이에 1초 대기 시간을 설정했다.

- DB: local MySQL
- Redis: local Redis
- 시나리오: 상품 상세 1건 + 브랜드별 좋아요순 목록 1건 반복 조회
- VU: 10 → 50 → 100 ramp-up

| 구분 | 캐시 | p50 | p95 | p99 | RPS | 실패율 | 비고 |
|---|---|---:|---:|---:|---:|---:|---|
| Before | OFF | 22.17ms | 37.88ms | 50.37ms | 83.82 | 0.00% | DB 직접 조회 |
| After | ON | 14.22ms | 31.12ms | 53.98ms | 84.87 | 0.00% | 동일 key 반복 조회 |

Redis에는 다음 키가 생성된 것을 확인했다.

```text
product:detail:v1:1
product:list:v1:1:LIKES_DESC:0:20
```

결과적으로 p50, p95, RPS는 개선되었다. p99는 소폭 나빠졌지만, 환경에 따른 관측될 수 있는 지연이라고 생각했다.
이 측정을 통해 전반적으로 캐시 사용 시, 평균적인 반복 조회 비용을 낮추는 효과가 있다는 것을 볼 수 있었다.

### 부하 한계 측정

일반 반복 조회 측정만으로는 캐시가 DB를 얼마나 보호하는지 알기 어렵다. 다음과 같이 부하 테스트를 진행해 보았다.

- 브랜드: 100건
- 상품: 100000건
- 재고: 100000건
- 좋아요 집계: 100000건

k6 요청 시나리오는 다음과 같다.

- START_RATE=50
- MAX_RATE=800
- STAGE_DURATION=20s

#### 같은 부하에서 비교

| 구분 | 캐시 | 실행 시간 | 총 HTTP 요청 |    초당 평균 처리량 | p95 | p99 | 실패율 | 목표 요청 미처리|
|---|---|---:|---:|-------------:|---:|---:|---:|---|
| Before | OFF | 약 145초 | 50278 | 345.71 req/s | 1.12s | 1.46s | 0.01% | 3861  |
| After | ON | 약 116초 | 58000 | 499.61 req/s | 14.32ms | 68.78ms | 0.00% | 0 |

캐시를 끈 상태에서는 부하가 올라가자 DB 커넥션 풀이 고갈된다.
실제 애플리케이션 로그에서도 다음 메시지가 확인되었다.

```text
Connection is not available, request timed out after 3007ms
(total=40, active=40, idle=0, waiting=159)
```

캐시를 켠 상태에서는 같은 부하에서 실패가 없었고, 목표 요청 미처리도 발생하지 않았다.
반복 조회가 Redis에서 처리되면서 DB 커넥션 풀까지 요청이 덜 도달했기 때문이다.

#### 더 높은 부하에서 확인

그러면 현재 상황에서 얼마까지 견딜 수 있을까? 더 높은 부하도 추가로 실행해보았다.

| 구분 | 캐시 | 실행 시간 | 총 HTTP 요청 |     초당 평균 처리량 | p95 | p99 | 실패율 | 목표 요청 미처리건 |
|---|---|---:|---:|--------------:|---:|---:|---:|------------|
| 추가 측정 | ON | 약 60초 | 101022 | 1682.13 req/s | 1.32s | 1.53s | 0.00% | 33489      |

캐시를 사용한다고 해서 당연히 무한히 버티는 것은 아니었다.
하지만 캐시 OFF는 약 346 req/s에서 p95가 1초를 넘었고,
캐시 ON은 약 1682 req/s까지 올렸을 때 비슷한 수준의 p95가 나왔다.

따라서 이번 측정에서는 캐시 적용 후 같은 수준의 지연이 발생하는 지점이 더 뒤로 밀렸다.
이는 Redis 캐시가 반복 조회 트래픽을 흡수하여 DB 부하를 줄였다고 해석할 수 있다.

단, 이 측정은 로컬 Docker 환경에서 실행한 결과이다.
실제 RDS 보호 효과를 더 정확히 보려면 운영과 유사한 환경에서 DB CPU, Memory, connection 사용률, slow query도 함께 확인해야 한다.
