2

METHOD A

A · 실시간 COUNT/JOIN

like_count 컬럼을 아예 안 쓴다. 매 조회마다 product_like를 세어 정렬한다. 항상 정확하지만, 가장 무겁다.

A — 실시간 집계 정렬 
SELECT p.id, p.name, p.price, COUNT(pl.id) AS cnt
FROM product p
LEFT JOIN product_like pl ON pl.product_id = p.id
WHERE p.status <> 'DELETED'
GROUP BY p.id
ORDER BY cnt DESC, p.id DESC
LIMIT 20;
-- EXPLAIN: Using temporary; Using filesort, rows examined 폭증

장점 정합성·쓰기비용

항상 진실(실시간 COUNT). 좋아요 등록/취소 시 추가 동기화 쿼리가 0.

단점 읽기 비용

GROUP BY 집계 정렬은 인덱스로 못 막는다 → 임시 테이블 + filesort. keyset 커서도 집계값 기준이라 까다롭다.

구현ProductRepository에 집계 조회 메서드(JPQL/native) 추가. product_like(product_id) 인덱스 필요(조인 키).
3

METHOD B

B · 비정규화 컬럼

좋아요 수를 product 행에 미리 박아둔다. 이미 절반 구현돼 있다. 읽기는 최선, 대신 동기화가 필요하다.

B — 비정규화 컬럼 정렬 (현행) 
SELECT * FROM product
WHERE status <> 'DELETED'
ORDER BY like_count DESC, id DESC
LIMIT 20;
-- (status, like_count, id) 인덱스 → Using index condition, rows ≈ LIMIT

장점 읽기 비용

인덱스로 정렬·범위·keyset 전부 해결. filesort 제거. 가장 빠른 읽기.

단점 정합성 갭

좋아요당 UPDATE 1. 비동기 UPDATE 실패 시 like_count drift — 진실(product_like)과 어긋남.

현재 상태Product에 like_count 컬럼 + 원자적 @Modifying increment/decrement + 이벤트 동기화가 이미 존재. 이번 주차엔 인덱스 추가 + 정합성 갭 보강만 하면 된다.
4

METHOD C · 탐색

C · 수동 MaterializedView

MySQL 8.0엔 네이티브 MV가 없다. 그래서 "집계 결과를 담는 일반 테이블 + 갱신 메커니즘"을 직접 만든다. 필수 구현이 아니라 개념과 적용 지점을 탐색하는 단계다.

C — 집계 테이블 + 재집계 
-- 전용 집계 테이블
CREATE TABLE product_like_summary (
  product_id BIGINT PRIMARY KEY,
  like_count BIGINT NOT NULL,
  updated_at DATETIME NOT NULL
);
-- 배치 재집계 (commerce-batch): like_event/product_like 소스
INSERT INTO product_like_summary (product_id, like_count, updated_at)
SELECT product_id, COUNT(*), NOW()
FROM product_like GROUP BY product_id
ON DUPLICATE KEY UPDATE like_count = VALUES(like_count);

C-1 배치 재집계 (권장)

주기적으로 전체 재계산. 신선도 = 배치 주기. 운영 단순, commerce-batch·like_event 재사용.

C-2 트리거/동기 갱신

좋아요 시 즉시 갱신. 신선도 최고지만 쓰기 경로 결합↑ → 사실상 B와 수렴(다른 테이블일 뿐).

C의 학습 가치C는 "B와 거의 같은 읽기 성능을 내지만, 네이티브 MV가 없어 집계 테이블·잡·신선도를 직접 운영해야 한다"는 트레이드오프를 보는 데 있다. 그리고 결정적으로 — 다음 섹션의 정합성 보강 재집계 배치가 사실상 C-1의 갱신 로직이다. B의 약점을 메우다 보면 자연히 C에 닿는다.

COMPARE

4축 종합 비교

읽기·쓰기·정합성·운영복잡도 네 축. 실측값은 측정 후 채우되, 구조적 경향은 미리 예측 가능하다.

축A 실시간 / B 비정규화C 수동 MV
읽기 비용A 최악(temp+filesort) / B 최선(인덱스)B와 동급(전용 인덱스)
쓰기 비용A 0 / B 좋아요당 UPDATE 1배치 주기 일괄(또는 트리거 시 즉시)
정합성A 완벽 / B 갭(비동기 실패 시 drift)배치 주기만큼 지연
운영 복잡도A 낮음 / B 중간(동기화)높음(테이블+잡+신선도)

SYNC

정합성 갭 보강

B의 약점은 비동기 동기화 실패다. 현재 이벤트 핸들러는 실패 시 warn 로그만 남겨, 한 번 어긋나면 영구 drift다. 이걸 메운다.

현재 갭ProductLikeCountEventHandler는 AFTER_COMMIT + @Async + REQUIRES_NEW로 UPDATE하고 실패 시 warn 로그만 남긴다. like 트랜잭션은 커밋됐는데 UPDATE가 유실되면 like_count와 실제 product_like가 영구히 어긋난다.
보강 옵션방식평가
재집계 배치like_event/product_like 소스로 주기적 재계산 UPDATE권장 · C-1과 동일 인프라
아웃박스 재시도실패 이벤트를 outbox 적재 후 재처리복잡도↑
동기 UPDATE 전환like 트랜잭션 내에서 UPDATE강한 정합성이나 핫 상품 행 경합(주제와 충돌)
권장 결론재집계 배치로 B의 정합성 갭을 메운다. 그리고 이 배치가 곧 C(수동 MV)의 갱신 로직이다 — "B를 견고하게 만들다 보면 C의 인프라에 닿는다"가 이번 주차의 좋은 결론이다. A는 갭 자체가 없다(항상 실시간)는 대비도 함께 기록한다.
