② 도메인 엔티티 계층

③ 빈 협력 관계

SERVICE · TX①

OrderService.place() — Tx①

가장 크고 중요한 메서드다. 재고 차감 → 쿠폰 사용 → 금액 박제 → PENDING_PAYMENT 저장이 전부 트랜잭션 ① 하나에서 끝난다. 어느 분기에서 실패하든 Tx① 이 롤백되어 재고·쿠폰이 원복된다.

재고는 FOR UPDATE 로 일괄 조회하되 productId 오름차순으로 정렬해 잠근다 — 두 주문이 같은 상품 집합을 다른 순서로 잠그면 데드락이 난다. 쿠폰 검증·할인 계산이 끝난 뒤 expected 3종 변동 게이트를 통과해야 주문이 만들어진다.

place(userId: Long, command: OrderCreateCommand) → OrderInfoMUT · @Transactional
입력userId · command (items · couponId · expected 3종)
반환OrderInfo — status = PENDING_PAYMENT (결제는 아직)
책임재고 차감 + 쿠폰 사용 + 금액 3종 재계산·박제 + 변동 게이트 + Order 저장. 전부 Tx① 안
실패아래 표의 에러 전부 — 어느 지점이든 Tx① 롤백으로 재고·쿠폰 원복
왜 3종을 다 비교하나총액 1개만 비교하면 상품가 +1,000 / 할인 +1,000 이 상쇄되어 게이트가 뚫린다 — 유저가 본 계산서와 실제 구성이 달라졌는데 통과한다. 그래서 originalAmount · discountAmount · totalAmount 3종을 전부 비교한다. 이 값은 결제 금액의 근거가 아니라 비교 전용이고, 결제는 항상 서버 재계산값으로 한다.

PAYMENT · TX②

결제 진행 — Tx 밖 + Tx②

D1-b 의 핵심 — PG 호출은 트랜잭션 밖이다. 느린 외부 호출이 DB 락을 잡지 않고, 결과 3종(성공·거절·타임아웃)을 짧은 Tx② 에서 확정한다.

PaymentGateway.approve 는 박제된 totalAmount 로만 호출한다 — 현재 상품가를 재조회하지 않는다 (②→③ 의 짧은 틈은 박제가 막는다, 07 문서). 멱등키를 함께 보내 재시도 시 이중 결제를 막는다.

approve(orderId: Long, amount: Money, idempotencyKey: String) → PaymentGatewayResult외부 I/O · Tx 밖
입력orderId · amount — Order.totalAmount 박제값 · idempotencyKey — 재시도 멱등성
반환PaymentGatewayResult — SUCCESS / DECLINED / TIMEOUT 3종 (sealed/enum)
책임외부 PG 승인 요청. 인터페이스만 확정 — 구현 깊이(D8)·Payment 엔티티(D7)는 미결
UNKNOWN 의 의미타임아웃은 "실패"가 아니라 "모른다"다. 여기서 재고·쿠폰을 복원하면 실제로는 결제된 주문의 재고가 다른 사람에게 팔린다. UNKNOWN 은 복원 금지 + 보류가 정답이고, 후속 확인(PG 조회·배치)은 이번 범위 밖이다.
미결 사항D8 (PaymentGateway 구현 깊이) 과 D7 (Payment 엔티티 분리) 은 아직 결정하지 않았다. 이 문서는 인터페이스 시그니처(approve + 결과 3종)까지만 고정하고, 구현은 점선으로 둔다 — place 와 상태머신은 이 결정과 무관하게 지금 만들 수 있다.

COUPON METHODS

UserCoupon.use · Coupon.validateUsable

쿠폰 도메인에 새로 들어가는 메서드 두 개. use 는 상태를 바꾸는 쪽(@Version 낙관락), validateUsable 은 검증만 하는 쪽(기존 코드)이다.

UserCoupon 에는 usedAt: LocalDateTime? 과 @Version 필드를 추가한다. 같은 쿠폰을 두 요청이 동시에 사용하면 둘 다 AVAILABLE 을 읽고 통과하지만, 커밋 시점의 @Version 검사가 한쪽을 떨어뜨린다 — 이 충돌도 409 ALREADY_USED 로 변환한다.

use(now: LocalDateTime) → UnitMUT · @Version 낙관락
입력now — 사용 시각 (테스트 주입 가능하게 파라미터로)
변경status = USED · usedAt = now
실패status ≠ AVAILABLE → ConflictException(ALREADY_USED) · 커밋 시 @Version 충돌 → 409 변환
validateUsable(orderAmount: Money, now: LocalDateTime) → UnitPURE · 상태 변경 없음
입력orderAmount — 할인 전 originalAmount · now — 현재 시각
반환통과 시 아무것도 안 함 (Unit)
실패최소 주문 금액 미달 → 400 MIN_ORDER_NOT_MET · 만료 → 400 EXPIRED
비고기존 코드 그대로 — 이번에 수정 없음, place 가 새로 호출하기만 한다

DISCOUNT POLICY

DiscountPolicy.calculateDiscount

무상태 object — 입력만으로 결과가 정해지는 순수 함수다. 정률/정액 분기 후, 할인이 주문 금액을 넘지 않게 캡을 씌운다.

calculateDiscount(couponType: CouponType, value: Long, price: Money) → MoneyPURE · 부작용 없음
입력couponType — RATE/FIXED · value — 할인율(%) 또는 정액 · price — 할인 전 originalAmount
반환Money(discount) — 항상 0 ≤ discount ≤ price
책임할인액 계산만. 검증(만료·최소금액)은 validateUsable 의 몫
비고기존 구현 그대로 — place 가 새로 호출하기만 한다

ORDER ENTITY

Order.create · 상태 전이

create 는 박제를 완성하는 팩토리, 전이 메서드 3종은 상태머신의 게이트다 — PENDING_PAYMENT 가 아닌 상태에서의 전이는 전부 예외다.

기존 create(userId, snapshots) 시그니처에 couponId · 금액 3종이 추가된다. 전이 검증을 서비스가 아니라 Order 엔티티 메서드에 두는 이유 — 어떤 경로(API·배치·테스트)로 호출돼도 PAID → FAILED 같은 역전이가 불가능해야 하기 때문이다.

create(userId, couponId, originalAmount, discountAmount, totalAmount, snapshots) → Order팩토리 · 박제
입력place 가 재계산한 금액 3종 + couponId + OrderItemSnapshot 목록
반환Order — status = PENDING_PAYMENT, 저장은 place 가
실패snapshots 빈 목록 → 400 EMPTY_ORDER_ITEMS · quantity < 1 → 400 INVALID_ORDER_QUANTITY
전이confirmPayment() → PAID · failPayment() → FAILED · markUnknown() → UNKNOWN (전부 PENDING_PAYMENT 에서만)

CHECKLIST

구현 체크리스트

의존성 순서대로 — 아래 단계가 위 단계를 필요로 한다. 1·2 는 서로 독립이라 어느 쪽을 먼저 해도 된다.

  • UserCoupon 확장 — use(now) · restore() · usedAt · @Version + CouponErrorCode 에 ALREADY_USED 추가. 단위 테스트로 닫는다 Step 1
  • Order 확장 + 상태머신 — couponId · originalAmount · discountAmount 필드, OrderStatus 4종(CREATED 대체), confirmPayment/failPayment/markUnknown 전이 검증 Step 2
  • place 통합 — 쿠폰 조회·검증·사용 + 금액 3종 계산 + expected 변동 게이트 (OrderErrorCode 에 PRICE_CHANGED 추가, UserCouponRepository 에 findByUserIdAndCouponId 추가) Step 3
  • PaymentGateway + 결제 배선 — 인터페이스(approve + 결과 3종) 정의, Tx 밖 호출 → Tx② confirmPayment/failPayment/markUnknown 연결 (D7·D8 결정 후 구현) Step 4
  • 보상 로직 — DECLINED 시 inventory.increase + userCoupon.restore. TIMEOUT 은 보상 금지(UNKNOWN 보류) 테스트로 고정 Step 5
  • OrderController 재작성 — OrderCreateRequest(DTO 동거) · toCommand() · @RequestAttribute(ACCOUNT_ID) · OrderInfo 그대로 반환 Step 6
  • 동시성 테스트 3종 — ① 재고 차감 경합(FOR UPDATE) ② 쿠폰 중복 사용(@Version → 409) ③ 주문 생성-결제 흐름 통합 Step 7
진행 메모Step 1·2 는 06/07 의 미결(D7·D8)과 무관하게 지금 시작 가능하다. Step 4 만 결정 대기가 걸리고, 그 전까지 place 는 그림 5 의 형태로 완성해 둘 수 있다.
