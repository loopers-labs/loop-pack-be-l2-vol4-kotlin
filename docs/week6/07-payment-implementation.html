OVERVIEW

무엇을 구현했나

주문과 분리된 별도 결제 호출(Model A)을 구현했다. 클라이언트는 orderKey + 카드정보만 보내고, 서버가 주문을 조회해 금액을 확정한 뒤 PG(key-in)로 직접 제출한다. 결과 미확정·콜백 유실은 reconcile 이, 확실 실패는 보상이 처리한다.

  • payment 도메인 — Payment 엔티티 + 상태기계(PENDING→SUCCESS/FAILED/UNKNOWN), CardType, PaymentErrorCode domain
  • 제출 오케스트레이션 — PaymentFacade 가 prepare(@Tx) → PG submit(Tx 밖) → reflectSubmit(@Tx) application
  • 2-PG OpenFeign + failover — PgAClient :8082 / PgBClient :8092, PgPaymentGatewayImpl 이 Attempt sealed 로 분기 infrastructure
  • 콜백 수신 — /api/v1/payments/callback(인증 제외)이 orderKey 로 조회해 결과 반영 (멱등) interfaces
  • reconcile 스케줄러 — UNKNOWN 결제를 GET 조회로 해소, 30분 grace, 미해소 시 AlertSender application
  • 실패 보상 — Rejected·Failed 는 결제 FAILED + 주문 취소 + 재고·쿠폰 롤백(orderFacade.cancelAndCompensate)
  • 배선 — @EnableFeignClients · @EnableScheduling · 보안 제외 2곳 · pg url/timeout · resilience4j CB config
핵심 원칙금액은 클라이언트가 아니라 주문에서 확정(위변조 차단). raw 카드번호는 주문이 아닌 결제 요청에만 싣고 Payment 에 영속화하지 않는다(PCI 회피). PG 호출은 @Tx 바깥(외부 I/O 를 트랜잭션에 가두지 않음).

DATABASE

DB 테이블 (payment)

신규 테이블은 payment 1개. 마이그레이션 파일은 없고, local 프로파일의 ddl-auto 가 Payment 엔티티 매핑에서 Hibernate 로 생성한다.

Hibernate 생성 DDL (MySQL) — Payment + BaseEntity 매핑
create table payment (
    id              bigint       not null auto_increment,
    created_at      datetime(6)  not null,   -- BaseEntity
    updated_at      datetime(6)  not null,   -- BaseEntity
    deleted_at      datetime(6)  null,       -- BaseEntity (soft delete)
    order_id        bigint       not null,
    user_id         bigint       not null,
    amount          bigint       not null,   -- Money @AttributeOverride
    card_type       varchar(20)  not null,   -- CardType (EnumType.STRING)
    transaction_key varchar(100) null,       -- 접수 후 PG 발급 키
    status          varchar(20)  not null,   -- PaymentStatus
    reason          varchar(255) null,
    primary key (id)
) engine=InnoDB;
미적용 — 개선 후보cardNo 는 일부러 컬럼에 없다(PAN 비영속). 또 콜백은 findByOrderId(order.id), reconcile 는 findByStatus(UNKNOWN) 로 조회하는데 order_id · status 인덱스가 아직 없다 — 호출마다 풀스캔. 운영 전 인덱스 추가 + order_id 유니크(주문당 결제 중복 방지) 필요.

DOMAIN

Payment 상태기계

상태 전이는 엔티티가 소유한다(Tell-Don't-Ask). 잘못된 전이는 ConflictException 으로 거절. accept() 는 transactionKey 만 채우고 상태는 PENDING 유지(승인은 콜백/조회에서).

payment/domain/Payment.kt — 행위 + 상태기계
fun accept(transactionKey: String) { this.transactionKey = transactionKey }  // 접수: PENDING 유지
fun success() = transitionTo(PaymentStatus.SUCCESS)
fun fail(reason: String?) { this.reason = reason; transitionTo(PaymentStatus.FAILED) }
fun markUnknown() = transitionTo(PaymentStatus.UNKNOWN)

private fun transitionTo(target: PaymentStatus) {
    if (!status.canTransitionTo(target))
        throw ConflictException(PaymentErrorCode.INVALID_STATUS_TRANSITION)
    status = target
}

enum class PaymentStatus {
    PENDING, SUCCESS, FAILED, UNKNOWN;
    fun canTransitionTo(target) = when (this) {
        PENDING -> target in (SUCCESS, FAILED, UNKNOWN)
        UNKNOWN -> target in (SUCCESS, FAILED)   // reconcile 로 해소
        SUCCESS, FAILED -> false                 // 종결
    }
}
왜 UNKNOWN 이 종결이 아닌가제출 타임아웃·5xx 는 PG 에서 됐을 수도 있는 in-doubt 상태다. 함부로 FAILED 로 닫으면 실제 승인된 결제를 잃는다. 그래서 UNKNOWN 으로 두고 조회 reconcile 이 SUCCESS/FAILED 로 확정한다.

APPLICATION

트랜잭션 경계 · 결과 반영

Facade 는 @Tx 가 없다. DB 쓰기(prepare·reflectSubmit)만 각자 짧은 트랜잭션이고, 느린 PG 호출은 그 사이 트랜잭션 바깥에 둔다 — 커넥션을 외부 I/O 동안 잡지 않기 위해.

payment/application/PaymentFacade.kt
fun pay(command: PaymentCommand): PaymentInfo {
    val prepared = paymentService.prepare(           // @Tx #1
        PaymentPrepareCommand(command.userId, command.orderKey, command.cardType))

    val result = pgPaymentGateway.submit(            // Tx 밖 — 외부 호출
        PgSubmitCommand(command.userId, command.orderKey, command.cardType,
            command.cardNo, prepared.amount, callbackUrl))   // callbackUrl = @Value pg.callback-url

    return paymentService.reflectSubmit(prepared.paymentId, result)  // @Tx #2
}
payment/application/PaymentService.kt — prepare · reflectSubmit · handleCallback
@Transactional
fun prepare(command): PreparedPayment {
    val order = orderRepository.findByOrderKey(command.orderKey)
        ?.takeIf { it.userId == command.userId }       // 소유 검증 (ID enumeration 차단)
        ?: throw NotFoundException(OrderErrorCode.ORDER_NOT_FOUND)
    if (order.status != OrderStatus.PENDING_PAYMENT)    // 결제 가능 상태?
        throw ConflictException(PaymentErrorCode.ORDER_NOT_PAYABLE)
    val payment = paymentRepository.save(
        Payment.create(order.id, command.userId, order.totalAmount, command.cardType))
    return PreparedPayment(payment.id, order.totalAmount.amount)  // 금액은 주문에서
}

@Transactional
fun reflectSubmit(paymentId, result): PaymentInfo {
    val payment = paymentRepository.findById(paymentId) ?: throw NotFound(...)
    when (result) {
        is Accepted -> payment.accept(result.transactionKey)            // PENDING 유지
        is Rejected -> failAndCompensate(payment, result.reason)         // 400 = 우리 버그
        is Failed   -> failAndCompensate(payment, "PG 사용 불가로 결제 실패")  // 전송 확실 실패
        is Unknown  -> { payment.markUnknown(); markOrderUnknown(payment.orderId) }  // timeout/5xx
    }
    return PaymentInfo.from(payment)
}

@Transactional
fun handleCallback(command) {                  // 콜백 = orderKey 로 결제 조회
    val order = orderRepository.findByOrderKey(command.orderKey) ?: throw NotFound(...)
    val payment = paymentRepository.findByOrderId(order.id) ?: throw NotFound(...)
    resolve(payment, command.status, command.transactionKey, command.reason)  // 멱등(terminal 이면 무시)
}
실패 = 보상까지failAndCompensate() 는 결제를 FAILED 로 닫고 orderFacade.cancelAndCompensate(order) 로 주문 취소 + 재고·쿠폰을 되돌린다. Rejected(400)·Failed(전 PG 미전송)·콜백 FAILED 가 모두 이 경로를 탄다 — "결제 실패 = 주문도 원복" 을 한 곳에서 보장.

PG ADAPTER

Feign · failover · 조회

두 Feign 클라이언트는 부모 인터페이스를 상속해 같은 계약을 공유한다(Spring Cloud OpenFeign inheritance). 제출(POST)과 reconcile 조회(GET)를 둘 다 정의한다.

payment/infrastructure/pg/PgPaymentClient.kt
interface PgPaymentClient {
    @PostMapping("/api/v1/payments")
    fun request(@RequestHeader("X-USER-ID") userId: String,
                @RequestBody request: PgPaymentRequest): PgApiResponse<PgTransactionResponse>

    @GetMapping("/api/v1/payments")                          // reconcile 조회
    fun findByOrderId(@RequestHeader("X-USER-ID") userId: String,
                     @RequestParam("orderId") orderId: String): PgApiResponse<PgOrderResponse>
}
@FeignClient(name = "pg-a", url = "\${pg.clients.a.url}") interface PgAClient : PgPaymentClient
@FeignClient(name = "pg-b", url = "\${pg.clients.b.url}") interface PgBClient : PgPaymentClient

CB(@CircuitBreaker)는 별도 PgPaymentRequester 빈에 부착한다 — 같은 빈 self-invocation 에는 AOP 가 안 먹기 때문(이 레이어의 비용은 §10 개선안에서 다룬다).

payment/infrastructure/pg/PgPaymentRequester.kt
@Component
class PgPaymentRequester(val pgAClient: PgAClient, val pgBClient: PgBClient) {
    @CircuitBreaker(name = "pg-a")
    fun requestToPgA(userId, request) = pgAClient.request(userId, request)
    @CircuitBreaker(name = "pg-b")
    fun requestToPgB(userId, request) = pgBClient.request(userId, request)
}

failover 의 핵심은 "호출이 안 일어난 게 확실한가"로 결과를 가르는 것(O9). 게이트웨이는 한 번 시도의 결과를 sealed Attempt 로 만들어 when 으로 분기한다 — 예외를 control-flow 로 흘리지 않는다.

payment/infrastructure/pg/PgPaymentGatewayImpl.kt
override fun submit(command): PgSubmitResult =
    when (val primary = attempt { requester.requestToPgA(userId, request) }) {
        is Accepted    -> PgSubmitResult.Accepted(primary.transactionKey)
        is Rejected    -> PgSubmitResult.Rejected(primary.reason)
        is InDoubt     -> PgSubmitResult.Unknown               // 보냈을 수도 → reconcile
        is Unavailable -> failover(userId, request)            // 안 됐음 확실 → B
    }

private fun failover(userId, request) =
    when (val secondary = attempt { requester.requestToPgB(userId, request) }) {
        is Accepted    -> PgSubmitResult.Accepted(secondary.transactionKey)
        is Rejected    -> PgSubmitResult.Rejected(secondary.reason)
        is InDoubt     -> PgSubmitResult.Unknown
        is Unavailable -> PgSubmitResult.Failed                // 둘 다 미전송 = 확실 실패
    }

private fun attempt(call): Attempt =
    try { Attempt.Accepted(call().data?.transactionKey ?: return Attempt.InDoubt("응답 본문 없음")) }
    catch (e: CallNotPermittedException) { Attempt.Unavailable(e.message) }   // CB OPEN → B
    catch (e: RetryableException) {
        if (e.cause is ConnectException) Attempt.Unavailable(e.message)         // refused → B
        else Attempt.InDoubt(e.message) }                                    // timeout → UNKNOWN
    catch (e: FeignException.BadRequest) { Attempt.Rejected(e.contentUTF8()) }   // 400
    catch (e: FeignException) { Attempt.InDoubt(e.message) }                     // 전송 후 5xx

private sealed interface Attempt {
    data class Accepted(val transactionKey: String) : Attempt
    data class Rejected(val reason: String) : Attempt
    data class Unavailable(val message: String?) : Attempt   // 미전송 → 다음 PG
    data class InDoubt(val message: String?) : Attempt       // 보냈을 수도 → 중단
}

제출 결과 매핑 — Failed vs Unknown

"실패"는 한 덩어리가 아니다. 전송이 확실히 안 된 경우(Failed)와 보냈을 수도 있는 경우(Unknown)는 응답이 정반대여야 한다.

Failed 전 PG unavailable

connect-refused / CB-open 으로 전송 0회 = 확실히 미결제. → 결제·주문 FAILED + 재고·쿠폰 보상. 재시도 안전.

Unknown in-doubt

timeout / 5xx 로 PG 가 받았을 수도 있음. → UNKNOWN 유지 + reconcile 로 확정. 절대 "실패"로 응답하지 않음(재시도 시 이중결제).

함정 (O9)in-doubt 에 "실패" 응답을 주면 유저가 재시도 → 이중결제. 그래서 failover 는 "호출이 안 일어난 게 확실한" Unavailable(CB OPEN·refused)일 때만 B 로 넘기고, InDoubt(timeout·전송 후 5xx)는 B 금지하고 UNKNOWN 으로 둔다.

reconcile 용 조회는 A·B 를 모두 본다. 한쪽이라도 Found 면 그 결과, 둘 다 못 찾으면 한쪽이라도 닿지 않았으면 Unreachable, 아니면 NotFound(미전송).

PgPaymentGatewayImpl.query — reconcile 조회
override fun query(command): PgQueryResult {
    val onA = queryOne(pgAClient, userId, orderKey); if (onA is Found) return onA.result
    val onB = queryOne(pgBClient, userId, orderKey); if (onB is Found) return onB.result
    return if (onA is Unreachable || onB is Unreachable) PgQueryResult.Unreachable
           else PgQueryResult.NotFound
}
orderKey 그대로PG 로 보내는 PgPaymentRequest.orderId 는 주문의 orderKey(비즈니스 식별자)를 그대로 싣는다 — 이전의 padStart(6,'0') 인코딩은 제거됐다. 조회도 같은 orderKey 로 한다.

RECONCILE

reconcile 안전망 (스케줄러)

콜백은 유실 가능하고 제출은 UNKNOWN 으로 끝날 수 있다. 스케줄러가 UNKNOWN 결제를 주기적으로 조회해 PAID/FAILED 로 확정하는 것이 진짜 안전망이다.

payment/application/PaymentReconciler.kt
@Component
class PaymentReconciler(service, gateway, alertSender) {
    @Scheduled(fixedDelayString = "\${pg.reconcile.fixed-delay:60000}")   // 기본 60s
    fun reconcile() {
        val targets = service.findReconcileTargets()           // status = UNKNOWN
        targets.forEach { t ->
            val q = gateway.query(PgQueryCommand(t.userId, t.orderKey))   // A·B 조회
            if (service.applyReconcile(t.paymentId, q) == NEEDS_ALERT)
                alertSender.alert("reconcile 미해소 (paymentId=\${t.paymentId}): \$q")
        }
    }
}

applyReconcile 은 결제 생성 후 30분 grace(RECONCILE_DEADLINE) 를 두고, 조회 결과별로 확정/대기/알림을 가른다.

조회 결과grace(30분) 전grace 후
Found · SUCCESS즉시 PAID 확정 + 주문 confirm (멱등)
Found · FAILED즉시 FAILED 확정 + 보상
Found · PENDING대기(PENDING)NEEDS_ALERT
NotFound (미전송)대기(PENDING)FAILED 확정 (과금 없음 → 안전)
Unreachable (PG 장애)대기(PENDING)NEEDS_ALERT (함부로 실패 X)
멱등 + 충돌 감지resolve() 는 이미 종결(SUCCESS/FAILED)된 건은 무시한다. 단 FAILED 로 닫힌 건에 PG SUCCESS 통보가 오면 AlertSender 로 "수동 확인 필요" 알림을 쏜다. LoggingAlertSender 는 현재 [PAYMENT-ALERT] ERROR 로그로 구현(후속에 실제 알림 채널 교체 가능).

+     ignore-exceptions: [FeignClientException]                       # 4xx 는 CB 무시
+   instances: { pg-a, pg-b → base-config: default }
보안 제외 2곳 이유콜백은 PG 가 호출해 로그인 헤더가 없다. permitAll 만 하면 인가는 통과하지만 헤더 필터가 인증을 시도한다. 필터 shouldNotFilter 까지 빼야 불필요한 인증 시도가 없다 — 그래서 SecurityConfig + 필터 둘 다.

REDESIGN · 미적용

게이트웨이 개선안

지금 PG 한 번 부르는 경로는 Facade → port → GatewayImpl → Requester → Feign 5클래스다. 그중 PgPaymentRequester 는 오직 @CircuitBreaker 가 같은 빈 self-invocation 에 안 먹는 AOP 제약 때문에 프록시 경계를 만들려고 존재한다 — 비즈니스 의미 0의 AOP 세금.

이미 반영된 것이 재설계안 중 (1) throw control-flow → 내부 sealed Attempt 반환, (2) PgSubmitResult 에 Failed 추가(전송 확실 실패 ↔ 미확정 분리) 는 이미 §6 코드에 적용됐다. 아래 구조 변경(Requester 제거·strategy·프로그래밍 CB)이 남은 제안이다.

애너테이션(@CircuitBreaker)을 버리고 resilience4j 프로그래밍 API(CircuitBreakerRegistry)로 전환하면 self-invocation 문제가 사라져 Requester 레이어가 통째로 증발한다. 그리고 PG 선택을 하드코딩(requestToPgA/requestToPgB)이 아니라 순서 있는 클라이언트 목록(List<NamedPgClient>)으로 두면 목록 순서가 곧 우선순위인 진짜 strategy 가 된다.

네이밍

현재문제재설계
PgPaymentGatewayImplImpl 접미사 = 의미 0FailoverPgPaymentGateway
PgPaymentRequester무의미 + AOP 세금(제거)
requestToPgA / requestToPgBA/B 를 메서드에 하드코딩clients 목록 (데이터)
PgAClient / PgBClient그 자체론 CB 이름 분리 안 됨NamedPgClient(name, client)

4xx 매핑 비대칭

지금은 BadRequest(400)만 Rejected 로 잡고, 429·404·409 같은 다른 4xx 는 마지막 catch(FeignException) 으로 떨어져 조용히 InDoubt(→UNKNOWN) 가 된다. CB 는 4xx 전부를 ignore 하는데(FeignClientException) 게이트웨이 매핑은 BadRequest 만 다뤄 비대칭이다.

응답현재재설계
400 BadRequestRejectedfail-fast 노출 (시뮬레이터는 동기 거절 없음 → 400 = 우리 요청 버그)
429 / 404 / 409 등조용히 UNKNOWN (누수)명시적으로 분류
5xx · timeoutInDoubt → Unknown유지 (의도대로)
관심사 분리는 유지timeout 은 여전히 Feign 몫(HTTP 를 쏘니까), CB 만 애너테이션 → 레지스트리로 바뀐다. timeout=Feign / CB=resilience4j 분리는 그대로 유지되고 겹치지 않는다.
