01

OVERVIEW

개요

관리자가 미리 생성된 쿠폰을 특정 사용자 한 명에게 지급하는 관리자 전용 엔드포인트다.

CouponController.grantCoupon은 path의 couponId와 body의 userId를 받아 CouponService.grant로 위임한다. 쿠폰이 존재하고 만료되지 않았으며, 대상 사용자가 존재하고, 아직 같은 쿠폰을 받지 않았을 때만 발급된다.

발급 결과는 UserCoupon 엔티티로 영속화되며, 발급 경로(grantedType = ADMIN)와 발급 주체(grantedBy = 관리자 accountId)가 함께 기록된다.

핵심경로는 /api-admin/v1/** 아래에 있어 관리자만 접근할 수 있다. AdminLdapAuthenticationFilter가 X-Loopers-Ldap: loopers.admin 헤더 + 로그인 자격증명을 검증하고 계정 role 이 ADMIN 인지까지 확인한 뒤(아니면 401) ACCOUNT_ID를 주입하며, 이 값이 발급 주체(grantedBy)로 기록된다.

// 관리자 인증 필터가 ACCOUNT_ID 를 request attribute 로 주입한다
@PostMapping("/api-admin/v1/coupons/{couponId}/grant")
fun grantCoupon(
    @PathVariable couponId: Long,
    @RequestBody couponGrantRequest: CouponGrantRequest,
    @RequestAttribute(ACCOUNT_ID) requestAccountId: Long,
) = couponService.grant(couponId, couponGrantRequest.userId, requestAccountId)

data class CouponGrantRequest(
    val userId: Long,
)

04

BUSINESS LOGIC

비즈니스 로직

CouponService.grant는 단일 @Transactional 안에서 4단계 검증 후 발급한다.

1. 쿠폰 존재 검증

couponRepository.findById(couponId)가 null 이면 NotFoundException(COUPON_NOT_FOUND) → 404. 쿠폰이 먼저 검증된다.

2. 만료 검증

조회한 쿠폰에 coupon.isExpired(LocalDateTime.now())를 호출한다. expiredAt < now이면 BadRequestException(EXPIRED) → 400. 만료 판정은 Coupon 도메인이 소유한다(expiredAt < now).

3. 대상 사용자 존재 검증

accountRepository.findById(userId)가 null 이면 NotFoundException(AccountErrorCode.ACCOUNT_NOT_FOUND) → 404. 존재하지 않는 사용자에게는 발급하지 않는다.

4. 중복 발급 방지

userCouponRepository.existsByUserIdAndCouponId(userId, couponId)가 true 면 ConflictException(ALREADY_GRANTED) → 409. 한 사용자에게 같은 쿠폰은 한 번만 발급된다.

5. UserCoupon 생성·저장

모든 검증을 통과하면 UserCoupon을 생성해 저장한다. 발급 경로는 grantedType = ADMIN, 발급 주체는 grantedBy = 관리자 accountId로 기록한다. 초기 상태는 status = AVAILABLE이며 @Version 낙관적 락 필드를 가진다.

CouponService.kt 
@Transactional
fun grant(couponId: Long, userId: Long, grantedBy: Long) {
    val coupon = couponRepository.findById(couponId)
        ?: throw NotFoundException(CouponErrorCode.COUPON_NOT_FOUND)
    if (coupon.isExpired(LocalDateTime.now())) {
        throw BadRequestException(CouponErrorCode.EXPIRED)
    }
    accountRepository.findById(userId)
        ?: throw NotFoundException(AccountErrorCode.ACCOUNT_NOT_FOUND)
    if (userCouponRepository.existsByUserIdAndCouponId(userId, couponId)) {
        throw ConflictException(CouponErrorCode.ALREADY_GRANTED)
    }

    userCouponRepository.save(
        UserCoupon(
            userId = userId,
            couponId = couponId,
            grantedType = UserCouponGrantedType.ADMIN,
            grantedBy = grantedBy,
        ),
    )
}

중복 방지의 이중 방어선

코드에는 중복 발급을 막는 두 겹의 방어선이 있다.

1차 사전 existsBy 체크

service 에서 existsByUserIdAndCouponId로 선제 검증 → 409. 정상 경로에서 의미 있는 에러 코드를 돌려준다.

2차 DB unique 제약

user_coupon 테이블의 uk_user_coupon_user_id_coupon_id 유니크 제약. 동시 요청이 1차 체크를 동시에 통과해도 DB 레벨에서 한 건만 저장된다.

발급 수량 제한

참고현재 Coupon 엔티티와 grant 로직에는 총 발급 수량/재고 한도 필드가 없다(코드 확인). 사용자 1인당 1매 중복 방지(유니크)만 존재하며, "선착순 N매" 같은 발급 총량 제한은 구현되어 있지 않다.

05

CAUTION

주의사항

동시성 — 중복 발급사전 existsBy 체크는 동시 요청 사이의 race 를 단독으로 막지 못한다. 같은 (userId, couponId) 로 두 요청이 동시에 1차 체크를 통과하면, 최종 방어는 user_coupon 의 유니크 제약(uk_user_coupon_user_id_coupon_id)이다. 두 번째 INSERT 는 DataIntegrityViolationException으로 실패하므로, 이 경로의 변환 정책(409 vs 500)을 확인해야 한다.
검증 순서현재 순서는 쿠폰 존재 → 만료 → 사용자 존재 → 중복이다. 만료 검증이 사용자 존재보다 먼저이므로, 존재하지 않는 사용자에게 만료된 쿠폰을 발급하려 하면 404(ACCOUNT_NOT_FOUND)가 아니라 400(EXPIRED)이 먼저 반환된다.
인가 범위SecurityFilterChain의 .requestMatchers(ADMIN_PATH).authenticated()는 인증만 요구하는 백스톱이고, 실제 관리자 인가는 그 앞에 등록된 AdminLdapAuthenticationFilter가 강제한다 — X-Loopers-Ldap 헤더 값 + 자격증명 + role == ADMIN 세 가지를 모두 통과해야 하며, 하나라도 어긋나면 401. 따라서 일반 사용자는 이 경로에 접근할 수 없고, grantedBy에는 인증된 관리자의 ACCOUNT_ID 가 기록된다.
발급 주체 신뢰grantedBy는 body 가 아니라 인증 필터가 주입한 @RequestAttribute(ACCOUNT_ID)에서 온다. 클라이언트가 임의로 발급자 ID 를 위조할 수 없는 구조다.
