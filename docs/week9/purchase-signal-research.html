구매 신호는 어떻게
인기 점수가 되는가

실시간 상품 랭킹의 주문 스코어를 정하기 위해, 구매(주문) 지수를 랭킹 점수로 치환한 실제 서비스 13곳을 공식 출처로만 조사했다. 결론 — 인기 랭킹은 금액을 세지 않는다. 건수를 센다.

QUESTION & ANSWER

조사 질문과 한 줄 결론

질문: 주문(구매) 신호를 인기 점수에 반영할 때, 실제 서비스들은 무엇을 세는가 — 금액인가, 수량인가, 건수인가?

과제 요구사항은 주문 스코어 예시로 price × amount (정규화 시 log)를 제시하면서 "우리 기준으로 재산정"을 요구했다. 재산정의 근거를 만들기 위해 구매 신호를 랭킹에 쓰는 서비스들의 공식 문서·공식 기술블로그·공개 소스코드만 조사했다.

"인기" 랭킹에서 구매를 금액으로 반영하는 공증된 사례는 한 곳도 없었다. 구매는 건수 또는 전환율로 세고, 금액을 쓰는 서비스는 스스로를 "인기"가 아니라 "판매(Top Sellers)" 랭킹이라 부른다.

— 13개 사례 조사 결론 (2026-07-15)
조사에서 제외한 곳 (출처 불충족 — 지어내지 않음) 쿠팡 랭킹순 · 배달의민족 노출 순위 · 교보문고 판매지수 · App Store 차트 — 산식 비공개 또는 공식 출처 미확인으로 비교표에서 제외. 예스24와 네이버쇼핑은 널리 알려진 내용이 있으나 공식 원문 URL을 확인하지 못해 † 표시(참고용)로만 포함했다.
2

TAXONOMY

치환 방식 4분류 지도

13개 사례의 치환 방식은 정확히 4가지로 수렴한다. 갈림길은 "무엇을 세는가"와 "점수 공식이 존재하는가"다.

핵심"가격을 반영하는 게 맞나"라는 질문에 업계가 이미 답해 놓았다 — 랭킹의 이름이 '인기'라면 반영하지 않는다. 금액을 쓰려면 Steam처럼 이름부터 "Top Sellers(판매 랭킹)"로 바꾸는 것이 정직하다.
3

CASE BY CASE

사례별 치환 상세 (13곳)

각 서비스가 구매 신호를 정확히 무엇으로 바꾸는지, 공식 원문 근거와 함께 정리했다.

① 건수 카운트 — 금액·수량을 버린다

사례구매 신호의 치환원문 근거
Shopify상품이 포함된 주문의 개수만 센다. 한 주문에 수량 100개여도 1건[1][2]"the all-time number of orders that include the product"
Amazon BSR판매 건수 기반 + 최근 판매 가중. 조회수·리뷰는 반영 안 함[3][4][5]"based on Amazon sales… recent sales count more"
예스24 †산식 비공개(영업기밀). 보도 기준 기간 가중 건수 + 구매자 다양성 가중(1인 100권 ≠ 100인 1권)공식 원문 없음 — 참고만

② 매출 합산 — 스스로 "판매 랭킹"이라 부른다

사례구매 신호의 치환원문 근거
Steam Top Sellers최근 24시간 매출 합산 + 최근 3시간 추가 가중. DLC·인앱 포함 전 매출원[6]"roll up all the player spending from the trailing 24 hours, add extra weight to the last 3 hours"
Billboard Hot 100판매·스트리밍·라디오를 명시적 환산율로 통일 — 1 판매 = 1,250 스트림, 유료 스트림 1점 vs 광고 스트림 ⅔점[7]이종 신호 → 공통 단위 환산의 대표 사례

③ 압축·지수화 — 금액/카운트를 눌러서 혼합한다

사례구매 신호의 치환원문 근거
Elasticsearch인기 수치에 log1p 압축 후 관련성 점수에 곱함 — 원시값이 다른 신호를 압살하는 문제의 공식 해법[8]"new_score = old_score × log(1 + number_of_votes)"
Reddit hotlog10(순추천수) — 첫 10표 = 다음 100표 = 다음 1,000표[9]공개 소스 _sorts.pyx
네이버쇼핑 †인기도의 판매실적 = 최근 2·7·30일 판매수량+판매금액을 지수화, 카테고리 상대화공식 SEO 가이드 원문 URL 미확인 — 참고만
Algoliasales count를 custom ranking으로 — 단 텍스트 관련성의 동점자 처리(tie-break)로만[10]인기도는 관련성을 이기지 못한다

④ ML feature — 점수 공식 자체가 없다

사례구매 신호의 치환원문 근거
Etsyclicks·views·favorites·purchases → listing quality score(구매 전환 확률 예측)[11][12]Seller Handbook + 법정 공시
Airbnb위시리스트 저장·예약 빈도·메시지 등 engagement가 랭킹 입력[13]공식 Help "how often guests book"
Instacart전환율(Search Conversion Rate·Add-to-Cart Rate)이 랭킹 feature[14]공식 tech blog
eBay Best Matchrelevance + item popularity + value 종합 score (세부 비공개)[15]공식 Help
어뷰징 관점의 공통 방향Shopify는 수량 100개 주문을 1건으로 세고, 예스24는 1인 100권과 100인 1권을 다르게 가중한다(보도 기준). 방향은 같다 — "몇 명이 결정했나"를 세고, "얼마짜리를 몇 개"는 세지 않는다. 건수 카운트는 저가 대량 사재기가 점수를 선형으로 밀어올리는 구멍이 없다.
4

COMMON PATTERN

공통 패턴 — 시간 감쇠

무엇을 세든, 조사한 모든 랭킹이 "최근"에 가중을 둔다. 우리의 일간 버킷 + carry ×0.1은 이 보편 패턴의 한 구현이다.

서비스시간 장치우리 설계와의 대응
Amazon BSR전체 이력 반영하되 최근 판매에 더 큰 가중[4]일간 버킷 = 오늘에 최대 가중
Steam24h 롤링 윈도우 + 최근 3h 추가 부스트[6]일간 tumbling window와 동일 계열
네이버쇼핑 †2일 / 7일 / 30일 다중 기간 구간오늘 판 + 내일 판(×0.1) 2계층
Reddit시간항을 점수에 직접 합산 (45,000초당 1점)[9]감쇠를 쓰기 시점에 반영하는 발상이 carry와 동일
함의어제 결정한 dual write carry(오늘 판 +Δ, 내일 판 +Δ×0.1)는 업계 보편 장치(recency weighting)를 우리 저장 구조(일간 버킷)에 맞게 번역한 것이다. 방향이 표준과 일치한다.

DECISION

우리 가중치 확정

조사 결과를 반영해 스코어 모델을 확정한다 — 주문은 Shopify·Amazon 계열의 "건수 카운트"를 채택한다.

이벤트Δ (오늘 판)carry (내일 판)근거
상품 조회+0.1+0.01요구사항 가중치 그대로
좋아요+0.2+0.02요구사항 가중치 그대로
좋아요 취소−0.2−0.02대칭 차감 — product_metrics와 동작 일치, 반복 어뷰징 차단, ZINCRBY 의미론과 동일
주문 (order line당)+0.7 고정+0.07건수 카운트 채택 (Shopify·Amazon 계열). 가격·수량 미반영
score-model.txt
// 스코어 델타 (이벤트 1건당)
delta(view)         = 0.1
delta(like)         = +0.2   // unlike = -0.2 (대칭)
delta(order line)   = 0.7    // 가격·수량 미반영 — 구매 "결정"을 센다

// dual write carry (날짜 경계, 2026-07-15 확정)
on event: 오늘 판 += Δ, 내일 판 += Δ × 0.1

// 검증 요건 충족
주문 1건 0.7 > 좋아요 3건 0.6  ✓  // weight 0.6~0.7 허용 범위에서 0.7 채택

버린 대안 2개

기각 B수량 반영 — 0.7 × quantity

판매량 랭킹 의미론. 직접 대응 사례가 없고(Shopify는 오히려 수량을 버림), 저가 상품 100개 주문이 +70으로 선형 부스트되는 어뷰징 구멍이 있다. 수량·매출 정보는 이미 product_metrics에 남으므로 정보 손실도 없다.

기각 C금액 log — 0.6 × ln(1+price×qty)

요구사항 예시 형태(Elastic·네이버 계열). 그러나 log 압축 후 가격 100배 차이가 점수 1.5배로 줄어 사실상 상수 + 미세 보정이 된다 — 유지할 실익이 작고, "인기 랭킹에 왜 가격이 있나"라는 의미론 문제는 그대로 남는다.

요구사항 예시와 다른 점 (의도된 이탈)요구사항 예시는 주문 Score = price × amount였다. 우리는 order line당 0.7 고정으로 재산정했다. 근거 — ① 인기 랭킹에서 금액을 반영하는 공증 사례가 없음 ② 금액을 쓰는 곳(Steam)은 스스로 "판매 랭킹"이라 명명 ③ 요구사항 자체가 "예시, 우리 기준으로 재산정"을 요구. 이 결정은 WRITING-LOG에 기록한다.
