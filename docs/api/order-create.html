OVERVIEW

개요

한 번의 요청으로 여러 상품·수량을 묶어 주문을 만든다. 인증된 사용자의 ACCOUNT_ID 를 주체로, 상품 조회 → 금액 계산 → 기대 금액 검증 → 쿠폰 할인 → 재고 차감을 하나의 트랜잭션 안에서 순서대로 처리한다.

이 엔드포인트는 가장 복잡한 교차 도메인 흐름이다. 한 요청이 product · coupon · inventory · order 네 도메인의 애플리케이션 서비스를 차례로 호출하며, OrderFacade.place 가 오케스트레이션과 트랜잭션 경계를 책임진다. 어느 단계든 실패하면 전체가 롤백되어 부분 반영이 남지 않는다.

핵심클라이언트가 보낸 expected* 금액 3종은 신뢰하지 않는다. 서버가 상품 가격·쿠폰으로 다시 계산한 금액과 다르면 PRICE_CHANGED 로 거절한다. 가격 변동 중 주문을 막는 낙관적 방어선이다.

관여 도메인

도메인서비스이 흐름에서의 책임

참고이 흐름에는 포인트 차감도, 도메인 이벤트 발행도 없다. 주문은 PENDING_PAYMENT 상태로 생성될 뿐 결제·이벤트 처리는 이 엔드포인트의 책임이 아니다 (코드 기준).

3

SEQUENCE

시퀀스 다이어그램

한 번의 place() 호출이 네 도메인을 순서대로 거친다. 점선 박스 = 단일 @Transactional 경계 — 그 안의 모든 DB 변경은 전부 커밋되거나 전부 롤백된다.

핵심재고 차감(비관적 락)이 일부러 마지막 단계다. OrderFacade 주석 그대로 — "비관락(재고)은 맨 마지막 — 행 점유 시간 최소화". 락을 잡은 채로 상품 조회·금액 검증 같은 다른 작업을 기다리지 않게 한다.
4

BUSINESS LOGIC

비즈니스 로직

코드에서 확인된 단계만 순서대로 정리한다. 모든 단계는 OrderFacade.place 의 단일 트랜잭션 안에서 실행된다.

  • ① 인증 — 인증 필터가 주입한 @RequestAttribute(ACCOUNT_ID) 로 주체 userId 확보.
  • ② 빈 주문 검증 — items 가 비어 있으면 BadRequestException(EMPTY_ORDER_ITEMS).
  • ③ 상품 일괄 조회·활성 확인 — ProductService.getActiveProducts(ids) 가 활성 상품을 Map으로 반환. 요청 ID 중 하나라도 없으면 NotFoundException(PRODUCT_NOT_FOUND). 가격은 이 시점의 상품 가격을 스냅샷으로 사용.
  • ④ 원금액 계산 — originalAmount = Σ (상품 price × quantity) 를 서버가 직접 계산.
  • ⑤ 쿠폰 적용 (선택) — couponId 가 있을 때만 CouponService.use 호출. 사용자 보유 쿠폰 조회(없으면 COUPON_NOT_FOUND), validateUsable 로 최소주문금액(MIN_ORDER_NOT_MET)·만료(EXPIRED) 검증, 이미 사용 시 ALREADY_USED, 그 후 할인액 계산. 없으면 할인 0.
  • ⑥ 기대 금액 검증 — OrderService.create 가 재계산한 original·discount·total 과 요청의 expected* 3종이 하나라도 다르면 ConflictException(PRICE_CHANGED). 클라이언트 금액은 신뢰하지 않는다.
  • ⑦ 주문 저장 — Order.create(userId, snapshots, couponId, discountAmount) 로 항목·금액·할인을 채우고 orderRepository.save. 초기 상태는 PENDING_PAYMENT.
  • ⑧ 재고 차감 (비관적 락) — InventoryService.decreaseStock 가 SELECT … FOR UPDATE (PESSIMISTIC_WRITE) 로 재고 행을 productId 정렬 순서로 잠그고 decrease(). 재고 부족 시 ConflictException(STOCK_INSUFFICIENT), 행 없으면 INVENTORY_NOT_FOUND.
  • ⑨ 원자적 커밋 — 위 모든 단계가 성공하면 트랜잭션이 커밋된다. 어느 단계든 예외가 나면 전체 롤백 — 주문도 재고도 쿠폰 사용도 반영되지 않는다.

할인 계산 규칙

참고DiscountPolicy.calculateDiscount — RATE: price × value / 100, FIXED: value. 두 경우 모두 minOf(raw, price) 로 캡 — 할인이 주문 금액을 넘지 않는다.

주문 상태 전이

참고생성 직후 PENDING_PAYMENT. 이후 PAID / FAILED / UNKNOWN 로만 전이 가능하며, PAID·FAILED 는 종착 상태다. 잘못된 전이는 INVALID_STATUS_TRANSITION. (이 엔드포인트는 PENDING_PAYMENT 생성까지만 책임)

심화금액 검증은 왜 OrderService 안에서 일어나나

OrderFacade 는 상품 Map과 할인액을 모은 뒤 OrderService.create 에 넘긴다. create 가 스냅샷 기준으로 originalAmount 와 totalAmount = original − discount 를 다시 계산하고, 이 세 값이 요청의 expected* 와 일치하는지 마지막으로 검산한다. 즉 금액 진실의 출처는 항상 서버이고, 클라이언트 값은 "내가 본 가격이 맞나" 확인용일 뿐이다.

CAUTION

주의사항

주의 · 동시성재고 차감은 비관적 쓰기 락(PESSIMISTIC_WRITE) 으로 보호된다. JPQL SELECT … FOR UPDATE 에 ORDER BY productId 를 강제해 여러 주문이 동일 상품 집합을 교차로 잠글 때 데드락을 막는다 (락 획득 순서 통일). 락 구간은 트랜잭션 맨 마지막에 두어 행 점유 시간을 최소화한다.
주의 · 금액 신뢰expected* 금액을 그대로 믿으면 안 된다. 결제액·할인액은 서버가 상품 가격과 쿠폰으로 재계산한 값이 진실이고, 요청의 expected* 는 대조용 방어선이다. 불일치 시 PRICE_CHANGED 로 거절해 가격 변동 중 잘못된 금액의 주문 성립을 막는다.
주의 · 부분 실패상품 조회 · 쿠폰 사용 · 주문 저장 · 재고 차감이 하나의 트랜잭션이다. 마지막 재고 차감에서 STOCK_INSUFFICIENT 가 나면 앞서 처리된 쿠폰 사용(UserCoupon.use)과 주문 저장까지 전부 롤백된다. 부분 반영(쿠폰만 소진, 주문만 생성 등)은 발생하지 않는다.
참고 · 확장 지점OrderFacade 주석에 따르면 추후 PG 연동(O-F1) 시 트랜잭션 구간을 안쪽 메서드로 분리하고 외부 호출은 트랜잭션 밖에 둘 예정이다. 현재 코드에는 외부 결제 호출·포인트 차감·도메인 이벤트 발행이 존재하지 않는다.
