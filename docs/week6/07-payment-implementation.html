OVERVIEW

무엇을 구현했나

주문과 분리된 별도 결제 호출(Model A)을 그대로 구현했다. 클라이언트는 orderId + 카드정보만 보내고, 서버가 주문을 조회해 금액을 확정한 뒤 PG(key-in)로 직접 제출한다.

  • payment 도메인 — Payment 엔티티 + 상태기계(PENDING→SUCCESS/FAILED/UNKNOWN), CardType, PaymentErrorCode domain
  • 제출 오케스트레이션 — PaymentFacade 가 prepare(@Tx) → PG 호출(Tx 밖) → reflectSubmit(@Tx) application
  • 2-PG OpenFeign — PgAClient :8082 / PgBClient :8092 + PgPaymentGatewayImpl failover infrastructure
  • 콜백 수신 — /api/v1/payments/callback (인증 제외) 가 결과를 주문/결제에 반영 (멱등) interfaces
  • 배선 — @EnableFeignClients · 보안 제외 2곳 · pg url/timeout 설정 config
핵심 원칙금액은 클라이언트가 아니라 주문에서 확정(위변조 차단). raw 카드번호는 주문이 아닌 결제 요청에만 싣고 Payment 에 영속화하지 않는다(PCI 회피). PG 제출은 @Tx 바깥(외부 I/O 를 트랜잭션에 가두지 않음).

DATABASE

DB 테이블 (payment)

신규 테이블은 payment 1개. 마이그레이션 파일은 없고, local 프로파일의 ddl-auto: create 가 Payment 엔티티 매핑에서 Hibernate 로 생성한다.

Hibernate 생성 DDL (MySQL) — Payment + BaseEntity 매핑
create table payment (
    id              bigint       not null auto_increment,
    created_at      datetime(6)  not null,   -- BaseEntity
    updated_at      datetime(6)  not null,   -- BaseEntity
    deleted_at      datetime(6)  null,       -- BaseEntity (soft delete)
    order_id        bigint       not null,
    user_id         bigint       not null,
    amount          bigint       not null,   -- Money @AttributeOverride
    card_type       varchar(20)  not null,   -- CardType (EnumType.STRING)
    transaction_key varchar(100) null,       -- 접수 후 PG 발급 키
    status          varchar(20)  not null,   -- PaymentStatus
    reason          varchar(255) null,
    primary key (id)
) engine=InnoDB;

컬럼 의미

컬럼 ↔ 엔티티 매핑
order_id        결제 대상 주문 id (다른 애그리거트는 FK 아닌 id 참조 — DDD)
user_id         소유자 accountId (제출 시 소유 검증에 사용)
amount          주문 totalAmount 를 박제 (클라이언트 금액 아님)
card_type       SAMSUNG | KB | HYUNDAI
transaction_key 제출 200 응답으로 받은 PG 키. 콜백/조회의 조회 키
status          PENDING → SUCCESS | FAILED | UNKNOWN (UNKNOWN → SUCCESS|FAILED)
reason          실패/처리 사유 (콜백 reason 또는 제출 거절 사유)
미적용 — 개선 후보cardNo 는 일부러 컬럼에 없다(PAN 비영속). 또 콜백이 findByTransactionKey 로 조회하지만 transaction_key 인덱스가 아직 없다 — 콜백마다 풀스캔. 운영 전 @Index(transaction_key) · order_id 인덱스 추가 필요.

DOMAIN

Payment 상태기계

상태 전이는 엔티티가 소유한다(Tell-Don't-Ask). 잘못된 전이는 ConflictException 으로 거절. accept() 는 transactionKey 만 채우고 상태는 PENDING 유지(승인은 콜백에서).

payment/domain/Payment.kt — 행위 + 상태기계
fun accept(transactionKey: String) { // 접수: PENDING 유지
    this.transactionKey = transactionKey
}
fun success() = transitionTo(PaymentStatus.SUCCESS)
fun fail(reason: String?) { this.reason = reason; transitionTo(PaymentStatus.FAILED) }
fun markUnknown() = transitionTo(PaymentStatus.UNKNOWN)

private fun transitionTo(target: PaymentStatus) {
    if (!status.canTransitionTo(target))
        throw ConflictException(PaymentErrorCode.INVALID_STATUS_TRANSITION)
    status = target
}

enum class PaymentStatus {
    PENDING, SUCCESS, FAILED, UNKNOWN;
    fun canTransitionTo(target) = when (this) {
        PENDING -> target in (SUCCESS, FAILED, UNKNOWN)
        UNKNOWN -> target in (SUCCESS, FAILED)   // reconcile 로 해소
        SUCCESS, FAILED -> false                 // 종결
    }
}
왜 UNKNOWN 이 종결이 아닌가제출 타임아웃·5xx 는 PG 에서 됐을 수도 있는 in-doubt 상태다. 함부로 FAILED 로 닫으면 실제 승인된 결제를 잃는다. 그래서 UNKNOWN 으로 두고 조회 reconcile 이 SUCCESS/FAILED 로 확정한다.

APPLICATION

트랜잭션 경계

Facade 는 @Tx 가 없다. DB 쓰기(prepare·reflectSubmit)만 각자 짧은 트랜잭션이고, 느린 PG 호출은 그 사이 트랜잭션 바깥에 둔다 — 커넥션을 외부 I/O 동안 잡지 않기 위해.

payment/application/PaymentFacade.kt
fun pay(command: PaymentCommand): PaymentInfo {
    val prepared = paymentService.prepare(           // @Tx #1
        PaymentPrepareCommand(command.userId, command.orderId, command.cardType))

    val result = pgPaymentGateway.submit(            // Tx 밖 — 외부 호출
        PgSubmitCommand(command.userId, command.orderId, command.cardType,
            command.cardNo, prepared.amount, callbackUrl))

    return paymentService.reflectSubmit(prepared.paymentId, result)  // @Tx #2
}
payment/application/PaymentService.kt — prepare · reflectSubmit · handleCallback
@Transactional
fun prepare(command): PreparedPayment {
    val order = orderRepository.findById(command.orderId)
        ?.takeIf { it.userId == command.userId }       // 소유 검증 (ID enumeration 차단)
        ?: throw NotFoundException(OrderErrorCode.ORDER_NOT_FOUND)
    if (order.status != OrderStatus.PENDING_PAYMENT)    // 결제 가능 상태?
        throw ConflictException(PaymentErrorCode.ORDER_NOT_PAYABLE)
    val payment = paymentRepository.save(
        Payment.create(order.id, command.userId, order.totalAmount, command.cardType))
    return PreparedPayment(payment.id, order.totalAmount.amount)  // 금액은 주문에서
}

@Transactional
fun reflectSubmit(paymentId, result): PaymentInfo {
    val payment = paymentRepository.findById(paymentId) ?: throw NotFound(...)
    when (result) {
        is Accepted -> payment.accept(result.transactionKey)            // PENDING 유지
        is Rejected -> { payment.fail(result.reason); failOrder(...) }   // 400=우리 버그
        is Unknown  -> { payment.markUnknown(); markOrderUnknown(...) }  // timeout/5xx
    }
    return PaymentInfo.from(payment)
}

@Transactional
fun handleCallback(command) {
    val payment = paymentRepository.findByTransactionKey(command.transactionKey) ?: throw NotFound(...)
    if (payment.status == SUCCESS || payment.status == FAILED) return   // 멱등: 이미 종결이면 무시
    when (command.status) {
        SUCCESS -> { payment.success(); confirmOrder(payment.orderId) }  // → Order PAID
        FAILED  -> { payment.fail(command.reason); failOrder(payment.orderId) }
        PENDING -> Unit
    }
}

PG ADAPTER

Feign · failover

두 Feign 클라이언트는 부모 인터페이스를 상속해 같은 계약을 공유한다(Spring Cloud OpenFeign inheritance). 게이트웨이는 부모 타입으로 호출해 A/B 를 동일 코드로 다룬다.

payment/infrastructure/pg/PgPaymentClient.kt
interface PgPaymentClient {
    @PostMapping("/api/v1/payments")
    fun request(
        @RequestHeader("X-USER-ID") userId: String,   // 인터셉터 대신 명시 인자
        @RequestBody request: PgPaymentRequest,
    ): PgApiResponse<PgTransactionResponse>
}
@FeignClient(name = "pg-a", url = "\${pg.clients.a.url}") interface PgAClient : PgPaymentClient
@FeignClient(name = "pg-b", url = "\${pg.clients.b.url}") interface PgBClient : PgPaymentClient

failover 의 핵심은 "호출이 안 일어난 게 확실한가"로 예외를 가르는 것(O9). connection refused·CB OPEN 은 안 됐으니 B 로, 타임아웃·전송 후 5xx 는 됐을 수 있으니 UNKNOWN(이중결제 함정 회피).

payment/infrastructure/pg/PgPaymentGatewayImpl.kt
override fun submit(command): PgSubmitResult =
    try { request(pgAClient, command) }
    catch (e: PgUnavailableException) { failover(command) }   // refused / CB OPEN → B
    catch (e: PgInDoubtException)    { PgSubmitResult.Unknown }  // timeout / 5xx → UNKNOWN

private fun request(client: PgPaymentClient, command): PgSubmitResult {
    try {
        val response = client.request(command.userId.toString(), PgPaymentRequest.from(command))
        val data = response.data ?: throw PgInDoubtException("응답 본문이 비어 있습니다.")
        return PgSubmitResult.Accepted(data.transactionKey)
    } catch (e: CallNotPermittedException) { throw PgUnavailableException(e.message) }  // CB OPEN
      catch (e: RetryableException) {
          if (e.cause is ConnectException) throw PgUnavailableException(e.message)  // refused → failover
          throw PgInDoubtException(e.message)                                // SocketTimeout → UNKNOWN
      }
      catch (e: FeignException.BadRequest) { return PgSubmitResult.Rejected(e.contentUTF8()) }  // 400
      catch (e: FeignException) { throw PgInDoubtException(e.message) }                    // 전송 후 5xx
}
payment/infrastructure/pg/PgDto.kt — orderId 패딩
PgPaymentRequest(
    orderId = command.orderId.toString().padStart(6, '0'),  // pg 검증: 6자 이상
    cardType, cardNo, amount, callbackUrl)
현재 한계resilience4j 임계값을 아직 안 걸어서 CallNotPermittedException(CB OPEN)은 발생하지 않는다 — 지금 실제 발동하는 failover 는 connection refused 뿐(= PG-A 프로세스 down). CB OPEN 트리거는 임계값 설계(후속) 후 활성화.

DECISIONS

의도적 변경 · 보류 · 개선

계획 대비 의도적 변경

  • X-USER-ID 는 RequestInterceptor 대신 @RequestHeader 인자 — ThreadLocal 의존 간접화 제거. 명시 인자가 더 명확·테스트 용이 (YAGNI)
  • orderId padStart(6,'0') — pg-simulator 의 6자 검증 충족. 콜백은 transactionKey 로 조회하므로 이 인코딩은 무해
  • cardNo 비영속 — PAN 을 Payment 에 저장하지 않음(PCI). 제출 시 전달만

보류 (이전 합의대로)

후속resilience4j 임계값(@CircuitBreaker/Retry/Timeout — readTimeout·failureRateThreshold·slidingWindow·waitDurationInOpenState) · reconcile 스케줄러(UNKNOWN·콜백유실을 GET 조회로 해소) · 테스트(PaymentService 단위 + 콜백/failover). 현재는 콜백 경로만 자동, UNKNOWN 은 수동 해소.

개선 후보 (운영 전)

개선transaction_key · order_id 인덱스(콜백 풀스캔 방지) · 주문당 결제 중복 방지(동시 prepare 가 2건 생성 가능) · callbackUrl 호스트 외부화(현재 localhost:8080 하드코딩, 프로파일별 분리).
