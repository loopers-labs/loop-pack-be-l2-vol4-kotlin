APPROACH

구현 방식 선택

상세와 목록은 캐시 특성이 다르다. 상세는 단순 key=id라 선언적 @Cacheable이 깔끔하고, 목록은 세밀한 제어가 필요해 RedisTemplate을 직접 쓴다.

상세 @Cacheable

key=id 하나라 선언적 캐시가 명확. @CacheEvict로 무효화도 간단. RedisCacheManager + JSON 직렬화 구성.

목록 RedisTemplate

조합키·TTL 지터·negative caching·첫 페이지 한정 등 세밀 제어가 필요. 직접 다룬다.

선결 작업현재 @EnableCaching·CacheManager가 없고 RedisTemplate<String,String>만 있다. 객체 캐싱하려면 spring-boot-starter-cache 추가 + JSON(Jackson) 직렬화 RedisCacheManager를 새로 구성해야 한다.
2

KEY

캐시키 설계

목록 키의 함정: 정렬+브랜드+커서+size를 다 넣으면 커서 때문에 키가 사실상 무한이 된다. 적중률은 바닥, 메모리는 폭발.

캐시키 규칙 
// 상세 — 단건
product:detail:{id}

// 목록 — 커서 없는 "첫 페이지"만 캐싱
products:list:{sort}:{brandId|all}:p1:{size}

// 커서가 붙은 딥 페이지는 캐싱하지 않는다 → 미스 → DB(인덱스로 충분히 빠름)
왜 첫 페이지만인가트래픽은 첫 페이지에 압도적으로 쏠린다(인기 상품 1페이지가 가장 핫). 딥 페이지는 요청도 적고 키 종류가 무한이라 캐싱 효율이 낮다. 첫 페이지만 캐싱하는 게 적중률 대비 메모리 효율 최적이다.
3

TTL

TTL · 무효화

좋아요 수는 계속 변한다. 목록을 매 좋아요마다 정밀 무효화하는 건 비현실적이라, 짧은 TTL로 약한 일관성을 받아들인다.

대상TTL무효화 전략
상세60s ~ 5m좋아요 변경 시 해당 키 @CacheEvict
목록 첫 페이지30s ~ 60s + 지터TTL 자연 만료(약한 일관성)
무효화 판단목록은 정렬×브랜드 조합마다 키가 달라, 좋아요 1건에 영향받는 모든 목록 키를 정밀히 지우는 건 비현실적이다. 짧은 TTL로 "최대 N초 지연"을 허용하는 게 합리적 — 과제 요구("TTL/키설계/무효화 중 1개+")도 충족한다.
4

DEFENSE

stampede · penetration

캐시엔 고유한 실패 모드가 있다. 동시 만료(stampede)와 없는 키 반복 조회(penetration)를 미리 막는다.

stampede 동시 만료

같은 키가 동시에 만료되면 미스가 한꺼번에 DB로 몰린다. TTL 지터(±랜덤)로 만료 시점을 흩뿌린다. (선택) 단일 갱신 락.

penetration 없는 키

존재하지 않는 id를 반복 조회하면 매번 DB를 친다. negative caching(짧은 TTL 빈값 마커) 또는 존재 가드.

5

RESILIENCE

미스 fallback

과제의 마지막 요구: 캐시 미스에도 정상 동작. Redis가 죽어도 서비스는 DB로 응답해야 한다.

검증 (Step 7)Redis 컨테이너를 내린 상태에서 목록·상세가 정상 응답하는지 확인한다. 캐시 접근을 try 후 실패 시 조용히 DB로 가는 구조 — 캐시 예외가 비즈니스 실패가 되어선 안 된다.
