EVALUATION AXIS

평가 기준 — 정합성 트릴레마

비정규화 카운터는 아래 셋을 동시에 갖기 어렵습니다. 모든 방법은 무엇을 얻고 무엇을 포기하느냐로 갈립니다. 여기에 읽기 비용과 부품 수(운영 복잡도)를 더해 평가합니다.

F 신선도

좋아요 즉시 화면에 반영되는가 (real-time).

D 내구성 · 수렴

실패해도 결국 올바른 값에 도달하는가 (= 진짜 eventual consistency).

K 디커플링

좋아요 저장과 분리 + 인기 상품 핫-행 UPDATE 경합 회피.

# 부품 수

유지·운영해야 하는 구성요소 개수. 적을수록 단순·견고.

핵심 구분"집계 실패해도 좋아요는 성공"(디커플링)과 "결과적 정합성"(수렴)은 다른 보장입니다. 비동기 핸들러가 실패 시 로그만 남기고 버리면 디커플링은 되지만 수렴하지 않아 eventual consistency가 아닙니다. 수렴하려면 실패한 갱신을 언젠가 반드시 적용하는 durable 복구 경로가 있어야 합니다.

AT A GLANCE

마스터 비교표

7가지 방법을 한 표로. ✅=충족 · 🟡=부분/조건부 · ❌=미충족.

방식신선내구디커플부품평가
A1 · in-tx (DB행)✅✅❌1미측정 규모 최선 — 현 추천
A2 · async (현재)✅❌✅2디커플만, 유실 → eventual 아님
A2+ · 재집계 보정✅🟡✅+배치절대 SET이 live 증분과 race·풀스캔 비용
A3 · outbox+polling❌✅✅4진짜 eventual, 실시간 X → 분석용
A4 · outbox+CDC🟡✅✅+Debezium셋 다 주나 like엔 과함 · 대규모 정답
B1 · Redis read + relay❌✅✅多신선도 relay 종속 + 읽기 오프로드 이득 0
B2 · Redis INCR + outbox✅✅✅6~7셋 다 주나 부품 폭증 · 둘 다 실측병목시만
B3 · Redis primary + flush✅🟡✅多대규모 카운터 정석 · 미측정엔 과함
읽는 법윗쪽(A1~A2)은 단순하지만 한 축을 포기, 아랫쪽(A4·B2)은 세 축을 다 채우지만 부품·인프라가 폭증합니다. 가운데(A3)는 균형점이되 실시간을 포기 — 그래서 분석용으로 분류됩니다.

GROUP A · COUNT IN DB

그룹 A — 카운트를 DB 행에

Product.like_count 컬럼에 둔다. 목록 쿼리에 공짜로 딸려오고 ORDER BY 정렬이 SQL로 가능한 게 공통 장점.

A1 · in-tx — 좋아요 트랜잭션에서 like_count++

저장과 카운트 증가를 한 트랜잭션에 묶는다. 신선 ✅ 내구 ✅(강한 일관성) 디커플 ❌. 유일한 비용은 인기 상품 핫-행 UPDATE 경합과 주요/부가 미분리. 그런데 그 경합은 아직 측정된 적이 없어, 피하려 다른 방법으로 가는 건 조기 최적화. store 1개, dedup·relay 0개. → 현 추천.

A2 · async — @Async + @TransactionalEventListener(AFTER_COMMIT) (현재 구현)

커밋 후 비동기로 증감, 실패 시 로그만. 신선 ✅(~즉시) 디커플 ✅ 내구 ❌. "집계 실패해도 좋아요 성공"은 되지만 실패한 증분이 영구 유실 → 수렴 안 함 → eventual consistency가 아니다. 신선하지만 내구성이 없는 게 약점.

A2+ · 재집계 보정 (논의 후 기각)

주기적으로 COUNT(*) 재계산해 SET. 수렴을 노리나, 절대값 SET이 동시 진행 중인 원자 증분과 충돌(덮어쓰기 vs 증분 race)해 오히려 정합성을 깬다. 10만 상품 풀스캔도 낭비. 단일 writer 원칙 위반 → 부적합.

A3 · outbox + Polling Publisher

좋아요 트랜잭션에 outbox 레코드를 원자 저장, 폴링 relay가 읽어 발행/적용. 내구 ✅(at-least-once 수렴) 디커플 ✅ 신선 ❌(폴링 주기만큼 지연). 촘촘히 돌리면 서버 부담, 느리면 반영 지연. 멀티 인스턴스면 중복 폴링 → ShedLock/단일 relay 필요.[2][4] 실시간 노출엔 부적합, 분석 집계(product_metrics)에 적합.

A4 · outbox + CDC (Debezium)

relay 대신 DB binlog를 tailing해 outbox insert를 감지·발행. Debezium Outbox Event Router가 표준.[1][3] 지연 ms 수준 → 신선 🟡(거의 즉시) 내구 ✅ 디커플 ✅ — 셋 다. 단 Kafka Connect + Debezium 커넥터 인프라가 like 숫자 하나엔 과함. 우아한형제들도 이 방식으로 outbox를 흘린다.[5] 대규모 정답.

4

GROUP B · COUNT IN REDIS

그룹 B — 카운트를 Redis에

서빙을 Redis로. 공통 함정 둘: ① count는 어차피 product 행 컬럼이라 읽기 오프로드 이득이 거의 0, ② 정렬은 SQL이 아니라 ZSET이 필요.

B1 · Redis read model + relay 갱신 (sync INCR 없음)

relay만 Redis를 갱신, 읽기는 Redis. 신선 ❌ 내구 ✅ 디커플 ✅. 읽는 곳을 Redis로 옮겨도 신선도는 relay(폴링)가 정한다 — "빠른 읽기 ≠ 신선한 읽기". 게다가 오프로드 이득 0. 이득 없이 복잡도만 증가.

B2 · Redis sync INCR + outbox backstop (event_id 멱등)

좋아요 시 Redis INCR(실시간) + outbox relay가 실패분만 멱등 보정. 신선 ✅ 내구 ✅ 디커플 ✅ — 셋 다 달성. 그러나 sync INCR은 DB 트랜잭션과 atomic이 아닌 dual-write라, 이를 바로잡으려면 부품이 폭증한다:

  • DB ProductLike (누가 눌렀나의 진실)
  • outbox 테이블 + event_handled 멱등표 (이중 카운트 방지)
  • 내구 카운트 저장소 (Redis 휘발 대비 DB like_count)
  • Redis (서빙) + sync INCR + relay (backstop)

→ 부품 6~7개. 읽기·쓰기가 둘 다 실측 병목일 때만 정당.

B3 · Redis primary + 주기 DB flush

Redis INCR이 진실, 주기적으로 DB flush + 재시작 시 복구. 신선 ✅ 내구 🟡(flush 주기 사이 손실은 bounded) 디커플 ✅. 대규모 view/like 카운터 정석. dual-write·reconcile 복잡도 → 미측정엔 과함.

Redis 공통 결론Redis 계열은 모두 "읽기·쓰기가 실측 병목으로 올라왔을 때"의 escalation입니다. 카운트는 이미 product 행 컬럼이라 읽기가 공짜이고, sync INCR은 dual-write를 재도입하므로, 미측정 현 상황에선 전부 과설계.

DECISION

결정 프레이밍 · 결론 · 멘토링 질문

가장 중요한 한 줄: 하나의 값에 모든 걸 요구하지 말고, 용도로 가른다. 실시간 노출과 분석 집계는 SLA가 다른 별개의 읽기 모델이다.

노출 실시간 중요

A1 · in-tx. 신선 + 강한 일관성 + 공짜·정렬가능 읽기. Product.like_count.

분석 지연 허용

A3 · outbox + polling → product_metrics. 폴링 지연이 문제 안 됨. 과제의 eventual consistency는 여기서 충족.

현 라운드 결론

  • like_count (노출) = A1 in-tx — 강한 일관성으로 둔다 확정 후보
  • product_metrics (분석) = A3 outbox + polling (Step 2) 확정 후보
  • B2 · B3 · A4 = 읽기·쓰기 규모 실측 후 꺼내는 카드 보류
멘토링 질문 초안"실시간 노출 값은 in-tx, 지연 허용 분석은 outbox" — 이 분리 기준이 타당한가요?sync Redis INCR + outbox backstop(event_id 멱등)까지 그려봤는데, 부품이 6~7개로 늘고 Redis 휘발 대비 DB 카운트가 또 필요해, 경합이 실측되기 전엔 in-tx 한 트랜잭션이 낫다고 판단했습니다. like_count까지 디커플링할 가치가 생기는 기준(트래픽·규모·경합)은 보통 어디서 잡나요?
한 줄 요약정합성·실시간·디커플 셋을 한 값에 다 욱여넣으면 부품이 폭증한다. 용도로 가르면(노출=in-tx, 분석=outbox) 각각은 단순해진다. Redis·CDC는 규모를 측정한 뒤의 escalation 경로다.
