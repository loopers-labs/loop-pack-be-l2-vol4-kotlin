1

SEQUENCE · 동기 구간

제출 + Fallback

제출은 동기로 "접수"까지만. PG-A 실패 유형에 따라 B 로 넘기거나 UNKNOWN 으로 둔다.

이중결제 함정 (O9)타임아웃·전송 후 5xx 는 PG-A 에서 결제가 됐을 수도 있다. 이때 B 로 재전송하면 이중 결제. 그래서 failover 는 "호출이 안 일어난 게 확실한" CB OPEN·connection refused 일 때만. 나머지는 markUnknown() → 조회로 확정.
2

SEQUENCE · 비동기 구간

콜백 + reconcile

승인 결과는 콜백으로 1차 확정. 콜백은 유실 가능하므로 조회가 2차 안전망.

3

CONTRACT · 레포 소스 그대로

정확한 API 계약 스펙

시퀀스 화살표를 코드 계약으로 못박는다. 아래는 전부 apps/pg-simulator 실제 소스(PaymentApi · PaymentDto · TransactionInfo · PaymentCoreRelay)에서 그대로 옮긴 것. 추측 아님.

1) 클라이언트 → commerce-api (우리 결제 API · Model A)

POST /api/v1/payments — 주문과 분리된 별도 결제 호출
요청 헤더 : 로그인 인증 (commerce-api 자체 인증) — accountId 식별
요청 body : { orderId, cardType, cardNo }     # 카드정보는 결제요청에만 싣는다
응답      : { paymentId, status: PENDING }     # 승인 안 기다리고 즉시 반환
왜 orderId만 받나주문은 먼저 생성(PENDING_PAYMENT)되어 있고, 서버가 orderId로 조회 → 소유검증 → 금액확정한다. amount·callbackUrl 은 클라이언트가 아니라 서버가 채운다(금액 위변조 차단). raw 카드번호는 주문이 아니라 결제 요청에만.

2) commerce-api → pg-simulator (PG 제출 · key-in)

POST /api/v1/payments — PaymentDto.PaymentRequest
헤더 : X-USER-ID                 # 필수. 누락 시 400
body : {
  orderId     : String           # 6자 이상
  cardType    : SAMSUNG | KB | HYUNDAI
  cardNo      : "xxxx-xxxx-xxxx-xxxx"        # ^\d{4}-\d{4}-\d{4}-\d{4}$
  amount      : Long             # > 0
  callbackUrl : "http://localhost:8080/..."  # 이 prefix 로 시작해야 함
}
동기 응답 : 200 ApiResponse { data: { transactionKey, status: PENDING, reason } }
           # Thread.sleep 100~500ms 후 · 40% 확률로 500 INTERNAL_ERROR 던짐

3) pg-simulator → commerce-api (콜백 · 비동기 결과)

POST {callbackUrl} — body = TransactionInfo
body : { transactionKey, orderId, cardType, cardNo, amount,
         status: SUCCESS | FAILED, reason }
전송 : RestTemplate.postForEntity · runCatching · no timeout → 유실 가능
유실 대비콜백은 타임아웃도 재시도도 없다(runCatching, 실패 시 로그만). 콜백만 믿으면 PENDING 영구 잔존 → GET 조회 reconcile 이 진짜 안전망.

4) commerce-api → pg-simulator (조회 · 안전망)

GET — 둘 다 X-USER-ID 필수
GET /api/v1/payments/{transactionKey}
  → { transactionKey, orderId, cardType, cardNo, amount, status, reason }
GET /api/v1/payments?orderId={orderId}
  → { orderId, transactions: [ { transactionKey, status, reason } ] }

5) 응답 코드 · 비동기 결정 확률

ErrorType (code = HttpStatus reasonPhrase) · 결정 분기
제출(POST) 응답
  200 PENDING        접수 성공 (~60%)       → transactionKey 저장 후 결과 대기
  400 BAD_REQUEST    검증 실패 (우리 버그)   → 재시도 X · failPayment + 알림
  500 INTERNAL_ERROR 40% 인위적 / 예상외     → 제한 재시도 → 계속 실패 시 CB open
  무응답 · 타임아웃 · CB OPEN              → in-doubt → markUnknown (UNKNOWN)

비동기 결정 (콜백 · 조회 공통)
  approve        70%               → SUCCESS → Order.confirmPayment() PAID
  limitExceeded  20% (rate 1~20)   → FAILED(한도초과)   → Order.failPayment() FAILED
  invalidCard    10% (rate 21~30)  → FAILED(잘못된 카드) → Order.failPayment() FAILED

조회(GET)
  200 SUCCESS/FAILED  확정  ·  200 PENDING 처리중(재조회)  ·  404 미접수 → FAILED 확정
4

WIRING

연결 배선 체크리스트

의존성(spring-cloud-starter-openfeign)은 이미 있고, 아래만 연결하면 된다.

  • @EnableFeignClients 추가 — CommerceApiApplication 또는 com.loopers.config
  • FeignClient 2개 각각 — PgAClient(url=:8082) · PgBClient(url=:8092), pg-simulator PaymentApi 계약 그대로
  • X-USER-ID RequestInterceptor — 로그인 accountId(RequestAttribute ACCOUNT_ID)를 헤더로 주입 필수
  • 콜백 보안 제외 2곳 — AccountSecurityConfig permitAll + AccountHeaderAuthenticationFilter.shouldNotFilter 둘 다
핵심pg-simulator 의 모든 호출은 X-USER-ID 헤더가 필수(UserInfoArgumentResolver). 누락 시 400 "유저 ID 헤더는 필수입니다." → RequestInterceptor 로 한 번에 주입한다.
5

RUN · OUT OF SCOPE

2-PG 기동 · 범위 밖

두 인스턴스 기동

run two pg-simulators
# 같은 앱, 포트만 다르게 (bootRun)
./gradlew :apps:pg-simulator:bootRun --args='--spring.profiles.active=local --server.port=8082'
./gradlew :apps:pg-simulator:bootRun --args='--spring.profiles.active=local --server.port=8092'

# 또는 같은 이미지로 docker (8082 / 8092)
docker run -d -p 8082:8082 --name pg-a pg-simulator:local
docker run -d -p 8092:8082 --name pg-b pg-simulator:local
참고두 인스턴스는 같은 paymentgateway DB 를 공유하지만 transactionKey 가 고유 생성이라 충돌 없음. http/http-client.env.json 에 pg-simulator-a / pg-simulator-b 를 추가하면 호출 테스트가 편하다.

이번 문서 범위 밖 (후속)

후속resilience4j @CircuitBreaker / Retry / Timeout 임계값 설계(readTimeout, failureRateThreshold, slidingWindow, waitDurationInOpenState)와 payment 도메인 코드(Payment·PaymentStatus), 실제 Kotlin 구현은 다음 단계에서. 이 문서는 시퀀스·배선 합의까지.
