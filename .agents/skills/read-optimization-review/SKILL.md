# Read Path Optimization Review

읽기 경로(조회 API)의 성능을 구조적으로 점검·설계하기 위한 스킬이다.
정답을 단정하지 않고, 전제·병목·정합성을 드러내 **무엇부터 손댈지**를 판단하게 한다.

## Use this skill when

- 상품 목록 / 상세 / 인기 상품 등 조회 API의 성능 저하를 분석할 때
- 브랜드 필터 + 좋아요 순 정렬 같은 정렬/필터 쿼리를 최적화할 때
- Redis 캐시 도입(TTL·키·무효화)을 설계할 때
- 좋아요 수 등 집계값의 정합성과 조회 성능을 함께 다룰 때

## Do not use this skill when

- 단순 CRUD 추가 등 성능 고민이 없는 작업
- 쓰기 트랜잭션 경계 / 영속성 컨텍스트 / flush·락 분석이 핵심인 경우
  → 이 영역은 `analyze-query` 스킬로 라우팅한다.
- 도메인 모델링·바운디드 컨텍스트 설계가 목적인 경우 → `domain-driven-design`

## 📐 분석 범위

조회 흐름을 메서드 단위로 떼어내지 않고 **Controller → Facade → Service → Repository 전체 경로**를 기준으로 본다.

대상 유즈케이스(이 프로젝트):
- 상품 목록 (브랜드 필터 + 좋아요 순 정렬) — `domain/product/port/ProductSearchCondition.kt`, `domain/product/vo/ProductSort.kt`
- 상품 상세
- 인기 상품 조회

## 🤖 설계 전제 점검 (시니어 아키텍트 6관점)

구현에 들어가기 전, 가정한 설계를 다음 6관점으로 먼저 점검한다.
이 단계는 **구조적 리스크와 사고 관점만** 다룬다 — 구현 코드나 설정값(인덱스 DDL, TTL 숫자 등)은 여기서 제시하지 않는다.

1. 이 설계가 성립하려면 반드시 참이어야 하는 **전제 조건**은 무엇인가?
2. 트래픽이 **10배** 증가하면 가장 먼저 병목이 될 지점은 어디인가?
3. **캐시 적중률이 30% 이하**로 떨어지면 어떤 문제가 발생하는가?
4. **데이터 정합성이 깨질 수 있는 시나리오**를 2가지 이상 제시한다.
5. 이 설계를 유지하면서 **가장 나중까지 미룰 수 있는** 개선은 무엇인가?
6. 반대로, **가장 먼저 손대야 할** 위험 요소는 무엇인가?

> 입력으로 받을 정보: 조회 API 목적 / 주요 조회 조건 / 사용 테이블·데이터 / 인덱스 / 캐시 적용 여부·위치 / 캐시 키 전략 / TTL 가정.

**출력 예시**

```markdown
[전제] 좋아요 수 분포가 한쪽으로 치우치지 않는다고 가정 → 깨지면 정렬 인덱스 효율 저하
[10x 병목] 좋아요 순 정렬 시 filesort + 카운트 조인이 첫 병목
[적중률 30%↓] 캐시가 오리진 보호막 역할을 못해 DB 부하가 캐시 도입 전으로 회귀
[정합성 위험] (1) 캐시 TTL 윈도우 동안 stale 카운트 노출 (2) 동시 like/unlike와 캐시 무효화 경합
[미룰 수 있는 것] Materialized View
[먼저 손댈 것] 정렬·필터 복합 인덱스
```

## 🔍 구현 플레이북

각 레버를 "언제 / 방법 / 검증 / 함정" 순으로 판단한다. Must-have는 ①~③, ④는 Nice-to-have.

### ① DB Index (Must)
- **언제**: 브랜드 필터 + 정렬 쿼리가 풀스캔/filesort를 유발할 때.
- **방법**: 유즈케이스별로 필요한 복합 인덱스를 도출하고 **컬럼 순서**(등치 필터 → 정렬 키)를 결정. `EXPLAIN`으로 인덱스 사용 여부·정렬 방식 확인. 정렬+필터 커버링 인덱스 가능성 검토.
- **검증**: 10만 건 이상(값 분포 다양하게) 데이터로 AS-IS / TO-BE 쿼리 시간 비교. `EXPLAIN` before/after 첨부.
- **함정**: 인덱스 남발로 쓰기 비용 증가, 카디널리티 낮은 컬럼 선두, 정렬 방향 불일치로 인덱스 정렬 미사용.

### ② 비정규화 — 좋아요 수 (Must)
- ⚠️ **이미 부분 구현됨**: `product_like_counts` 테이블(`ProductLikeCountJpaEntity`, PK=`product_id`, `like_count`)이 존재하고, `LikeService.like()/unlike()`가 **같은 트랜잭션 안에서** `increment`/`decrement`(`update ... set like_count = like_count ± 1`)로 동기화한다.
- 따라서 새로 만드는 게 아니라 **다음을 점검**한다:
  - (a) **정합성**: like/unlike 와 카운트 갱신이 같은 트랜잭션인지, 동시성(원자적 UPDATE vs 읽고-쓰기), 중복 like/unlike 시 카운트 어긋남, 실패 시 보정 경로.
  - (b) **조회 결합**: 목록 조회에서 카운트를 매 행 서브쿼리로 가져오는지 vs `countByProductIds` 배치 조회/조인으로 N+1을 피하는지.
  - (c) **정렬 위치**: 좋아요 순 정렬을 비정규화 카운트 컬럼 기준으로 DB에서 수행하는지(애플리케이션 정렬은 페이징과 충돌).
- **검증**: like → 카운트 일치 테스트, 동시 like/unlike 부하 시 카운트 정확성, 정렬 결과 일관성.
- **대안**: 비정규화 대신 Materialized View(④)로 집계할 수도 있음 — trade-off는 ⚖️ 참고.

### ③ Redis 캐시 (Must, 신규)
- **현황**: `modules:redis` 모듈과 docker compose(redis-master/redis-readonly) 인프라는 있으나 상품 API에 캐시 미적용.
- **방법**: 상품 상세 / 목록에 캐시 적용. **TTL·캐시 키 설계·무효화 전략 중 최소 1개** 이상 포함.
  - 키 설계: 조회 파라미터(브랜드·정렬·페이지)를 키에 반영해 충돌·과캐싱 방지.
  - 무효화: 상품 변경/좋아요 변동 시 관련 키 무효화 vs 짧은 TTL로 수렴 — 둘의 trade-off 명시.
- **검증**: 캐시 **미스 시에도 서비스 정상 동작**(graceful degradation), 히트율 측정, 무효화 후 최신값 반영 확인.
- **함정**: 캐시 스탬피드(동시 미스 폭주), TTL 윈도우 동안 stale 노출, 캐시-DB 정합성 경계.

### ④ Materialized View (Nice-to-have)
- **언제**: 정렬·집계가 무거워 인덱스/비정규화로도 부족할 때.
- **trade-off**: 갱신 주기 ↔ 데이터 지연(stale 허용 범위), 갱신 비용. `commerce-batch` 앱과 연계해 주기 갱신 가능.
- **검증**: 갱신 지연이 요구 정합성 안에 드는지, 뷰 조회 성능 이득이 갱신 비용을 상회하는지.

## ⚖️ Trade-off 프레이밍

정답을 단정하지 말고 선택지 + 영향도로 제시한다.

- **정합성 vs 성능**: 강한 일관성(즉시 반영) ↔ 캐시/비정규화로 인한 stale 허용.
- **쓰기 비용 vs 읽기 비용**: 비정규화·인덱스는 읽기를 빠르게 하되 쓰기를 무겁게 한다.
- **즉시 무효화 vs 짧은 TTL**: 정확성 ↔ 단순성·부하 안정성.

## 📤 출력 형식

블로그/테크노트 제출에 바로 쓸 수 있는 형태로 정리한다.

- **AS-IS / TO-BE** 구조 비교 (왜 그렇게 판단했는지 중심)
- `EXPLAIN` **before/after** 결과
- 측정 수치 표 (쿼리 시간, 캐시 적중률 등) — 10만 건+ 데이터 기준

```markdown
| 항목 | AS-IS | TO-BE |
| --- | --- | --- |
| 목록 조회(좋아요순, 브랜드필터) | filesort, 320ms | idx 사용, 18ms |
| EXPLAIN type | ALL | ref |
```

## 톤 & 스타일

- 강의가 아니라 **설계 리뷰** 톤을 유지한다.
- 정답으로 단정하지 말고, 대안이 있으면 영향도와 함께 선택지로 제시한다.
- 코드보다 **의도·전제·경계**를 먼저 다룬다.
- "무엇을 했다"보다 **"왜 그렇게 판단했는가"**가 드러나게 정리한다.
