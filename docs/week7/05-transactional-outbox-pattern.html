1

WHY

문제 — Dual Write

서로 다른 두 시스템(DB · Kafka)에 써야 하는데, 이 둘을 하나의 트랜잭션으로 묶을 수 없다.

비즈니스 로직은 보통 ① DB에 상태를 저장하고 ② 그 사실을 메시지로 발행한다. Kafka 전송은 DB 롤백을 따라 되돌릴 수 없으므로, 이 둘은 원자적이지 않다. 2PC(분산 트랜잭션)는 느리고 서비스를 강결합시켜 쓰지 않는다.[3] 그래서 항상 두 가지 실패가 남는다.

한 줄커밋 후 발행(AFTER_COMMIT)은 유령은 막지만 유실은 못 막는다. 그 마지막 빈틈을 메우는 것이 Transactional Outbox다.
2

MECE

해결책 스펙트럼 4가지

"DB↔Kafka 경계 유실"을 다루는 방법은 크게 넷. 보장 수준과 비용이 다르다.

방식동작보장 · 언제 쓰나
A. 커밋 후 직접 발행커밋 후 리스너가 Kafka로 바로 발행. outbox 없음보장 없음(유실) · 손실 허용 부가처리(재집계로 복구 가능한 카운트)
B. Outbox + 폴링 릴레이같은 Tx에 outbox INSERT → 배치/스케줄러가 폴링해 발행at-least-once · 팀에 CDC 경험 없을 때, 메시지 가공 필요할 때
C. Outbox + CDC같은 Tx에 outbox INSERT → Debezium이 binlog 테일링해 발행at-least-once · 저지연·대규모, CDC 운영 역량 있을 때
D. 하이브리드B/C + 커밋 후 즉시 발행(저지연) + 릴레이 backstopat-least-once + 저지연 · 즉시성과 보장을 둘 다 원할 때

A 커밋 후 직접 발행

가장 단순하지만 발행 보장이 없다. Spring 공식도 이 리스너를 "커밋 후 트리거"로 규정할 뿐 전달 보장 장치로 보지 않는다.[1] 유실돼도 복구되는 데이터에만.

B Outbox + 폴링 릴레이

발행할 이벤트를 롤백되는 DB(outbox)에 같은 Tx로 적재하고, 별도 릴레이가 읽어 발행·재시도. AWS가 Spring 폴링 릴레이 코드를 그대로 제공한다.[5] Round 7 시작점.

3

HOW

Outbox 전체 플로우

핵심은 "Kafka는 롤백 안 되니 직접 쏘지 않고, 롤백되는 DB(outbox)에 먼저 적재"다.

phase 규칙outbox INSERT는 반드시 같은 트랜잭션 안(트랜잭션 본문 직접 저장, 동기 @EventListener, 또는 BEFORE_COMMIT). AFTER_COMMIT에서 저장하면 안 된다 — 그 시점엔 원본 Tx가 이미 커밋돼 원자성이 깨진다. Kafka '발행'만 AFTER_COMMIT/릴레이가 담당한다.
4

RELAY

릴레이 — 폴링 vs CDC

outbox 테이블을 Kafka로 흘려보내는 릴레이는 두 방식이다.[3][4]

폴링 Polling Publisher

앱의 스케줄러/배치가 outbox를 주기적으로 SELECT → 발행 → 상태 갱신. 구현 단순, 메시지 가공 자유. 대신 폴링 지연·부하. 팀에 CDC 경험이 없다면 여기서 시작.

CDC Log Tailing

Debezium이 DB의 binlog/WAL을 테일링해 outbox 변경을 자동 발행. 앱 코드 없음·저지연. 대신 CDC 인프라(Kafka Connect) 운영 부담, 메시지가 테이블 스키마에 의존.

빅테크 실제우아한형제들은 outbox의 릴레이로 Debezium CDC(binlog 테일링)를 쓴다 — 처리량을 위해 outbox 테이블을 토픽별로 분리하고 커넥터도 나눈다.[7] "프로덕션 outbox의 발행은 릴레이가 책임진다"의 실증.

부하는 어디에 걸리나 — 스케줄러 vs 폴링 쿼리

"outbox 조회 + 스케줄링이 각각 부하가 되지 않을까"는 두 축으로 갈라 보면 실체가 다르다. 스케줄러 쪽은 사실상 0이고, DB 쪽은 산수로 무시 수준 — 진짜 위험은 아래 설계 실수 3가지다.

앱 스케줄러 부하 — 사실상 0

@Scheduled는 스케줄러 스레드가 다음 실행 시각까지 잠들어 있다 깨어나는 구조라 트리거 오버헤드는 마이크로초 수준. fixedDelay는 이전 실행 완료 시점부터 딜레이를 재므로 중첩 실행이 없다.[11] Tomcat 요청 스레드풀과도 별개 — 접점은 커넥션 풀 공유(초당 수 ms 점유)뿐. 단 기본 스케줄러는 스레드 1개[11]: relay가 오래 걸리면 다른 스케줄 태스크가 밀린다(부하가 아니라 경합 문제). 스케줄 태스크가 늘면 relay 전용 TaskScheduler를 분리한다 — 지금은 relay 하나뿐이라 불필요.

DB 폴링 쿼리 부하 — 무시 수준

fixedDelay 1초 + (status, id) 인덱스 + LIMIT 100 = 인스턴스당 ~1 QPS의 인덱스드 SELECT — MySQL 처리 능력 대비 소수점 이하 점유. outbox가 비어 있는 대부분의 시간엔 인덱스에서 0건 반환으로 끝나 비용 ≈ 0.

부하 팩트체크 (2026-07 서치)폴링 부하의 정량 벤치마크는 공식 문서·빅테크 블로그 어디에도 공개된 것이 없다. 패턴 원전도 부하를 정성적으로만 기술하고[9], Debezium 창시자 Gunnar Morling도 "폴링 시도마다 DB에 부하 스파이크를 만들 수 있고, 저지연과 과도한 폴링 사이에 본질적 긴장이 있다"고 쓰면서 outbox 테이블 오버헤드에 대해서는 "실증적으로 입증된 문제라기보다 이론적 우려"라고 평가한다.[10]
실제 위험 3가지 + 자체 검증부하가 진짜 생기는 경로는 ① status 인덱스 없는 풀스캔(매초 반복) ② SENT 행 방치로 테이블 비대 → 폴링 쿼리 점진 저하 ③ 다중 인스턴스 × 과도하게 짧은 주기 — 셋뿐이고 전부 설계로 회피 가능. 공개된 정량 자료가 없으므로 Round 7 load-test에서 릴레이 on/off로 DB CPU·API p99를 직접 측정해 기록하면 그 자체가 근거 자료가 된다.

GUARANTEE

보장의 산수

"정확히 한 번 발행"은 현실적으로 불가능하다. 목표는 최소 한 번 발행 + 멱등 소비다.

outbox 릴레이조차 "① Kafka 발행 → ② outbox를 SENT 표시"가 또 하나의 dual write다. ① 성공 후 ② 전에 죽으면 다음 폴링에서 재발행된다. 그래서 보장은 at-least-once(최소 한 번, 가끔 두 번)이다.[3]

Outbox(유실 0) + 멱등 소비(중복 무해) = 사실상 "정확히 한 번"

— Round 7 전달 보장 정리 (03-delivery-guarantees)

발행측 최소 한 번

outbox + 릴레이가 책임. 유실을 0으로 만든다. 멱등성만 있고 이게 없으면 이벤트가 안 나가고, dedup할 대상 자체가 없다.

소비측 멱등

event_handled(event_id PK)로 이미 처리한 event_id는 skip. 이게 없으면 재발행 중복이 그대로 두 번 처리돼 카운트가 뻥튀기된다.

둘 다여야 한다at-least-once와 멱등은 OR가 아니라 AND다. 발행측은 "최소 한 번", 소비측은 "중복 무해" — 역할이 갈린다.

CASE STUDY

실전 검증 — 29CM 사례

이론이 아니라 22년 8월부터 운영 중인 실제 구현. 폴링 릴레이 방식의 정석을 보여준다.[8]

29CM는 상품 도메인에서 outbox 패턴을 ApplicationEventPublisher + @TransactionalEventListener로 구현했다. 최종 설계는 이벤트 발행 이후 로직을 전부 리스너로 모아 일관성을 높였다.

29CM 최종 구현 (요지) 
// 도메인 트랜잭션 — 도메인 로직 + 이벤트 발행만
@Transactional
fun updateInventory(cmd: Command): Info {
    val result = updateQuantity(cmd)                // 1. 도메인
    eventPublisher.publish(InventoryEvent.from(result)) // 발행만
    return Info.of(result)
}

// 2-A. 같은 Tx 안에서 outbox 기록 (BEFORE_COMMIT)
@TransactionalEventListener(phase = BEFORE_COMMIT)
fun record(e: InventoryEvent) = recorder.save(e.toRecord()) // status=INIT

// 2-B. 커밋 후 즉시 발행 (AFTER_COMMIT + @Async)
@Async(EVENT_EXECUTOR)
@TransactionalEventListener(phase = AFTER_COMMIT)
fun send(e: InventoryEvent) = sender.send(e) // 성공 시 send_success 로 갱신

// 3. 배치 릴레이 — send_success 아니면서 created_at 10분↑ → 재발행

세 가지 핵심 결정

  • outbox 기록을 BEFORE_COMMIT 리스너로. 아직 Tx 안이라 원자성 유지. 단, 트랜잭션 본문에서 직접 저장해도 correctness는 동일 — 코드 일관성 선택일 뿐. phase
  • 상태를 3단계로 세분화. init(등록) / send_success / send_fail. init = 리스너가 이벤트를 읽지도 못한 상태(배포 중 shutdown). state
  • 배치 릴레이가 진짜 보장. AFTER_COMMIT 발행은 happy path일 뿐, 실패·누락분은 배치가 재발행해 eventually consistency. relay
전쟁 이야기@Async graceful shutdown 사고

증상: outbox에 init 상태로 영영 남는 이벤트들 → 전부 배포 직후 발생.

원인: Kafka 전송이 @Async(ThreadPoolTaskExecutor)인데, 배포로 pod가 롤링될 때 async 스레드가 커밋 직후 이벤트를 읽지도 못하고 죽음. setAwaitTerminationSeconds 누락으로 graceful shutdown 실패.

graceful shutdown 설정
executor.setWaitForTasksToCompleteOnShutdown(true)
executor.setAwaitTerminationSeconds(10)

구원: outbox + 배치가 이 init 이벤트들을 나중에 재발행해서 살렸다. → "AFTER_COMMIT 즉시 발행만으로는 배포 한 번에 뚫린다"의 산 증거.

이 글이 안 다루는 절반29CM 글은 producer 측 최소-한-번은 철저하지만 consumer 멱등은 거의 안 짚는다. 발행 성공 후 상태 갱신 전에 죽으면 배치가 또 보내 중복이 난다 → §5의 event_handled 멱등을 반드시 같이 넣어야 완성된다.
설계 노트BEFORE_COMMIT 저장이 정말 바람직한가

먼저 사실: BEFORE_COMMIT은 별도 트랜잭션이 아니다. 원본 트랜잭션이 커밋되기 직전, 같은 스레드·같은 트랜잭션에서 동기 실행된다.[1] 그래서 여기서의 outbox.save()는 메인 로직과 같은 트랜잭션에 포함되어 원자적으로 커밋/롤백된다. "트랜잭션이 분리돼 원자성이 깨진다"는 우려는 AFTER_COMMIT + REQUIRES_NEW의 문제이지 BEFORE_COMMIT엔 해당 없다.

왜 BEFORE_COMMIT을 썼나: 기술적 필연이 아니라 코드 일관성("발행 이후 로직은 전부 리스너")뿐이다. 29CM 글도 "직접 저장과 큰 차이 없다"고 인정한다.[8]

회의적 판정: outbox 저장 하나엔 과한 기교다. 리스너 뒤로 숨기면 도메인 메서드만 봐선 outbox 기록이 안 보인다(숨은 제어 흐름). 명확함 > 영리함 + YAGNI 기준으로, 트랜잭션 본문에서 직접 outbox.save() 하는 게 더 낫다 — 원자성은 동일하고 흐름이 드러난다(§7 권장 코드).

"저장 실패로 메인이 롤백되는 게 이상한가": 발행이 필수인 이벤트라면 "발행 의도조차 기록 못 하면 상태 변경도 무효"가 outbox의 의도된 계약이다 — 롤백이 옳다. 부가 이벤트라면 애초에 outbox가 아니라 best-effort로 가야 한다. 게다가 outbox는 메인과 같은 DB·커넥션·트랜잭션이라 "메인 성공 + outbox만 실패"는 사실상 불가능하다(그래서 outbox는 반드시 같은 DB에 둔다).

리스너 타입·동기/비동기·REQUIRES_NEW에 따라 뒤이은 쓰기가 어느 트랜잭션에서 도는지는 06 · 리스너 트랜잭션 문서에서 전부 정리한다.

RECOMMEND

추천 패턴 — 나는 이렇게

Round 7에서는 B(Outbox + 폴링 릴레이)로 시작하고, 저지연이 필요해지면 AFTER_COMMIT 즉시 발행을 얹어 하이브리드로.

이유: 인프라를 안 건드리고 like 도메인의 이벤트 분리 패턴을 그대로 옮기면 되므로 즉시 가능하고, AWS가 동일 구조의 Spring 코드를 제공한다.[5] CDC는 운영 역량이 쌓인 뒤 선택지로 남긴다.

Round7 — Design B 뼈대 
// ① 도메인 + outbox INSERT 를 한 트랜잭션에 (원자성)
@Transactional
fun place(cmd: OrderCommand): OrderInfo {
    val order = orderService.save(cmd)          // 도메인
    outbox.save(OutboxEvent.of(order))            // status=PENDING · 같은 Tx
    return OrderInfo.from(order)
}

// ② 폴링 릴레이 — PENDING 을 읽어 발행하고 SENT 로 전이 (진짜 보장)
@Scheduled(fixedDelay = 1000)
fun relay() {
    outbox.findPending(batchSize).forEach { e ->
        kafkaTemplate.send(e.topic, e.key, e.payload)
        outbox.markSent(e.id)                    // ← 빠지면 안 됨
    }
}

// ③ 컨슈머 — event_handled 로 중복 흡수 (at-least-once 의 짝)
fun consume(e: Event) {
    if (eventHandled.existsById(e.eventId)) return // 멱등
    process(e); eventHandled.save(e.eventId)
}

지금 Design B

outbox + 폴링 릴레이 + 컨슈머 멱등. at-least-once 확보. 폴링 지연(1~2초)은 집계·알림엔 충분.

나중 하이브리드(D)

여기에 @Async @TransactionalEventListener(AFTER_COMMIT) 즉시 발행 + markSent를 얹으면 happy path 저지연. 릴레이는 backstop으로 유지.

핵심즉시 발행(AFTER_COMMIT)은 최적화, 보장은 릴레이. 순서를 헷갈리지 말 것 — 릴레이부터 만들고 즉시 발행을 얹는다.

PITFALLS

함정 체크리스트

구현 전에 이 다섯 개를 점검한다. 앞의 스니펫 예시가 어중간했던 이유가 여기에 있다.

  • outbox INSERT는 같은 Tx. AFTER_COMMIT/REQUIRES_NEW에서 저장하면 독립 Tx가 되어 원자성이 깨진다 — 커밋 후 INSERT 전 죽으면 유실.
  • markSent(상태 전이)가 있는가. 발행 성공 표시가 없으면 릴레이가 뭘 주울지 모르고, outbox가 죽은 테이블이 된다.
  • 릴레이(폴러/CDC)가 있는가. 커밋 후 즉시 발행만으로는 best-effort. 보장은 릴레이가 한다.
  • @Async면 graceful shutdown 설정. setAwaitTerminationSeconds 누락 시 배포마다 이벤트가 init으로 샌다.
  • 컨슈머 멱등(event_handled). at-least-once는 중복을 만든다 — 소비측 dedup이 없으면 이중 집계.
phase 정리outbox INSERT = 같은 Tx(직접 저장 / 동기 @EventListener / BEFORE_COMMIT) · Kafka 즉시 발행 = AFTER_COMMIT · DB 쓰기 하는 AFTER_COMMIT 리스너는 @Transactional(REQUIRES_NEW) 필수(아니면 부팅 실패).[2]
