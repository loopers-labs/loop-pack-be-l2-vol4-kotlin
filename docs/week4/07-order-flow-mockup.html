SCREEN · TIMELINE

등장 요소 — 화면과 3개 시점

화면은 하나(주문서)지만, 가격이 결정되는 시점은 셋이다. 이 셋을 구분하지 못하면 "결제 직전에 또 계산하나?"에서 계속 막힌다.

주문서 화면은 조회로 받아 그린 그림이다. 유저가 본 금액을 서버로 되돌려보내 주문을 만드는 게 아니라, 서버가 식별자(무엇을·몇 개·어떤 쿠폰)만 받아 자기 DB에서 금액을 다시 계산한다. 아래 와이어프레임의 각 영역이 어느 시점에 무엇이 되는지 본다.

시점무엇이 일어나나가격 처리
① 견적주문서 표시 (조회/클라). Order 안 만듦now 계산 → 보여주기만 (stale 가능)
② 결제 클릭POST /orders = 주문 생성·결제 진입now 재계산 → expected 3종 비교 → 박제
③ PG 승인박제값으로 외부 결제재계산 안 함, 박제값 고정
핵심 한 줄가격 변동은 락으로 막지 않는다. 주문 생성(②) 시점에 금액을 스냅샷해서, 그 이후의 변동과 결제 금액을 분리한다. ①→②의 긴 틈은 재계산으로, ②→③의 짧은 틈은 박제로 막는다.
2

FLOW ①

주문서 진입 — 견적

유저가 쿠폰을 이것저것 적용해보고 최종 계산서를 본다. 이 단계는 전부 조회다 — 서버는 아무것도 저장하지 않는다.

이 단계의 책임

  • 현재가로 계산해서 금액을 응답한다 (상품가 · 쿠폰 할인 · 최종액)
  • 아무것도 저장하지 않는다 — 재고도 안 깎고 쿠폰도 안 쓴다 읽기
  • 여기서 본 계산서 3종(original·discount·total)이 ②의 expected echo가 된다
범위Loopers 스펙에는 견적(preview) API가 없다. "쿠폰 여러 개 시뮬레이션"은 클라이언트 또는 상품 조회 API 조합으로 충분하다. 서버에 장바구니 도메인을 만들 필요는 지금 없다 — 필요해지면 그때.

FLOW ②

결제 클릭 = 주문 생성 · 박제

결제 버튼을 누른 순간이 곧 POST /orders다. 여기서 서버가 now로 다시 계산하고, 그 값을 박제한 뒤 결제로 들어간다. "다시 확인하고 확정한다"가 정확히 이 시점이다.

OrderService.kt — place (의사코드) 
@Transactional
fun place(userId: Long, command: OrderCreateCommand): OrderInfo {
    val now = LocalDateTime.now()
    // 1·2. 현재가 조회 + 재고 비관락 차감
    val products = productRepository.findAllActiveByIdIn(ids)
    val inventories = inventoryRepository.findAllByProductIdInForUpdate(ids)
    inventories.forEach { it.decrease(qty) }

    // 3·4. 금액 계산 (+ 쿠폰이 있으면 now 기준 검증 후 use)
    val original = products.sumOf { it.price * qty }
    val discount = command.couponId?.let { id ->
        val uc = userCouponRepo.find(userId, id)   // @Version 낙관락
        coupon.validateUsable(original, now)        // 만료·최소금액
        val d = DiscountPolicy.calculateDiscount(...)
        uc.use(now); d
    } ?: Money(0)
    val total = original - discount

    // 5. 변동 게이트 — ①에서 본 계산서 3종과 재계산값 비교 (§4)
    if (command.expectedOriginalAmount != original.amount ||
        command.expectedDiscountAmount != discount.amount ||
        command.expectedTotalAmount != total.amount)
        throw ConflictException(OrderErrorCode.PRICE_CHANGED)  // 409 + 현재 3종

    // 6. 박제 저장 → 결제 진입 (PG 호출은 Tx 밖, D1-b)
    val order = orderRepository.save(Order.create(userId, snapshots, couponId, original, discount, total))
    return OrderInfo.from(order)
}
박제 = 계약 성립주문 생성 = 계약 성립 시점이다. 박제 후 상품가가 올라도 유저는 박제된(싼) 가격으로 산다. "주문 넣을 때 5만원이었으면 5만원에 산다" — 모든 커머스의 기본 원칙이다.
4

FLOW ③

가격 변동 — 재확인

①에서 본 금액과 ② 재계산값이 다를 수 있는 구간은 딱 하나 — 주문서를 오래 켜놨거나, 그새 할인 기간이 끝난 경우다. 이때 결제로 들어가면 안 된다.

하면 안 됨 새 금액으로 그냥 결제

유저가 동의한 적 없는 81,300원으로 결제를 진행. 고객이 본 가격 ≠ 결제 가격이 그대로 터진다.

해야 함 409로 재확인

주문을 만들지 않고 새 금액을 응답. 유저가 다시 확인하고 누를 때까지 결제로 못 들어간다.

할인 기간 만료도 여기서주문서를 12시간 켜놨다가 누르면, ② 시점 now 기준으로 Coupon.validateUsable(now)가 돈다. 그새 만료된 쿠폰은 EXPIRED(400)로 막히고, 가격만 바뀐 경우는 PRICE_CHANGED(409)로 재확인된다. ②에서 now로 검증하므로 "12시간 전 화면" 문제가 자동으로 풀린다.
확정 — 이번 범위변동 게이트는 expected 3종 echo로 이번 범위에 포함한다. 총액 1개만 비교하면 "상품가 +1000 / 할인 +1000"이 상쇄돼 통과하는 구멍이 있어 original·discount·total 3종을 비교한다. 이 값은 결제 금액의 근거가 아니라 비교 전용이다 — 결제는 항상 서버 재계산값으로 하므로 위변조(D9)와 무관하다. 업계도 같은 패턴: 토스는 승인 전 저장 금액 대조[1], Amazon은 리뷰 페이지 변동 알림[2], Stripe·Shopify는 서버측 스냅샷(PaymentIntent·draft order price lock)[3] — ②→③ 짧은 틈은 우리도 PENDING Order 박제가 같은 역할을 한다.

FLOW ④

PG 결제 — 결과 3종

박제값(totalAmount)으로 외부 결제를 호출한다. 현재 상품가는 더 이상 안 본다. 결과는 성공·거절·타임아웃 셋이고, 상태 전이가 갈린다.

PG 결과서버 동작최종 상태
승인 성공박제값으로 결제 확정 (현재가 안 봄)PAID
거절재고 increase · 쿠폰 복원 (보상)FAILED
타임아웃복원 금지. 재확인/배치로 결과 확정UNKNOWN → D5
②→③ 짧은 틈박제부터 PG 승인까지의 수백 ms ~ 수 초는 박제값으로 가니 가격 변동에 안 흔들린다. 그래서 이 구간에는 락이 필요 없다.
6

ERROR PATHS

실패 경로 — 재고 · 쿠폰

②(주문 생성)에서 터질 수 있는 비즈니스 실패들. 전부 박제 전에 막혀서, 주문이 만들어지지 않는다.

케이스터지는 지점에러 / HTTP
상품 없음/비활성현재가 조회 (1단계)PRODUCT_NOT_FOUND · 404
재고 부족FOR UPDATE 차감 (2단계)STOCK_INSUFFICIENT · 409
쿠폰 만료 · 최소금액 미달validateUsable(now) (3단계)EXPIRED · MIN_ORDER_NOT_MET · 400
이미 사용한 쿠폰 (동시)use() — @Version 충돌 (3단계)ALREADY_USED · 409
가격 변동변동 게이트 (5단계)PRICE_CHANGED · 409
동시성 한 줄재고는 비관락(FOR UPDATE)으로 직렬화 — 늦은 쪽이 재고 부족(409). 쿠폰은 낙관락(@Version)으로 — 동시 사용 시 늦은 쪽이 충돌해 ALREADY_USED(409). 자원이 둘 다 productId 정렬로 잡혀 데드락은 차단된다(03 문서).

FLOW

전체 흐름 한 장

①~④를 한 장으로. OrderFacade(Tx 없음)가 Tx① → PG 호출 → Tx②를 순서대로 지휘한다. 먼저 비즈니스 흐름으로 — 어디서 갈라지고, 갈라진 곳마다 뭐가 남는지.

같은 흐름을 시퀀스로 — §9의 PG 장애 케이스 A~E가 어디에 꽂히는지까지 한 장에 담았다. 파란 점선이 DB 트랜잭션 경계, 빨간 화살표가 신뢰할 수 없는 외부 호출이다.

DECISION

DTO · 범위 확정

화면을 다 따라가도, 서버가 받는 건 결국 셋뿐이다 — 무엇을 · 몇 개 · 어떤 쿠폰으로.

OrderCreateRequest.kt 
data class OrderCreateRequest(
    val items: List<OrderLineRequest>,   // 필수
    val couponId: Long?,                 // 주문 전체 적용 1장 — 미적용이면 null
    val expectedOriginalAmount: Long,     // ① 계산서 echo — 비교 전용 (§4)
    val expectedDiscountAmount: Long,
    val expectedTotalAmount: Long,
)
data class OrderLineRequest(val productId: Long, val quantity: Int)

// userId 는 헤더 인증에서 — body 에 안 넣는다
// expected 3종은 비교 전용 — 결제 금액은 항상 서버 재계산값. 배송지 — 스펙 밖, 스킵
  • items + couponId 로 확정 필수
  • 가격은 서버 재계산 — 클라가 금액을 결제 근거로 못 보냄
  • 배송지 · 주문자 정보 스킵 — 스펙 0회 언급, 단순 CRUD라 학습 가치 없음
  • expected 3종 변동 게이트 — 이번 범위 확정. 불일치 시 409 PRICE_CHANGED + 현재 금액 응답 확정
  • 쿠폰은 주문 전체 적용 1장(couponId) — 상품별 적용은 추후 확장 (Coupon에 적용대상 개념 신설 필요) 확정
다음이 플로우가 곧 06 문서의 D1-b(PENDING 저장 → Tx 밖 PG → 확정)다. Step 1(UserCoupon.use·@Version)은 결정과 무관하게 지금 시작 가능 — 작고 테스트로 닫힌다.

PG FAILURE MODES

외부 PG 장애 케이스 전수

판별축은 단 하나 — "승인 요청이 PG에 도달했을 가능성이 있는가." 도달 전 실패는 안심하고 FAILED+보상, 도달 후 불확실은 무조건 UNKNOWN+보상 금지다.

구분케이스돈이 나갔나?지금 처리향후 보강
A. 요청 전 실패
(PG 미도달)		PG 점검·다운 — 커넥션 거부확실히 아님FAILED + 보상서킷브레이커로 빠른 차단[5]
Connect 타임아웃 (연결 자체 실패)확실히 아님FAILED + 보상connect/read 타임아웃 분리 설정
B. 응답 수신 실패
(제일 위험)		Read 타임아웃 — 요청은 갔는데 응답 없음모름UNKNOWN · 보상 금지멱등키 재시도(D4) · 상태 조회 배치(D5)[4]
응답 수신 중 커넥션 끊김모름UNKNOWN · 보상 금지〃
C. 명시적 거절
(정상 흐름의 일부)		잔액 부족 · 한도 초과아님FAILED + 보상 · 사유 안내재시도 무의미 — 다른 결제수단 유도
카드 정지·도난·유효기간 만료아님FAILED + 보상〃
FDS(사기 의심) 차단아님FAILED + 보상안내 문구에 차단 사유 노출 금지
D. PG 서버 오류PG 5xx 응답모름 (애매)UNKNOWN · 보상 금지멱등키로 안전 재시도(D4)[4]
승인 유효시간 초과 (토스 기준 10분)아님 — 데이터 유실FAILED + 보상PENDING 만료 정책(D5)[4]
E. 사후 불일치
(응답 이후 판명)		늦은 웹훅 — 우리는 UNKNOWN, PG는 성공나감UNKNOWN 행과 매칭 → PAID 확정웹훅 엔드포인트 + 서명 검증
우리 FAILED 처리 후 PG 성공 판명나감— (범위 밖)망취소(net-cancel) 또는 대사 후 취소[6]
중복 승인 — 재시도가 2번 승인됨2번 나감— (범위 밖)멱등키로 예방(D4) · D+1 대사로 검출[4][6]
PG 성공 직후 Tx② 실패·서버 사망나감PENDING 잔류복구 배치 — 오래된 PENDING → PG 조회 → 확정(D5)
설계 함의이 표의 13케이스가 전부 FAILED / UNKNOWN / PENDING 잔류 셋 중 하나로 수렴한다 — 상태머신 4종이면 케이스 전수를 담을 수 있다는 뜻. 이번 범위에서는 A·C → FAILED+보상, B·D → UNKNOWN+보상 금지의 두 갈래만 구현하면 되고, E열(멱등키·웹훅·대사·복구 배치)은 전부 미결 D4·D5 영역이다. 토스 가이드 기준 read timeout은 60초, 승인은 결제 요청 후 10분 이내[4].
