GOAL

무엇을 증명하는 측정인가

이번 측정의 최종 산출물은 단계별 비교표 하나다 — Stage 1a / 1b / 2 / 3 × {p95, 최대 RPS, 신선도, 개별 순위 비용, 쓰기 경로 부하, 운영 복잡도}.

랭킹은 쓰기(컨슈머가 이벤트를 소비하며 점수 누적)와 읽기(API가 Top-N·개별 순위 조회)가 분리된 시스템이다. 그래서 측정도 두 경로를 따로 재고, 마지막에 혼합 런으로 상호 간섭을 잰다. 여기에 랭킹 특유의 세 번째 축 — 정합성(이벤트 수 × 가중치 = 점수)과 날짜 경계(자정 판 전환 · carry-over) — 을 추가한다. 성능 숫자가 아무리 좋아도 점수가 틀리면 랭킹이 아니기 때문이다.

읽기랭킹 조회 경로

GET /api/v1/rankings 페이지 조회 + 상품 상세의 개별 순위. Stage별로 p95·최대 RPS가 어떻게 붕괴/개선되는지. Stage 1a의 filesort 전체 스캔 → Stage 2의 TTL 캐시 → Stage 3의 ZREVRANGE 비용 차이를 같은 잣대로.

쓰기이벤트 → 점수 누적 경로

Kafka 3토픽 → commerce-streamer 배치 소비 → 점수 upsert. 컨슈머 랙이 발산하지 않는 최대 유입률(소비 천장), dual write(오늘판 +Δ · 내일판 +0.1Δ)의 추가 비용, 이벤트 발행 → 랭킹 반영까지의 신선도 지연.

정합성점수가 맞는가

부하 종료 후 정산: k6가 성공시킨 이벤트 수 × 가중치와 저장소의 점수 합이 일치하는가. 멱등(재소비·재기동) 상황에서 중복 가산이 0인가. §6에서 검증식·허용 오차까지 고정.

경계리셋이 안전한가

자정 판 전환 시 조회 열화·콜드 스타트가 없는가(EXP-01에서 사전 시딩 채택 근거 확보 완료), carry-over 점수가 내일판에 정확히 ×0.1로 실려 있는가, TTL/보존 삭제가 조회를 방해하지 않는가.

측정 조건 고정 (checklist.md 로드맵과 동일)같은 시드 데이터 · 같은 k6 시나리오 · 같은 지표로 Stage만 바꿔 잰다. 변인은 항상 하나 — 랭킹 저장소/조회 방식뿐. 이 조건이 깨지면 비교표가 무효가 된다.

METHOD

R8 방법론 승계 원칙

R8 대기열 측정에서 검증된 6가지 원칙을 그대로 가져온다. 전부 실측 실패에서 나온 교훈이라 생략하지 않는다.

원칙내용R8에서의 근거
이중 관측k6 http_req_duration(체감)과 actuator http_server_requests(서버 처리)를 동시 수집. 두 수치의 갭이 벌어지는 시점 = 포화 시작점평균 rate는 램프 스케줄의 그림자 — week7 EXP-01 오독 교훈
하네스 사전 검증본 런 전 harness-ceiling-smoke.js로 부하 경로 천장 확인. 하네스 천장 ≥ SUT 포화 RPS × 3이어야 유효SSH 터널로 부하 시 macOS ssh 사망(poll: Invalid argument) → 1런 무효
웜업 필수앱 재기동 후 웜업 런 생략 금지. 콜드 런은 *-COLD.* 파일명으로 별도 보존EXP-05 콜드 런에서 enter 실패 121건 — 웜업 후 전부 소멸
변인 통제비교 런은 같은 시드·같은 리소스·같은 인프라. 차이는 브랜치(Stage) 하나M1↔M2 비교 설계 그대로
기록 계약런마다 run-meta(커밋·기동 인자·부하 조건·시각), 결과는 k6 JSON + 샘플러 CSV, EXP 문서 5섹션(조건→가설→수치→판독→결정)week7 PLAN.md §10 포맷 승계
지연 절대치 주의부하가 공인망을 지나면 지연에 인터넷 RTT 포함 → 천장 판정은 처리량·에러율·서버측 지표 기준EXP-04 §1 명시

R9에서 새로 필요한 것

R8과 달리 SUT가 앱 2개다. commerce-api(읽기 API + 이벤트 발행)와 commerce-streamer(소비 + 점수 쓰기)가 같은 노드에서 뜨므로, 샘플러도 두 앱의 actuator를 각각 긁어야 한다. 또 R8의 샘플러는 HTTP·Hikari·Tomcat만 수집했고 CPU·GC·힙은 빠져 있었다(CPU는 별도 보완 런으로 수집). R9에서는 §5의 표준 메트릭 세트로 샘플러를 확장해 보완 런 없이 한 번에 수집한다.

주의 — 컨슈머는 k6가 안 보인다쓰기 경로의 병목은 HTTP 응답에 나타나지 않는다. 이벤트는 202/200으로 접수된 뒤 Kafka 뒤편에서 처리되므로, k6 지표만 보면 쓰기 천장을 영영 못 본다. 소비 천장은 반드시 컨슈머 랙(records-lag)과 신선도 프로브(§4 S-FRESH)로 관측한다.

노드사양 / 구성R9 변경점

확정 (2026-07-15)토폴로지 확정 — EC2 2대, 앱 노드에 JVM 2개 동거, HTTP 부하는 api만 수신. streamer 포트는 이미 분리돼 있음: server 8083 / management 8084 (application.yml에 api 8081과의 충돌 회피 주석 존재). 간섭이 판정을 흐리면 노드 분리 + 전 Stage 재런.

SCENARIOS

부하 시나리오 (k6)

기존 자산 2개를 재사용하고, 랭킹 전용 3개를 새로 만든다. 전부 open model(arrival-rate) — 도착률이 통제 변수다.

시나리오내용재사용/신규
S-READranking-read.js — GET /api/v1/rankings ramping-arrival-rate 50→100→200→400/s 각 1분. 페이지 분포: page1 80% · page2~5 15% · deep(6~50) 5%. date: 오늘 90% · 어제 10%. size=20 고정. 태그 api:rankings신규
S-DETAIL상품 상세(개별 순위 포함) 조회 암 — browse-journey.js의 detail 경로 재사용. Stage 1a의 "개별 순위 = 전 행 2중 스캔" 비용이 여기서 드러난다재사용
S-WRITE이벤트 유입 — browse-journey.js(view, RATE 100/s) + order-ramp.js(order, MODE=warmup 수준 상수율) + like 토글. ⚠️ 블로커(2026-07-15 확인): like HTTP 엔드포인트가 현재 브랜치에 없음(like 도메인에 interfaces 레이어 부재, LikeService 호출 컨트롤러 0건). like 암은 ① 엔드포인트 추가 ② 테스트 프로듀서로 Kafka 직접 발행 중 결정 필요 — 그전까지 S-WRITE는 view+order 2종으로 진행재사용+블로커
S-MIX실전 혼합: S-READ 200/s + S-WRITE 동시. 읽기와 쓰기(같은 테이블/키에 upsert)의 상호 간섭 측정 — Stage 1b에서 INDEX(ranking_date, score DESC) 재배치 경합이 조회 p95를 얼마나 미는가조합
S-FRESHranking-freshness.js — 센티널 상품 1개에 like 1건 발사 → rankings API를 500ms 간격 폴링 → 점수 변화 감지까지의 시간. 부하 배경(S-WRITE) 위에서 30회 반복해 신선도 p50/p95 산출. Stage 2에서는 이 값이 TTL 60s에 수렴함을 숫자로 확인신규
쓰기 유입률의 앵커R8에서 확보한 천장 — 주문 C=200/s(hot), 배경 탐색 100명/s(≈340 req/s) — 을 유입 기준선으로 쓴다. 탐색 유저 1명 ≈ view 2건 + like 0.2건이므로, 배경 100명/s ≈ 이벤트 220/s 유입이 S-WRITE의 1× 기준. 소비 천장 탐색은 이 배수(1×/2×/4×)로 올린다.
ranking-read.js — 골격 (신규)
// R8 order-ramp.js 패턴 승계: open model + 사후 판정(threshold 없음)
export const options = {
  scenarios: { read: {
    executor: 'ramping-arrival-rate', startRate: 50, timeUnit: '1s',
    stages: [ // 50→100→200→400/s 각 1분
      { target: 50, duration: '1m' }, { target: 100, duration: '1m' },
      { target: 200, duration: '1m' }, { target: 400, duration: '1m' } ],
    preAllocatedVUs: 300, maxVUs: 2000, gracefulStop: '10s',
  }},
  summaryTrendStats: ['avg','med','p(90)','p(95)','p(99)','max'],
};
export default function () {
  const page = pickPage();          // 80% p1 / 15% p2~5 / 5% deep
  const date = pickDate();          // 90% 오늘 / 10% 어제 (?date=yyyyMMdd)
  http.get(`${BASE}/api/v1/rankings?date=${date}&size=20&page=${page}`,
    { tags: { api: 'rankings' }, timeout: '10s' });
}

CORRECTNESS

정합성 · 날짜 경계 · 멱등 검증

성능 런이 끝날 때마다 정산(reconciliation)을 돌린다 — 부하 중 점수가 하나라도 새면 그 Stage는 성능과 무관하게 탈락이다.

정산식 — 이벤트 수 × 가중치 = 점수 합

k6가 커스텀 카운터로 성공 응답 기준 이벤트 수를 센다: view는 상세 조회 200 건수(V), like는 등록 성공(L⁺)·취소 성공(L⁻), order는 주문 성공의 order line 수(O). 부하 종료 + 랙 0 도달 후 저장소를 조회해 대사한다.

verify-ranking.sql — 정산 (런마다 실행)
-- 기대값: E = 0.1·V + 0.2·(L⁺ − L⁻) + 0.7·O   (V·L·O는 k6 카운터 출력)
-- [1] 오늘판 점수 합 = E 인가
SELECT SUM(score) FROM product_ranking_daily WHERE ranking_date = :today;
-- [2] 내일판 = 오늘판 × 0.1 인가 (dual write carry 검증)
SELECT SUM(score) FROM product_ranking_daily WHERE ranking_date = :tomorrow;
-- [3] R7 집계와 교차 대사 (같은 트랜잭션이므로 Stage 1b에선 완전 일치해야 함)
SELECT SUM(view_count), SUM(like_count), SUM(order_count) FROM product_metrics;
-- [4] Stage 3: ZSET vs MySQL 진실원 Top-100 비교 (ZREVRANGE ↔ ORDER BY score DESC)
이벤트발행 경로허용 오차
like / orderoutbox(BEFORE_COMMIT) → OutboxRelay → Kafka — 본 트랜잭션과 원자적0 — 정확히 일치해야 한다. 불일치 = 버그
viewAFTER_COMMIT + @Async 직접 발행 — 설계상 유실 허용결손만 허용(저장소 ≤ k6 카운트). 유실률을 기록해 executor 큐 적체와 상관 분석. 초과는 0 — 중복 가산은 어떤 경우에도 버그

멱등 — 재소비·재기동 카오스 런

S-WRITE 부하 중간에 commerce-streamer를 1회 kill → 재기동한다. 재기동 직후 Kafka가 마지막 커밋 오프셋부터 배치를 재전달하므로, EventHandled(event_id PK) 멱등이 실전 부하에서 중복 가산을 막는지 확인한다. 판정: 정산식 [1]~[3]이 카오스 없는 런과 동일하게 성립. 부수 관측: 재기동~랙 회복 시간(복구 소요), 회복 구간의 신선도 악화 폭.

날짜 경계 — 판 전환·carry-over·보존

  • 판 전환 정확성 — 시스템 시계를 돌릴 수 없으므로 occurredAt 주입으로 검증: 테스트 프로듀서로 UTC 14:59:59 / 15:00:00(KST 23:59:59 / 00:00:00) 이벤트를 발행해 각각 D판·D+1판에 적재되는지 확인. 통합 테스트에 이미 있는 케이스를 부하 환경에서 재확인 EXP-06
  • 경계 시점 조회 열화 — 판 전환 시각 전후로 S-READ를 걸어 p95 변화 기록. dual write 모델은 배치가 없어 EXP-01의 −10%보다도 좋아야 정상 — 실측으로 확정 EXP-06
  • 어제 판 조회 — 전환 후 ?date=어제가 전환 전 최종 순위와 동일한지(과거 판 불변성) EXP-06
  • 보존/TTL — Stage 1b: D-2 DELETE 배치 실행 중 S-READ p95 열화 측정. Stage 3: 키 TTL 2d 부여 확인 + TTL 미부여 키 0건 스캔 EXP-06
  • Stage 3 드리프트 — MySQL 집계와 ZSET이 트랜잭션 경계 밖으로 갈라진 뒤, 부하 종료 시점의 점수 차(드리프트)를 상품별로 측정. WRITING-LOG 미결 #3(ZSET 갱신 위치)·#7(유실·복구)의 판단 입력 EXP-05

EXP목적 · 부하 · 산출판정 기준

EXP-05Stage 3 ZSET — 동일 부하 전체 재실행(S-READ·S-WRITE·S-MIX·S-FRESH) + 드리프트 측정 + Redis 메모리 점유(판 3개 공존)비교표 완성이 목적. 추가로 evicted_keys=0 · TTL 미부여 키 0건 · 카오스 런 정산 성립
EXP-06날짜 경계 통합 검증 — §6 체크리스트 전체(occurredAt 주입·경계 조회 열화·과거 판 불변·보존 배치)체크리스트 5항목 전부 통과. 경계 전후 p95 변화 기록
