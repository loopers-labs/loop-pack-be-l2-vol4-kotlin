BIG PICTURE

큰 그림 — 무엇이 오가고 저장되나

주문 한 건은 단일 트랜잭션 안에서 네 협력자를 순서대로 부르고, 그 결과로 두 테이블이 새로 생기고 두 곳의 상태가 바뀐다.

OrderController는 인증 필터가 넣어준 userId와 요청 본문만 받아 OrderFacade.place()에 위임한다. place()는 @Transactional 하나로 묶여 있고, 외부 호출(결제 PG)은 아직 없다.

한 문장주문은 상품 조회 → (쿠폰) → 주문 저장 → 재고 차감 순서로 한 트랜잭션 안에서 끝나고, 마지막 상태는 항상 PENDING_PAYMENT다. 결제는 이 다음에 별도로 일어난다.

STEP BY STEP

세부 스텝 — place() 한 줄씩

OrderFacade.place(userId, command)가 위에서 아래로 실행하는 그대로다. 각 스텝의 입력·처리·결과(저장)를 분리해 본다.

place(command) → OrderInfo@Transactional · 상태 변경
입력OrderCreateCommand(userId, items, couponId?, expected 금액 3종) — userId 포함
가드items 비어 있으면 BadRequestException(EMPTY_ORDER_ITEMS)
책임아래 ①~④ 오케스트레이션 + 트랜잭션 경계
컨벤션인증된 principal(userId)은 command에 담는다. command가 작업에 필요한 입력을 모두 가지는 단일 객체이기 때문이다. 단 값은 @RequestAttribute(ACCOUNT_ID)(인증)에서만 채우고 요청 DTO 필드로 두지 않는다. Microsoft eShop(CreateOrderCommand)·DDD/CQRS 권위 출처가 따르는 패턴.
① productService.getActiveProducts(productIds) → Map<Long, Product>
처리요청 라인의 productId로 활성 상품을 모아 조회
사용가격 합으로 originalAmount 계산 (price × quantity 합)
저장없음 (읽기 전용)
② couponService.use(userId, couponId, originalAmount, now) → Money(할인액)couponId 있을 때만
처리UserCoupon·Coupon 조회 → validateUsable → userCoupon.use(now)
정합성낙관락 + 중복 사용 차단. 할인액은 DiscountPolicy.calculateDiscount
저장user_coupon UPDATE(used). couponId 없으면 할인액 Money(0)
③ orderService.create(command, products, discount) → OrderInfo
스냅샷라인마다 OrderItemSnapshot(productId, brandId, productName, brandName=null, unitPrice, quantity)
금액 검증계산한 original/discount/total ≠ 요청의 expected 3종 → ConflictException(PRICE_CHANGED)
생성Order.create() → status=PENDING_PAYMENT, item 추가, 할인 적용
저장orders + order_item INSERT (cascade ALL)
④ inventoryService.decreaseStock(lines) → Unit비관락 · 맨 마지막
처리productId 정렬 후 findAllByProductIdInForUpdate(SELECT … FOR UPDATE) → 각 inventory.decrease(qty)
왜 마지막행 점유(락) 시간을 최소화 — 외부 조회·검증을 모두 끝낸 뒤 잠근다
저장inventory UPDATE (재고 차감)
반환OrderInfo가 컨트롤러로 돌아가 OrderCreateResponse로 변환된다 — orderId · status(PENDING_PAYMENT) · originalAmount · discountAmount · totalAmount.

CONTRACT

요청 · 응답 데이터

클라이언트가 보내는 것과 받는 것. 금액 3종(expected)을 요청에 함께 실어 서버 계산값과 다르면 거절(PRICE_CHANGED)한다.

요청 — OrderCreateRequest

필드타입설명
itemsList<{productId, quantity}>주문 라인
couponIdLong?선택 — 있으면 쿠폰 사용
expectedOriginalAmountLong클라이언트가 본 원금액
expectedDiscountAmountLong클라이언트가 본 할인액
expectedTotalAmountLong클라이언트가 본 결제 예정액
인증본문에 userId는 없다. X-Loopers-LoginId / Pw 헤더 → AccountHeaderAuthenticationFilter → @RequestAttribute(ACCOUNT_ID)로 주입된 뒤 request.toCommand(userId)로 command에 합쳐진다.

응답 — OrderCreateResponse

필드타입값
orderIdLong생성된 주문 id
statusOrderStatusPENDING_PAYMENT
originalAmountLong서버 확정 원금액
discountAmountLong서버 확정 할인액
totalAmountLong서버 확정 결제 예정액

PERSISTENCE

저장되는 데이터 (테이블)

주문 한 건이 만들어내는 것: 새 행 2종(orders · order_item)과 상태 변경 2종(user_coupon · inventory).

orders — 새 행 1개

컬럼타입값 / 비고
user_idLong주문자 (updatable=false)
ordered_atLocalDateTime생성 시각
coupon_idLong?사용한 쿠폰 (nullable)
original_amountMoney원금액
discount_amountMoney할인액
total_amountMoneyoriginal − discount
statusString(20)PENDING_PAYMENT

order_item — 라인 수만큼 (1:N)

컬럼타입값 / 비고
order_idLongFK → orders
product_idLong주문 시점 상품
brand_idLong?스냅샷
product_nameString주문 시점 이름(스냅샷)
brand_nameString?현재 항상 null로 저장
unit_priceMoney주문 시점 단가(스냅샷)
quantityInt≥ 1 (init 검증)

상태① user_coupon

couponId가 있을 때만 used로 UPDATE (낙관락, 중복 사용 차단). 새 행 아님.

상태② inventory

해당 상품 재고를 FOR UPDATE로 잠그고 차감 UPDATE. 새 행 아님.

결제 흔적 없음이 시점에 payment 관련 데이터는 한 줄도 생기지 않는다. Order에는 transactionKey 필드조차 없다. 결제는 §5의 별도 흐름.

ROUND 6

Payment 연동 지점 (추가 예정)

현재 플로우는 PENDING_PAYMENT에서 끝난다. 결제는 여기서부터 별도 요청·별도 도메인으로 이어질 예정이며, 아직 코드에 없다.

지금 코드에 있는 것

Order의 상태 전이 메서드 confirmPayment() / failPayment() / markUnknown()와 상태머신만 준비돼 있다. 호출하는 쪽은 아직 없음.

예정 Round 6에서 붙는 것

별도 POST /api/v1/payments → Payment 도메인이 transactionKey·status 보관 → 콜백/조회로 PAID/FAILED 확정.

Payment에 들어갈 데이터 (계획)

필드출처비고
orderId요청어떤 주문의 결제인지
amount주문 확정 금액주문의 totalAmount
cardType / cardNo요청 → PG 제출PG로만 전달
transactionKeyPG 응답제출 성공 시 수신·저장
status도메인PENDING → PAID / FAILED
설계 근거위 결제 흐름의 결정(별도 Payment 도메인 · 비동기 접수 · Fallback 시 UNKNOWN)은 00-plan의 D1~D4에 정리돼 있다. 이 페이지는 현재 코드 사실까지만 다루고, 결제 흐름 상세는 그 문서를 따른다.
