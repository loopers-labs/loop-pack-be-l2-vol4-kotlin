0왜 이 글을 만들었나

3주차 과제는 Brand / Product / Inventory / Like / Order 다섯 도메인을 DDD 방식으로 구현합니다. 그런데 코드를 짜기 전에 개념이 분명하지 않으면 같은 단어를 서로 다른 의미로 쓰게 되고 (예: "Brand 도메인의 Brand 엔티티"라는 표현에서 도메인과 엔티티가 무엇인지), 결과적으로 패키지 구조도 어긋나기 시작합니다.

이 문서가 다루는 네 가지 개념은 다음과 같습니다.

  • Layered Architecture — 코드를 4개의 층으로 어떻게 나누는가, 그리고 전통적인 3계층과 무엇이 다른가
  • Entity vs Value Object — 왜 같은 도메인 안에서도 두 가지를 따로 두는가, 그 이점은 무엇인가
  • Domain Service vs Application Service — 같은 이름의 "Service" 두 개가 무엇이 다른가
  • Entity vs Domain — 헷갈리는 이 두 단어가 정확히 무엇을 가리키는가

각 개념은 비유 → 정의 → 본 프로젝트 코드 매핑 → 장단점 → 실무 패턴 (공식 docs / 빅테크 블로그) 순서로 다룹니다. 개념만 외우는 게 아니라 "본 프로젝트 어디에 어떻게 박힌다"가 명확해야 Phase 1 ~ 4 구현이 흔들리지 않습니다.

1DDD Layered Architecture — 전통 3-tier와 무엇이 다른가

1.1 음식점 비유

Analogy
레스토랑은 4개의 공간으로 나뉩니다
손님이 들어오는 홀(presentation)이 있고, 주문을 받아 주방에 전달하고 결제까지 챙기는 매니저(application)가 있습니다. 실제로 음식을 만드는 요리사(domain)는 가장 안쪽 주방에 있고, 식자재와 가스·수도는 외부 공급망 — 식자재 창고(infrastructure)가 관리합니다.

손님은 요리사를 직접 만나지 않습니다. 요리사도 식자재를 직접 사 오지 않습니다. 각자의 책임이 분명해야 가게가 굴러갑니다. DDD Layered Architecture는 코드를 이렇게 4개의 층으로 나누는 방식입니다.

1.2 전통적 Layered Architecture — "3-tier"의 한계

전통적인 엔터프라이즈 애플리케이션은 보통 3개의 층(tier)으로 나뉘었습니다.

이 구조의 의존 방향은 위에서 아래로입니다. Presentation이 Business에 의존하고, Business가 Data에 의존합니다. 이 자체는 자연스러워 보이지만, 실제로는 다음과 같은 문제를 만듭니다.

  • DB 중심 설계: Business 로직이 Data Tier(DB 스키마)에 의존하므로 비즈니스 모델이 "테이블이 곧 모델"이 되어버립니다. 객체에 행위가 없고 데이터만 담는 Anemic Domain Model이 양산됩니다.
  • 변경 전파: DB 컬럼 하나 바뀌면 Service → Controller → DTO까지 줄줄이 영향을 받습니다.
  • 도메인 지식의 분산: "주문 총액은 어떻게 계산하나" 같은 핵심 로직이 Service 여러 곳에 흩어집니다. 어디가 진실인지 찾기 어려워집니다.
  • 테스트 곤란: 비즈니스 로직을 단위 테스트하려 해도 DB가 옆에 붙어 있어 Spring/JPA 전체를 띄워야 합니다.

1.3 DDD Layered Architecture — Domain이 중심이다

Eric Evans는 2003년 책 Domain-Driven Design(Ch.4 "Isolating the Domain")에서 위 3-tier의 한계를 짚으며 4개의 layer를 제안했습니다. 핵심은 단순히 한 층이 더 늘었다는 것이 아니라 의존 방향이 바뀐다는 점입니다.

핵심 차이
전통 3-tier에서는 Business → Data로 의존이 흘렀습니다. DDD에서는 Infrastructure → Domain입니다 (점선이 가리키는 방향). Domain이 가장 안쪽에 있고, Infrastructure가 Domain이 정의한 인터페이스(예: BrandRepository)를 구현(implements)합니다. 이를 Dependency Inversion Principle (DIP)이라 부릅니다.

이 작은 화살표 방향의 차이가 만드는 결과는 큽니다.

  • Domain은 Spring · JPA · Redis 같은 프레임워크를 모릅니다. 순수 Kotlin/Java만으로 작성됩니다.
  • Domain 테스트는 DB나 Spring 컨텍스트 없이 단위 테스트로 검증 가능합니다.
  • Repository 구현이 JPA에서 MyBatis로 바뀌어도 Domain 코드는 한 줄도 안 바뀝니다.
  • 비즈니스 로직이 Anemic해지지 않습니다 — Entity에 행위(method)가 살고, Service는 협업만 담당합니다.

1.4 4개 Layer 각각의 책임

Presentation Layer
외부 요청을 받아 내부로 전달하고, 결과를 외부 형식으로 변환해 응답하는 가장 바깥쪽 입출구
▼ 의존
Application Layer
Use Case를 조립한다. 여러 도메인 객체를 어떻게 부를지 결정하고, 트랜잭션 경계와 인증을 다룬다. 비즈니스 규칙 자체는 가지지 않는다.
▼ 의존
Domain Layer ← 가장 중심
비즈니스 규칙·불변식·도메인 객체가 모두 사는 곳. 프레임워크 의존성 0. 추상(Repository 인터페이스 등)을 정의한다.
▲ 구현 (Infrastructure가 Domain의 추상을 구현)
Infrastructure Layer
기술적 디테일 — JPA · Redis · 외부 API · 메시지 큐. Domain이 정의한 인터페이스를 구현해 끼워 넣는다.

1.5 각 Layer의 개념 상세 — 무엇이 들어가고 무엇이 안 들어가는가

PRESENTATION

Presentation Layer (본 프로젝트는 interfaces)

책임 — 외부 세계(브라우저 · 다른 시스템)와 애플리케이션 사이의 통역사입니다. HTTP 요청을 받아 내부 호출로 바꾸고, 내부 결과를 JSON / HTML로 바꿔 응답합니다. 외부 형식이 바뀌어도(REST → GraphQL, JSON → Protobuf) 다른 layer는 영향받지 않게 합니다.

들어가는 것

  • Controller (HTTP 매핑)
  • Request / Response DTO
  • API Spec (OpenAPI)
  • 인증 필터 / 인터셉터
  • 요청 검증 (@Valid)

들어가지 말아야 할 것

  • 비즈니스 규칙 (예: 가격 ≥ 0)
  • 트랜잭션 관리 (@Transactional)
  • JPA 호출
  • 외부 API 직접 호출
  • 도메인 객체를 그대로 JSON 직렬화 (DTO 변환 필요)
본 프로젝트 매핑
apps/commerce-api/src/main/kotlin/com/loopers/interfaces/api/{도메인}/
  • BrandV1Controller.kt, AdminBrandV1Controller.kt — HTTP 매핑
  • BrandV1Dto.kt — Request/Response 객체
  • BrandV1ApiSpec.kt — OpenAPI 스펙 인터페이스
  • ApiControllerAdvice.kt — 도메인 예외를 HTTP 상태로 변환 (이미 존재)
본 프로젝트는 presentation 대신 interfaces라는 이름을 씁니다. 이는 Hexagonal Architecture (Ports & Adapters)의 영향으로, 외부와 맞닿는 모든 어댑터(HTTP · CLI · gRPC 등)를 한 곳에 모은다는 의미입니다. 이름만 다를 뿐 책임은 Presentation Layer와 같습니다.
APPLICATION

Application Layer

책임 — Use Case를 조립합니다. "주문하기"라는 행위가 들어오면 Product를 조회하고, Inventory를 차감하고, Order를 저장하는 흐름을 한 트랜잭션 안에 엮습니다. 비즈니스 규칙 자체는 가지지 않습니다 — 그건 Domain의 책임. 오케스트라의 지휘자라고 보면 됩니다.

들어가는 것

  • Application Service (Facade) — Use Case 진입점
  • @Transactional 트랜잭션 경계
  • Command / Query 객체 (도메인 입력 모델)
  • 인증된 사용자 컨텍스트 소비
  • 여러 Domain 객체 / Domain Service 협업

들어가지 말아야 할 것

  • 비즈니스 규칙·불변식 (Domain의 책임)
  • HTTP 관련 코드 (Presentation의 책임)
  • SQL · JPA 메서드 호출 (Infrastructure의 책임)
  • "if 상품이 활성 상태면" 같은 정책 판단 (Entity 메서드로)
본 프로젝트 매핑
apps/commerce-api/src/main/kotlin/com/loopers/application/{도메인}/
  • BrandService.kt — Use Case, @Transactional
  • BrandFacade.kt — DTO 매핑 + 인증 컨텍스트 소비
  • OrderService.kt — 주문 Use Case를 한 트랜잭션으로 묶음
  • Command/Info 객체는 같은 파일에 동거 (CLAUDE.md §4)
DOMAIN

Domain Layer ★ 가장 중심

책임 — 비즈니스의 핵심 지식이 농축되는 곳입니다. "브랜드 이름은 1~50자다", "재고는 0 미만이 될 수 없다", "주문 총액은 단가 × 수량의 합이다" — 이런 규칙들이 살아있는 Entity와 VO 안에 모여 있어야 합니다. 프레임워크 의존성 0이 원칙입니다. (Spring/JPA가 사라져도 Domain 코드는 그대로 컴파일됩니다.)

들어가는 것

  • Entity (식별성 있는 도메인 객체)
  • Value Object (속성 동일성 + 불변)
  • Aggregate Root (일관성 경계)
  • Domain Service (여러 객체 협업, stateless)
  • Repository 인터페이스 (구현은 Infrastructure)
  • ErrorCode enum (owning 도메인)
  • 도메인 이벤트 (자리만)

들어가지 말아야 할 것

  • JPA @Repository 구현체
  • Redis / Kafka / HTTP 클라이언트
  • Spring @Service (단, 본 프로젝트는 Domain Service에 한해 허용 — Pragmatism)
  • Request/Response DTO (Presentation의 책임)
  • @Transactional (Application의 책임)
본 프로젝트 매핑
apps/commerce-api/src/main/kotlin/com/loopers/domain/{도메인}/
  • Brand.kt — Entity
  • BrandName.kt, ProductName.kt, domain/shared/Money.kt — Value Object (Price/Quantity/LikeCount는 VO 아님 — 엔티티 필드)
  • BrandRepository.kt — 인터페이스만
  • ProductCatalogService.kt, OrderPlacementService.kt — Domain Service
  • BrandErrorCode.kt — owning 도메인 에러 코드
INFRASTRUCTURE

Infrastructure Layer

책임 — 기술적인 디테일을 모두 떠안습니다. Domain이 "BrandRepository로 저장한다"고 약속만 하면, Infrastructure가 그 약속을 JPA로 구현해 끼워 넣습니다. 구현이 JPA에서 MyBatis로, MySQL에서 PostgreSQL로 바뀌어도 Infrastructure 안에서만 갈아끼우면 됩니다.

들어가는 것

  • Repository 구현체 (BrandRepositoryImpl)
  • Spring Data JPA 인터페이스 (BrandJpaRepository)
  • 외부 시스템 어댑터 (PG · 알림 · 검색)
  • Redis 캐시 어댑터
  • 메시지 큐 Producer / Consumer
  • 기술 환경 설정 (Datasource · Properties)

들어가지 말아야 할 것

  • 비즈니스 규칙 판단 (예: 재고 부족인지 결정)
  • 도메인 객체의 가공·변환 (그건 Domain Service / Application의 책임)
  • HTTP 응답 형식 결정 (Presentation의 책임)
본 프로젝트 매핑
apps/commerce-api/src/main/kotlin/com/loopers/infrastructure/{도메인}/
  • BrandJpaRepository.kt — Spring Data JPA 인터페이스
  • BrandRepositoryImpl.kt — Domain의 BrandRepository 구현
  • JPA 설정(JpaConfig)은 modules/jpa 모듈에 공통화

1.6 의존 방향 한 줄 요약

화살표 방향이 핵심입니다. 위에서 아래로가 아니라, 바깥에서 중심으로 향합니다. 

// 의존 방향
Presentation → Application → Domain ← Infrastructure
                                      ↑
                              여기 화살표 방향이 핵심
                              (DIP — Infrastructure가 Domain의 추상을 구현)

본 프로젝트의 BrandRepository를 예로 들면 다음과 같이 박힙니다. 

// domain/brand/BrandRepository.kt — 인터페이스
interface BrandRepository {
    fun save(brand: Brand): Brand
    fun findById(id: Long): Brand?
    fun existsByName(name: BrandName): Boolean
}

// infrastructure/brand/BrandRepositoryImpl.kt — 구현
@Repository
class BrandRepositoryImpl(
    private val jpa: BrandJpaRepository
) : BrandRepository {
    override fun save(brand: Brand): Brand = jpa.save(brand)
    // ...
}

BrandService는 BrandRepository 인터페이스에만 의존합니다. JPA 구현이 무엇인지는 모릅니다. 이 한 가지가 Domain Layer를 프레임워크로부터 독립시키는 핵심입니다.

1.7 Repository 인터페이스를 Domain에 두는 이유 (본 프로젝트 결정)

DDD에서 Repository 인터페이스는 "Domain Model의 일부"로 간주됩니다 (Eric Evans, DDD Ch.6). 본 프로젝트는 이 원칙을 따라 BrandRepository 인터페이스를 com.loopers.domain.brand 아래에 둡니다. 구현은 com.loopers.infrastructure.brand에 둡니다.

참고로 account 모듈은 다른 방식(Repository 인터페이스를 persistence 모듈에)을 쓰는데, 이는 학습 목적상 의도적으로 다르게 두어 두 패턴을 모두 경험해 보기 위한 결정입니다. 자세한 배경은 docs/week3/00-plan.md §3.7을 참조하세요.

1.9 장단점

장점

  • 비즈니스 로직이 한 곳(Domain)에 모여 변경에 강해진다
  • Domain은 프레임워크 없이 테스트 가능 — 빠르고 안정적
  • 인프라(DB, 큐, 캐시) 교체가 국지적으로 끝난다
  • 도메인 어휘(ubiquitous language)가 코드에 살아남는다 — 비개발자도 읽을 수 있다

단점

  • 초기 학습 곡선이 있다 — 단순 CRUD에는 과한 구조
  • 같은 데이터를 Entity / DTO / JPA Entity로 여러 번 변환하게 됨
  • Domain Service / Application Service 구분 기준이 흐릿할 때가 있음
  • 팀 전체가 약속을 공유하지 않으면 layer 침범이 쉽게 일어난다 (Domain에서 Spring import 등)

1.10 실무 활용 패턴

  • 핵사고날(Hexagonal) / 어니언(Onion) / 클린 아키텍처(Clean Architecture)은 모두 DDD Layered Architecture를 출발점으로 한 변형입니다. 동심원이냐 6각형이냐의 차이일 뿐 "Domain이 중심, Infrastructure가 어댑터"라는 본질은 같습니다.
  • Spring Boot 프로젝트에서의 현실: Domain Layer 안의 객체에 JPA 어노테이션(@Entity, @Column)을 붙이는 것은 엄밀한 DDD 관점에서는 프레임워크 침범입니다. 그러나 두 객체(도메인용 / JPA용)를 따로 유지하는 비용이 크므로 실무에서는 절충해 같이 쓰는 경우가 많습니다 (본 프로젝트도 이 절충안).
  • 모듈 분리: 도메인이 커지면 Gradle / Maven 모듈로 layer를 강제 분리해 컴파일러가 침범을 차단하게 합니다. 본 프로젝트의 modules/account-*가 그 예시입니다. commerce-api는 본 주차에는 단일 모듈이지만 패키지로 계층을 분리합니다 (YAGNI).

2Entity vs Value Object — 왜 따로 두는가

2.1 비유 — 학생과 색깔

Analogy
학생은 학번으로 구분하지만, 색깔은 그 자체가 본질입니다
교실에 김민지라는 학생이 두 명 있어도 학번이 다르면 서로 다른 학생입니다. 이름이 바뀌어도, 키가 자라도, 머리를 잘라도 학번만 같으면 같은 학생입니다. 이런 객체를 Entity라고 합니다.

반대로 "빨강"이라는 색깔은 어떨까요? 미술실의 빨강과 운동장 페인트의 빨강이 RGB 값이 같다면 같은 빨강입니다. 색깔에는 식별자가 없고, 값 그 자체가 본질입니다. 이런 객체를 Value Object (VO)라고 합니다.

도메인을 모델링할 때 "이 객체는 학생 같은 거야, 색깔 같은 거야?"를 구분하는 것이 첫 단추입니다.

2.2 정의

Entity
식별자(id)로 동일성이 결정되는 도메인 객체. 시간이 지나며 속성이 변해도 id가 같으면 같은 객체로 본다. 라이프사이클(생성 → 수정 → 삭제)을 가진다.
Value Object (VO)
속성들의 조합으로 동일성이 결정되는 도메인 객체. 식별자가 없다. 한 번 만들어지면 바뀌지 않는다(불변, immutable). 같은 값이면 같은 객체로 본다.

2.3 코드로 보는 차이

// Entity — id로 동일성 판단
class Brand(
    val id: Long,
    var name: BrandName,         // 시간이 지나 바뀔 수 있음
    var description: String?
) {
    override fun equals(other: Any?) = other is Brand && other.id == this.id
}

// Value Object — 값 자체로 동일성 판단, 한 번 만들면 못 바꿈
@Embeddable
data class BrandName(val value: String) {
    init {
        require(value.isNotBlank()) { "브랜드 이름은 비어있을 수 없습니다" }
        require(value.length in 1..50) { "브랜드 이름은 1~50자입니다" }
    }
}

핵심 차이 두 가지:

  • Entity는 변할 수 있지만 같다: Brand(id=1, name="Nike")가 name="Nike Inc."로 바뀌어도 id가 1이면 여전히 같은 Brand.
  • VO는 변할 수 없다: BrandName("Nike")를 "Nike Inc."로 만들고 싶으면 새 BrandName 객체를 만들어 갈아끼웁니다. 기존 객체를 수정하지 않습니다.

2.4 왜 VO를 따로 두는가 — 4가지 이점

이점 1 — 자기 검증 (Self-Validation)

BrandName 객체가 존재한다는 것 자체가 "유효한 브랜드 이름"임을 보장합니다. 어디서 받아왔든, 어떻게 만들었든 init 블록을 통과한 객체만 존재할 수 있기 때문입니다. 매번 "이 String이 유효한지" 검증할 필요가 없습니다. 

// VO 없이
fun createBrand(name: String) {
    if (name.isBlank()) throw ...
    if (name.length > 50) throw ...
    // ↑ Brand 만드는 모든 곳에서 이 검증을 반복해야 함
}

// VO 사용
fun createBrand(name: BrandName) {
    // 이 함수 시작 시점에 name은 이미 유효함이 보장됨
}

이점 2 — 도메인 의미를 코드로 표현 (Make Implicit Explicit)

price: Long이라고 쓰면 그게 원 단위인지 달러인지, 음수가 가능한지 알 수 없습니다. price: Price라고 쓰면 "이건 가격이다, 음수가 될 수 없다"가 타입에 박힙니다. 코드를 읽는 사람이 도메인을 더 빨리 이해합니다.

이점 3 — 같은 타입 헷갈림 방지 (Primitive Obsession 회피)

fun transfer(from: Long, to: Long, amount: Long)이라는 함수가 있을 때, 인자 순서를 헷갈리기 쉽습니다. fun transfer(from: AccountId, to: AccountId, amount: Money)라면 컴파일러가 잘못된 호출을 막아줍니다. 같은 Long이지만 의미가 다른 값을 구분합니다.

이점 4 — 불변성으로 인한 안정성

여러 쓰레드 / 여러 객체가 같은 VO를 공유해도 누군가 값을 바꿔서 다른 곳에 영향을 주는 일이 없습니다. 전달해도 안전합니다. 캐싱·해싱·비교가 단순해집니다.

2.5 본 프로젝트 매핑

Entity
  • Brand — 브랜드 (id로 식별, 이름·설명 변경 가능)
  • Product — 상품 (id로 식별)
  • Inventory — 재고 (id로 식별, productId 1:1)
  • ProductLike — 좋아요 (id로 식별, UK (userId, productId))
  • Order, OrderItem — 주문 / 주문 항목

2.7 장단점

VO 도입의 장점

  • 검증이 한 곳에 모임 — DRY
  • 도메인 의미가 타입에 박힘 — 가독성
  • 불변이라 동시성 안전
  • 같은 타입 헷갈림 방지 (Primitive Obsession)

단점 / 비용

  • 객체 수가 늘어남 — 작은 도메인에는 과함
  • JPA @Embeddable 매핑 학습 필요
  • 변환(VO ↔ String)이 곳곳에 필요
  • VO 내부 필드명이 DB 컬럼 prefix가 되는 등 영속성 디테일 누수 가능

2.8 실무 활용 패턴

3Domain Service vs Application Service — 두 Service는 왜 다른가

3.1 비유 — 요리사와 매니저

Analogy
둘 다 음식점 직원이지만, 일이 완전히 다릅니다
요리사(Domain Service)는 음식을 만드는 사람입니다. 재료 손질, 굽기, 플레이팅 — 이게 음식점의 본질적인 가치를 만들어내는 일입니다. 손님이 누구인지, 어떤 카드로 결제하는지는 모릅니다.

매니저(Application Service)는 손님의 주문을 받고, 요리사에게 전달하고, 음식이 나오면 손님에게 가져다 드리고, 결제까지 챙기는 사람입니다. 직접 요리하지는 않습니다. 조립(orchestration)이 일입니다.

둘 다 "Service"라 부르지만 책임이 다릅니다. Domain Service는 도메인의 본질적인 행위, Application Service는 그것들을 엮는 흐름입니다.

3.2 정의

Domain Service
어떤 도메인 행위가 특정 Entity 하나에 자연스럽게 속하지 않을 때 그것을 담는 곳. 여러 도메인 객체 / Aggregate가 협업해야 할 때 사용한다. stateless (자기 상태를 가지지 않음). Domain Layer에 속한다. 비즈니스 규칙·정책이 들어 있어야 한다.
Application Service
Use Case의 진입점. 여러 도메인 객체 / Domain Service를 호출해 한 트랜잭션 안에서 흐름을 조립한다. 트랜잭션 경계 · 인증 · DTO 변환 · 외부 어댑터 호출 같은 "흐름 관리"만 다룬다. 비즈니스 규칙은 가지지 않는다. Application Layer에 속한다.

가장 명확한 예시는 주문 생성 흐름입니다.

역할을 다시 한 번 정리하면:

  • OrderPlacementService (Domain Service) — 주문 생성의 도메인 로직: 상품 조회 → 스냅샷 만들기 → 재고 차감 → Order 객체 만들기. 이 협업이 "주문이 무엇인지"를 결정합니다.
  • OrderService (Application Service) — Use Case 흐름: @Transactional로 트랜잭션 시작, items 비었으면 400, Domain Service 호출, save, 응답.
  • OrderFacade (Application Service의 또 다른 진입점) — Request → Command 매핑, 인증 컨텍스트 소비, Response 변환.
// Domain Service — 본질적 로직
@Service
class OrderPlacementService(
    private val productRepository: ProductRepository,
    private val inventoryService: InventoryService,
) {
    fun place(userId: Long, items: List<OrderItemCommand>): Order {
        // 1. product 조회 + 누락 검증
        val products = productRepository.findAllByIdIn(items.map { it.productId })
        if (products.size != items.size) {
            throw NotFoundException(ProductErrorCode.PRODUCT_NOT_FOUND)
        }

        // 2. snapshot 만들기
        val snapshots = buildSnapshots(products, items)

        // 3. 재고 차감 (부족 시 ConflictException throw → 트랜잭션 롤백)
        inventoryService.decreaseAll(items)

        // 4. Order aggregate 생성 (invariant 검증 포함)
        return Order.create(userId, snapshots)
    }
}

// Application Service — 흐름 조립
@Service
class OrderService(
    private val orderPlacementService: OrderPlacementService,
    private val orderRepository: OrderRepository,
) {
    @Transactional
    fun place(userId: Long, command: OrderCommand): OrderInfo {
        if (command.items.isEmpty()) {
            throw BadRequestException(OrderErrorCode.EMPTY_ITEMS)
        }
        val order = orderPlacementService.place(userId, command.items)
        val saved = orderRepository.save(order)
        return OrderInfo.from(saved)
    }
}

3.5 모든 도메인에 Domain Service가 필요한가? — 아니다 (YAGNI)

Brand는 단순 CRUD입니다. 생성·조회·수정·삭제만 있고 여러 객체 협업이 없습니다. 이런 경우 Domain Service를 만드는 것은 과한 설계입니다. Application Service가 Repository를 직접 호출하면 충분합니다.

언제 Domain Service를 만드는가
두 개 이상의 도메인 객체가 협업해야 하고, 그 행위가 어느 한 객체에 자연스럽게 속하지 않을 때. 한 Entity의 메서드로 표현 가능하다면 그곳에 두는 게 먼저입니다 — Anemic Domain Model을 만들지 않기 위해.

3.6 본 프로젝트 Domain Service 2개

Domain Service (본 주차)
  • ProductCatalogService — Product + Brand + Inventory를 합성해 상품 카탈로그 응답을 만듭니다. 어느 한 객체로 표현 불가.
  • OrderPlacementService — 주문 생성 시 상품 조회 + 스냅샷 + 재고 차감 + Order 생성을 협업. 여러 도메인이 얽힘.
Application Service (Facade)
  • BrandFacade, ProductFacade, LikeFacade, OrderFacade — Use Case 진입점
  • BrandService, ProductService, LikeService, OrderService, InventoryService — 트랜잭션 경계와 흐름
Facade와 Service를 둘 다 두는 이유: Facade는 DTO/인증 등 외부 형식과 닿고, Service는 도메인 객체 단위 협업. 본 주차는 둘 다 application/ 아래에 둡니다.

3.7 흔히 하는 실수 — Anemic Domain Model

DDD를 처음 적용할 때 가장 흔한 함정입니다. Entity는 데이터만 들고 있고 (getter/setter만), 모든 로직이 Service에 절차적으로 쌓이는 패턴입니다. Martin Fowler가 2003년에 "Anemic Domain Model"이라는 이름으로 비판한 안티 패턴입니다. 

// 안티 패턴 — Anemic
class Product(var likeCount: Long) // 데이터만

class LikeService {
    fun like(productId: Long) {
        val product = productRepository.findById(productId)
        product.likeCount = product.likeCount + 1  // 로직이 Service에
        productRepository.save(product)
    }
}

// 권장 — Rich Domain Model
class Product(var likeCount: Long) {
    fun like() {
        likeCount = likeCount.increment()  // 로직이 Entity에
    }
}

class LikeService {
    fun like(productId: Long) {
        val product = productRepository.findById(productId)
        product.like()  // 흐름만 조립
        productRepository.save(product)
    }
}

구분 기준: "단일 Entity의 상태 변경이라면 Entity 메서드로"가 첫 번째 원칙. Service로 빼는 것은 단일 Entity로 표현 불가할 때만.

3.8 장단점

장점

  • 비즈니스 로직이 Domain에 농축 — 변경 영향 좁음
  • Application Service가 가벼워 가독성 좋음
  • Domain Service는 Spring 없이 단위 테스트
  • 같은 Domain Service를 여러 Use Case에서 재사용

단점

  • Domain Service / Application Service 경계가 모호할 때가 있음
  • 단순 CRUD에 강제로 Domain Service를 만들면 오히려 과함
  • Facade / Service / Domain Service 3종이 늘어나면 추적 비용 증가
  • "이 로직이 어디에 사는가"를 팀이 합의하지 않으면 일관성 깨짐

3.9 실무 활용 패턴

  • Eric Evans (원전): Service는 stateless여야 하고, 도메인 어휘로 이름 지어야 한다. OrderPlacementService는 좋은 이름, OrderHelper는 나쁜 이름.

4Entity vs Domain — 헷갈리는 두 단어 정리

4.1 비유 — 동물원과 사자

Analogy
동물원 안에 사자가 있습니다
동물원은 큰 공간이자 영역입니다. 사자도 있고, 호랑이도 있고, 관리인도 있고, 우리(cage)도 있습니다. 이 큰 영역이 Domain입니다.

사자는 동물원 안에 사는 한 마리의 동물입니다. 학번처럼 식별표가 붙어 있고, 태어나서 자라고 늙고 죽습니다. 이런 식별성 있는 객체가 Entity입니다.

"동물원에는 사자가 있다" — Domain 안에 Entity가 있다. 이 한 줄이 두 단어의 관계입니다.

4.2 "Domain"이라는 단어의 3가지 의미

혼란의 진짜 원인은 "Domain"이 맥락마다 다른 의미로 쓰인다는 점입니다. 같은 글 안에서도 세 가지 의미로 등장합니다.

의미 1DDD 비즈니스 영역

비즈니스의 한 영역 자체. "전자상거래 도메인", "결제 도메인", "물류 도메인". 코드와 무관한, 비즈니스 세계의 한 영역을 가리킵니다. 본 프로젝트에서 "Brand 도메인 / Product 도메인 / Order 도메인" 같은 표현이 여기 해당합니다.

의미 2Layered Architecture 의 한 층

코드의 한 계층(layer). "도메인 레이어", "com.loopers.domain.brand". Section 1에서 다룬 Presentation / Application / Domain / Infrastructure 중 가장 중심에 있는 그 층입니다.

의미 3도메인 객체 총칭

도메인 레이어에 사는 객체 전체. Entity + VO + Aggregate + Domain Service + Repository 인터페이스 + ErrorCode 등을 통칭. "도메인 객체(domain object)"라는 표현이 여기 해당합니다.

4.3 "Entity"라는 단어의 함정 — JPA Entity와의 혼동

Spring/JPA를 쓰는 환경에서 "Entity"라고 하면 두 가지 의미가 겹칩니다.

DDD EntityJPA Entity (@Entity)
정의식별성 있는 도메인 객체DB 테이블과 매핑되는 클래스
레이어Domain Layer일반적으로 Infrastructure (또는 Domain에 어노테이션을 같이 박는 절충)

"도메인 로직은 도메인 레이어에 둔다"

4.6 추가 어휘 정리 — Bounded Context

"Brand 도메인"이라고 부를 때 정확히는 Bounded Context(경계 지어진 맥락)를 가리킵니다. DDD에서 큰 비즈니스를 작은 영역으로 쪼개 각자 독립된 모델을 가지게 하는 것을 Bounded Context라고 부릅니다. 본 주차의 5개 도메인은 사실상 5개의 Bounded Context이고, 그 사이는 id로만 참조합니다 (FK 안 씀, 같은 객체를 공유 안 함). 자세한 결정 배경은 직전 의견 형성에서 결정한 "Brand → Product 단방향" 결정 참조.

5.1 매트릭스에서 보이는 패턴

7.2 그림 2 — Brand 클래스 안에는 무엇이 함께 사는가

"같이 붙인다"가 무슨 의미인지 클래스 내부를 펼쳐봅니다. 한 클래스 안에 JPA 어노테이션 + 도메인 invariant + 비즈니스 메서드가 모두 살아 있습니다. Spring 어노테이션(@Service · @Component)은 들어오지 않습니다. 

// com.loopers.domain.brand.Brand
@Entity                                         // ← JPA
@Table(name = "brand")
class Brand protected constructor(    // ← JPA가 요구 (protected로 외부 차단)
    @Embedded
    var name: BrandName,                       // ← VO 같이 살음
    @Column(length = 500)
    var description: String? = null,
    @Column(length = 500)
    var logoUrl: String? = null,
) : BaseEntity() {                              // ← id, createdAt, updatedAt, deletedAt 상속

    // ── 도메인 행위 (Rich Domain Model) ──
    fun rename(newName: BrandName) {            // 비즈니스 메서드
        this.name = newName
        // ↑ @Transactional 안이라면 dirty checking이 UPDATE 자동 생성
    }

    fun updateDescription(newDesc: String?) {
        this.description = newDesc
    }

    // markDeleted()는 BaseEntity.delete()를 사용 (deletedAt = now)

    companion object {
        fun create(name: BrandName, description: String?, logoUrl: String?): Brand =
            Brand(name, description, logoUrl)   // factory — invariant 검증은 BrandName.init에서
    }
}

// com.loopers.domain.brand.BrandName — VO
@Embeddable
data class BrandName(
    @Column(name = "name", length = 50, nullable = false, unique = true)
    val value: String
) {
    init {
        require(value.isNotBlank()) { "브랜드 이름은 비어있을 수 없습니다" }
        require(value.length in 1..50) { "브랜드 이름은 1~50자입니다" }
    }
}
관찰 포인트
  • JPA 어노테이션과 비즈니스 메서드가 한 클래스 — 분리 안 함
  • protected constructor — Hibernate가 요구하는 no-arg 생성자를 외부에서 못 부르게 차단 (Kotlin은 kotlin-jpa 플러그인이 자동)
  • var 필드 — JPA가 setter로 hydration. 외부에서 직접 set하지 않고 도메인 메서드(rename)를 통해서만 변경
  • VO는 @Embeddable — 별도 테이블 없이 같은 row에 컬럼으로 펼쳐짐 (name 컬럼)
  • invariant 검증은 init — DB 레벨까지 못 가게 fail-fast

    private val jpa: BrandJpaRepository
) : BrandRepository {

왜 굳이 한 단계 더 감싸나 (BrandJpaRepository를 직접 안 쓰고)

핵심은 두 가지:

  • brand.rename(newName)만 호출하고 save()를 부르지 않음 — Service 코드가 단순해짐
  • 트랜잭션 commit 시점에 Hibernate가 snapshot과 현재 상태를 비교해 변경된 필드만 UPDATE — 자동 변경 추적

만약 Domain Entity와 JPA Entity를 분리했다면 이 흐름이 다음처럼 바뀝니다:

  1. jpa.findById → BrandEntity 로드
  2. mapper.toDomain(brandEntity) → Brand (도메인) 생성
  3. brand.rename(newName) → 도메인 필드 변경
  4. mapper.toEntity(brand) → 새 BrandEntity 생성
  5. jpa.save(brandEntity) → 명시적으로 다시 저장 (영속 상태 객체가 아니라 merge 또는 새 row 위험)

매번 매핑 + 명시적 save가 필요하고, 영속 상태 객체의 id identity를 직접 관리해야 하는 부담이 생깁니다. 이게 plan §3.4에서 "같이 붙이는 절충안 채택"의 실제 이유입니다.

8Domain Service 깊게 보기 + Facade는 꼭 필요한가

§3에서 Domain Service와 Application Service의 책임을 간단히 다뤘는데, 두 가지를 더 깊게 짚습니다. (1) Domain Service가 정확히 무엇이고 언제 만드는가, (2) Application Service와 Facade를 둘 다 두는 본 프로젝트의 결정이 정당한가.

8.1 Domain Service의 정확한 정의 — Eric Evans의 3가지 조건

Evans는 책에서 Domain Service의 자격 조건 3가지를 명시했습니다.

Evans의 Domain Service 3 조건
  1. The operation relates to a domain concept that is not a natural part of an Entity or Value Object.
  2. The interface is defined in terms of other elements of the domain model (즉 도메인 객체를 주고받음).
  3. The operation is stateless.

핵심 신호 한 줄: "이 행위를 어느 Entity의 메서드로 옮길까 고민했는데 딱 맞는 자리가 없다 — 그리고 그 행위가 도메인의 한 개념이다". 이때 Domain Service를 만듭니다. Vaughn Vernon은 더 강하게 표현합니다.

"Rather than creating a static method on an Aggregate Root class, which is a code smell, you should use a Service instead." — Vaughn Vernon, Implementing DDD Ch.7

8.2 본 프로젝트 Domain Service 2개가 왜 Domain Service인지 — 3 조건 적용

8.5 Facade는 꼭 두어야 하는가 — 비판적 검토

본 프로젝트는 모든 도메인에 BrandService + BrandFacade처럼 Service와 Facade를 둘 다 둡니다. 이게 정말 필요한가? DDD 원전과 빅테크 실무를 모두 검토합니다.

8.5.1 DDD 원전 — Facade라는 별도 layer는 없다

Evans와 Vernon 책에는 Service와 Facade를 별도로 두라는 권장이 없습니다. Application Service 자체가 Facade 역할을 합니다. Medium의 정리가 가장 명확합니다.

"An application service acts as a facade through which clients interact with the domain model. The term 'facade' in DDD essentially refers to the role that Application Services play." — "Application Services VS Domain Services in DDD"

Microsoft .NET DDD 공식 docs도 동일합니다. Application Service 하나가 "Use Case 조립 + 트랜잭션 + 인증 + DTO 변환 + 외부 어댑터 호출"을 모두 책임지는 것이 정석입니다.

8.5.2 Spring 커뮤니티 — Facade를 별도 두는 패턴은 흔하지만 조건부

Spring 진영에서는 Facade를 별도 두는 패턴이 자주 등장합니다. Baeldung, Spring Framework Guru, JavaGuides 모두 다루는 패턴입니다. 다만 그 정당화는 다음 한 가지에 모입니다.

"As your Spring Boot project grows, you'll often see controllers or service classes bloated with multiple service calls. That's a sign it's time for a facade." — Java Guides 2025

핵심은 "여러 Service 호출이 한 곳에 쌓이기 시작할 때"입니다. 단순 위임만 하는 Facade는 오버엔지니어링이라고 같은 글들이 경고합니다.

"Sometimes the pattern can be overused in simple scenarios, which will lead to redundant implementations." — Spring Framework Guru

객관적 평가:

  • Order는 명확히 필요: 시나리오 17개 + 다중 도메인 협업 + 인증 + 응답 DTO 분리 — Facade가 빛나는 자리.
  • Brand · Product · Like는 경계 케이스: 본질적으로는 Service에 흡수해도 됨. 두면 사실상 passthrough.
  • 학습 컨텍스트에서의 가치: 5개 도메인에 같은 패턴을 반복하는 것이 layer 책임 분리를 손에 익히는 데 도움. 일관성 우선.
  • 실서비스로 가면 다시 평가: 단순 도메인의 Facade를 합치는 리팩토링이 자연스럽게 등장할 가능성. 그때 합치면 됨.
결론
Facade는 DDD 원전 필수가 아니라 Spring 커뮤니티 관습입니다. 본 주차에서는 plan §3.6에 잡힌 대로 모든 도메인에 두되 (학습 일관성), Brand/Product/Like의 Facade가 사실상 passthrough라는 점을 인식하고 진행합니다. 실서비스 단계에서는 도메인별로 정당성을 재평가해 합치는 것을 검토할 수 있습니다.

8.8 한 줄 가이드

  • Domain Service는 Evans 3 조건을 만족할 때만 (단일 entity 협업이면 만들지 마라).
  • Application Service는 모든 Use Case에 필요 (트랜잭션 경계).
  • Facade는 Application Service가 비대해질 때 분리. 본 프로젝트는 일관성 위해 모든 도메인에 두지만 단순 도메인은 사실상 passthrough.
