CONCEPT & FLOW

PG란 무엇이고 왜 필요한가

PG는 가맹점을 대신해 여러 카드사·은행·간편결제와 결제 데이터를 안전하게 주고받고, 매출 정산까지 대행하는 사업자입니다.

PG(Payment Gateway, 결제대행사)가 없다면 쇼핑몰 하나가 신한·국민·삼성 등 모든 카드사와 개별 계약을 맺고, 카드사마다 다른 전문 규격을 직접 구현하고, 카드 원문 데이터를 직접 취급해야 합니다. PG를 경유하면 통합 API 하나로 다수 결제수단을 한 번에 연결하고, 민감한 카드 데이터 취급 부담(PCI)을 PG로 떠넘길 수 있습니다.[1][4]

한 줄 정의가맹점은 PG 한 곳만 붙이면 된다. 카드사·간편결제와의 N:N 연동을 PG가 1:N으로 추상화해 준다 — 이게 PG의 본질입니다.

결제 생태계의 참여자

카드 결제 한 건에는 생각보다 많은 주체가 등장합니다. 각자의 역할을 알면 "승인이 왜 거절됐는지", "정산이 왜 며칠 걸리는지"가 이해됩니다.[4]

인증 · 매입 · 정산 — 같은 결제의 세 단계

"결제했다"는 말은 사실 세 가지 다른 사건을 뭉뚱그린 것입니다. 이걸 분리해서 봐야 환불·부분취소·정산 지연이 설명됩니다.[5]

단계무슨 일이 일어나나자금 이동
인증 (Authorization)발급사가 한도·도난 여부 검증 후 금액만큼 한도를 보류(hold)없음 (보류만)
매입 (Capture)매입사가 실제 자금 회수를 시작. 인증과 분리·부분 매입 가능회수 시작
정산 (Settlement)발급계좌 → 가맹점 계좌로 실제 입금. 보통 며칠 뒤 배치가맹점 입금
참고국내 PG 문서(토스)는 보통 인증 단계(카드소유자 본인 확인)와 승인 단계(한도/계좌 차감, 영문 capture에 해당)로 부릅니다. 글로벌(Stripe)은 authorization → capture로 부르며, capture_method=manual로 선승인-후매입을 구현합니다.[5]

연동 방식 — 결제창 vs SDK vs 직접연동

같은 PG라도 붙이는 방식이 여러 가지고, 카드 데이터가 어디를 지나가느냐에 따라 PCI 부담이 크게 달라집니다.[4]

결제창 Redirect / Hosted

PG가 띄운 결제 페이지로 이동. 카드 데이터가 가맹점을 거치지 않아 PCI 부담 최소. 구현 빠름, UX 통제는 약함.

SDK 임베디드 위젯

PG의 보안 iframe을 페이지 안에 끼움(예: Stripe Elements, 토스 결제위젯). 브랜딩 유지 + PCI 중간.

권장 대부분 결제창·SDK로 충분

학습/일반 커머스는 결제창이나 SDK 위젯이면 충분합니다. PCI 부담을 PG로 넘기는 게 핵심 이득.

직접연동 API Key-in

카드번호를 가맹점 서버가 직접 받아 PG API로 전송. 통제 최대지만 PCI 부담(SAQ D)도 최대. 특별한 이유 없으면 피한다.

STANDARD FLOW

표준 결제 승인 플로우

현대 PG 연동의 표준은 "인증은 클라이언트, 최종 승인은 서버"로 나누는 2단계 패턴입니다. 이유는 단 하나 — 클라이언트를 믿을 수 없기 때문입니다.

왜 서버가 한 번 더 "승인"해야 하나

브라우저 자바스크립트는 사용자가 얼마든지 조작할 수 있습니다. 결제창에서 "5,000원"을 "50원"으로 바꿔치기하는 금액 위변조(amount tampering)를 클라이언트 단에서 막을 방법은 없습니다. 그래서 인증이 끝난 뒤 서버가 자기 DB의 주문 금액과 대조한 다음에야 최종 승인 API를 호출합니다.[1][4]

멱등성 — 결제에서 가장 중요한 한 단어

네트워크가 타임아웃 나면 클라이언트는 "결제가 된 건지 안 된 건지" 알 수 없습니다. 그냥 재시도하면 이중 청구(double charge)가 납니다. Idempotency-Key는 "같은 키로 온 요청은 한 번만 처리하고, 두 번째부터는 첫 결과를 그대로 돌려준다"는 약속입니다.[6][2]

Webhook — 받되, 그대로 믿지 마라

가상계좌 입금처럼 비동기로 끝나는 결제는 결과를 webhook(콜백)으로 통지받습니다. 하지만 webhook은 위조·중복·순서 뒤섞임이 가능하므로, 표준 처리는 세 단계입니다.[7][3]

  • 서명 검증 — Stripe-Signature 등 HMAC-SHA256 서명을 raw body로 검증. 타임스탬프로 replay 공격 차단(기본 tolerance 5분).
  • 중복 제거 — webhook은 최소 1회 이상 전달(at-least-once). event id를 DB에 저장해 두 번째부터 무시.
  • 재조회 검증 — payload를 믿지 말고 그 안의 ID로 PG에 다시 조회해 최신 상태를 확인한 뒤 처리.
핵심webhook 핸들러는 무거운 로직 전에 먼저 2xx를 빠르게 반환하고 실제 처리는 비동기로 넘깁니다. 응답이 늦으면 PG가 "실패"로 보고 계속 재전송하기 때문입니다.[7]
3

REAL-WORLD CASES

실제 PG 3사 비교 분석

같은 "결제"라도 세 회사의 설계 철학은 다릅니다 — 토스는 명시적 2단계 승인, Stripe는 상태 머신, PortOne은 통합 추상화입니다.

토스페이먼츠 — 명시적 2단계 승인(직연동 PG)

SDK v2 하나로 결제위젯·결제창·브랜드페이·REST API를 모두 제공합니다. 철학은 "요청과 승인을 분리해 금액 위변조를 구조적으로 막는다". 인증 후 POST /v1/payments/confirm으로 서버가 명시적으로 승인을 호출해야 결제가 확정됩니다.[1]

Stripe — 결제를 상태 머신으로 모델링(글로벌 PG)

결제 한 건을 PaymentIntent라는 객체의 상태 전이로 봅니다. requires_payment_method → requires_confirmation → requires_action(3DS) → processing → succeeded. 금액·통화를 서버가 PaymentIntent.create에서만 정하므로 위변조가 구조적으로 차단되고, 3DS 등 추가 인증을 lifecycle 안에 흡수합니다.[5]

PortOne(구 아임포트) — 여러 PG를 하나로 묶는 아그리게이터

PortOne은 PG사가 아닙니다. 30개 이상의 PG를 단일 인터페이스로 추상화하는 아그리게이터입니다. 결제 후 서버가 GET /payments/{paymentId}로 실제 결제금액을 재조회해 내 DB와 대조하는 사후검증이 핵심 패턴입니다. PG를 바꿔도 연동 코드를 거의 그대로 둘 수 있는 게 장점.[9][10]

심화국내 직연동의 무게감 — KG이니시스 예시

KG이니시스 표준결제(INIStdPay)는 아그리게이터 없이 PG와 직접 붙는 사례입니다. INIStdPay.js로 결제창을 띄우고, SHA256 서명을 직접 생성(signature = SHA256(oid+price+timestamp))한 뒤, 인증 결과로 받은 authUrl로 서버가 직접 승인 요청(서버→서버)을 보내 resultCode 0000이면 성공입니다.[11]

즉 인증→승인 2단계, 서명 생성·검증, signKey 비밀키 관리, 응답코드 분기를 전부 가맹점이 직접 구현합니다. PortOne 같은 아그리게이터는 이 저수준 작업을 대신 흡수해 줍니다 — 이게 직연동 vs 아그리게이터의 실질적 차이입니다.

CODE ANALYSIS

pg-simulator 메커니즘 분석

우리 레포의 pg-simulator는 "잘 동작하는 PG"가 아니라 "현실처럼 불안정하고 비동기적인 PG"를 의도적으로 흉내 내는 학습용 앱입니다.

포트 8082로 뜨는 별도 Spring Boot 앱(apps/pg-simulator)이며, 커머스 서비스(8080)와 동시에 띄워 결제 연동을 연습합니다. 결제 요청 → 비동기 처리 → 콜백 통지의 3박자가 핵심입니다.[12]

전체 처리 흐름

핵심 1 — 요청 API는 일부러 느리고, 일부러 실패한다

컨트롤러가 Thread.sleep으로 네트워크 지연을 흉내 내고, 40% 확률로 500을 던집니다. 연동하는 쪽이 타임아웃·재시도·멱등성을 진지하게 다루도록 강제하는 장치입니다.

PaymentApi.kt 
@PostMapping
fun request(userInfo: UserInfo, @RequestBody request: PaymentDto.PaymentRequest) {
    request.validate()
    Thread.sleep((100..500L).random())          // 100~500ms 인위적 지연
    if ((1..100).random() <= 40) {              // 40% 확률로 요청 실패
        throw CoreException(INTERNAL_ERROR, "현재 서버가 불안정합니다.")
    }
    return paymentApplicationService.createTransaction(...)  // 즉시 PENDING 반환
}

핵심 2 — 결과는 트랜잭션 커밋 후 비동기로 결정된다

이벤트 리스너가 @TransactionalEventListener(AFTER_COMMIT) + @Async로 동작합니다. 결제 저장 트랜잭션이 커밋된 뒤에 별도 스레드에서 1~5초 더 지연한 다음 승인/실패를 확률로 정합니다. "응답은 PENDING, 결과는 나중에"라는 비동기 결제의 본질을 그대로 보여줍니다.

PaymentEventListener.kt / PaymentApplicationService.kt 
@Async @TransactionalEventListener(phase = AFTER_COMMIT)
fun handle(event: PaymentEvent.PaymentCreated) {
    Thread.sleep((1000L..5000L).random())     // 카드사 승인 시간 흉내
    paymentApplicationService.handle(event.transactionKey)
}

// handle() 안의 확률 분기
val rate = (1..100).random()
when (rate) {
    in 1..20  -> payment.limitExceeded()  // 20% 한도초과 → FAILED
    in 21..30 -> payment.invalidCard()    // 10% 잘못된 카드 → FAILED
    else        -> payment.approve()        // 70% 정상 승인 → SUCCESS
}

핵심 3 — 상태 머신과 콜백

상태는 PENDING → SUCCESS 또는 PENDING → FAILED 단방향이며, 각 전이 메서드는 PENDING이 아닐 때 호출되면 예외를 던져 중복 처리·잘못된 전이를 막습니다. 결과가 정해지면 또 한 번 AFTER_COMMIT 비동기로 커머스의 callbackUrl에 POST합니다.

참고조회 API와 transactionKey 형식

콜백을 못 받았거나 믿을 수 없을 때를 대비해 두 가지 조회 API가 있습니다 — GET /api/v1/payments/{transactionKey}(단건), GET /api/v1/payments?orderId=(주문별 목록). 이건 실제 연동에서 polling 재조회 / reconciliation에 해당하는 안전망입니다.

transactionKey는 yyyyMMdd:TR:{uuid6} 형식(예: 20250816:TR:9577c5)으로 생성됩니다. X-USER-ID 헤더로 사용자를 식별합니다.

CRITICAL VIEW

pg-simulator vs 실제 PG — 한계

시뮬레이터는 "불안정함"과 "비동기"를 가르치는 데 충실하지만, 실제 PG의 안전장치 상당수는 의도적으로 빠져 있습니다. 이 차이를 아는 것이 학습의 핵심입니다.

학습 포인트빠진 것들은 결함이 아니라 "네가 직접 채워 넣어야 할 숙제"입니다. 시뮬레이터의 불안정함을 보고 연동하는 쪽(커머스)에서 멱등성·타임아웃·reconciliation을 구현하는 게 이 모듈의 목적입니다.
관점pg-simulator실제 PG (토스/Stripe)
멱등성없음 — 같은 orderId로 재요청 시 매번 새 transactionKey 생성 → 중복 결제 가능Idempotency-Key로 중복 차단
금액 검증클라이언트가 보낸 amount를 그대로 신뢰서버 주문금액과 대조, 불일치 시 취소
콜백 신뢰성fire-and-forget · 1회 실패하면 끝(로깅만)실패 시 수 차례 재전송 + 서명
콜백 서명없음 — 위조 검증 불가HMAC-SHA256 서명 검증
이벤트 내구성인메모리 ApplicationEvent — 앱 죽으면 유실내부적으로 영속 큐/재처리
콜백 타임아웃기본 RestTemplate — 타임아웃 미설정타임아웃·서킷브레이커 적용

회의적 리뷰어의 눈으로 본 두 가지 위험

위험 1 콜백 유실

PaymentCoreRelay는 runCatching으로 콜백 실패를 삼키고 로깅만 합니다. 커머스가 잠깐 죽어 있으면 그 결제 결과는 영영 통지되지 않습니다. → 연동 측은 반드시 조회 API 기반 reconciliation을 둬야 합니다.

위험 2 콜백 무한 대기

콜백용 RestTemplate에 타임아웃이 없습니다. callbackUrl 대상이 응답을 안 주면 비동기 스레드가 묶입니다. 실제 외부 호출이라면 connection/read timeout을 반드시 설정해야 합니다.

균형 잡기이건 시뮬레이터를 깎아내리는 게 아닙니다. 학습용 앱은 의도적으로 거칠게 만들어 연동하는 쪽이 방어 코드를 짜도록 유도합니다. 다만 이 코드를 그대로 프로덕션 패턴으로 베끼면 안 된다는 점은 분명히 짚어둡니다.
6

RELIABILITY CHECKLIST

외부 연동 유의점 체크리스트

한 줄 요약 — 타임아웃은 "실패"가 아니라 "결과 미확정"이다. 재시도는 반드시 멱등키 + 지터 백오프로. DB와 PG는 한 트랜잭션으로 못 묶으니 Outbox·reconciliation으로 결국 맞춘다.

① 타임아웃 (Timeout)

  • connection · read 타임아웃을 둘 다 명시한다. 연결 실패와 "응답 없음"은 다른 사건이다.[12]
  • 타임아웃 값은 감이 아니라 downstream 지연 분포(p99.9 등)로 정한다.[12]
  • 타임아웃 = 실패가 아니라 결과 미확정(in-doubt). 500도 "성공도 실패도 아님"으로 취급한다.[8]
  • 타임아웃 후엔 무작정 재시도 말고 멱등키 재전송 또는 상태 재조회로 마무리.[19]

② 리트라이 (Retry)

  • 결제 호출 재시도는 반드시 멱등키와 함께. 그냥 재시도하면 이중 결제.[6]
  • 지수 백오프 + 지터(jitter)로 재시도 시점을 흩뿌려 thundering herd를 막는다.[13]
  • 재시도 가능 에러(네트워크·5xx·429)와 재시도 불가(4xx 검증 실패)를 구분한다.[8]
  • retry budget으로 증폭을 막는다 — 한 계층에서만, 요청당 최대 2~3회, 클라이언트 재시도율 10% 이하.[14]

③ 트랜잭션 · 데이터 정합성

  • 로컬 DB 트랜잭션과 외부 PG 호출은 하나의 ACID로 묶을 수 없다. ROLLBACK은 내 테이블만 되돌린다.[15]
  • 열린 DB 트랜잭션 안에서 외부 API를 호출하지 않는다 — 커넥션 점유·락 장기화·롤백 불가.[15]
  • dual write 문제는 Transactional Outbox로 — 비즈니스 변경 + outbox insert를 한 로컬 트랜잭션으로 커밋, 릴레이가 발행.[15][20]
  • 결제 결과와 주문 상태는 eventual consistency + reconciliation 배치로 맞춘다(PENDING 건 주기적 재조회).
  • 다단계 트랜잭션은 SAGA + 보상 트랜잭션으로. 자동 롤백이 없으니 되돌림을 직접 설계.[16]

④ 그 밖의 방어선

  • Circuit Breaker로 PG 장애의 연쇄 전파를 끊는다(Closed → Open → Half-Open).[17]
  • webhook은 서명 검증 + event id 멱등 처리(at-least-once 가정). 순서 의존 설계 금지.[7]
  • 로그·추적에서 카드번호 등 PII 마스킹(앞 6 + 뒤 4만). 도메인 VO를 직접 문자열 보간/로깅하지 않는다.[18]
  • 금액·통화 검증 — 받은 amount/currency를 주문 기대값과 대조. 금액은 정수 최소 단위(원/센트)로 다뤄 부동소수점 오차 회피.
  • rate limiting(429) 대응 — 단, Stripe는 Retry-After를 안 쓰는 등 PG별 규약이 다르니 문서 확인.[8]

"타임아웃이나 실패가 곧 부수효과가 일어나지 않았다는 뜻은 아니다."
