SETUP

로컬 환경 구성

측정은 사용자 로컬 PC에서 진행한다. MySQL과 Redis를 띄우고, 서버가 붙는지 먼저 확인한다.

의존 없음산출 측정 가능한 로컬 환경
  • 인프라 기동 — docker compose -f docker/infra-compose.yml up -d (MySQL+Redis master/replica+kafka). compose.yaml은 MySQL만이라 Redis 위해 infra-compose 사용
  • 서버 부팅 확인 — ./gradlew :apps:commerce-api:bootRun --args='--spring.profiles.active=local' (프로파일 미지정 시 기동 실패)
  • MySQL 접속 확인 — mysql -h127.0.0.1 -uapplication -papplication loopers
  • 측정 도구 확인 — k6 설치(k6 version), redis-cli 접속(redis-cli -p 6379 ping)
주의ddl-auto=create라 부팅마다 스키마가 새로 생성된다. 시딩은 부팅 이후에 하고, 부팅으로 데이터가 날아가지 않게 측정 세션 동안 서버를 재시작하지 않는다.
1

ENDPOINT

측정 엔드포인트 확보

k6는 HTTP를 친다. 부하·EXPLAIN을 하려면 조회 엔드포인트가 필요한데 현재 컨트롤러가 없다. 목록·상세 2개만 최소로 만든다.

의존 Step 0산출 GET /api/v1/products, /{id}
  • ProductV1Controller 신규 — product/interfaces/. GET /api/v1/products(sort, brandId, cursor, size) + GET /api/v1/products/{id}
  • 커서 인코딩 — base64 opaque 인코딩/디코딩은 interfaces 레이어 책임(CursorPage 주석 규약). 도메인 커서를 노출하지 않는다
  • security permitAll — AccountSecurityConfig에 GET /api/v1/products/** 추가(인증 없이 부하 가능). 앱 소유 config라 허용
  • 응답 DTO — 목록은 id, brandId, name, price, like_count. brandName은 N+1 회피 위해 초기 미포함. ApiResponse 래핑 규약 준수
  • 요청 검증 — sort enum 파싱, size 상한(예: 100) 가드. 잘못된 값은 경계에서 fail fast
범위 제한인기 상품 전용 엔드포인트는 만들지 않는다. ?sort=LIKES_DESC 첫 페이지가 곧 인기 상품 조회 — YAGNI.
2

SEED

데이터 분포 시딩

10만 상품을 균등하게 넣으면 현실과 다르다. 빅테크처럼 소수 브랜드에 상품이 쏠리고, 좋아요도 롱테일이어야 인덱스 선택성이 드러난다.

의존 Step 0산출 load-test/perf-seed-l5.sql
  • 브랜드 500 + 상품 10만 시딩 — 멱법칙 4티어(메가 5×8k / 대형 20×1.5k / 중형 75×250 / 소형 400×28). 상세 수치는 03-데이터 분포 참조
  • like_count 롱테일 — ~1%(1천개) 10k~500k · ~9% 100~10k · ~90% 0~100. price 로그분포(1k~2M)
  • 방식 A용 product_like 실제 행 — 핫 상품 한정, 총 300만~500만 행 캡(전체 like_count 합만큼 풀시딩하면 수천만 행 → 캡으로 부담 제거, 측정 의미 유지)
  • 분포 검증 — 브랜드별 상품수 분포 쿼리, like_count 히스토그램으로 의도대로 들어갔는지 확인
시딩 방식SQL(INSERT…SELECT…숫자생성기)을 기본으로 한다. 10만 건이 수초~수십 초, 재현성 높고 like_count를 컬럼에 직접 박아 B/C 초기상태 세팅이 쉽다. 코드 시더는 분포 검증용 보조.
3

BASELINE

베이스라인 측정 (인덱스 전)

처방 전 숫자를 먼저 박제한다. 인덱스 없는 상태의 filesort·rows examined·p95가 "before"다.

의존 Step 1·2산출 before 수치(EXPLAIN+k6)
  • S1/S2/S3 EXPLAIN ANALYZE — 인덱스 없는 상태에서 세 시나리오 실측. Using filesort · Using temporary · rows examined 기록
  • k6 베이스라인 — 목록·상세 처리량/p95. load-test/k6/products-read.js 신규(constant-arrival-rate)
  • 수치 기록 — 표로 정리(시나리오 × 지표). 이후 모든 비교의 기준선
측정 원칙EXPLAIN은 raw SQL을 MySQL에 직접 날려 수집한다(JPA 로그가 아니라). 같은 쿼리를 인덱스 전/후로 비교해야 처방 효과가 분리된다.
4

INDEX

인덱스 적용 + 재측정

정렬 키 순서와 정확히 일치하는 복합 인덱스를 붙여 filesort를 없앤다. 어노테이션이 아니라 수동 SQL로 붙였다 뗐다 하며 비교한다.

의존 Step 3산출 after 수치 + 전후 비교표
  • 복합 인덱스 생성 — (status, like_count, id) 인기상품 · (brand_id, like_count, id) 브랜드+좋아요순 · product_like(product_id) A용. 상세는 04-인덱스 참조
  • 비교 실험 — status 선두 vs 비선두(카디널리티 낮음), 커버링 vs 비커버링(name VARCHAR라 커버링 비용↑). Using index condition vs Using index 관측
  • 동일 시나리오 재측정 — S1/S2/S3 EXPLAIN+k6 재실행. filesort 제거·rows≈LIMIT 확인 → 전후 비교표 작성
  • 확정 인덱스 코드화 — 최종 선택분만 @Table(indexes=...)로 ProductJpaRepository/엔티티에 반영
5

STRUCTURE

집계 A/B/C 구조 비교

좋아요 집계를 한 방식으로 고르지 않는다. 세 방식을 직접 구현해 같은 측정 틀로 돌려, 읽기·쓰기·정합성의 트레이드오프를 몸으로 본다.

의존 Step 4산출 A/B/C 비교표 + 재집계 배치
  • B (현행) 측정 — 비정규화 like_count + Step4 인덱스 경로. 읽기 최선 / 정합성 갭 확인
  • A 구현·측정 — product_like LEFT JOIN + GROUP BY + ORDER BY cnt. ProductRepository에 집계 조회 추가. Using temporary; filesort · rows 폭증 관측. 정합성 완벽 / 쓰기비용 0
  • A vs B 비교표 — 읽기비용·쓰기비용·정합성·운영복잡도 4축. 상세는 05-집계 A/B/C
  • 정합성 갭 보강 — like_event/product_like를 소스로 like_count 재계산 UPDATE하는 재집계 배치(commerce-batch). 비동기 핸들러 실패 드리프트를 결과적으로 치유
  • C (탐색) — 재집계 배치가 사실상 "집계 테이블 없는 MV 갱신"임을 인지. product_like_summary 전용 테이블 분리 시 구조·트레이드오프(배치 vs 트리거)를 문서로 정리, 시간 여유 시 배치 방식으로 시도. 필수 아님 탐색
동기화 갭 보강 옵션(1) 재집계 배치 권장 — C 인프라와 시너지 · (2) 이벤트 재시도/아웃박스 — 복잡도↑ · (3) 동기 UPDATE 전환 — 강한 정합성이나 핫 상품 행 경합(주차 주제와 충돌). A는 갭 자체가 없다(항상 실시간) — 이 대비가 좋은 결론이 된다.
6

CACHE

Redis 캐시 적용

인덱스로 빨라진 쿼리도 반복되면 DB를 때린다. 가장 핫한 상세·목록 첫 페이지를 Redis로 가린다. 미스에도 서비스는 정상이어야 한다.

의존 Step 4·5산출 캐시 계층
  • 캐시 인프라 구성 — spring-boot-starter-cache + @EnableCaching + JSON(Jackson) 직렬화 RedisCacheManager. 현재 RedisConfig가 출발점
  • 상세 @Cacheable — key=product:detail:{id}, TTL 60s~5m
  • 목록 RedisTemplate 직접 — 첫 페이지만 캐싱 products:list:{sort}:{brandId|all}:p1:{size}. 커서 들어가면 키 카디널리티 무한 → 딥페이지는 미스→DB. TTL 30~60s + 지터(stampede 완화)
  • 무효화 — 좋아요 변경 시 해당 상세 키 evict. 목록은 TTL 자연 만료(약한 일관성 수용)
  • penetration 방어 — 없는 id negative caching(짧은 TTL 빈값 마커) 또는 존재 가드
  • 미스 fallback — Redis 장애/미스 시 DB로 정상 응답. 캐시는 가속이지 의존이 아니다
캐시키 설계 핵심목록은 정렬+브랜드+커서 조합이라 전부 캐싱하면 적중률↓·메모리 폭증. 가장 핫한 "커서 없는 첫 페이지"만 캐싱하는 게 적중률 대비 효과 최적이다. 상세는 06-캐시 설계 참조.
