WHY · FRAME

배경 — 3-축 프레임

랭킹(Redis ZSET)과 metric은 Kafka 이벤트를 소비해 만든 파생 상태(projection)입니다. 진실은 이벤트 스트림에 있고, 저장소들은 그걸 접어 만든 결과일 뿐입니다. 이 관점을 잡으면 "무엇을 지켜야 하나"가 세 가지로 갈립니다.

위협 (상호 배타)무엇이 깨지나대응 장치담당 §
① 이벤트 유실발행·소비 실패로 이벤트가 파이프라인에서 사라짐 → projection이 애초에 틀림Outbox 상태 격리(발행) + Kafka DLQ(소비)§3
② Redis 장애ZSET을 못 읽어 랭킹 서빙 자체가 멈춤 (스파이크 중엔 치명적)집계 fallback projection(C) + read circuit§5
③ 파생 상태 파손ZSET/metric이 유실·오염 → 되살릴 원천이 필요replay 3소스(Kafka · event store · C) + 컷오버§6
이 세 축이 MECE인 이유 ①은 이벤트가 저장소에 닿기 전, ②는 장애가 지속되는 동안(서빙), ③은 장애가 끝난 뒤(재구축) — 실패 생애주기의 서로 겹치지 않는 세 구간을 각각 덮습니다. ②와 ③을 섞으면 안 됩니다: ②는 "죽어 있는 동안 계속 보여주기", ③은 "살아난 뒤 되살리기"로 목적이 다릅니다.
범위 · 우선순위 (밀어붙이는 규칙) 이 문서 전체는 과제 Must가 아니라 후속 안정화입니다. Must는 여전히 05의 Consumer→ZSET 적재 + Ranking API입니다. 그것을 먼저 구현·측정해 닫은 뒤, 이 안정화를 별도 세션에서 진행합니다. 단 원천 저장(A)과 서빙 fallback(C)은 둘 다 구현 대상으로 확정됐습니다 — Technical Writing의 핵심 소재이기도 합니다.

DATA MAP

데이터 3종 지도 (A·B·C)

이 설계에는 성격이 다른 세 데이터가 있습니다. 이걸 하나로 뭉뚱그리면 "복구 원천"과 "서빙용 집계"를 같은 것으로 착각하게 됩니다 — 실제로는 shape·소비자·용도·멱등이 전부 다릅니다.

데이터shape먹이는 소비자용도멱등 근거
A 원천 event storeraw event append (무가중)metrics consumer에 얹기복구 후 재구축 (실시간 서빙 안 함)event_id = row PK (자연)
C 집계 fallback집계 (productId, date, score) (가중)독립 배치 consumer (~0.5s)장애 중 읽기 서빙 · 트렌드 추종별도 inbox 원장 (§5)
B 실패 이력실패 레코드 + 예외 헤더DLT consumer운영 관측 · 재처리 판단해당 없음 (소량)
관계 — SoT 하나, projection 둘 Kafka(+ A 원천 저장) = source of truth. Redis ZSET(05)과 C 집계 MySQL = 둘 다 그 로그에서 파생된 projection입니다. 그래서 둘이 잠깐 어긋나도 "충돌"이 아니라 lag 차이일 뿐이고, 화해는 병합이 아니라 로그 재생(replay)으로 합니다 — split-brain이 원리적으로 안 생깁니다. A는 raw(무가중)라 자기 자신이 곧 멱등 원장이고, C는 사전 집계(가중)라 가중치 계산 로직을 Redis 경로와 공유해야 합니다(§5 로직 단일화).
A와 C를 왜 안 합치나 A는 "정확한 재구축을 위한 raw 로그", C는 "빠른 서빙을 위한 사전 집계"입니다. A로 서빙하려면 매 조회마다 SUM(가중치) GROUP BY productId — Stage 1a의 O(N) 스캔이라 장애 중 서빙에 부적합합니다. 반대로 C만으로는 가중치 변경 재계산·retention 초과 복구가 안 됩니다. 둘은 대체가 아니라 역할 분담이라 각각 둡니다.
3

THREAT ① · LOSS

위협 ① 유실 방지 — 발행 + 소비

유실 방지는 하나의 장치가 아니라 파이프라인의 두 구간에서 각각 일어납니다. 발행 실패는 Kafka가 죽은 상황일 수 있어 Kafka DLQ로 못 막습니다 — 그래서 발행은 outbox 상태, 소비는 Kafka DLQ로 지킵니다.

발행 구간 — Outbox FAILED 상태

먼저 — 유실은 지금도 안 난다 현재 OutboxRelay는 발행 실패 시 break 후 markSent를 안 하므로, 실패분은 INIT 상태로 남아 다음 폴링에서 계속 재시도됩니다. 즉 발행 실패로 이벤트가 사라지진 않습니다. FAILED 상태 추가의 실익은 유실 방지가 아니라 아래 둘입니다.

1Head-of-line blocking 해소

지금은 실패 시 break라 맨 앞 독약 레코드 하나가 뒤 전부를 영원히 막습니다. N회 초과분을 FAILED로 빼면 나머지가 다시 흐릅니다.

2관측 · 알림

계속 실패하는 레코드를 사람이 인지하도록 FAILED 전이 시 NotificationSender로 알립니다.

  • OutboxStatus에 FAILED + retry_count 컬럼 schema
  • relay 시도마다 retry_count++, N회 초과 시 FAILED 마킹 + 알림
  • FAILED는 자동 폴링 재시도 제외 — 수동 재처리 대상
  • break 정책 재검토 — aggregate 다르면 독립이니 실패분만 건너뜀. 같은 파티션 키 순서 보존이 필요하면 그 키만 막음

소비 구간 — 배치 리스너 DLQ

배치 리스너의 두 제약 streamer consumer가 모두 배치 리스너(isBatchListener=true)입니다. ① 편한 @RetryableTopic(non-blocking)은 배치 리스너 미지원[2]. ② 배치 DLQ는 실패 레코드를 담아 BatchListenerFailedException을 던져야 — 안 던지면 실패 하나에 배치 전체가 통째로 재시도됩니다.[1]
"대상·시도·예외"는 프레임워크가 헤더로 준다 DeadLetterPublishingRecoverer가 DLT 레코드에 자동 첨부 — DLT_EXCEPTION_FQCN · _MESSAGE · _STACKTRACE + DLT_ORIGINAL_TOPIC · _PARTITION · _OFFSET · _CONSUMER_GROUP. 직접 만들 필요 없이 "어떤 대상이 뭘 시도했는데 무슨 예외로 실패했나"가 확보됩니다.[1]
  • DefaultErrorHandler(recoverer, FixedBackOff(간격, N회)) + addNotRetryableExceptions(...) — 소진 시 <topic>-dlt, 재시도 무의미 예외는 바로 DLT[1]
  • 배치에서 실패 인덱스 BatchListenerFailedException으로 지정 — 성공분 재처리 방지

SOURCE OF TRUTH

원천 저장 (A) — 복구 SoT

A는 복구를 위한 raw 이벤트 append 로그입니다. 파일 로그가 아니라 "데이터" — 순서대로 재생 가능하고 유실 불허가 핵심입니다. 발단은 조회(ProductViewedEvent)로, 현재 @Async+AFTER_COMMIT 직접 발행이라 실패 시 warn 로그만 남기고 버려집니다.

저장 위치 — metrics consumer에 얹기 (accepted-risk)

전용 consumer·새 원천 토픽을 만들지 않고, 이미 3토픽(조회·좋아요·주문)을 받는 ProductMetricsKafkaConsumer의 각 리스너에서 EventSubscription.EVENTSTORE + handleOnce(eventId, EVENTSTORE)로 append합니다. metrics가 이미 이 멱등 패턴이라 재시도 중복이 없습니다.

결합의 대가 — 명시적으로 감수 + 분리 트리거 SoT를 metrics consumer에 얹으면 복구 소스가 복구 대상(metrics)과 실패 모드를 공유합니다 — metrics 로직의 독약 레코드가 "그 metrics를 복구할 원천"의 적재까지 DLT로 보냅니다. SoT는 실패 표면이 가장 작아야 한다는 원칙과는 반대 방향입니다. 그럼에도 지금은 감수합니다(전용 consumer 추가 = YAGNI). 대신 두 가지를 문서로 못박습니다: ① event store append를 리스너에서 가장 먼저·최소 로직으로 수행해 자기 실패 확률을 낮춘다. ② 분리 트리거 — DLT에서 "metrics 로직 실패로 event store까지 막힌" 사례가 관측되면 그때 thin 전용 consumer로 승격한다.
A는 자기 자신이 멱등 원장 raw append는 event_id를 row PK로 두면 INSERT ... ON DUPLICATE KEY UPDATE id=id가 중복을 무해화합니다 — 별도 dedup 테이블이 필요 없습니다 (실서비스 like 아카이브에서 관찰되는 패턴[3]). 이 점이 가중 집계인 C와 결정적으로 다릅니다: C는 score += Δ라 재적용이 이중 가산이므로 별도 inbox가 필요합니다(§5).

THREAT ② · AVAILABILITY

위협 ② 장애 중 서빙 — 집계 fallback (C)

Redis 전체(master+replica)가 죽은 동안에도 랭킹이 트렌드를 따라가야 합니다 — 드라마 광고·PPL·라이브 커머스 스파이크는 랭킹이 가장 중요한 순간이자 정지가 가장 눈에 띄는 순간입니다. 그래서 C는 Kafka를 독립 소비해 항상 ~0.5s 뒤처진 warm standby로 유지합니다 — Redis에 의존하지 않으니 Redis가 죽어도 계속 자랍니다.

먼저 — 단일 replica 죽음은 C 트리거가 아니다 현재 RedisConfig는 정적 master/replica + ReadFrom.REPLICA_PREFERRED입니다. 이건 strict가 아니라 "replica 없으면 마스터로 fallback"이라, replica 하나 죽으면 읽기가 마스터로 흡수돼 살아남습니다. 따라서 C(MySQL)는 master까지 실패한 total Redis 소실에서만 뜨는 최후 읽기 경로입니다. (이 전제 — REPLICA_PREFERRED의 마스터 fallback — 은 replica kill 실측 1회로 확인 필요, §9.)

먹이는 방식 — 배치 소비 (~0.5s)

핵심은 per-event 증분이 아니라 마이크로 배치입니다. per-event MySQL upsert는 Stage 1의 쓰기 천장(드레인 185/s)을 재현하지만, 배치로 묶으면 그 병목을 우회합니다. "0.5초"는 Kafka가 공짜로 줍니다 — fetch.max.wait.ms(브로커가 이 시간까지만 모으고 응답, 기본 500ms) + max.poll.records(건수 상한)[4]. 데이터 적으면 ~500ms마다, 스파이크로 많으면 즉시 차서 sub-second로 — 평소 0.5s / 스파이크 시 더 빠르게가 자동입니다.

멱등 — inbox 패턴 + ack 순서

C는 집계라 event_id가 row 키가 아닙니다(키는 (date, productId)). 그래서 별도 inbox 원장을 score upsert와 같은 트랜잭션에 넣어 재전달 이중 가산을 막습니다. ack는 트랜잭션에 못 묶이므로(2PC 없이 불가) 커밋 후에만 호출하고, 정확성은 트랜잭션 안 멱등이 책임집니다.

RankingFallbackConsumer — 검토용 스케치 (구현 시 TDD로 확정)
// ① 리스너는 비-트랜잭셔널: 커밋과 ack의 순서를 손으로 보장
@KafkaListener(batch)
fun consume(records, ack) {
  rankingFallbackService.applyBatch(records)  // @Transactional — 리턴 = 커밋 완료
  ack.acknowledge()                            // 커밋 후에만 ack (실패해도 재전달→멱등 흡수)
}

// ② 집계 + inbox 를 한 트랜잭션에
@Transactional
fun applyBatch(records) {
  val fresh  = records.filter { inbox.insertIfAbsent(it.eventId) }  // inbox = dedup 원장
  val deltas = fresh.groupBy { it.productId }
                     .map { (id, es) -> id to es.sumOf { RankingWeights.delta(it) } }
  rankingDailyDao.bulkUpsertAdd(deltas)   // score += Δ (오늘) · +Δ×carry (내일)
}   // inbox insert + score upsert 가 함께 커밋되거나 함께 롤백
= at-least-once + 멱등 sink = effectively-once 커밋 후 ack 실패·크래시·리밸런스 → 같은 배치 재전달 → inbox에 event_id가 이미 있어 Δ=0 → score 불변. 트랜잭션 중간 실패 → inbox·score 함께 롤백 → 깨끗이 재시도. ack는 원자성의 일부가 아니라 재시도 트리거일 뿐입니다. inbox 원장도 랭킹 윈도우 지나면 DELETE로 청소(daily 키와 동일). @TransactionalEventListener는 쓰지 않습니다 — 순차 호출로 이미 "커밋 후 ack"가 되고, AFTER_COMMIT은 롤백 불가 + Acknowledgment를 이벤트에 실어야 하는 레이어 냄새만 더합니다.

로직 단일화 — 드리프트 방지 (우리 항목 2)

이제 가중치(view 0.1 / like 0.2 / order 0.7)와 carry(+Δ×0.1)가 Redis 실시간 경로(05)와 C 배치 경로 두 곳에 존재합니다. 둘이 어긋나면 fallback이 다른 랭킹을 줍니다. 그래서 이벤트→가중 델타 계산을 단일 컴포넌트(RankingWeights.delta())에서 산출하고, 양쪽이 그 값을 쓰게 합니다. 05에서도 가중치는 이미 JVM에서 계산해 Lua ARGV로 넘기므로(Lua는 ZINCRBY만), 이 계산기를 공용 origin으로 두면 두 경로가 정의상 같은 델타를 씁니다.

read circuit — 읽기에만, total-loss에만

읽기circuit 대상

랭킹 조회가 Redis(replica→master fallback 포함)를 다 소진하고도 실패 → circuit open → C(MySQL)에서 서빙. 재구축 완료 기준으로 close(§6).

쓰기circuit 아님

쓰기(Redis ZINCRBY)는 circuit이 아니라 Kafka backpressure — Redis 죽으면 ack 안 하고 lag 쌓다가 복구 후 드레인. MySQL로 우회하지 않음(C는 별도 배치가 이미 먹이고 있음).

fallback 중 개별 순위는 저하됨 상품 상세의 개별 순위를 C(MySQL)에서 주면 Stage 1의 COUNT(score > 내 score) = O(rank)로 떨어집니다. Redis ZCOUNT의 O(log N)이 아닙니다. 드문 total-loss 동안만이라 수용하되, 명시된 저하입니다.
근거 — 실서비스 선례 "Redis 실시간 hot store → 소비 종료 후 MySQL 영구 저장"은 LINE LIVE에서 확인되는 구조입니다 — sorted set으로 이벤트를 쌓고 방송 종료 시 전량 MySQL 정규화 테이블로 이관[3]. Redis 자체 영속(RDB/AOF)은 재시작 복구용이지 죽어 있는 동안의 서빙이 아니라는 점[5]이 C(별도 저장소가 읽기를 이어받음)의 존재 이유입니다.
6

THREAT ③ · RECOVERY

위협 ③ 복구 — replay & 컷오버

Redis가 total loss에서 돌아오면 비어 있습니다. 재구축 소스와 "언제 읽기를 Redis로 되돌릴지"를 정해야 합니다. 세 재구축 소스를 역할로 나눕니다.

재구축 소스커버 범위비용 · 특성
C 집계 → ZSET 복사1차 · 가장 빠름C는 이미 ~0.5s 뒤 warm — 그대로 ZSET에 부어 즉시 복원. carry 로직 일치 필요
Kafka replay (offset 리셋)retention 내 정합성 보정05 D1-B(Redis 멱등)면 유실 시 함께 사라져 재소비로 이중 가산 없이 재구축
A event store replayretention 초과 · 장기가중치 변경 재계산도 여기서. 느리지만 완전
컷오버 게이팅 — "ping 됨"이 아니라 "재구축 완료" 읽기를 Redis로 되돌리는 기준은 Redis 재구축 완료여야 합니다. ping 되자마자 flip하면 절반만 채워진 ZSET을 서빙합니다. 순서: ① Redis 복구 감지 → ② C→ZSET 복사(+필요 시 Kafka replay로 보정) → ③ 재구축 완료 확인 후에만 read circuit close → Redis 서빙 재개. 그 사이 읽기는 C가 계속 담당합니다.
왜 split-brain이 없나 (재확인) 복구가 "Redis와 MySQL을 병합"이 아니라 "로그(Kafka/A)에서 재생"이기 때문입니다. Redis도 C도 로그의 파생 projection이라, 복구 시점에 둘이 달라도 그건 lag일 뿐 충돌이 아닙니다 — 권위는 항상 이벤트 로그에 있습니다.

OPS · FAILURE LOG

실패 이력 (B) + 알림

알림을 로그로 끝내지 않고 이벤트로 처리한 뒤 DB에 적재합니다. DLT 토픽 자체가 실패 이벤트 스트림이므로, <topic>-dlt를 구독하는 DLT consumer가 헤더를 읽어 실패 이력(B)에 남기고 알립니다.

  • DLT consumer → DLT_EXCEPTION_* · DLT_ORIGINAL_* 헤더 파싱 → 실패 이력(B) MySQL 적재 → NotificationSender.notify(...)
  • NotificationSender 인터페이스 + LoggingNotificationSender 구현체까지만 (실제 채널은 추후) 범위 고정
B를 A와 섞지 않는 이유 A는 대량 append(복구 원천), B는 소량·예외적(운영 판단). 한 테이블에 몰면 대량 write와 예외 이력이 서로의 보관·조회 정책을 방해합니다. B는 "어떤 대상이 뭘 시도했는데 무슨 예외로 실패했나"라 검색·집계 관점이 어울립니다.
같은 알림 원칙이 적용되는 다른 배치 — carry 스케줄러 05 §6-D3에서 랭킹 carry를 dual write → 23:50 스냅샷 + 00:00 tail 병합 스케줄러로 교체했습니다. 이 스케줄러는 여기서 정한 실패 알림 원칙(NotificationSender 인터페이스 + 로그 구현)을 배치 실패에 그대로 적용합니다 — 스냅샷/병합 잡이 실패하면 알리고, 00:00 병합은 SET NX carry:merged:{D+1} 가드로 재실행 시 이중 가산을 막습니다. 다만 carry 꼬리 보정은 Redis tail ZSET로 자체 완결하므로, 이 문서의 event store(A) 재적재에는 의존하지 않습니다 — 복구 원천(A)과는 별개 경로입니다. A는 metric/랭킹 전체 재구축용, tail은 날짜 경계 seed 보정용으로 스코프가 다릅니다.

STORAGE

저장소 결정 — MySQL 먼저

A·B·C 셋 다 우선 MySQL, 테이블만 분리합니다. 이유는 "없는 병목을 위해 인프라를 늘리지 않는다"입니다.

후보판단결론
MySQL운영 중, 추가 인프라 0. append + 시간 파티셔닝(월별, 오래된 파티션 드롭)이 로그성 데이터 정석. C는 집계 upsert + 인덱스가 Stage 1 자산 그대로. 복구 재생의 순서·정확성 검증이 쉬움채택 (A·B·C)
MongoDB문서 삽입·샤딩 편의. 단 write 우위는 샤딩 규모(수억 건/일)에서만 유의미. MySQL이 못 버틸 근거 없음학습 목적일 때만 (A) 한정
Elasticsearchwrite 특화가 아님 — 검색·집계 특화. 역색인으로 write 무겁고 near-real-time 색인이라 즉시 정확 재생 부적합원천(A)에서 배제
④ raw event store(A) YAGNI 판단 — 유지 checklist #7이 "전일 조회까지만 요구, 과거는 TTL 소실 수용"이라, retention 초과 재구축은 하드 요구가 아닙니다. 그럼 Kafka replay + C만으로도 복구가 되고, A의 순수 추가 가치는 "retention 초과 복구 · 가중치 변경 재계산 · 지금 버려지는 조회 이벤트 포획" 셋입니다. 이번엔 A를 유지합니다(사용자 결정: A·C 둘 다 구현 대상) — 특히 조회 이벤트 포획은 독립적 가치가 있습니다. 다만 "왜 유지하는가"의 근거를 이 세 항목으로 한정해 둡니다(무한 확장 금지).

OPEN

열린 결정 — 검토 요청

E1. 조회 원천의 유실 방지 수준

a조회도 발행 outbox 편입

producer 유실까지 막힘. 대신 getDetail()의 readOnly 트랜잭션이 쓰기 트랜잭션이 됨 — 고트래픽 조회에 outbox INSERT 부하. Stage 3의 읽기 부하 감소 방향과 상충.

b ?producer 유실 허용, 소비 저장만 DLQ

"Kafka까지 온 것만 확실히 저장". 읽기 경로에 쓰기 안 얹음. 발행 유실은 감수(조회 가중치 0.1로 낮음). 결정 필요.

E2. C 컷오버 자동화 수준

read circuit의 open/close를 자동(재구축 완료 감지)으로 할지, 초기엔 수동 플래그로 두고 관측만 자동화할지. 자동 flip은 "재구축 완료" 판정 로직이 필요 — 초기엔 보수적으로 수동 승인 후 close를 권장.

E3. 재시도 파라미터

발행 FAILED 임계 N, 소비 FixedBackOff 간격·횟수, C 배치의 max.poll.records·fetch.max.wait.ms. 실측 없이 보수값(예: 소비 3회/1s · C 배치 500건/500ms)으로 두고 조정.

E4. 검증 미결 — REPLICA_PREFERRED fallback

"단일 replica 죽음 → 마스터 읽기 fallback"이라는 §5 전제는 replica(6380) kill 후 읽기 성공 테스트 1회로 확인해야 합니다. 실패로 나오면 단일 replica 죽음도 C 트리거가 되어 범위가 넓어집니다.

ORDER · SCOPE

작업 순서 & 범위

05의 Must(ZSET 적재 + Ranking API)를 먼저 닫은 뒤 별도 세션. 각 단계는 통합테스트 1개 green을 닫힌 칸으로 잡습니다.

  • 선행05 Must 완료 — Consumer→ZSET + Ranking API + 측정 (이 문서는 그 후)
  • A원천 event store 테이블 + metrics consumer 저장 얹기 — EVENTSTORE handleOnce, 3리스너 각각, MySQL append (event_id PK 멱등)
  • 유실소비 DLQ — DefaultErrorHandler + DeadLetterPublishingRecoverer + BatchListenerFailedException
  • BDLT consumer + 실패 이력 + 알림 — 헤더 파싱 → B 적재 → NotificationSender(로그)
  • 유실발행 outbox FAILED 확장 — status/retry_count + N회 격리 + 알림 + break 정책 재검토
  • C집계 fallback consumer — 배치 소비 + inbox 트랜잭션 + 커밋후 ack + RankingWeights.delta() 공용화 (05 Lua 경로와 단일 origin)
  • Cread circuit + 컷오버 — total-loss 트리거, 재구축 완료 게이팅, 상세순위 O(rank) 저하 명시
  • 검증replay & 복구 — C→ZSET 복사 · Kafka replay · event store replay 역할 확인 + replica kill fallback 테스트(E4)
