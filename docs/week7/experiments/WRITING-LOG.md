## 2026-07-02 — Phase 0-b 베이스라인 구현 (PR #6)

PR: https://github.com/shoeone96/loop-pack-be-l2-vol4-kotlin/pull/6 (2026-07-03 merged, `479046f`)

### 결정 1 — 베이스라인은 동기 + 비관적 락

- **왜 비관적 락**: 선착순은 충돌이 확실한(경합이 기본인) 워크로드. 낙관적 락은 충돌 시 재시도 폭풍이 되고, 조건부 UPDATE는 엔티티 dirty checking 관례를 벗어남. 코드베이스에 inventory `@Lock(PESSIMISTIC_WRITE)` 선례가 있어 같은 패턴 채택.
- **단, 이 선택은 잠정**: Phase 1에서 A(비관) / B(조건부 원자 UPDATE) / C(낙관+재시도) 3변형을 같은 부하로 비교해 실측으로 재평가한다. 베이스라인의 역할은 "정합성이 보장되는 가장 단순한 기준점"이지 최종 답이 아님.
- 전략 패턴 등 변형 추상화는 지금 만들지 않음(YAGNI) — 변형은 Phase 1에서 필요해질 때.

### 결정 2 — `totalQuantity`는 nullable, null이면 발급 거부

- 기존 쿠폰은 전부 관리자 지급 전용 → 한도 개념이 없음. `Long? = null`로 하위 호환.
- null 쿠폰에 self-issue 시도 → `NOT_ISSUABLE`(400). **null = 무제한이 아니라 "선착순 발급 대상 아님"** — 관리자 지급 전용 쿠폰을 아무나 가져가는 구멍 차단.
- 검증 순서: NOT_ISSUABLE → EXPIRED → SOLD_OUT → 증가. grant의 "존재→만료→중복" 순서와 정합 유지.

### 결정 3 — 중복 방어 2겹 + 롤백에 의한 수량 원복

- 락 안에서 `existsByUserIdAndCouponId` 체크(1차) + `uk_user_coupon` unique 제약(최종 방어).
- 중복이면 예외 → 트랜잭션 전체 롤백 → **먼저 증가한 issuedQuantity도 함께 원복**. "증가 후 중복 체크" 순서라도 정합성이 깨지지 않는 이유가 트랜잭션 원자성.
- unique race의 잔여 케이스는 서비스 try-catch가 아니라 `ApiControllerAdvice`의 `DataIntegrityViolationException` 핸들러가 409로 변환(레포 관례 — 서비스에 영속성 디테일 누수 금지).

### 결정 4 — userId는 body가 아니라 인증 컨텍스트에서 (`@RequestAttribute`)

- 논의 발단: "raw 헤더(`X-USER-ID`)로 받으면 어떤가" → **반려**. 클라이언트 자칭 값은 한 명이 id를 바꿔가며 전량 수령 가능 → "userId 중복 0" 불변식이 애초에 무의미해짐.
- 현재 구조가 이미 "헤더 추출"이 맞음: `AccountHeaderAuthenticationFilter`가 로그인 헤더를 **검증한 뒤** `ACCOUNT_ID` attribute로 넘김. 컨트롤러의 `@RequestAttribute`는 검증 끝난 결과물.
- 일반화: **본인 대상(self-service) API의 식별자는 인증에서, 요청 body에서 받지 않는다.** 대조군 — grant(`/api-admin`)는 관리자가 제3자에게 지급하므로 body userId가 정당.
- 계정 존재 검증 생략 근거: issue의 userId는 인증 필터를 통과한 본인 ACCOUNT_ID라 존재가 이미 보장됨(grant는 임의 userId라 검증 필요).

### 결정 5 — application 입력은 Command 클래스로 통일 (`CouponIssueCommand`)

- 처음엔 파일 내 grant/use 선례를 따라 `issue(couponId, userId)` 개별 파라미터로 갔다가, **기존에 확정한 일반 규칙("application 유스케이스 입력은 application 소유 Command로")에 맞춰 리팩터**.
- 규칙의 근거: ① interfaces DTO가 application에 새지 않도록 입력 계약의 소유권을 application에 둠 ② 동일 타입(Long) 파라미터 swap 버그 방지 — 실제로 기존 코드에 `grant(couponId, userId, ...)` vs `use(userId, couponId, ...)` 순서 불일치가 있음.
- 기존 grant/use/cancelUse의 통일은 이 PR 스코프 밖 → 별도 리팩터 후보.

### 결정 6 — 애그리거트 경계: Coupon과 UserCoupon은 별개 (DDD 점검)

- 리뷰 중 질문: "CouponService가 UserCoupon 로직을 다뤄도 되나? 애그리거트가 이어져 있나?"
- 답: **별개 애그리거트 루트 2개, ID 참조**(`UserCoupon.couponId: Long`, JPA 연관관계 없음, 리포지토리 각각). 한 애그리거트로 묶으면 루트가 무한 증가(한도 십만이면 십만 행)하고 use/cancel까지 발급 락에 경합.
- 불변식 배치: "발급 ≤ 한도"는 `Coupon.issue()` 내부(카운터를 루트 안에 둔 이유). "userId 중복 0"은 집합 불변식(set-based invariant)이라 단일 애그리거트가 못 지킴 → 리포지토리 exists + DB unique 제약이 정석.
- 정직한 한계: **한 트랜잭션에서 두 애그리거트 수정**("1 tx = 1 aggregate" 경험칙 위반). 단일 DB 모놀리스라 의도된 완화이고, 이 규칙을 정석대로 지키는 형태가 곧 Phase 4의 이벤트 기반 지연 발급 — **실험 계획이 DDD 권장 방향으로 수렴하도록 설계돼 있음** (글에서 쓸 만한 포인트).
- 남은 개선 여지: 서비스가 `FIRST_COME`/`SYSTEM_GRANTED` 조립 지식 보유 → `coupon.issue(userId, now): UserCoupon` 팩토리 메서드가 더 DDD다움. 단 grant도 같은 스타일이라 함께 옮기는 별도 리팩터 단위로.

### 결정 7 — 동시성 테스트는 300 스레드 (1,000 아님)

- 테스트 Hikari 풀이 10이라 1,000 스레드는 증명력 추가 없이 runConcurrently 10초 하드 타임아웃 flaky 위험만 늘림. 한도(100)의 3배인 300으로 "정확히 100건 + 중복 0" 증명.
- 진짜 스파이크(10초 내 1만 요청)는 통합 테스트의 일이 아니라 **Phase 1 k6 + 실 MySQL**의 일 — 검증 수단마다 책임이 다름.
- 테스트 5종: 단건 발급 / 순차 중복 / 매진 / 300 동시 → 정확히 100 + 200 전부 SOLD_OUT / 같은 사용자 10 동시 → 1건.

### 잔가지 (글에는 안 들어갈 수도)

- 주석 정리: "코드가 왜 맞는지" 설명하는 리뷰어용 주석 3개 삭제, 타입으로 표현 불가한 null 시맨틱 주석 1개만 유지.

## 2026-07-03 — 인프라 결정: SSH 터널은 어디까지 쓰나

배경: 홈서버가 여전히 공인 IP 직결 + DHCP(원격 검증 결과 PLAN.md §3). Docker publish 포트는 iptables 직접 규칙으로 ufw를 우회하므로, 이 상태로 컨테이너를 publish하면 공인 인터넷에 그대로 노출된다.

### 결정 8 — 노출은 "포트 0개 + SSH 터널"로 막되, 터널을 부하 측정 경로에는 두지 않는다

- **보안 결정(먼저)**: 컨테이너를 publish하지 않거나 `127.0.0.1`에만 bind하고, 맥에서 `ssh -L` 터널로 필요한 포트만 접근. 공인 IP에 열린 포트가 0개가 되어 ufw 우회 문제가 원천 소멸. 공유기 이사를 "실험 착수" 블로커로 만들지 않음.
- **그런데 이 결정의 최초 기록엔 트레이드오프 하나가 빠져 있었다**: 터널이 k6 부하 경로 안에 들어온다는 것. `ssh -L`은 모든 포워딩 연결을 **단일 SSH TCP 연결 위 채널**로 다중화한다 — ① 패킷 손실 1건이 전 채널을 막고(head-of-line blocking) 포화 근처 터널 큐잉이 p99에 섞임 ② 터널이 병목이면 변형 A/B/C가 같은 천장에 부딪혀 "상대 비교" 원칙 자체가 붕괴. 보안은 풀었지만 이 실험의 존재 이유(측정 타당성)를 건드리는 결정이었다.
- **보강 결정**: 터널의 적용 범위를 나눔 — 셋업·시드·스모크·Prometheus scrape(5초 간격 저볼륨)는 터널 OK / **P1 본 측정은 터널 금지**. 공유기 이사 + 내부 IP 고정을 "P1 본 측정 착수 전" 선행 조건으로 승격. 지금 진행에는 아무 변화 없음(0-b는 서버 불필요, 셋업·스모크는 터널로 충분) — 측정 신뢰성만 지키는 구조.
- **Fallback**(이사 지연 시): no-op 엔드포인트로 터널 자체의 천장을 선측정, SUT 상한의 3배 이상 여유 확인 시에만 터널 경유 측정 허용 + 기록에 조건 명시. "추측 말고 실측" 원칙을 인프라 의심에도 적용.
- 부수 확인 항목: 현 토폴로지(서버 공인 IP 직결, 맥은 공유기 아래)는 "같은 LAN" 전제와 다를 수 있음 → 스모크 시 `ping` RTT로 같은 L2 세그먼트 여부 판정(<1ms vs 수 ms).
- 글 포인트: **부하 실험 인프라에서 "경로 위에 뭐가 있나"는 측정 대상만큼 중요하다** — 관측 스택을 SUT 밖으로 뺀 것과 같은 이유로, 터널도 측정 경로 밖으로 뺀다.

### 결정 9 — "오늘 router 없이 측정" 전제: 오늘 숫자는 잠정치, 절대 상한은 이사 후 확정

- 제약: 오늘 쿠폰 테스트를 진행하되 공유기 이사는 못 함(사용자 확정 2026-07-03). 결정 8의 "P1 본 측정 전 이사" 게이트를 오늘에 한해 무른다.
- **그대로 따르지 않고 측정 무결성을 지키는 조건을 붙임**: router 없이 측정하면 경로에 터널 또는 k6-on-localhost 인공물이 낀다(터널=p99 지터·최악 시 벽 / localhost=부하생성 CPU가 SUT와 경합 → 락 차이가 CPU-bound에 가려짐). 따라서 **오늘 얻는 건 A/B/C 상대 신호까지**. §1의 "절대값 아니라 변형 간 상대 비교" 목적엔 충분하지만, **"DB-only 구조적 상한 = N RPS" 같은 절대 수치는 오늘 확정하지 않고 이사 후 LAN 직결에서 재측정해 갱신**한다. 오늘 런은 기록에 `경로: 터널/localhost, 잠정` 태그.
- **경로 선택은 실측으로**: ① 맥→서버 `ping` RTT(같은 세그먼트 판정) ② actuator health로 60초 터널 천장 스모크 ③ 터널 최대 RPS가 SUT 관측 상한의 3배 이상이면 터널 경유, 아니면 localhost k6(CPU 경합 감수·태그). 미니PC 코어 수가 적으면 localhost가 더 위험 → 1순위는 터널 + 천장 확인.
- 글 포인트: **제약이 방법을 바꿀 때, 결론의 등급을 낮춰서 정직성을 지킨다** — "오늘 못 하니 그냥 이 숫자로 간다"가 아니라 "오늘은 상대 신호까지만, 절대 상한은 조건 갖춰 재측정"으로 결론의 유효 범위를 명시.

### 결정 9-보강 — "단일 박스 용량 측정" 프레이밍: router 게이트 강등 + 남는 가드는 하나

- 사용자 지적(2026-07-03): 목적은 "이 한 박스가 얼마나 견디나 + 변형 간 상대 비교". 같은 요청을 부하량 무관하게 **동일 조건**으로 재니까, 경로가 끼어도 모든 런에 동일하면 결론은 유효하다. → 타당. §1 "절대값 아니라 상대 비교" 원칙의 재확인.
- **강등**: 이 프레이밍에선 router 이사가 오늘의 하드 게이트에서 빠진다. "DB-only 절대 상한 = N rps"를 블로그에 발표용 절대치로 못박을 때만 필요한 선택 조건으로 격하. (결정 9 원안의 "P1 본 측정 전 필수"는 → "절대치 발표 런에 한해 필요"로 완화)
- **그래도 남는 가드 하나 — 상수 세금 vs 천장의 구분**:
  - 인증 BCrypt(cost 4, ~1ms)·credential 조회 = **상수 세금**. 모든 요청에 균등 가산 → 상대 비교 유지 + 절대치는 약간 보수적. 문제 아님.
  - 터널/k6-on-box CPU = **천장**이 될 수 있음. 천장은 상수가 아니라 벽 → 서버가 2000 낼 수 있어도 하네스가 800에서 막히면 "서버 한계=800"이라는 **오답**(측정 대상이 서버→하네스로 바뀜). "얼마나 견디나"의 답이 하네스 한계가 되어버림.
  - 따라서 값비싼 셋업은 버리되 **60초 하네스 천장 스모크**만 유지: no-op 엔드포인트로 하네스가 서버 포화점 ×3 이상 내는지 확인. 넘으면 그대로 진행(숫자는 "박스 용량"으로 유효), 못 넘으면 경로 교체. 이 한 줄이 "서버를 쟀다 vs 하네스를 쟀다"를 가름.
- 글 포인트: **부하 측정에서 "무엇을 상수로 두고 무엇이 변수인가"의 구분** — 상수 세금은 결론을 안 흔들지만 숨은 천장은 측정 대상 자체를 바꾼다. 이걸 가르는 게 스모크 한 번.

### 결정 10 — Phase 0-b 측정 하네스: 무엇을 상수로 고정하고 무엇을 안 건드렸나

- **무의존 no-op 경로 = actuator liveness**: 하네스 천장 스모크는 서버 비용이 0에 가까워야 "하네스가 낼 수 있는 최대"만 측정된다. `/actuator/health`(전체)는 redis/db health 를 건드려 서버 로직이 섞이므로 제외, `/actuator/health/liveness`(probes.enabled=true, 외부 의존 0)를 씀. `/actuator`는 인증 필터 `shouldNotFilter` 대상이라 무인증 접근 가능 → 인증세도 안 섞임. **왜**: 천장 측정에 서버 코드가 끼면 "하네스 병목 판별" 자체가 오염된다.
- **시드 유저 1만 (한도 100의 100배)**: 유저가 적으면 재요청이 ALREADY_ISSUED 로만 떨어져 SOLD_OUT 경합을 못 만든다. distinct 유저 1만이라야 ① userId 중복 0 불변식 ② SOLD_OUT 경합을 **동시에** 실측한다. **왜**: 두 불변식은 유저 다양성이 있어야만 관측된다.
- **컨테이너화 = local 프로파일 + 명령행 override (modules yml 무수정)**: jpa.yml·redis.yml 은 `modules` 소유(수정 금지 관례). 새 profile 을 modules 에 못 넣으니, 기존 profile 을 베이스로 잡고 datasource·ddl-auto 를 **명령행 args**(최고 우선순위)로 갈아끼웠다. **왜 app-{profile}.yml 이 아니라 명령행인가**: `spring.config.import`(jpa.yml)와 profile 파일 간 precedence 가 미묘해 추측이 필요한데, 명령행 args 는 항상 최우선이라 모호성이 0. 부하 셋업에서 "확실히 이긴다"가 영리함보다 낫다. **왜 dev 가 아니라 local 인가**(dry-run 에서 정정 — 아래 보강): dev/qa/prd 는 logback 이 `slack-appender` + `properties/slack-log-*.xml` 을 include 해 Slack 웹훅 프로퍼티가 없으면 부팅이 깨진다. local 은 plain-console 로깅(외부 의존 0)이라 부하 SUT stdout 로그에 정확히 맞다.
- **ddl-auto=create → 재시작마다 재시드 (수용)**: 스키마 재현성(매 런 clean state)을 얻는 대신 api 재시작 시 시드 재적재가 필요. 부하 실험은 매번 깨끗한 시작이 이득이라 트레이드오프 수용, 문서에 명시.
- 글 포인트: **부하 하네스 설계 = "무엇을 상수로 고정하는가"의 연속 결정** — no-op 경로(서버 로직 배제), 유저 다양성(불변식 관측 가능), override 방식(precedence 모호성 배제), 스키마 리셋(재현성). 각각 측정을 오염시킬 변수를 하나씩 상수로 눌렀다.

### 결정 10-보강 — 로컬 dry-run 실검증: 문서상 "설정 완료"와 "실제로 뜨는가"는 다르다

> 2026-07-03. 홈서버 본 측정 전에 맥에서 core 스택을 실제로 부팅→시드→스모크→S1/S2 로 끝까지 돌려 artifact 를 검증. **`docker compose config` 통과·`node --check` 통과는 "구문이 맞다"까지만 보증했고, 런타임에서 두 개의 실패를 잡았다.** 부하 실험은 코드가 아니라 셋업이 먼저 무너진다는 예시.

- **버그 1 — Dockerfile ENTRYPOINT 가 compose command 인자를 통째로 버림**: `ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar app.jar"]` 형태는 뒤따르는 인자(`--spring.profiles.active=…` 등)가 `sh -c` 스크립트의 위치 파라미터($1,$2…)로 들어가 **java 에 전달되지 않는다**. 그 결과 profile·datasource override 가 전부 무시되고 기본값으로 떠서 컨테이너 안에서 `localhost:3306` 에 붙으려다 connection refused. 수정: `ENTRYPOINT ["sh","-c","exec java $JAVA_OPTS -jar app.jar \"$@\"","--"]` — `"$@"` 로 인자를 java 로 넘기고 `exec` 로 PID 1 교체(시그널 전파). **왜 놓쳤나**: `$JAVA_OPTS` 확장 때문에 shell form 이 필요했는데, shell form + 인자전달은 `"$@"` 를 명시해야만 동작한다는 걸 config 검증으론 알 수 없다.
- **버그 2 — dev 프로파일 logback 크래시**: 위 인자전달을 고치자 이번엔 profile 이 실제로 dev 로 적용되면서 logback 이 `slack-log-dev.xml` 의 `<property>` 를 못 채워 `environmentPrepared` 단계에서 죽음. → 프로파일을 local 로 교체(결정 10 본문 반영). **왜**: dev 는 배포 환경용(Slack 알림)이고, 격리된 부하 SUT 는 plain-console 로 충분하다. 프로파일 선택이 "환경 시맨틱"이지 "아무거나 되는 값"이 아니었다.
- **검증 결과(불변식 전부 충족)**: S1(한도 100, 1000/s×10s) → 발급 **정확히 100** · distinct 유저 100 · 유저당 최대 1건(userId 중복 0) · unexpected 0%. S2(한도 10만, USER_POOL 1만 재활용) → 발급 10000(= 유저 전원 1회) + 재요청은 ALREADY_ISSUED 로 거절 · 중복 0. 하네스 천장 스모크(liveness) → ~4000 rps 에서 p99 2.2ms·실패 0 → 하네스는 병목 아님(S1 1000/s 대비 충분한 여유).
- **관찰(Phase 1 예고)**: S1 은 단일 hot row(한도 100) 경합으로 결정 지연 avg 362ms·p95 1.04s 까지 오르고 k6 가 arrival rate 를 못 채워 395 iteration 을 drop — 비관적 락의 직렬화가 지연으로 드러남. S2 는 hot row 경합이 없어(한도 10만) avg 4ms 로 평탄. **이 대비가 곧 Phase 1 "DB-only 구조적 상한" 서사의 씨앗.**
- 글 포인트: **"설정했다"와 "실제로 뜬다" 사이의 간극** — 부하 실험 신뢰도는 SUT 가 의도한 구성으로 정확히 떠 있느냐에서 시작한다. dry-run 없이 홈서버에서 바로 돌렸다면 두 버그를 측정 오염(또는 전량 실패)으로 뒤늦게 만났을 것.

### 결정 11 — 홈서버를 접고 EC2로: "측정 환경의 변동성 자체가 측정을 오염시킨다" (결정 8·9 topology 대체)

> 2026-07-03. 결정 8·9·9-보강은 전부 **홈서버 + SSH 터널/공유기 이사** 전제 위에 쌓였다. 실제 본 측정은 그 전제를 버리고 **AWS EC2 `m5.xlarge` 단일 박스 + k6 co-located**로 갔다. 8·9는 히스토리로 남기고, topology 결정은 이걸로 대체한다.

- **왜 홈서버를 접었나 (세 겹의 변동성)**: ① **네트워크** — 공인 IP 직결 + DHCP 라 재부팅마다 IP 가 바뀌고, ufw 를 우회하는 Docker publish 포트가 공인 노출 위험(결정 8). 터널로 막으면 이번엔 터널이 k6 경로에 끼어 HOL-blocking·p99 지터로 측정을 오염(결정 8-보강). ② **성능** — 미니PC 는 서멀 스로틀·백그라운드 부하가 있어 "오늘 숫자는 잠정치, 절대 상한은 이사 후 재측정"이라는 단서를 달아야 했다(결정 9). ③ **결국 이 세 제약이 전부 "측정 대상(쿠폰 발급 시스템)이 아닌 것" 때문**이었다 — 환경을 통제하려고 결정 8·9·9-보강 세 개를 쌓았는데, 그 복잡도 자체가 냄새였다.
- **EC2가 세 변동성을 한 번에 제거**: ① 보안 그룹으로 22/8080/8081 을 **내 공인 IP `/32`에만** 열고 컨테이너는 `127.0.0.1` bind → 공인 노출 0, 터널 불필요(결정 8 문제 소멸). ② `m5.xlarge` = **고정 성능**(T-계열 버스트 아님) → 서멀·크레딧 스로틀 없음 → "잠정치" 단서를 뗄 수 있음, **절대 수치를 발표용으로 확정 가능**(결정 9 의 잠정치 프레이밍 해제). ③ k6 를 **같은 박스에 co-located** → 인터넷 왕복이 decision_ms(초 단위 게이트)에서 빠짐. co-located 의 유일 리스크(부하생성 CPU 경합)는 하네스 천장 스모크로 판정 — **실측 ≥4000 rps = SUT 포화점(~250)의 16배**라 하네스는 병목이 아님이 증명됨(EXP-01 §1).
- **트레이드오프(정직하게)**: ① **비용·수명** — 공유 계정의 유료 인스턴스라 측정 후 즉시 terminate 필요(SG 도 삭제). 홈서버의 "공짜로 계속 켜둠"을 잃음. ② **co-located 의 이론적 오염** — 부하생성기와 SUT 가 CPU/메모리를 공유하므로 원리적으로 완전 격리는 아님. 스모크로 16배 여유를 확인해 이번 측정에선 무해하다고 판정했으나, 더 높은 RPS(Phase 3~4 Redis/Kafka)에서 SUT 가 co-located 여유를 잠식하면 부하생성기를 **같은 AZ 별도 노드(SUT private IP 직결)**로 분리한다 — 이게 결정 8-보강의 "하네스를 측정 경로에서 뺀다" 원칙을 EC2 위에서 잇는 형태.
- **관측 스택 분리 원칙은 그대로**: SUT 밖으로 빼는 이유(측정 오염 제거)는 환경이 바뀌어도 불변. 필요 시 Prometheus/Grafana 를 별도 컨테이너/노드로, 셋업 절차는 홈서버 문서 Stage 0~3 재사용.
- 글 포인트: **"측정 환경을 통제하려고 규칙이 세 개씩 쌓이면, 통제 대상이 잘못됐다는 신호다."** 홈서버에서 네트워크·성능·경로를 각각 우회하는 장치를 세 겹 쌓았는데, 고정 성능·IP 통제·co-located 를 기본 제공하는 환경(EC2)으로 옮기니 세 규칙이 한꺼번에 사라졌다. 부하 실험의 첫 설계 결정은 코드가 아니라 **"측정 대상 외의 변수를 어디까지 0으로 만들 수 있는 환경인가"**다.

### 결정 12 — 변형 B 구현: 스크래치 브랜치 in-place, 사전 체크 유지, UPDATE→insert 순서

> 2026-07-03. EXP-02 착수 시점의 구현 방식 결정 3개.

- **스크래치 브랜치 in-place (`exp/week07-coupon-variant-b`), strategy 추상화 없음**: B/C는 천장 탐색용이라 최종 채택 코드가 아닐 수 있다. 변형을 갈아끼우는 strategy 인터페이스는 "단일 구현 인터페이스 금지 + 투기적 확장 포인트 금지"에 정면 위배 — 브랜치가 곧 변형이다. 채택 판단은 Phase 1 종료 시점에 EXP 수치로.
- **existsBy 사전 체크는 유지**: A에선 X락이 existsBy를 직렬화해줘 신뢰 가능했지만 B는 무락이라 race 창이 생긴다. 그래도 유지하는 이유 — 순차 중복(대부분)에 `ALREADY_ISSUED`라는 의미 있는 에러 코드를 주고, race를 뚫은 소수만 `uk_user_coupon` → advice 409로 방어. 서비스 try-catch 금지 관례(계정 가입 패턴)와 동일 구조.
- **UPDATE 먼저, insert 나중**: insert-first면 성공 100건의 락 구간이 더 짧지만, 이 부하는 매진 거절이 지배적(1만 요청 vs 100장)이라 거절마다 insert+rollback(undo·auto_increment 소모)을 내는 순서가 손해. UPDATE-first면 거절 경로가 affected-0 UPDATE 한 문장 + 즉시 rollback으로 끝난다. 부하 프로파일이 순서를 정했다.
- **인덱스 추가 안 함(검토 후 기각)**: B의 쿼리 4경로 전부 기존 인덱스(PK, uk)로 커버. `issued_quantity` 세컨더리 인덱스는 발급마다 인덱스 갱신을 얹어 hot row 경로에 역효과 — "락 구간 축소"라는 실험 목적과 반대 방향이라 기각.

### 결정 13 — aggregate 평균을 천장으로 읽는 함정: 타임라인 보존을 표준 절차로

> 2026-07-03. EXP-02 분석 중 EXP-01 해석 오류를 발견해 정정.

- **발견**: EXP-01의 S2 "~270/s 천장"은 램프 스케줄(0→100→…→800/s)의 **평균 도착률**과 일치하는 값이었다. A도 의도 발사량 69k 중 65.8k를 완료 — 즉 아그리게이트 총량으론 A도 스케줄을 거의 소화했고, 평균 http_reqs rate는 천장이 아니라 스케줄의 그림자였다. 천장을 말하려면 "어느 시점에 도착률을 못 따라가기 시작했나"가 필요하다.
- **교정**: EXP-02부터 k6 진행 로그(10초 간격 완료 수)를 보존하고 차분으로 시계열 처리량을 복원 → B의 무릎을 ~550~590/s로 **실측**. EXP-01엔 정정 부기를 달았다(A의 무릎은 미보존이라 영구 미상 — 지연 급등 기반 추정만 남음).
- **부수 교훈 2개**: ① 원격 sleep 기반 스냅샷 타이밍은 SSH 왕복 누적으로 어긋난다(B의 800/s 구간 스냅샷이 k6 종료 후에 찍혀 무효) — 다음 런은 k6 시작 시각 기준 절대 시각으로. ② B가 ~600/s 영역에 들어서자 load avg 13/4코어 — 결정 11이 예고한 "co-located k6의 SUT 잠식"이 현실화되기 시작. 변형 간 상대 비교는 유효하지만, 절대치 발표 런은 부하생성기 분리가 선행 조건.
- 글 포인트: **부하 실험의 결론 문장은 지표가 아니라 지표의 시간축에서 나온다.** 평균은 스케줄을 되비출 뿐이고, 천장은 "따라가다 꺾이는 순간"에만 있다.

### 결정 14 — 변형 C(낙관 @Version) 스킵: 반례의 가치 < 시간

> 2026-07-03. 사용자 결정(시간 제약).

- C의 목적은 처음부터 "극단 경합에서 @Version 재시도 폭풍" **반례 확보용 1회 측정**이었다(PLAN §5). Phase 1의 종료 기준(DB-only 구조적 상한 확정)은 B의 실측 수치로 이미 충족 — C가 없어도 결론이 바뀌지 않는다.
- 예상 결과도 자명한 편: 같은 hot row에 낙관 락이면 대부분의 트랜잭션이 version 충돌 → 재시도 → DB 왕복 수가 곱으로 증가. "안 되는 걸 확인하는 실험"에 유료 인스턴스 시간을 더 쓰지 않기로 했다. 글에서는 원리 설명으로 대체(실측 아님을 명시).
- 이에 따라 teardown 규율 조건 충족 → EC2 인스턴스 terminate + SG 삭제.
